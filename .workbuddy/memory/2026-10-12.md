### 值得记的四条

**① 「退出门」的唯一口径 = `door_targets` 该侧为空串那扇。**
安全房两扇门里，`north`→`room_01` 是免费通行门，`east` 是空目标门（封闭抵达 /
「[E] 退出战局」）。这不是猜的，是 2026-10-12「入口安全房不再默认掉钥匙」那篇留下的
判据（`_room_produces_room_key` 跳过空 target 门）。摆位代码直接复用同一口径。

**② 安全房的外挂件挂「房间根」，不挂 `SafeRoomArtRoot`。**
`art_root` 会按本层门向整房绕 Y 旋转 0/90/180/270°，而「哪一扇是退出门」要在原生局部
坐标之外判断。挂根节点、位置与朝向全按**世界门向**推导，与门扇 `_build_door` 同口径；
挂 art_root 下反而要把世界方位反算回原生方位。旋转取 `rotation = (PI/2, yaw, 0)`
（YXZ 序）：`Rx(90°)` 放平 + 发光面朝上，`Ry(yaw)` 把深度方向对准门法向。

**③ 🔴 最贵的一条：自发光文字必须看真实渲染截图 —— 几何探针抓不到镜像。**
初版在 Blender 里用 `Rx(+90°)` 立起 EXIT 字样，结果正面落到 **-Y**（契约声明的是 +Y），
导出后平铺时玩家看到的是背面的**镜像字**（截图上读到「TIX3」）。
而几何探针断言的「发光面朝上 / 长边平行门洞 / 贴地」三条**在镜像版本里同样成立** ——
镜像不改法向、不改包络。**只有渲染能发现。**

正确写法：绕轴 `(0,1,1)` 转 180°，`R = [[-1,0,0],[0,0,1],[0,1,0]]`（det=+1，纯旋转不镜像）：
正面 +Z→+Y、字上 +Y→+Z、字右 +X→-X（面向 -Z 侧观察者时右手边就是 -X）。
**教训：以后做平面文字/贴花/标牌类资产，Blender 里立起来的旋转必须验证 det=+1，
且验收清单里强制带一张真实渲染截图。**

**④ 颜色只能靠 PaletteUV 指向色盘单格 —— 色盘第 1 行是「红→灰」轴。**
第 10 列（col 9）是冷调灰阶（深→浅），第 1 行（row 1）是红→灰。
红色取 `(col 4, row 1) = #650D20`。色盘 UV 的 v 在 Blender 里从图片**底部**起算，
`v_blender = 1 - (row+0.5)/10`；导出 GLB 时 Blender 会翻转回来，所以 GLB 里
`floor(v*10) == row`。**这条要用 GLB 的 TEXCOORD_0 实测复核**，别靠推理。

**⑤ 新建 GLB 后必须给 `.glb.import` 补 `import_script`。**

## 事故：共享色盘 .import 被我跑坏了（业主追责「材质球不能加 MipMap」）

**业主问对了，是我。** 我做 EXIT 霓虹灯时跑 `godot --headless --import`，
用了一个**全新新建的隔离 APPDATA**（`D:\ssappdata_exitsign`）⇒ Godot 按「首次导入」
处理 ⇒ 把 `assets/art/shared/palette/设施低亮多巴胺色盘_10x10_512.png.import` 按默认值重写。

被改的 5 处（对照 `d1cfe5d9`）：`compress/mode 0→2`、`mipmaps/generate false→true`、
`uid dtuahqaj31kp2 → b7d71mrdyk8vc`、无损单 ctex → s3tc+etc2、`size_limit 1024→0`。
连带的还有 `tex_normal_....png.import` 的 `normal_map 1→2`。

**「很多纹理叠加」的机理**：色盘 10×10 纯色格 + MipMap ⇒ 各级 mip 把相邻色格平均到一起
⇒ `PaletteUV` 岛稍有越界/采样半径就取到糊掉的颜色；再叠块压缩跨格扩散。

**根因边界（我实测出来的）**：
| 条件 | `--import` 会改写 `.import` 吗 |
|---|---|
| 全新 APPDATA（无 `uid_cache.bin`） | ❌ 会（本次事故） |
| 有 `uid_cache.bin` 的既有环境 | ✅ 不会（sha256 前后一致） |
| 项目既有 `/d/ssverif/appdata` | ⚠️ 只有 `app_userdata`、无编辑器缓存 ⇒ 同样危险 |

**修复**：`git show 02bcd6c5:<path>` 写回工作区（**不用 `git checkout`，避免动索引**）→
与正确基线逐字节一致 → 删孤儿 s3tc/etc2 + md5 强制重导 → 单无损 ctex(694B) →
`check_runtime_texture_policy.py` **OK errors=[]** → 探针 OK。

**门禁加固**：给 `check_runtime_texture_policy.py` 加了 `shared_palette_contract` 断言
（锁 `compress/mode=0` + `mipmaps/generate=false`），**反向对照已验证会红**
（注入 mipmaps=true 报 1 条、再叠 mode=2 报 2 条、还原后逐字节一致且 OK）。
该脚本本来就在套件静态段 ⇒ 再有人污染，套件直接红。

**教训（已进 MEMORY.md 红线）**：
1. 🔴 **被 git 跟踪的 `.import` 是契约文件，不是缓存** —— 它们靠 `!` 例外专门入库来锁参数。
   导入后出现"我没改过的 `.import` 却被改了"，先怀疑导入环境。
2. 🔴 **不要用一次性新建的隔离 APPDATA 跑 `--import`**；要用就选有缓存的环境，
   且跑完**必比对 sha256**。
3. 🔴 我上一轮把 import 日志里 16 条 `invalid UID ... using text path instead` 当既有噪声放过了。
   其中确有历史成因（`dtuahqaj31kp2` 只 13 字符、Godot 4.6 合法 UID 为 14 字符；
   项目 2026-10-09 块00文档已记录过该回退），**但成片出现时该先核对 `.import` 的 `uid=` 有没有被动过**。

⚠️ 顺带发现同源风险、**未擅自改**：`enm_boss_monitor002_visual_top3d_body_palette.png.import`

## 事务：99F 基地「灯的模型不该投影」——打包后地板出现悬空圆斑

业主给两张对比图：图1（编辑器）无投影，图2（打包后）地板上出现一块大的悬空圆形暗斑。

### 🔴 根因（三方叠加，全部实测确认）

1. **99F 中央玩法主灯挂在 11.62m 高空**：`DungeonRoom3D._install_base99_facility_lights()`
   里 `light_root.position.y = TOWER_GEOMETRY.FLOOR_HEIGHT_M - 2.72`
   （12m 层高 − 2.72m 灯具顶装高度）。主灯 prefab
   `assets/art/props/dungeon_3d/prp_base99_facility_main_light_top3d.tscn`
   写着 **`cast_shadow = true`**，`light_range = 28.05`。
2. **吊灯挂在 ~2.5m** ⇒ 灯在灯罩**正上方**，灯罩轮廓被放大投到地板。
3. **灯具外壳没关阴影**。GLB 导入出的 `MeshInstance3D`，`cast_shadow` **默认 ON**；
   而规约只有 `61_仓库防爆吊灯组` 显式写了 `cast_shadow = 0` —— 同批 v021 的

**为什么编辑器看不出来**：那盏主灯由**代码在运行时实例化**，编辑器视口里根本不存在 ⇒
没有任何光源去投这个影。属「只在运行时才暴露」的契约缺口 —— 和第 4 条
（`.gdignore` / `exclude_filter` 只在导出后炸）是同一类病。

**主灯自身的投影不能关**：`WastelandLight3D.apply_performance_quality` 注明
「当前房主灯投影是玩法信息；档位只改变阴影图集精度，不移除投影」。⇒ 只能关灯罩。

### ✅ 修复（4 个预置件，与 61 同口径）

`get_path_to()` 打印 —— Godot 会把节点名里的 `.` 换成 `_`

## 事务：99F 基地东西两条走廊「南面墙反面朝走廊」（业主截图报障）

业主给一张 99F 基地实机截图：「东西两边走廊（基地与楼梯间中间那两条）**南面的墙是
反面对着走廊的**，把这几面墙翻转过来。」

### 🔴 根因：走廊两侧墙共用一个朝向常量，而墙件是**单面装饰**

`TowerDescent3D._build_stair_approach_corridor()` 里两侧墙用同一个 `wall_rotation_y`：

```gdscript
wall.position = module_center + perpendicular * side_sign * (PASSAGE_WIDTH_M * 0.5)
wall.rotation.y = wall_rotation_y        # ← 两侧共用
```

而墙件 `ENV-TOWER-WALL-SOLID-5M` 的**装饰面朝局部 +Z**，依据不是猜的 ——
`art_source/.../wall_height12/export_env_tower_wall_solid_5m_v004.py` 第 21–28 行写明：
源组件 `front_axis_blender="+Y"`，经 180° yaw 后落到 Godot **+Z**（塔楼 A 套
`EXPECTED_FORWARD_AXIS="+Z"`；对比 `verify_common_wall_door_components_v004` 里
战斗套是 `-Z`）。manifest 也印证：solidd 的 `bounds_blender.y ∈ [-0.3175, +0.15]`
**不对称**（单面），而门墙 v005 是对称的 `±0.3415` 并带 `double_sided: true`。

⇒ 走廊是通道，两侧墙必须「装饰面各自朝走廊内」，**朝向必须差 180°**。
共用同一个角度时：北（西）侧那面恰好对，**世界南（东）侧那面把结构背板朝了通道** ——
正是业主看到的那面。

**精确命中的证据**（反向对照日志里的失败名单）：失败的只有
`StairApproachWall_Lower_B_I00..I02`（3 模块 = 15m）与
`StairApproachWall_Upper_B_I00..I03`（4 模块 = 20m），即
**Stair_A 下段（基地西侧）＋ Stair_B 上段（基地东侧）**这两条 99F 走廊的 B（= 世界南）侧。
另外两段接驳走廊（100F 上段 / 98F 下段）`length <= 0.05` 短路、根本不生成墙，
所以全塔楼恰好只有业主报的这两条中招 —— 「东西两条」与失败清单一一对应。

### ✅ 修法（同一个逻辑错误两处，一起修）

`side_sign > 0`（世界南／东侧）的墙额外绕 Y 转 180°：

| 位置 | 改动 |
|---|---|
| `_build_stair_approach_corridor()`（业主报的接驳走廊） | `wall.rotation.y = wall_rotation_y + (PI if side_sign > 0.0 else 0.0)` |
| `_build_tower_horizontal_corridor()`（98F 那 15 条水平走廊，同源同错） | `var side_basis := wall_basis * Basis(Vector3.UP, PI) if side_sign > 0.0 else wall_basis` |

水平走廊是**同一段代码的同一个错误**，不修就是留坑 ⇒ 一并修掉（已如实告知业主范围）。
碰撞、门槽、`camera_lower_wall` 标记都**不看视觉旋转**，所以全无连带。

**副产物（是好事）**：翻转后走廊两壁的装饰凸出都朝内，视觉净宽
4.53m → **4.36m**，与碰撞盒净宽 4.40m 基本重合（改前视觉比碰撞宽 0.13m，

- 自动创建 `Godot/app_userdata/弹壳风暴2/base_save.json`，**revision = 4**，
  退出码 **0**、无崩溃 ⇒ **首次运行无存档可正常初始化**。
- 对比本机真实存档：revision = 55316 / 25058 B（新档 18083 B）⇒ 确实是全新档。
- **包内不含存档**：在 exe 二进制里检索 `base_save` / `save_reset_backup` /
  `expedition_debug_unlock` **均未出现**（对照 `res://scenes/` 命中，证明检索方法有效）。
  （`app_userdata` 字样命中，那是 Godot 引擎自带的路径模板字符串，非玩家数据。）

⇒ **你的进度不会跟着包发出去。**

### ⚠️ 但在自己机器上跑导出包 = 用你现有存档

导出包与编辑器**共用同一个 `user://` 目录**（实测：2026-10-12 18:35 跑导出包后，
本机 `弹壳风暴2/base_save.json` mtime 与 `revision` 均前进）。
⇒ **自测导出包会动真实存档**。要隔离测试就用：

```bash
APPDATA="<某个空目录>" ./ShellStorm2.exe
```

（Godot 无 `--user-data-dir` 参数，靠 `APPDATA` 环境变量重定向即可。）

### ⚠️ `config/name` 已锁死，发版前不得改

存档路径由它派生。**改名 = 所有人（含自己）的旧存档"凭空消失"**
（文件其实还在旧目录，只是新名字读不到）。要改必须先写迁移逻辑。

### ⚠️ 多实例并发写同一份存档

2026-10-12 18:3x 实测：本机同时有 **3 个 Godot 编辑器实例**在跑，
其中在运行游戏的实例持续写存档 —— 几分钟内 `revision` 从 55308 涨到 55316。
`BaseManager` 有 revision 保护（日志里的
`Refusing stale save: memory revision X < disk revision Y`），
表现为「在这个窗口的进度在另一个窗口看不到」。
⇒ **需要确定性存档状态时，同时只跑一个实例。**
