## 实测：四类通用物体的节点来源与资源分享性（回答「这些节点都指向同一个 prefab 吗」）

### 追加取证：塔楼内容为什么会污染远征场景（结构性根因）

用户追问「为什么塔楼的场景东西会污染到远征关卡的场景」。结论分四层：

1. **机制层：远征不是「新场景」，是塔楼场景的继承场景。** `scenes/ExpeditionLevel01_3D.tscn` 全文只有 `[node name="ExpeditionLevel01_3D" instance=ExtResource("1_parent")]` + 3 个属性覆盖（`expedition_mode` / `expedition_run_id` / `return_scene_path`）+ 1 个新节点 `Blocks/Expedition`。**全项目 25 个 `scenes/*.tscn` 里只有它是继承式关卡**（`BaseWorld3D` / `TrainingRange3D` / `Dungeon3D` 都是 `type="Node3D"` 独立根）。所以塔楼内容不是「泄漏」进来的，是**加载即在**。
2. **为什么塔楼没事、远征出事：塔楼靠「后续步骤」把它变无害，而那步骤的前置条件是塔楼独有。** 关键事实——`Blocks/Base/Art` 是整个 `Blocks` 子树里**唯一带实质内容的节点**（Rooftop/Battle/Stairs 在 tscn 里都是空容器，且 `Rooftop` 的 `facility_art_state=removed_by_user`）。它变无害**只靠** `_install_facilities()`（:4098）里的 `_facility_art_layout.reparent(facility_floor, false)`（:4106），把它挪进 99F `facility` 房（该房 `position.y=-12`）。而该函数第一行守卫 `if facility_floor == null ... return` —— 远征没有 `facility` 房（验收脚本本身断言它必须不存在）→ **守卫命中 → reparent 从未执行 → Art 停在作者坐标 y≈0**。场景文件里 `枪械工坊` 的 transform 末三元就是 `2.8696804, 0, -31.346287`，y=0 铁证。`_ready()` 的兜底 `visible=false` 只管渲染不管碰撞，从来挡不住。
3. **第二条通道：`floor_index == 0` 语义撞号。** 远征单层唯一层 index=0，而 0 被塔楼保留给 100F 天台 → `TowerFloorStage3D` 与 `_outer_visual_transform()` 静默给出窄轮廓/中庭洞/0.75m 女儿墙/0.5 纵向缩放。这是**语义污染**，不是节点污染。
4. **第三条通道：区块路由有 helper 却不用。** `_room_block_for_floor()`/`_block_id_for_floor()` 都写了远征分支，`_build_tower_horizontal_corridor()` 却直接 `_block("Battle").add_child()` 绕过。

**结构性根因（值得记住）**：`TowerDescent3D.gd` 里有 **31 处散落的 `is_expedition()` 判断**。架构是「先按塔楼算全部，再逐条减掉远征例外」，且守卫风格三类不统一：
- 显式门禁 ✅：`_install_simple_transit_door_components()`(:3458) `if is_expedition(): return`；`_install_main_entry_screen()`(:4456)；`_refresh_tower_hud()`(:4490)
- 隐式门禁（碰巧对）⚠️：`_install_facilities()`(:4098) / `_install_elevator_facility()`(:4194) 都靠 `facility_floor == null`
- 无门禁（可接受但说明无统一策略）：`_install_atmosphere()`(:4359) / `_install_tower_hud()`(:4369) / `_install_world_time_hud()`(:4416)

### 但深挖产出后抓到两个真缺陷（都是我上一轮引入的）
写探针把「按设计源生成」(数据驱动) 与「内置生成器」的产出**逐字段摆在一起比**，发现：

**缺陷 1 · 功能房的 `type` 整批丢失。**
| role | 内置写死 | 数据驱动曾产出 |
|---|---|---|
| `stair_entry` | `STAIR_LOBBY` | **空** |
| `stair_exit` | `STAIR_LOBBY` | **空** |
| `extraction` | `EXTRACTION` | **空** |
| `boss_prep` | `UPGRADE` | 曾被误赋 `BOSS` |

根因：内置路径的 `type` 是 `_room()` 调用时**写死的常量**，`_shuffle_content_types()` 只覆盖「内容房」；功能房的类型从来不来自洗牌。我上一轮只实现了「洗牌 + 排除功能房」，漏了「功能房的类型缺省值」。
**为什么静态校验抓不到**：这几个 `type` 不在设计源 schema 里（`content_type` 是可选覆盖、缺省空是合法状态），也不参与任何几何校验 → `LEVEL_PLAN_VALIDATE_OK` 全绿、生成器 `valid=true`，全程无声。

**缺陷 2 · `content_room_count` 算错。** 数据驱动算 6，内置远征硬编码 `EXPEDITION_ROOM_COUNT = 5`。因为只排除 `stair_entry/stair_exit`，**漏排 `extraction`**。

### 修复
1. 新增 `FloorPlanGenerator._default_type_for_role(role)`：功能房 role → type 缺省映射，**与内置房表逐值一致**（`STAIR_LOBBY`/`EXTRACTION`/`BOSS`/`UPGRADE`）；设计源显式写了 `content_type` 仍以设计源为准（钉死优先）。
2. 新增 `const FUNCTIONAL_ROLES := ["stair_entry","stair_exit","extraction","boss","boss_prep"]`，`content_room_count` 改为排除全部功能房（远征回到 5 ✅）。
3. `_assign_content_types_data_driven` 的 skip 列表改为「boss 恒 BOSS + 其余功能房保留缺省值」。

### 补的护栏：`verify_level_plan_design_source._verify_runtime_outputs()`
直接调生成器，逐房断言：功能房 type 命中期望值 / 内容房 type 非空且不是功能类型 / 尺寸非零 / `content_room_count` 与实际相符。
- **刻意把期望表在断言侧独立重写一遍**，不共用生成器常量 —— 共用会让断言失去意义。
- 新判据 `LEVEL_PLAN_RUNTIME_GUARD_OK levels=2 rooms=23 checks=2`，与 `LEVEL_PLAN_VALIDATE_OK` 并列（**两条都要看到**）。
- **负向测试已做**：把 `_default_type_for_role("extraction")` 改成返回空串 → `LEVEL_PLAN_RUNTIME_LEVEL_FAILED expedition_01 ... LEVEL_PLAN_RUNTIME_ERROR expedition_01 floor 0 room extraction: role=extraction 的 type 应为 EXTRACTION，实为 <空>`，而**同一轮 `LEVEL_PLAN_VALIDATE_OK` 仍然通过** —— 正好实证「静态自洽 ≠ 产出可用」。

### 比对结论：剩余差异全是设计意图，不是 bug
| 差异 | 性质 |
|---|---|
| 坐标（data 往 −y 蛇形，builtin 往 −x） | 设计源 `authored` 模式「表即最终版图」vs 内置每局随机旋转 → **设计要的效果** |

| `layout_id` 不同 | **存档问题的实证**：切过去玩家那层的身份记号会变 |

`entry` 修复后**完全一致**；`extraction` 只剩坐标差异。

## 新关卡怪物刷新控制点定位（16:57，只读查证，未改任何文件）

主人问「新关卡的怪物刷新是在哪里控制的」。全链定位如下（行号会漂，用函数名 grep）。

**唯一入口** `Dungeon3D._spawn_room_enemies(room)` (`src/world3d/Dungeon3D.gd:1926`)。

4. `desired`（:1945，仅 `_:` 默认分支即 COMBAT 等）：`4 + floor*2 + (2 if large / 4 if arena)`。
   单次 `MonsterInjector._generate_random_enemies` 出 `2 + floor` 只（`MonsterInjector.gd:93`），不足 `desired` 则**再抽**（上限 `ENEMY_FILL_ATTEMPT_LIMIT`=4，:41），仍不足走 `safe_fallback`。

**怪物种类 / 数值**：`_monster_injector`（`src/map/MonsterInjector.gd`，`class_name`，:720-722 构造并 `set_theme_profile(gameplay_theme)`）。

- 数值基数 `BASE_ENEMY_TYPES`（:6）+ 楼层缩放 `FLOOR_SCALING`（:41，按 floor 1-5）。

**刷在哪**：`room.enemy_spawn_points`（`DungeonRoom3D._build_spawn_points:2439`，环形均布、半径 = 房间尺寸 × 0.23，`configure()` 时算好，用 `global_position`）。**容器是 `$ActiveEnemies`，不是房间子树**（`Dungeon3D.gd:2064`）。

**能/不能按关卡定制（关键结论）**：设计源 JSON **只能定 `content_type`**（COMBAT/ELITE/BOSS…，决定走哪个分支），**定不了**数量/波次/怪物种类 —— 那些全是全局公式 + 主题。要按关卡定制只有三条路：① 换/改 `MapThemeProfile`（`enemy_rules`）② 改 `floor_level` 折算公式 ③ 在 `_spawn_room_enemies` 加关卡级 override。
