# 角色模型制作、反推与 Godot 导入

先证明角色的运行时契约，再改 Blender 文件或制作新角色。ShellStorm2 的新角色制作使用模型/动作双 Blend、共享骨架和严格导出中转台账；已有节点驱动消费者通过表现适配层接收骨动作，保持玩法功能层级。

处理 ShellStorm2 时先读项目 `docs/v0.1/16.1_角色美术制作与动作导入流程.md`，这是当前制作与导入标准；旧资料中的单文件、仅程序动作和 v006 当前版本描述不再作为生产规则。

## 边界

- 适用：玩家外观、可换装部件、NPC、敌人、Boss，以及角色专用的视觉根、挂点和动画资产。
- 不适用：枪械和近战武器使用 `game-weapon-model-pipeline`；独立可拾取道具使用 `game-prop-model-pipeline`；场景、关卡组件和固定设施使用环境与设施两套 skill。
- 角色资产提供视觉、角色骨架或节点层级、角色挂点和角色动画；角色控制器保留移动、主碰撞、HP、输入、AI、状态机、攻击判定与网络权威。

## 强制反推

每次创建、替换或导入角色前，建立或更新该角色的简短契约记录。至少完成：

1. 找到正式运行时消费者：PackedScene、角色脚本、动画/状态机、装备与换装代码、碰撞拥有者，以及针对该角色的验证测试。
2. 找到目标 `.blend`、对应 GLB、包装场景、资产清单和版本链；运行项目提供的 Blender 审计或验证脚本。没有 Blender 可执行文件时，只能记录“源文件未审计”，不能将清单或截图视为 Blender 验证。
3. 逐项确认根节点、单位、原点、前向、运行时缩放、真实包围盒、碰撞归属、动画形态、骨骼/节点名称、槽位和挂点。将“创作尺寸”和“运行时展示尺寸”分开记录。
4. 当 `.blend`、manifest、运行时代码或测试存在差异时，记录差异并以目标运行时消费者和对应验收测试为交付基准；不得通过隐藏缩放或单件脚本补偿掩盖冲突。
5. ShellStorm2 的当前玩家证据、Blender 审计入口与已知特殊约定见 [references/shellstorm2-character-reverse-contract.md](references/shellstorm2-character-reverse-contract.md)。处理其他项目时，按同一证据顺序重建对应资料，不套用 ShellStorm2 数值。

## Blender 制作

1. 从选定角色母版或已审计源文件的新版本开始，保留可维护的 `.blend`；不覆盖母版、旧版本或原始资产。
2. 模型与动作分别保存为两个主要文件，使用相同骨架 ID、骨名、父子关系、静止姿势和单位；动作文件预览关联模型几何。模型文件负责网格/UV/贴图/配件与绑定，动作文件负责可编辑 Pose Actions。导出时重新计算两文件骨架签名，差异必须先修复。
3. 模型集合采用“部件 / 配件名称”两级 Collection；配件名称本身也是集合，容纳该样式的多个网格。用 slot_id/variant_id 登记，颜色变体优先共用几何。预览环境与共享骨架各自分组，预览物不得导出。
4. 先判定运行时动画消费方式：
   - **骨骼角色**：保留已验证的 Armature、骨名、父子关系、静止姿势、权重、动画剪辑和根运动约定。骨骼改名、层级变化或重定向必须同步修改运行时消费者与测试。
   - **节点驱动角色**：保留功能节点和挂点层级，用固定骨名到表现节点映射消费 Blender 评估动作。明确用户要求迁移时，可一次性采样原表现用于建立可编辑骨骼动作基线；之后 Blender 动作文件为创作源，不再反复从程序覆盖美术关键帧。
5. 可换装角色仅在已有运行时支持的槽位内拆分 GLB 和包装节点；身体、头、手、脚、帽子、眼镜、下身、耳饰或其它槽位的实际名称以项目代码为准。部件不能改变角色主碰撞、控制器或武器逻辑。
6. 角色拥有装备/外观挂点，武器或道具拥有自己的握点。角色侧只维护已定义的 `WeaponSocket`、背负、背包、服装或饰品 socket；武器侧 `GripSocket`/项目定义握点与角色 socket 的对齐由现有装备流程验证，不新增每件资产专用的角色补偿。
7. 面向动画的部件必须在目标待机、移动、受击、攻击、装备与换装姿势中检查穿插和枢轴。动画仅驱动已确认的角色骨骼或节点，事件与伤害判定仍由项目状态机控制。
8. 导出副本使用二进制 `.glb`，只含视觉网格、经验证的骨骼/节点、动画和必要挂点。展示地面、相机、灯光、玩家碰撞体、武器和道具不进入角色 GLB。动作文件里的预览武器即使位于链接 Collection、父级 Empty 或非当前场景，也必须在动画 GLB 导出副本中物理剔除；不能只依赖 `use_selection` 或隐藏标记。

## Godot 导入与验收

导出前后必须有机器可校验中转账本，记录模型/动作源、骨架签名、部件/样式、各输出 SHA-256、动作时长/循环/轨道、消费者、版本、测试结果及回滚位置。顺序为 authored → exported_pending_godot_validation → validated → active；源或输出哈希变化后重新验证。资产 XLSX 是人工索引，版本包 JSON 是逐文件中转记录，两者引用同一个包。

ShellStorm2 在正式导入前还必须运行 `python3 scripts/asset_guard.py <版本包目录> --classify <reuse|replacement|version_increment|child_variant>`。同 AssetID 或同哈希不是自动错误，但必须明确归类并保留报告；未分类重复阻断接入。

Godot 状态机只输出状态和真实进度，表现适配器据此选择动作。动作不得写玩法根变换、碰撞、伤害或存档，也不得因动画播放结束改变功能状态。真实瞄准、武器握持、换弹/近战进度通过现有约束层处理；基础动画与约束不能在同一通道不加说明地重复驱动。只要武器存在，实时 `GripSocket`/支撑手约束拥有双手最终全局变换，Blender 持枪剪辑负责其余身体轮廓；采样身体后必须重新满足握点与枪口方向，不能让预览枪姿势反向移动运行时武器。

完整重制包的动作门槛必须是“玩法必需状态集合 + 明确登记的表现变体”的精确集合，校验状态 ID 唯一、无缺项、无额外临时 Action，并逐项核对循环标记。完整包不得继续静默读取旧版本动作；只有在台账中逐项列出依赖、用途和哈希的增量包才可回退。

1. 角色 GLB 放入稳定版本目录，建立或更新独立 PackedScene/变体场景。正式根的缩放保持 1；视觉尺寸变化回到源文件或按已批准的包装层契约处理。
2. GLB/角色变体只负责视觉、材质、角色组件、角色挂点和已批准的动画。`Player3D`、敌人控制器或 NPC 控制器继续拥有移动、碰撞、AI、HP、输入、战斗和状态机。
3. 换装只修改表现层并写入已有的合法外观/角色 ID 流程。所有未知、旧或无效 ID 都按项目既有回退策略处理，不能让存档加载失败。
4. 正式重新导入后，验证独立加载、节点/骨骼契约、根缩放、方向、包围盒、碰撞不变、挂点对齐、动画状态、换装/装备和实际场景截图。需要角色动画时，分别验证导入剪辑与角色状态机的时序，而不是只看 GLB 可播放；同时验证预览武器未进入动画 GLB、模型包装无碰撞节点、功能场景除 Avatar PackedScene 引用外没有结构性变化。
5. 更新源 Blend、GLB、PackedScene、资产 ID、角色类型、槽位、版本、包围盒、动画形态、运行时消费者、测试入口和回滚位置。

## 交付边界

- 新角色视觉或外观变体：交付新版本源 Blend、GLB、包装场景、预览、契约记录与通过的验证。
- 需要新增槽位、骨骼、动画状态、碰撞类型、AI/战斗接口或装备 socket：这是角色运行时系统改动，必须同时修改消费者与测试，不应伪装成单纯美术导入。
- 对可更换外观，先验证现有槽位和动画能容纳该部件；不以改 `Player3D` 主碰撞或临时缩放为捷径。
