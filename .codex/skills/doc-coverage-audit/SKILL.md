# 三层文档一致性审计（doc-coverage-audit）

## 何时用

主人问「设计文档 vs 里程碑文档差多少 / 缺什么 / 哪些规格没人接」时。
**核心产出不是「任务表漏了什么」，而是「断层在哪一层」。**

## 铁律（先读这条，否则必答错）

**不要只比一层。** 这类问题最容易被答成「两份文档一致、只是任务没写」——
而真正常见的形态是**断层在上游**：

```
设计文档 (GDD / M / P)      完整、自洽
      │
      │   ← ★ 断层常在这里（里程碑切分时窄化，整块范围没接）
      ▼
里程碑文档 (DEV-00 §3)      只吸收「主干」范围，丢了流程/模式/工具
      │
      │   ← 这层通常"基本忠实"
      ▼
任务表 (DEV-05)             于是"天然"没有这些行
```

⇒ **任务表缺的，往往是里程碑文档自己就漏掉的忠实投影。**
只补任务行 = 下一轮切分**会再丢一次**（F-154 族反复复发的机制）。
正确顺序：**① 修上游范围/冲突 → ② 补里程碑「范围内」→ ③ 才立任务行。**

## 步骤

1. **建清单**：把任务表解析成结构化行（ID / 标题 / 状态 / 状态计数）。
2. **抽设计项**：从设计文档抽「可命名功能项」（模式、流程步骤、HUD 组件、工具、发布项），
   每项标注**它应该在哪个里程碑**。
3. **逐层命中**：每项在 `里程碑文档` 与 `任务表` 各做一次命中统计 →
   分成「双零 / 单零 / 有承接」三档。
4. **★ 人工裁定（不可省）**：把零命中项逐条回查，分开
   - **真缺口**（设计文档以「首版 ✅」或「验收标准」形式写明 = 硬需求）
   - **同义改写误报**（例：`地块场景实例化`→任务行写`RoomTile 场景 + 地块实例化`）
   - **明确不算缺口**（写在「范围外 / 非目标 / 不实现」段）
5. **对账已登记缺陷**：回查 gap-log，已登记的不重复计数。
6. **找硬冲突**：逐个比对**枚举型内容**（状态机态数、模式清单、菜单项数）——
   这比关键词命中更能抓到真问题。
7. **出报告**：缺口清单分级（按应在里程碑 + 是否已进过里程碑「范围内」）+ 工作量估算 + 补救顺序。

## 血泪坑

### 1. 关键词匹配会**严重高报**——必须人工裁定
实测一次：脚本对 127 项报「零命中 37 项」，**人工裁定后真缺口仅 3–5 项**（32 项是同义改写）。
**永远不要把脚本输出直接当结论报上去。**

### 1b. **结构/标题扫描**比关键词高报更甚——几乎全是噪声
别用「抽出每份文档的 `##`/`###` 标题逐个查命中」当覆盖判据。
实测：对 51 份设计文档扫 H2 ⇒ flag **235 条**，其中 **≈99% 噪声**，成因两类：
- **共用模板**：模块文档 M01–M29 有一套固定节（`2. 玩家可见行为` / `3. 输入与输出` / `10. 待核对`），
  它们是**结构位**不是功能项（且已被「固定节齐备」审计盯着）；
- **概念级标题**：GDD 的 `电梯陈述` / `核心循环` / `配色规范` 本就不该在里程碑里字面出现。

⇒ 覆盖判据只认**两种可靠信号**：
| 信号 | 做法 | 抓什么 |
|---|---|---|
| **策划级探针** | 手拟「可命名功能项」（模式/流程步骤/HUD 组件/工具/发布项），每项带设计出处 | 真缺口 |
| **模块编号引用矩阵** | 数 `DEV-00` 对 `M01..M29` / `GDD-xx` / `P-xx` 的引用次数 | 整块未吸收的模块 |

**引用矩阵的读法**：零引用 ≠ 缺口，必须回查内容落点，分三档——
`内容缺口`（真的没有）/ `引用缺口`（内容在、只是没点编号）/ `非功能模块`（如制作计划 M27、路线图 GDD-08 本就无需被引用）。

### 2. 枚举型内容要**逐字比对**，别用关键词
最致命的一类冲突是**态数/清单项数不一致**，关键词命中抓不到。
例：设计文档写顶层**五态**（含 `Setup`），里程碑文档三处都写**四态** ⇒
`Setup` 从切分那刻就不存在，还被验收断言固化成「不存在」。
查法：把两侧的状态/模式/菜单清单**并列誊出**逐个数。

### 3. 大文件读不动
`gap-log` 这类文件可达 **0.5MB**，`Read` 会因超过上限失败。
⇒ 用 `Grep`（按 `F-`/`G-` 编号）或 Python 脚本按行筛，不要硬读。

### 4. Windows + 中文路径的取证姿势
- Bash 工具下**中文路径作参数或 `cd` 参数会静默失败**（`&&` 短路、后续命令不执行、退出码 1，
  且输出为空与「确实没搜到」**无法区分**）。⇒ `cd` 到纯 ASCII 位置后用**相对路径**。
- `grep` 输出中文可能**编码错乱**（GBK 乱码），无法阅读。
  ⇒ **一律用 Write 落一个 Python 脚本到 `_scratch/`，再 `python <脚本>` 输出到文件后用 `Read` 看**。
- 用 Python 时显式 `io.open(..., encoding="utf-8")`，输出也写 UTF-8 文件（不要靠终端）。

### 5. 脚本落位
临时脚本/中间表放**仓库外**的 `_scratch/`。
放仓库内会被 `git add -A` 扫进去，弄脏工作树。

### 6. 追加行到既有文件时守行尾
有的文件是 **LF-only**（追加前先断言 `b"\r" not in content`），有的是 CRLF。
**写错行尾 = 整个文件显示为 modified。** 用 `io.open(..., "ab"")` 追加字节最稳。

### 7. 只报告，不擅自改裁定类文档
「规格缺了什么」→ 补任务行属**验收方权限**；
改设计文档 / 里程碑范围 / 已验收产物 ⇒ **必须先经主人裁定**。
不要为了让报告「好看」而动文档（更不许放宽审计脚本）。

## 输出模板

```markdown
## 一句话结论
<断层在哪一层 + 总量>

## 三层一致性
| 层对 | 结论 | 证据 |
|---|---|---|
| 设计 ↔ 里程碑 | ? | 硬冲突 N 处 + 窄化清单 |
| 里程碑「范围内」↔ 任务表 | ? | X 项中真缺口 Y 项 |

## 硬冲突（逐字比对枚举型内容）
## 缺口清单（分级 + 应在里程碑 + 是否已登记）
## 明确不算缺口
## 工作量估算
## 补救顺序（① 上游 → ② 里程碑范围 → ③ 任务行）
```

## 自检

- [ ] 三层都查了，没有只答「任务表漏了」？
- [ ] 脚本输出经过**人工裁定**，误报已剔除并列出样例？
- [ ] 枚举型内容（态数/清单）逐字比对过？
- [ ] 已登记的缺陷没有重复计数？
- [ ] 报告写入**仓库外**，仓库工作树干净，行尾未错？
- [ ] 没有擅自修改任何裁定类文档？
