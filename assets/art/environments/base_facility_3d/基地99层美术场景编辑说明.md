# 基地 99 层美术场景编辑说明

日常关卡美术编辑请直接在 Godot 编辑器中打开主场景：

`res://scenes/TowerDescent3D.tscn`

在主场景树展开 `Blocks/Base/Art` 即可。运行时，代码会先隐藏 `Art`，再把它重新挂到程序生成的 99 层房间。

`../tower_zones/base/runtime/zone_base_v002.tscn` 是可复用子场景，一般不需要单独打开。

## 可以安全调整

- `设施交互节点_可移动旋转`：移动、旋转现有设施。保留每个设施的 `facility_id`，不要改变根节点类型。
- `基地结构组件_可移动旋转`：直接摆放楼中楼楼板、L型楼梯、外门小楼梯，以及完整的100层上层围护与封顶组合Prefab。每个实例自带局部结构碰撞，移动或旋转时碰撞会同步。
- `场景装饰_可自由增删`：添加或删除纯视觉模型、贴花、粒子和无玩法用途的小道具。
- `基地美术灯光_可编辑`：**这一组是受东/西墙那对开关控制的美术灯**（2026-09-24 接入，此前它们不受任何开关管 —— 曾因此出现「关了开关这盏灯还亮着」）。规则只有一条、不需要额外登记：**本节点下你手摆的原生 `OmniLight3D` 全部跟随墙面开关**，每盏灯自己的 `visible` 表示「这盏灯是否参与」；出厂三盏全 `false`（不参与、保持历史参考），开关只决定「此刻亮不亮」。实现在 `BaseFixtureGlow3D._collect_authored_art_lights()` + `_apply_spill_visibility()`：入树时记下 `visible` 作为作者意图，之后由开关状态与它做与运算。**开启时序（2026-09-24 业主指定）**：设施自发光走那条约 5 秒的 18 批启动序列，而**手摆美术灯不参与分批** —— 由 `BaseFixtureGlow3D.AUTHORED_ART_LIGHT_DELAY_SECONDS`（当前 **2.0 秒**）统一延后一次点亮，免得主光级的手摆灯抢在第一批「啪」地先亮；这条延迟与分批序列并行推进，不改变序列总时长。**要调这个延迟就改那个常量**（单位秒，实测口径见 `tests/verification/probe_facility_light_startup_timeline`）。关灯仍是瞬时的，延迟只作用于开启。它们保持原生 `OmniLight3D`、**不换成 `WastelandLight3D`**，以免被注册进玩法光照判定（`EnemyIllumination3D` 只认 `WastelandLight3D`）。
  ⚠️ **易混点**：「中央冷色主灯」**不是**玩法主灯 —— 真正的玩法主灯是运行时由代码生成、**在场景树里根本不存在**的 `FacilityCeilingLight_Main`（见下条）。这里的三盏数值必须写在 `scenes/TowerDescent3D.tscn` 的 override 上才有意义，改 `zone_base.tscn` 里的出厂默认值不会影响塔楼（塔楼实例的是 `zone_base.tscn`，但 override 会盖掉它）。当前 override：中央冷色主灯 `y = 9.273571`、`visible = true`、`light_energy = 16.0`、`light_color = (0.6439, 0.3917, 0.0770)`、`light_indirect_energy = 7.112`、`light_volumetric_fog_energy = 9.629`、`light_size = 0.084`；西北紫色／东南暖色两盏仍停用（`visible = false`），要启用就把 override 里的 `visible` 改成 `true`，它会自动进入开关控制。
- `res://assets/art/props/dungeon_3d/prp_base99_facility_main_light_top3d.tscn`：**99F 中央玩法主灯（东、西墙成对开关控制的那一组）的数值真源**。直接改 `light_color`／`energy`／`light_range`／`cast_shadow`／`failing`／`fixture_style` 即可，无需改代码。**它在编辑器场景树里找不到** —— 运行时才由 `DungeonRoom3D._install_base99_facility_lights()`（调用点 `ensure_shell_built()`）实例化，节点名 `FacilityCeilingLight_Main`，直挂 `DungeonRoom3D` 房间根、世界高度 11.62m，开关点开后由 `RoomLightSwitch3D.STAGED_MAIN_LIGHT_START_SECONDS` 在**第 4.5 秒**点亮（手摆美术灯早它一步、约 2 秒，见上条）；要现场确认它，用编辑器的远程/运行时场景树看这一层，或在游戏里按东西墙开关。三条硬约束：① **位置不许写进 prefab** —— 挂位由 `DungeonRoom3D._install_base99_facility_lights()` 按 `FLOOR_HEIGHT_M(12.0) − 2.72`（再加顶灯自身偏移 2.34）推算，写死在 prefab 里会在层高常量变更后静默错位；② Forward+ 下实际渲染能量 = `energy × 3.0`（见 `WastelandLight3D._get_render_energy`），即填 8.1 实渲染 24.3；③ `light_range` **必须 ≥ 28m**，`verify_facility_light_retoggle_visual` 的地板亮度门禁依赖它。**在该 prefab 内加灯**：新增的 `WastelandLight3D`（子树任意深度）会被自动收集、纳入同一组墙面开关统一控制，无需改代码。
- `玩法锚点_只移动不删除/99层电梯锚点`：可移动或旋转，以改变 99 层电梯的位置与朝向。

## 编辑器参考

`编辑器参考_运行时自动隐藏` 提供 30×30 米地面和四面墙边界，只用于摆放参考。代码桥接在运行时会自动隐藏它，不会生成碰撞，也不会进入正式画面。

## 结构模块

基地外圈和地面由 `DungeonRoom3D.gd` 按稳定Prefab组合；室内楼板和楼梯则放在可编辑美术布置层：

- 地面：6×6个5米单元，普通板与铆钉铁皮板各18个，棋盘式交错。
- 两种地板共用0.30米结构板顶面作为唯一摆放基准；铆钉板上方的铁皮压条和铆钉只负责表现，保留突出高度但不追加碰撞。承重始终由`TowerFloorStage/FloorSupport`的统一平面负责，禁止用铆钉板的AABB最高点下压整件模型。
- 99层外墙：14个普通墙、0个窗墙、2个带门墙；东、西门洞保持原玩法连接。窗墙只登记给100层上层围护，禁止放入99层外圈。
- 100层上层围护：从本地高度12米延伸到24米（`ENV-BASE100-UPPER-SHELL-30X30-H12`）。24块墙中：北面2块普通墙＋中间4块窗墙、东面1块门墙（东面 `z=-7.5` 门洞槽）保留 base99 件；东西南三面17块（南6／西6／东5）改由天台参考组件库 v002 的房间标准墙承接。北墙严格为“两端普通墙＋中间四块窗墙”，其余墙面不放窗墙。⚠️ 天台 v002 件外法线朝局部 +Z，与99F系（-Z 朝外）差 180°：同一条边 base99 用 -90°，v002 用 +90°。
- 24米封顶：由天台参考组件库 v002 房顶模块组成6×6、共36块（角板4＋边缘板16＋完整板16，摆 `y=24`、顶面 `y=24.3`）；它属 `ENV-BASE100-UPPER-SHELL-30X30-H12` 组合Prefab，不恢复此前移除的99/100层中间36块楼板。房顶收口在局部 +Z/-X 侧，6×6 网格四个角格 `rotation_y` 依次为 0°／+90°／180°／-90°。
- 门扇：2个独立滑升门模型，只挂到既有 `RoomDoor3D` 动画节点下。
- 二层：一个约20×10米、完成面5米高的楼中楼楼板，Blender母版初始坐标为 `(5, 0, -10)`。其子节点`楼中楼下方工业仓库挡板_随楼板移动`为独立组件，当前视觉为`v003`冷灰横向分板与约2.4米节距的竖向钢架；三面向内收0.55米，不得移动到楼板外缘或改为可交互物。包装场景提供永久阻挡，禁止玩家进入楼板底部。
- 楼梯：L型楼梯初始坐标约`(-9.58, 0, -9.15)`并连接`0→5m`；当前视觉为`v006`，由完整v002源组件重建，踏步、斜梁和平台不可缺失。两跑扶手在转角平台前收口，由平台L形护栏接管转角，禁止交叉穿插。H4外门小楼梯中心为`(10.78, 5, -7.5)`，使坡顶精确落在东墙`x=15m`的100层门槛，连接`5→12m`且不附加额外90度旋转。
- 99/100层贯通：100层位于基地正上方的6×6、共36块地砖及对应承重碰撞已移除，该处现由 `ENV-BASE100-UPPER-SHELL-30X30-H12` 的24米封顶（36块天台 v002 房顶模块）充当顶盖；99层自己的36块地面保留。

所有正式场景组件都接收光并产生投影：地面、墙体、门、楼板、楼梯、封顶及基地设施模型必须保持 `GeometryInstance3D.cast_shadow=ON`。阴影与物理碰撞仍是两套独立职责：一层地面、墙体、门使用原有Godot碰撞；楼板和两套楼梯由各自Prefab生成简化承重面。L梯的两段斜坡与转角平台是同一个`StaticBody3D`下的三个形状，坡面端点和平台边缘轻微重叠且顶面齐平；外门小梯使用一段斜坡，均不让逐级三角网格参与角色主行走碰撞。

100层围护与封顶统一封装在 `ENV-BASE100-UPPER-SHELL-30X30-H12`。24块围墙和36块封顶仍是可单独移动、旋转或替换的子Prefab（其中东西南三面17块墙与全部36块封顶现为天台参考组件库 v002 件，北面2块普通墙＋4块窗墙与东面1块门墙仍为 base99 件）；组合根脚本只生成连续墙碰撞、东侧门洞框与24米屋顶碰撞，并统一启用投影。东侧门洞现已组合既有 `RoomDoor3D`，门扇、碰撞、提示与开门状态仍由Godot持有；不得把门逻辑写进GLB。

低于12米的楼板和楼梯底部统一设置 `camera_stair_slab` 语义。角色从下方经过时，摄像机沿用99→98层楼梯间规则立即降低到结构底面以下；离开覆盖区后平滑恢复。不得用普通不可见大盒子代替这套规则，也不得把该标签放进GLB。

## 不要直接修改

- 不要删除或改写设施的 `facility_id`；菜单、存档和设施状态通过该 ID 桥接。
- 不要在装饰节点中加入看不见的碰撞盒；需要玩法碰撞时应建立正式组件并登记。
- 不要在该局部场景中加入 `WorldEnvironment`；塔楼全局环境仍由原架构管理，基地风格通过局部灯光、模型、贴花和粒子完成。
- 不要删除 `99层电梯锚点`；代码找不到时虽然会使用旧坐标回退，但编辑器布局将失去控制权。

## 运行时桥接

`TowerDescent3D._install_facilities()`实例化该场景，自动发现十个`BaseFacility3D`，连接原有激活信号，并隐藏编辑器参考节点。设施业务仍由`BaseFacilityCatalog`、`BaseManager`和既有菜单场景负责。

正式模型映射中，`保险柜` 复用赛博储物站模型，`命运卡收藏室` 复用复古游戏电视站模型。两者位于 `设施交互节点_可移动旋转`，允许在编辑器中调整位置和朝向，但不得移入纯装饰集合或清空 `facility_id`。

当前正式来源策略为：仓库内当前Blender源文件即正式资产，后续源更新时以最高`v###`版本为准；2026-09-12的基地主母版为`source/art/blender/base_facility_layout/source/base_facility_runtime_layout_hq_v026.blend`。结构模型的正式入口位于`assets/art/environments/tower_zones/base/runtime/zone_base_v002.tscn`；正式布局只实例化PackedScene包装场景，不直接实例化裸GLB。材质统一使用四个标准角色，素材、哈希和运行时版本通过`tools/asset_pipeline/repair_base99_asset_lineage.py`及`tools/asset_pipeline/sync_base99_current_ledger.py`同步。
