# ShellStorm2 3D 模型资产目录与命名规范

本规范用于让 Blender 美术文件、Godot 导入模型、运行包装场景和资产台账保持一一对应。正式运行场景只引用 `runtime/` 中的 PackedScene；不得直接引用整屋 Blender 文件，也不得把玩法碰撞、门逻辑或交互脚本烘焙进 GLB。

## 标准目录

```text
assets/art/<大类>/<资产套件>/
├─ source/<资产逻辑名>/<资产逻辑名>_source_v###.blend
├─ components/<资产逻辑名>/<资产逻辑名>_visual_top3d_v###.glb
└─ runtime/<资产逻辑名>/<资产逻辑名>_root_top3d_v###.tscn
```

- `source/`：可维护 Blender 母版或拆分后的干净资产包。
- `components/`：一个模块一个 GLB，只含视觉网格、UV和材质。
- `runtime/`：一个模块一个稳定 PackedScene，持有元数据；碰撞、挂点和脚本只在确有需要时放在这里。
- 环境模块使用 `env_`，道具使用 `prp_`，角色使用 `chr_`，敌人使用 `enm_`，武器使用 `wpn_`。
- 文件名必须为小写 `snake_case`，以 `_vNNN` 结尾；AssetID 使用稳定的大写连字符格式，版本变化不改变 AssetID。

## Godot 原生 Prefab 组合规则

- 正式运行入口使用 Godot 原生 `PackedScene (.tscn)`，不建立自定义 Prefab 格式。
- Prefab 通过 Godot 场景实例组合 GLB、碰撞体、脚本、挂点和必要的子 Prefab；不把这些内容重新烘焙成一个不可维护的大模型。
- GLB 只负责视觉网格、UV、材质和必要动画。功能脚本、碰撞、交互区域与挂点由 PackedScene 或台账中明确登记的外部 Godot 脚本拥有。
- 优先使用现有节点、场景继承、导出变量、Group、Signal、`Resource (.tres)`、`CollisionShape3D` 和 `AnimationPlayer`。不得为了资产管理另造一套运行时拼接系统。
- 没有脚本的 Prefab 不一定是纯模型：如果碰撞或排列由父场景、房间生成器等外部脚本负责，必须在台账中写明外部所有者。
- 当前需要的模块才建立 GLB 和 PackedScene。尚未投入使用的变化件只保留已确认的 AssetID、源文件和状态，不提前建立空壳 Prefab。
- 简单 Prefab 直接在一张总控表中登记。短期不建立组件明细表，不登记三角面数、DrawCall、显存、LOD等非必要指标；以后确实出现管理问题时再增加字段。

## 3D Prefab 分类账本

3D Prefab账本位于 `assets/registry/ShellStorm2_美术资产台账_v001.xlsx`。`3D Prefab总控` 只作为分类索引和数量汇总，不再把所有Prefab堆在同一个分页。每个分类使用独立分页，一行代表一个实际存在的 Godot Prefab：

- `3D-场景通用`
- `3D-设施`
- `3D-道具`
- `3D-角色`
- `3D-敌人`
- `3D-武器`
- `3D-物品`
- `3D-特效`
- `3D-其他`

资产身份仍统一登记在 `资产主表`。分类分页负责说明Prefab内部实际引用的GLB、脚本和碰撞；二者使用同一个AssetID关联。一个Prefab只能出现在一个分类分页中。没有独立Prefab的GLB、Blend、贴图、音频和程序数据不进入这些分页。

### Prefab 分类

每个 Prefab 必须进入一个主要分类分页；不能只依赖 AssetID 前缀判断用途。

- `场景通用组件`：用于搭建关卡结构的地板、墙、带门墙、带窗墙、转角、走廊、楼梯、楼板、栏杆等模块。
- `设施组件`：承担设施、服务或交互功能的门扇、开关、灯具、贩卖机、工作台、储物设施和终端等。
- `道具`：桌椅、箱子、家具、装饰物、杂物和其他以摆放或装饰为主的物件。
- `角色`、`敌人`、`武器`、`物品`、`特效`：分别用于对应类型的3D运行Prefab。
- `其他`：确实无法归入以上分类时临时使用，并在备注写明原因。

一个 Prefab 只进入一个主要分类分页。复合资产按其运行时主要职责归类；例如带门墙属于场景通用组件，独立可开关门扇属于设施组件。

固定字段如下：

| 字段 | 填写规则 |
|---|---|
| AssetID | 使用资产主表中的稳定ID，版本升级不改变ID |
| 中文名 | 与资产主表一致 |
| Prefab路径 | 正式 `.tscn` 路径；未建立时留空 |
| GLB模型路径 | 实际引用的视觉GLB；程序占位或未接入时留空；多个路径用分号分隔 |
| Blender源文件 | 可维护的 `.blend` 母版路径；没有则留空 |
| 功能说明 | 用一句话说明Prefab承担的功能；纯表现填写“仅表现” |
| 功能脚本路径 | Prefab自身或负责该模块功能的外部 `.gd`；没有脚本时留空 |
| 碰撞开关 | `开`、`关`或`无`，描述当前运行状态 |
| 碰撞归属 | `Prefab自身`、`外部脚本`、`混合`或`无` |
| 碰撞方式 | 例如 `BoxShape3D`、`CapsuleShape3D`、`手工Shape`、`模型生成`或`无` |
| 标准尺寸 | 只记录会影响模块拼装或玩法净空的米制尺寸 |
| 原点与朝向 | 记录原点位置和 local 正面方向 |
| 使用位置 | 关卡、系统或复用范围 |
| 制作状态 | 与资产主表状态保持一致 |
| 版本 | 当前Prefab或明确复用版本 |
| 备注 | 记录临时复用、外部所有者、替换限制和待办 |

账本用于回答四个问题：Prefab是什么、使用哪个模型、功能由谁负责、碰撞由谁负责。账本不直接驱动Godot运行；Godot场景和代码是实际引用依据，资产主表和分类账本负责身份、状态与维护记录。两者不一致时，先核对项目实际引用，再修正账本。

### 扫描与补登记规则

- 扫描范围包括 `assets/art/` 下包含3D节点的 `.tscn`，以及明确作为复用玩法Prefab的3D场景；测试场景、UI页面和整关卡入口不进入Prefab分类账本。
- 扫描到的Prefab必须先匹配资产主表AssetID；没有稳定ID时先补登记资产主表，再进入分类分页。
- Prefab直接引用的GLB和脚本按场景文件实际内容登记。资产主表虽然已有GLB，但Prefab尚未引用时，不得把该GLB伪装成Prefab当前模型，必须在备注标明“尚未接入”。
- 碰撞记录以Prefab实际节点和脚本为准；由房间、楼层或角色外部脚本生成时，碰撞归属填写“外部脚本”。
- 每次新增、删除、移动或替换3D Prefab后，重新扫描路径并更新分类数量、资产主表路径、版本记录和相关分类分页。

## 环境模块边界

房间资产按 `floor / wall_plain / wall_door / wall_window / corner / stair / platform` 拆分。一个GLB不得包含整间房，也不得夹带相邻模块、展示灯光、相机或碰撞体。

基地99层与通用塔楼即使暂时复用同一模型，也保留两套稳定身份：

- `ENV-BASE99-*`：基地99层专属表现。
- `ENV-TOWER-*`：战斗层、塔楼外圈及通用关卡表现。

二者可以临时指向同一个运行资源，但台账中的 AssetID、复用范围和未来替换目标必须分开。这样后续增加正式基地地板或墙体时，只更新基地包装场景，不波及战斗层。

## 坐标与替换契约

- 单位为米，Godot根节点缩放恒为 `1,1,1`。
- 环境直墙局部宽度沿 `X`，高度沿 `Y`，厚度沿 `Z`；正面为 local `-Z`。
- 墙体原点位于底边中心，5米直墙标准跨度为 `5×9m`；装饰允许超出0.30米结构厚度，但玩法碰撞仍由Godot的0.30米结构代理负责。
- 地板原点位于平面中心、结构底面；标准网格为 `5×5m`，结构碰撞厚度为0.30米。
- 同类地板Prefab共用统一的结构顶面和平面承重碰撞；运行时只能按结构顶面对齐，不得按整件模型AABB最高点对齐。铆钉、压条、盖板、线缆等突出细节是纯表现，可高于结构面但不生成额外阻挡。
- 带门墙、普通墙、带窗墙必须是不同 AssetID。门扇又是独立资产；门洞、锁定、开关、寻路、提示与碰撞由Godot保持所有权。
- GLB只更新表现。替换视觉模型不得改变房间尺寸、5米网格、碰撞层、导航、摄像机遮挡标记、门状态机或交互节点。
- 所有正式场景组件模型必须接收光并产生投影，运行时保持 `cast_shadow=ON`；包括地板、墙、门、窗墙、转角、楼板、楼梯、屋顶、设施主体和可摆放场景道具。纯特效面片、灯光可视化光池、玩家角色专用表现层和UI不属于场景组件模型，不套用此条。

## 基地99/100层正式组合与光照规则

基地99层当前模块化接入两种5米地板、普通墙、带门墙、带窗墙、独立滑升门，并以独立Prefab接入5米楼中楼、5米L型楼梯和4米外门小楼梯。运行时按模块实例化，不把整屋模型铺成单个GLB；其中L型楼梯当前正式视觉为v004，其余两件五米结构为v002。

- 30×30米地面按6×6网格组合：普通地板18块、铆钉地板18块；地面承重碰撞继续由既有 `TowerFloorStage` 负责。
- 99层四面墙使用14段普通墙、0段窗墙和2段带门墙；窗墙属于100层上层围护。0.30米结构碰撞与门洞规则继续由 `DungeonRoom3D` 负责。
- 楼板、L型楼梯和外门小楼梯作为独立Prefab放入基地美术布局 `.tscn`；Prefab持有简化行走碰撞，GLB仍只负责表现。
- 两个门扇只替换 `RoomDoor3D` 的动画视觉子节点；门状态机、锁定、提示、碰撞、寻路和信号不进入GLB。
- 楼板、L型楼梯和外门小楼梯的GLB只负责表现；运行包装使用连续斜坡、平台和栏杆的简化碰撞。L型楼梯的“斜坡＋平台＋斜坡”必须归属同一个`StaticBody3D`，三个形状边缘至少重叠0.04米且完成面同高；踏步不得直接作为角色主行走碰撞，避免卡脚。低于9米的承重结构设置`camera_stair_slab=true`。
- 上述基地结构模型全部接收场景光并保持`cast_shadow=ON`，与其他场景组件使用同一真实遮光规则。投影与物理阻挡彼此独立：墙、门、楼板和楼梯继续使用各自的玩法碰撞所有者。
- 基地安全体积覆盖99层与100层；设施交互只在99层地面带启用。角色登上5米楼板或9米天台时，楼层显示按世界高度更新，不依赖经过门触发。
- `ENV-BASE100-UPPER-SHELL-30X30-H9` 是场景通用组合Prefab：本地9—18米放置19块普通墙、北侧4块窗墙和东侧1块门墙；本地18米复用36块5米地板模块封顶。组合根允许整体移动旋转，内部60个模块仍可在 `.tscn` 中独立编辑。
- 100层组合Prefab自身脚本只负责连续结构碰撞与统一投影策略，不承接99层既有门、设施或房间业务。东侧门墙仅保留2.2×2.5米门洞框；需要功能门时必须组合现有Godot门Prefab，不能把门逻辑写入GLB。
- 99/100层之间的36块中间楼板继续保持移除；18米封顶是更高一层的屋顶，二者不得混淆。屋顶和上层围护必须投影并保留结构碰撞，以真实阻挡室外光线；基地中央灯位于封顶下方，仍由墙面开关独立控制。

## Blender 到 Godot 的更新流程

1. 在已登记的 `source/` 母版中更新对应游戏输出集合，保留稳定 AssetID 和底部中心原点。
2. 运行项目的 Blender 导出脚本，只导出目标 AssetID 到其既定 `components/` 路径。
3. 用 Godot 正式导入命令刷新 GLB；运行包装场景继续引用同一稳定路径。
4. 校验包围盒、材质、正面、底面和节点契约，并确认 GLB 不含碰撞与脚本。
5. 运行结构、门、碰撞、摄像机和实际关卡回归测试。
6. 在 `assets/registry/ShellStorm2_美术资产台账_v001.xlsx` 更新版本、SHA-256、尺寸、来源、状态、日期和验收记录。

基地99层当前5米结构母版使用：

```text
assets/art/environments/base_facility_3d/source/env_base99_modular_room/
env_base99_modular_room_assets_clean_v002.blend
```

5米楼中楼三件结构由`scripts/blender/export_base99_height5_runtime_modules_v002.py`按AssetID独立导出。再次替换时保持现有GLB路径、AssetID、尺寸、原点与材质槽契约；不得把碰撞、门状态机、楼层判定或摄像机规则写回Blender文件。

L型楼梯当前正式视觉为`v004`：源文件为`env_base99_modular_room_assets_clean_v004.blend`，运行包装为`env_base99_stair_l_z5_root_top3d_v004.tscn`。该版本从v002的91个可编辑源组件重新生成游戏输出，没有在合并网格上删连通块；完整保留踏步、斜梁、平台和导光条，只让两段跑道扶手在平台前收口，平台L形护栏独占转角。Godot包装持有单一行走体和独立护栏阻挡，GLB不持有玩法碰撞。

角色资产制作母版位于`assets/art/characters/player/chr_player_avatar_template_3d/source/chr_player_avatar_template_source_v001.blend`，参考高度1.50米、脚底中心原点、Blender前向`-Y`、根缩放1。七制作槽与九挂点的稳定名称由`skills_drafts/player-avatar-asset-standard/`记录；该Skill仅随项目保存，未安装到Codex全局目录。
