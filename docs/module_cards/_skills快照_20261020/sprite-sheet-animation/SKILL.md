# Sprite-Sheet Animation via ai-workflow

## When
- "Make me a 16-frame <action> animation" (idle / run / attack / shoot), or "split this sprite sheet into frames".
- Frames came out clipped or off-centre, or saving the workflow returns `The workflow is malformed.`
- The service is a **processor, not a generator** — it splits/crops/quantizes/extracts. Produce the source art first (see the `sofunny-image` skill), then cut it here.
- The source may also be a **generated video** rather than an image sheet — see "Video-source route" below.

## Key rule: cut with explicit geometry, never the auto-detect result
The service's "auto-detect" estimates the grid from content blobs. When a sheet's characters or gaps are not on an exact even grid, the returned grid **clips the character** — measured once: detect said `505×494, offset 0` while the real pitch was 506–516 px, so every frame lost 25–37 px off its right edge (gun barrel, flying hair). So:
1. Measure the real character bands yourself (step 3), then
2. repaste the characters into a **uniform** 4×4 sheet (equal cells, each centred, ≥20 px margin), and
3. cut that sheet with **explicit** `frameWidth/frameHeight/gapX/gapY/offsetX/offsetY` — do not re-run auto-detect, not even on the rebuilt sheet.

## Steps (image-sheet route)
1. Generate the sheet with one prompt, one image: 4×4 = 16 equal cells, pure white background, the character, the frame-by-frame pose list, "no text/labels/borders/watermark", "nothing crosses a cell line", frame 16 ≈ frame 1 for a loop.
2. Upload and keep the asset ref: `POST /api/projects/:pid/assets?name=<file>` (raw PNG). `params.image` needs that returned `{id,name,width,height}` **object**, not a string. Endpoints, node ports, params and defaults: `references/ai-workflow-api.md`.
3. Measure the true grid — do not skip: `ImageChops.difference(sheet, white).point(lambda v: 255 if v > 22 else 0)`, then a per-column / per-row "has content" profile, and take runs ≥8 px as the 4×4 character bands. If any band is wider than a detect window, the detect grid clips.
4. Rebuild a uniform sheet: crop each character band, paste it centred into an equal cell (e.g. 512×512) on pure white. Re-check that every cell's content bbox has ≥8 px margin on all sides.
5. Build the graph `image → removeBackground → spriteSheet` and `PUT` it. `removeBackground` takes **one image, not a sequence**, so the order is fixed: de-background the whole sheet first, then cut. Use `backgroundScope: "border"` so white parts of the character (apron, lace) survive.
6. Run and collect: `POST .../run` streams NDJSON; take the `node-result` whose `node.frames` is set, then download each `frames[i].url`.
7. Verify without eyes — three independent checks:
   - **No clipping**: per frame, the alpha bbox margin is ≥ ~8 px on every side. A bbox touching a crop edge means the character is cut (or a neighbour's sliver is in frame).
   - **Real motion**: silhouette (alpha) IoU between adjacent frames. ~0.73–0.85 (16–27 % pose change) is a lively cycle; IoU ≈ 1.0 means the model repeated one pose — regenerate the sheet.
   - **Content**: have an image-capable model describe grid / character / action. Keep the question **short** — a reasoning-style vision model spends the budget on its reasoning and returns **empty content** for a long prompt (shorten it, or raise `max_tokens`, before blaming the model or the image).
8. Deliver a looping GIF (≈12 fps / 80 ms a frame for a run, ~8 fps for idle) **and** a ZIP of the transparent PNGs, plus the project/workflow path so it can be re-run.

## Video-source route
Use when the animation is generated by a video model and then split here (the standing preference for this task class is the video model, not an image sheet). Generation is the `sofunny-video` skill; the split stays in this service.
1. Generate at the model's **minimum** duration, not the requested length. Seedance 2.0 rejects a shorter clip (`duration must be at least 5 seconds`), so a 4 s request fails outright — pass ≥5 s. Observed: a 5.04 s / 24 fps / 121-frame clip.
2. Build the graph `video → frameSample → …` and extract only the sub-range the deliverable needs (`startSec` / `endSec`, `fps`, `maxFrames`), so the animation is exactly the requested length (4 s at 8 fps = 32 frames observed). `frameSample` takes a video by frame number — see the reference.
3. Verify as in the image-sheet steps, minus the margin check: a video frame is full-bleed and the character legitimately reaches the frame edge (observed content bbox spanning the full width, ~93 px of content on the right edge). Check motion (IoU) and content instead, and confirm the trim range.
4. Deliver the same GIF + transparent-frame ZIP.

## Decision rules
- Explicit geometry beats auto-detect for cutting; auto-detect is at most a sanity hint.
- Requested duration shorter than the video model's minimum: generate at the minimum and trim by extracting the sub-range in the workflow — do not keep retrying the short duration.
- A video-source frame is full-bleed: do not judge it by the sheet route's edge-margin check.
- Check the geometry against measured content runs *before* running the graph — a bad grid only shows up as clipped frames after the run.
- Every frame being non-empty does not make it an animation: 16 identical poses pass an emptiness check and still fail. Measure motion.
- Keep node/edge ids ASCII `[A-Za-z0-9_-]{1,64}` — they become the output filenames.
- Regenerating the sheet is the fix for a repeated pose or a damaged character; re-running the cut only fixes geometry.

## Done when
The frames are downloaded and pass the applicable checks (margins only on the image-sheet route; motion and content on both), and the GIF, the ZIP of transparent frames, and the saved workflow's location have been delivered.
