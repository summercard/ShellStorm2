# 3D 场景美术生产流程

状态：`ASSET-SCENE-3D r2`，适用工程版本 `0.1.0`。本流程用于场景、关卡组件和固定设施；通用资产规则见[资产与内容规范](10_资产与内容规范.md)。

## 流程

```text
概念稿 / 场景需求
  ↓ 冻结范围、用途与情绪目标
白盒规范快照
  ↓ 从游戏设计取得网格、层高、门洞、楼梯、净空、碰撞与镜头规则
白盒组装与顶视图
  ↓ 先证明空间能拼、能走、能战斗
基于白盒顶视图的风格设计稿
  ↓ 只深化外观，不暗改已冻结的玩法空间
Blender 独立资产包制作
  ↓ 美术验收通过后生成可优化的游戏输出
优化、GLB 导出、Godot PackedScene 导入
  ↓ 独立加载、正式场景、性能与真实渲染验收
登记正式可用；保留上一版本回滚
```

## 全过程固定挂钩

每个 3D 场景生产批次从开始到正式接入都必须持续携带同一组定位信息：

- `block_id`：`rooftop / base / battle / stairs`；区块定义读取[关卡区块设计](05.1_关卡区块设计.md#3-四区块分布)。
- `floor_range` 与 `design_scope`：具体到楼层、房间、楼梯、设施或模块范围。
- `scene_design_docs`：对应场景设计文档；至少包含[关卡生成与爬楼](05_技术施工_关卡生成与爬楼.md)和[关卡区块设计](05.1_关卡区块设计.md)，基地设施另挂接[基地设施](07_技术施工_基地设施.md)。
- `asset_ledger`：指向[美术资产台账](../../assets/registry/ShellStorm2_美术资产台账_v001.xlsx)的 `3D-场景通用` 表及对应 AssetID 条目。

这些信息不是只写在概念稿里：白盒 JSON 写入字段；风格稿标注范围和引用；Blend 资产包、GLB、PackedScene、导出清单和验收记录均保留 `block_id / AssetID / 场景设计文档 / 台账定位`。缺少任一定位信息的资产不能进入下一阶段。

### 1. 概念稿 / 场景需求

- **规范：** 先明确本次设计属于哪个塔楼区块：`rooftop`（天台）、`base`（基地）、`battle`（战斗区）或 `stairs`（楼梯区）。范围必须写到具体楼层、房间、楼梯或设施，不能只写“做塔楼场景”。区块名称和边界以[关卡区块设计](05.1_关卡区块设计.md#3-四区块分布)为准。
- **白模数据：** 场景白模 JSON 统一遵循 `tools/3Dgame-design` v3：`coordinateSystem=blender-z-up`，距离单位米、旋转单位角度，布局放在 `groups[] / components[]`，墙和地板使用 `surfaceSettings`，楼梯使用 `stairSettings`。AssetID、区块、楼层范围、设计文档和输出路径等项目字段统一放入 `projectMetadata`，不得另建一套不兼容顶层格式。
- **数据：** `scene_id`、中文名、`block_id`、目标楼层、设计范围、涉及的房间/楼梯/设施 ID、用途、目标平台、风格关键词、参考图路径、禁止项、场景设计文档和资产台账定位。
- **挂钩：** 使用上方“全过程固定挂钩”；此处只建立首次范围说明，后续阶段不得丢失或另造一套定位。
- **Skill：** 暂无固定专用 Skill；以用户概念稿和场景主设计为准。

### 2. 白盒规范快照

- **规范：** 只从当前游戏设计和工程契约提取尺寸，不从旧模型或效果图猜数值。每项数据记录来源文档、章节和读取日期。
- **数据：** 平面网格、场景长宽高、层高、墙高/墙厚、地板厚度、门洞、楼梯起终点、平台高度、玩家/镜头净空、碰撞、导航、拼接插槽、坐标轴和单位。
- **当前塔楼示例：** 5m 平面网格、12m 逻辑层高、11.9m 可见墙高；正式制作仍以任务开始时的[关卡主设计](05_技术施工_关卡生成与爬楼.md)为准。
- **交付：** `whitebox_<scene_id>_v###.json`。
- **Skill：** 暂无固定专用 Skill；使用项目设计文档。

白盒 JSON 保持简单，至少包含：

### 3. 白盒组装与顶视图

- **规范：** JSON 是白盒尺寸和组合的唯一数据源。先验证网格拼接、门洞、楼梯、路线、碰撞、导航和镜头净空，再交给美术设计。
- **模块数据：** `module_id`、实例名、中文名、类型、尺寸、位置、旋转、所属组合、连接插槽。
- **组合数据：** `assembly_id`、组合名、用途、包含的模块实例、组合总尺寸。
- **图片：** 至少输出一张带场景总尺寸、网格、组合边界、组合名字、模块名字、门洞和楼梯标注的顶视图；另输出一张同机位无文字顶视图，供风格稿直接叠画。复杂多层场景补立面或剖面图。
- **目录：** `source/art/whitebox/<scene_id>/v###/` 固定分为 `data/`、`blender/`、`renders/`。`data/` 保存可编辑 JSON，`blender/` 保存根据同版本 JSON 输出的白盒 Blend，`renders/` 保存顶视图、无文字图、立面、剖面和效果图。
- **Skill：** 暂无固定专用 Skill；由对应场景的白盒验证入口检查。

### 4. 基于白盒顶视图的风格设计稿

- **规范：** 直接在无文字白盒顶视图上设计，保留可核对的白盒轮廓。可以改变颜色、材质、灯光、标识和表面细节，不得私自改变尺寸、门洞、楼梯、路线和净空。
- **数据：** 风格稿版本、使用的白盒 JSON 路径、顶视图路径、色彩、材质、灯光、视觉焦点、资产拆分名称和参考图。
- **图片：** 顶视风格稿为必需；需要说明高度和造型时补关键立面、近景或透视稿。
- **Skill：** 暂无固定专用 Skill；需要生成或修改风格稿图片时可使用 `$imagegen`。

### 5. Blender 独立资产包制作

- **规范：** 按白盒 JSON 的尺寸、名字和组合关系制作；每个可独立导入或替换的模块/设施建立独立资产包，不把整片场景焊成一个模型。
- **数据：** AssetID、白盒 JSON 路径和版本、资产包名、尺寸、原点、方向、包围盒、材质角色、公共色盘、输出集合、Blend版本。
- **交付：** 可维护 `.blend`、游戏输出集合、独立资产包清单、顶视/近景/完整预览图和 Blender 验收结果。
- **Skill：** **`$blender-game-prop-standard`（Blender 游戏资产制作规范）**。

### 6. 优化、GLB 导出与 Godot 导入

- **规范：** 从已通过美术验收的游戏输出制作优化派生文件；导出版本化 GLB，建立独立 PackedScene，并配置碰撞、材质、交互、标签和正式引用。不得靠 Godot 临时缩放修复上游尺寸错误。
- **数据：** 源 Blend、优化派生 Blend、GLB、PackedScene、版本、尺寸、方向、材质数、碰撞方式、使用场景、正式引用、上一版本回滚路径。
- **交付：** 优化 Blend、GLB、`.import`、PackedScene、导出清单、资产台账更新、独立加载结果和正式场景截图。
- **Skill：** **`$godot-model-asset-import-standard`（Godot 模型资产导入规范）**。

### 7. 登记正式可用

- **规范：** 只有独立加载、正式场景、玩法通行、性能和真实渲染验收均完成，才登记为正式可用。旧版本保留用于回滚。
- **数据：** AssetID、正式版本、源文件、运行路径、SHA-256、验收命令、退出码、错误、未执行项和回滚版本。
- **Skill：** 沿用 `$godot-model-asset-import-standard`，并执行项目对应的资产与场景专项测试。

任何一步发现尺寸或组合错误，都退回白盒阶段通过 `tools/3Dgame-design` 更新场景；工具同一次保存产出最终白模 `.blend` 与网页可逆编辑所需的伴随 JSON。JSON 不再作为独立于 Blend 的另一套人工编辑入口，也不能只在 Blender 或 Godot 中单独修正布局。工具生成的白模 Blend 尚不等于完成第5步美术验收的正式资产源。
