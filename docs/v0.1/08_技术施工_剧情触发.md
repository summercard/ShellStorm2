## 1. 职责与边界

剧情系统根据已发生的游戏事实判断是否触发叙事内容，并**在一个时间轴上按时刻调用其它系统干活**。它**不生成关卡、不杀死怪物、不直接发物品、不写其他系统私有字段**；所有游戏效果通过对应系统的命令执行。

<span style="color:#1565C0">**[用户设计 2026-09-21]** 三条定位：

1. 剧情触发器**以调用为主** —— 只负责"判断该不该演"和"按时刻喊人干活"，不自己实现动作、相机、对话或发道具。
2. **可能在任何时机触发** —— 进房间、走到某个位置、击杀、血量变化、拿到某物、过了一段时间……作者加一个触发脚本就能接一种。不是只有"进房间"一种入口。
3. **权限要大** —— 触发器几乎可以控制所有东西（输入、相机、角色、特效、音效、UI、门、灯、刷怪、道具、关卡流程）。因此配套的收口机制是硬要求，见 §6。

<span style="color:#EF6C00">**[Codex补充]** 三条边界：① 不实现任何表现（动画归角色系统、特效归 `VfxPool`、文字归对话 UI）；② 不抓节点路径，只经适配器按稳定 ID 转发；③ 不判断"演完了没有"——那是表现侧的账。</span>

## 3. 时间轴模型（本版核心）

### 3.1 为什么从「有序步骤」改成「时间轴」

v0.1 的模型是"有序步骤 + `wait_for: finish` 等完成才进下一步"。二次验收发现它有两个致命问题：

1. **会永久挂起**。等待的是事件，事件不到达 = 剧本卡死、玩家被锁输入出不来。而"降级并告警"的兜底条款本身没有超时机制，等于没有兜底。
2. **不能表达"同时发生"**。"角色说话的同时镜头推近"要写成嵌套结构，越写越深。

<span style="color:#1565C0">**[用户设计 2026-09-21]** 改为**时间轴**：作者写"第几秒发生什么"，系统按时刻触发。

```text
第 0.0 秒   锁输入
第 1.0 秒   角色说话
第 3.6 秒   镜头推近 + 特写特效（同时）
第 6.5 秒   镜头还原
第 8.0 秒   剧本结束，自动收口
```

**时间轴天然解决挂起**：时间轴按真实时间前进，到点就执行，不等任何东西。某个 cue 的对象不存在（演员没生成、资产缺失）→ 该条降级跳过并告警，**时间轴照走**，后面的 cue 不受影响。剧本一定会在 `duration` 时刻结束。这是本版最重要的结构性收益。

**时间轴天然表达并行**：同一时刻可以有多条 cue；"同时发生"就是写同一个 `at`。

### 3.2 剧本结构

剧本是 JSON（有序 + 时刻结构，扁表无法表达）。项目已有 JSON 内容先例（`anim_bunny01_library_v021.json`、关卡布局清单、`asset_manifest.json`）。

```json
{
  "narrative_id": "nar_expedition01_room03_intro",
  "schema_version": 1,
  "duration": 8.0,
  "trigger": {
    "kind": "point",
    "point": [42.5, 0.0, -12.5],
    "radius": 5.0,
    "once": "run"
  },
  "cues": [
    { "at": 0.0, "do": "player.lock_input", "locked": true },
    { "at": 0.0, "do": "player.combat", "enabled": false },
    { "at": 0.4, "do": "camera.focus", "target": "player", "distance": 5.0, "duration": 1.2 },
    { "at": 1.0, "do": "actor.say", "who": "player", "text": "……这里还有电。" },
    { "at": 3.6, "do": "fx.vfx", "asset_id": "vfx-narrative-glint-3d", "at_actor": "player", "anchor": "head" },
    { "at": 3.6, "do": "ui.subtitle", "speaker": "系统", "text": "检测到微弱信号源。", "auto": 3.0 },
    { "at": 6.5, "do": "camera.restore", "duration": 0.9 }
  ]
}
```

**字段：**

| 字段 | 必填 | 说明 |
|---|---|---|
| `narrative_id` | ✅ | 稳定 ID，落盘文件名与之同名；重写内容不改 ID |
| `schema_version` | ✅ | 当前 `1`；用于后续迁移 |
| `duration` | — | 总时长（秒）。缺省 = 最后一条 cue 的 `at` |
| `priority` | — | 默认 `0`。同一时刻只播一场，新剧本按此比较抢占（见 §3.4） |
| `trigger` | — | 触发条件（见 §4）。缺省 = 只能被代码手动触发 |
| `cues` | ✅ | 关键帧数组，**按 `at` 升序**，同一 `at` 按数组顺序执行 |

**cue 字段：**

| 字段 | 必填 | 说明 |
|---|---|---|
| `at` | ✅ | 相对剧本开始的**绝对秒数**，`>= 0` |
| `do` | ✅ | 指令名，`域.动作` 形式（见 §5） |
| 其余 | — | 该指令自己的参数 |

**剧本落位（唯一登记点）：**

| 件 | 路径 |
|---|---|
| 剧本本体 | `data/narrative/<narrative_id>.json` |
| 剧本索引 | `src/narrative/NarrativeCatalog.gd`（`id → 路径` 映射 + 存在性校验，沿用本工程 `MusicCatalog` / `EliteContentCatalog` 的内容目录写法） |

**为什么不把剧本写进 `.gd`**：时间轴是嵌套有序结构（每 cue 的参数各异），写成 GDScript 字面量既难读也无法被校验器逐值比对。项目已有 JSON 内容先例（关卡布局清单、`asset_manifest.json`）。

作者侧操作规范（怎么收集意图、怎么排时间、怎么写触发脚本）见配套 Skill `10-narrative-timeline-authoring`。

### 3.3 时间基准（数值口径）

```text
时间轴当前时刻：  t += delta
```

- `delta` 取 `_process(delta)` 的入参，**已自动含 `Engine.time_scale`**。因此子弹时间下剧情同步变慢，符合直觉，无需额外处理。
- **暂停即冻结**：本系统节点用 `process_mode = PAUSABLE`（Godot 默认值）。`get_tree().paused = true` 时 PAUSABLE 节点**根本不接收 `_process`**，时间轴自动停住 —— 无需额外代码。玩家按 ESC 开暂停菜单，演出冻结、不会偷偷播完。
- 但 `DialogueUI` 是 `ALWAYS`（`DialogueUI.gd:52`），暂停时它仍会打字并自动推进，与已冻结的剧情脱节 ⇒ **需给它补一个显式暂停入口**，由剧情系统在暂停/恢复时调用（见 §8.4）。
- **与帧率无关**：按累加计时，误差 ≤ 1 帧。同一时刻的多条 cue 在**同一帧内连续执行**，不跨帧。
- **不做"等信号"**：v0.2 没有 `wait_for`。需要"等对话读完再走下一步"，就用时间轴排版（估算时长写在 `at` 上），或把该内容拆成两个剧本。
- **`skip` 的语义**：见 §6.4（整场终止，不是逐句快进）。

### 3.4 多场并行的互斥

同一时刻只允许**一场**剧情在播（v0.2）。新剧本请求播放时：

| 情形 | 行为 |
|---|---|
| 当前无剧情 | 直接播放 |
| 当前有剧情，新剧本来 | 按 `priority` 比较：高的打断低的（先收口再播）；相等或更低则**丢弃新请求**并告警 |
| 同一剧本重复请求 | 忽略（`once` 之外的重复触发一律丢弃） |

`priority` 默认 `0`。强叙事（首次入 98 层）给正数，氛围提示给负数。**不排队** —— 排队的剧情在玩家已经走远后才播，比不播更糟。

## 4. 触发源

### 4.1 三种触发方式

<span style="color:#1565C0">**[用户设计 2026-09-21]** "剧情触发器可能在任何时机触发。添加一个触发脚本即可。比如进入触发位置，或者是特殊情况。"</span>

| 方式 | 载体 | 适用 |
|---|---|---|
| **位置** | 剧本 `trigger.kind = "point"`（+ `point` 世界坐标，或 `point_room` + `point_offset` 房间相对） | "走到这块地方" |
| **事件** | 剧本 `trigger.kind = "event"` | "某个既有事实发生了"（进房、清房、击杀、开门……） |
| **脚本** | 触发脚本调 `arm()` | **任意特殊情况**（组合条件、脚本自定义判定、镜头外的时序） |

前两种是数据驱动（作者只写 JSON），第三种是代码驱动（作者写几行 GDScript）。三者都落到同一个注册表，播放路径完全一致。

### 4.2 位置触发为什么不用 `Area3D`

**性能门禁不允许。** `verify_3d_performance_budget` 的 `total` 余量只剩 **11 个节点**（`world ≤ 2480` / `total ≤ 2560`，`verify_3d_performance_budget.gd:37-48`）。每个触发点加 `Area3D` + `CollisionShape3D` 就是 2 个节点，几个触发点就变红。

**改用距离判定**：触发点 = `Vector3` + 半径，由剧情系统在自己的 `_process` 里按固定间隔（默认每 0.1s）对玩家位置做一次比较。**零新增常驻节点**，也不给物理引擎添负担。

```text
命中条件：  player.global_position.distance_to(point) <= radius
                        且  |player.y - point.y| <= height_tolerance
```

`height_tolerance` 默认 `2.0`m —— 防止"在楼上走过、脚下正下方就是触发点"时误触发。判定用**水平距离 + 垂直带**两个条件，而不是纯球形距离。

**房间相对写法（2026-09-21 新增）**：`point` 要写世界坐标，而房间是**运行时生成**的 —— 把坐标写死，换布局 / 换楼层后会**静默失效**（症状是「剧情永不触发」）。所以位置触发也支持房间相对：

```json
"trigger": {
  "kind": "point",
  "point_room": "floor_01_main_02",
  "point_offset": [-14.0, 0.0, 0.0],
  "radius": 2.5,
  "once": "run"
}
```

`point_offset` 是**相对房间中心**的偏移，世界坐标 = `room_node(room_id).to_global(point_offset)`；由导演在运行期**惰性解析**（`arm()` 那一刻房间还不存在）并缓存。两种写法二选一，`point_room` 优先。

**实测（真机几何，`verify_opening_script_runtime` E 段）**：`floor_01_main_02`（会议室 40×15，西门在房间最西端）房间中心 world = `(−5.0, −24.0, 2.5)`，`point_offset = [-14, 0, 0]` ⇒ 触发点 `(−19.0, −24.0, 2.5)` = **进门 6m 处**。E 段断言「触发点在房间内部、且不在上一个房间里」。

**用法建议**：`room_entered` 在玩家**刚跨进门**那一刻就发 —— 那时门还没关、人还站在门口，一切「基于玩家位置」的刷怪与运镜都会贴着门口。要让演出发生在**进门之后**，就换成位置触发（`point_room` + 一个进深 offset）：玩家走进来、门自动关上，才起跑。

**刷怪站位也能房间相对（2026-09-22）**：`scene.spawn` 用与触发器同一套锚法 —— `point_room` + `point_offset` 把队列**钉在房间里的固定点**，不再是「玩家右前方 N 米」。
为什么需要：触发器改成位置触发后，玩家落点在一个半径内浮动 ⇒ 玩家相对的站位会跟着抖。
另两个排布参数：`axis`（`"forward"` 默认沿视线 / `"x"` 东西 / `"z"` 南北）决定队列**沿哪个方向排开**；`stagger_m` 让相邻两只沿排列轴的**垂直方向交替错开**，避免一条笔直的队（观感「太整齐」）。
实测：会议室中心 `(−5, −24, 2.5)` + `[6, 0, 0]` ⇒ 刷怪点 `(1.0, −24, 2.5)`。

**代价（明说）**：距离判定是**轮询**不是**事件**，理论上玩家单帧移动超过 `2*radius` 会穿过去而漏触发。按 0.1s 轮询、玩家最快约 8m/s 计算，单次间隔位移约 0.8m，只要 `radius >= 1.0` 就不会漏。**`radius` 下限 1.0，校验器强制。**

### 4.3 触发脚本

<span style="color:#1565C0">**[用户设计]** "添加一个触发脚本即可。"</span>

触发脚本是**普通 GDScript**，挂在任意已有节点上（玩家、房间、HUD、关卡根都行），在 `_ready()` 里向剧情系统登记：

```gdscript
extends Node
## 特殊情况触发：玩家血量低于 30% 且从未见过信使时，播一场。
## 挂在任意常驻节点下即可，本身不新增 Area3D。

const SCRIPT_ID := "nar_signal_messenger_first"

func _ready() -> void:
	NarrativeDirector.arm(SCRIPT_ID, {
		"on": "manual",
		"check": _should_play,
		"cooldown": 60.0,
		"once": "run",
	})

func _should_play() -> bool:
	var player := get_tree().get_first_node_in_group("player_3d")
	if player == null:
		return false
	return float(player.get("current_hp")) / float(player.get("max_hp")) < 0.3
```

| `arm()` 参数 | 说明 |
|---|---|
| `on` | `manual`（由 `check` 决定）/ `event`（事件名）/ `point`（点 + 半径，此项一般写在 JSON 里更省事） |
| `check` | `on = manual` 时的判定 `Callable`，返回 `bool`；被按 `interval` 周期调用 |
| `filter` | `on = event` 时的过滤字典（如 `{"room_id": "room_03"}`） |
| `once` | `run`（本局限一次）/ `forever`（每次满足都触发）/ `never`（不限制，仅受 `cooldown` 管） |
| `cooldown` | 距上次触发的冷却秒数，默认 `0` |
| `priority` | 覆盖剧本里的 `priority` |

**触发脚本的边界**：它**只做判定**，不执行任何演出动作。判定为真就交棒给时间轴。这样"什么时候演"和"演什么"彻底分开，作者改演出不用碰脚本。

### 4.4 当前可用的触发事实（诚实清单）

<span style="color:#791F1F">**下面这张表是"现在真的能接什么"。带 ⛔ 的接不上，别写进剧本。**</span>

| `on` 值 | 状态 | 依据 |
|---|---|---|
| `point` | ✅ 本系统自建 | 距离判定（§4.2） |
| `room_entered` | ✅ | `DungeonRoom3D.player_entered`（L6），过滤 `room_id`。**开场演出不许用，见下 ⚠️** |
| `gameplay_started` | ✅ 本系统自建（2026-09-21） | `TowerDescent3D.gameplay_started(room_id)`：开场页动画播完（点了开始 / 跳过之后）；**没有开场页时 = 场景 `_ready` 的帧末**。开场类剧本**只能**挂这个 |
| `room_cleared` | ✅ | `Dungeon3D.room_cleared`（L17） |
| `kill_recorded` | ✅ | `Dungeon3D.kill_recorded`（L16）——**但不带身份**，只能表达"又杀了一个" |
| `door_motion_finished` | ✅ | `RoomDoor3D.motion_finished(is_open)`（L13） |
| `light_toggled` | ✅ | `DungeonRoom3D.light_toggled(room, is_on)`（L11） |
| `extraction_started` / `completed` | ✅ | `Dungeon3D` 撤离链路（L4604 / L4665） |
| `run_completed` | ✅ | `Dungeon3D.run_completed(success, summary)`（L15） |
| `hp_ratio_below` | ✅ 本系统自建 | 监听 `Player3D.hp_changed`（L6）+ 阈值比较 |
| `kill_of_elite` | ⛔ | `kill_recorded` 无参；精英无"遇见"上行事件（只有内部 `_elite_encounter_id()` L2133 当种子用） |
| `boss_defeated` | ⛔ | 同上 —— **无法区分击败的是哪一个 Boss** |
| `floor_entered` | ⛔ | 代码中不存在，只在旧文档里出现过 |
| `item_acquired` | ⛔ | 未确认有上行事件 |

<span style="color:#791F1F">**开场演出（冷启动第一章）必须挂 `gameplay_started`，不能挂 `room_entered`。**</span>

`room_entered` 是在场景 `_ready()` 里就发的 —— 那一刻 `MainEntryScreen3D` 还在接管相机与输入。
剧情挂上去会在**菜单背后空跑**，并与开场页互相顶。四个症状**一个都不报错**，只能靠真机验收抓：

| 症状 | 机理 |
|---|---|
| 一开场玩家就能操控 | 开场页 `present()` 比剧情首帧晚跑，剧情先锁输入 ⇒ 开场页 `_finish_transition()` 又写回 `_previous_input_locked=false` |
| 镜头不"从上往下压" | 剧情抢到的相机基准是**近景机位**（俯角 24.6°），不是玩法机位（69.4°），后续运镜全建在错的基准上 |
| 中间错乱 | 开场页与剧情逐帧互写同一台 `Camera3D`（开场页 `_process` 钉近景、剧情 `_apply_camera_pose` 写叙事位姿） |
| 收工后键盘与开枪全废、鼠标还能转 | 收口把"接管瞬间的快照"写回 —— 那个快照是开场页刚写进去的 `true`（见 §6.1） |

⇒ **真机验收在 `tests/verification/verify_opening_script_runtime.tscn`**（§13.5）。

**结论（影响范围，请作者知悉）**：`08` 旧版 §9 承诺的三条垂直切片里，**「首次击败 Boss 并获得专钥匙」「首次遇见精英」两条当前落不了地** —— 因为买不到这两个事实。v0.2 的切片只做**「首次进入 98 层」**与**「首次进入某房间」**。要解锁另外两条，得先给 `Dungeon3D` 补身份化击杀事件与精英遭遇事件（登记为独立任务，不在本功能内顺手做）。

<span style="color:#791F1F">**要"镜头从上往下压"，必须给 `elevation_deg`；只改 `distance` 不叫俯冲。**</span>
相机只会沿同一条「玩家→相机」轴滑动，观感是**推近拉远**。实测老实现（只改距离）俯角全程 **69.4° 零变化**；
新实现 `elevation_deg: 34.0` 才真的 69.4° → 34.0°。
`elevation_deg` 是**世界仰角**（`atan2(相机高出玩家, 水平距离)`），**不是增量**；不给时沿用接管前玩法镜头那套俯角。
⚠️ 它的绝对数值**依赖房间几何与玩法镜头构图**，换房间要重测（见 §13.5 末）。

**运镜枢轴 `pivot`（2026-09-21 新增）**：默认 `player` —— 焦点钉在主角身上。要**脱开主角、整台机位平移过去拍别处**：
- `pivot: "last_spawn"` —— 绕**最近一次 `scene.spawn` 的队列中心**（作者不写坐标；同一段剧情里要先刷怪）。
- `pivot: "room_center"` + `room_id` —— 绕**房间中心**（房间节点原点即中心，见 `DungeonRoom3D` 的 ±dimensions/2 约定）。
- `pivot_m: [x, y, z]` —— 显式世界坐标（最优先，压过 `pivot`）。

枢轴按同一个 `duration` **平滑插值** ⇒ 是「平移过去」，不是瞬移；`camera.restore` 会把枢轴一起带回玩家。
拿不到目标点（没刷过怪 / 找不到房间 / `pivot` 写错）一律**告警并退回玩家**，不静默。
⚠️ 机位脱开后**不做遮挡处理**：枢轴离得太远时相机可能穿墙 —— 取景处要自己留空。

### 5.3 降级规则（时间轴不因降级停摆）

| 情况 | 行为 |
|---|---|
| 指令名不在表里 | `push_error` + 该条跳过，**时间轴继续** |
| 指令在表里但状态是 🔶/⚠️ 且尚未实现 | `push_warning` + 该条跳过，**时间轴继续** |
| 目标对象找不到（`who` / `room_id` / `actor` 不存在） | `push_warning` + 该条跳过，**时间轴继续** |
| 资产缺失（vfx / sfx / music ID 不存在） | 交给对应系统的既有降级（`_report_missing_asset`），本系统不额外报错 |
| 参数类型不对 | `push_error` + 该条跳过，**时间轴继续** |

**总原则（与对话 UI §7 一致）**：剧情的失败不得阻断玩法。最坏情况是"这一条没演好"，绝不能是"玩家被锁住出不来"。所以**收口（§6）永远无条件执行**，与中间的降级无关。

### 5.4 适配器纪律（硬约束）

<span style="color:#1565C0">**[用户设计]** 调用必须经**适配器**转发，不得抓节点路径：

```gdscript
# ❌ 禁止：剧情脚本与场景结构焊死
get_node("../../Player3D").set_input_locked(true)

# ✅ 正确：按稳定 ID 转发
_adapter.call_actor("player", "lock_input", {"locked": true})
```

适配器是剧情系统与场景之间**唯一的耦合点**；换场景只改适配器，剧情脚本一字不动。

**机器可查判据**：剧情系统源码（`src/narrative/**`）内**不得出现**任何 `get_node(` / `get_node_or_null(` 带路径字面量的调用，以及 `Player3D` / `Camera3D` / `DialogueUI` 的节点路径字符串。验收脚本用正则扫源码，命中即红（§11）。

### 5.5 关于 `player.invulnerable`

<span style="color:#791F1F">**这一条不是可选项，是 §6 收口的必要配套。**</span>

用户要求剧情**不冻结世界**（`_process` 照跑、敌人照动）。而剧本里几乎一定会 `player.lock_input(true)` —— 玩家不能动、不能打，敌人却照常攻击。**演 8 秒戏 = 站着挨 8 秒打**，还可能在演出中途被打死，直接触发 `run_completed` 让剧情悬空。

两条处置（v0.2 都要做）：

1. `player.lock_input` 期间，系统自动给玩家挂**受击免疫**（不是无敌，是不掉血），锁解除时自动摘除。这是**默认行为，作者不用写**。
2. 剧本若显式写了 `player.invulnerable`，以显式值为准（允许作者做"演出中被打"的效果）。

实现上需要在 `Player3D` 补一个"受击免疫"开关（当前没有）。**这是本功能对玩家系统的影响点**，需在玩家专项验收中一并核对。

## 6. 收口与现场恢复

<div style="color:#791F1F;background:#FCEBEB;padding:8px 12px;border-radius:8px">

**这一节是"大权限"能安全存在的前提。** 权限给得越大，收口就越不能靠作者自觉。

</div>

### 6.1 声明式占用 + 强制归还

**不是**"作者记得在最后一条 cue 里还原"，**而是**"系统登记谁占了什么，结束时无条件强制归还"。

机制：每条改动**独占资源**的 cue 执行时，登记到本场播放的占用清单：

| 独占资源 | 登记内容 | 归还动作 |
|---|---|---|
| 玩家输入 | **只登记「叙事持有输入」**，不记原始值 | 交回独占权后请地牢**重新裁决**一次（`Dungeon3D.refresh_player_input_lock()`）—— 不写回快照 |
| 玩家战斗 | 原始开关 | 还原 |
| 玩家受击免疫 | 原始值 | 还原 |
| 相机 | 接管前的 `transform` + `fov` | `interpolate_with` 回原位 |
| 音乐 | 接管前的 music_id | `MusicManager.restore()` |
| 屏幕黑边 | 原始开关 | 关闭 |
| 门 / 灯的临时策略 | 原始 policy | 还原 |

<span style="color:#791F1F">**输入锁的归还绝不能"写回快照"。**</span>
`input_locked` 是**多方共用**的：模态 / 背包 / 开场页各自都会改它。把接管瞬间读到的值当"原值"存下来、
收口再写回去，等于**替别的系统做决定**。实测反例：冷启动时开场页先锁 ⇒ 剧情登记 `before=true` ⇒
收口写回 `true` ⇒ 玩家**永久锁死：键盘与开枪全废、鼠标仍能转向**，且运行时零报错。
正确做法是交回独占权后**重新裁决**一次（`_has_exclusive_modal() or inventory_open or _narrative_holds_player_input()`），
这也是 `refresh_player_input_lock()` 必须是**函数调用**而不是字段赋值的原因。

**归还时机**（四个都要做，一个都不能漏）：

1. 正常演到 `duration`
2. `flow.end` 显式结束
3. 被高优先级剧本打断
4. **`abort()`** —— 玩家死亡 / 撤离 / 场景卸载 / 剧本解析失败

### 6.2 `abort` 必须最先做

终止路径（撤离 / 死亡，`Dungeon3D.gd:4935`）会在剧情演到一半时切场景。`abort` 的顺序是**先解锁输入、先还原相机**，再做清理 —— 因为这两项不还不只是观感问题，是**卡死玩家**。

### 6.3 暂停不冻结剧情（v0.1 遗漏，本版修正）

v0.1 的 §8.3 只写了"明确策略：禁用暂停或 abort"，没有定，也**没有发现 `DialogueUI` 在暂停时仍在推进**这个具体现象。

本版定：

| 系统 | `process_mode` | 理由 |
|---|---|---|
| 剧情系统 | `PAUSABLE` | 暂停即冻结时间轴，`paused` 时不收 `_process`，无需额外代码 |
| `DialogueUI` | `ALWAYS`（**保持现状**） | 它是跨场景系统，直接改它的 `process_mode` 会影响到它自己的独立验收 |

配套：`DialogueUI` 补一个显式**暂停/恢复入口**（如 `set_paused(bool)`），由剧情系统在暂停切换时调用，使底栏打字与自动推进同步冻结。**这是对对话 UI 的影响点**，登记在 §8.4。

### 6.4 `skip` 语义

`skip` = **整场终止**，不是逐句快进。行为：时间轴直接跳到 `duration`，**中间所有 cue 不执行**（尚未执行的表现与效果一律不做），然后走完整收口。已发生的效果不回滚（音效已响、门已开就保持了）。

为什么不做逐句快进：时间轴上的 cue 是"时刻"而非"句子"，快进意味着把中间所有时刻的动作挤在一帧里执行，会产生一帧内刷十几个特效的雪崩，观感与性能都不可接受。

| 对话 UI 持有的 | 当前行的显示与打字进度，**不含任何剧情进度** |

**v0.2 的变化**：时间轴不再"等对话结束"，所以**剧情不依赖 `dialogue_finished`**，只发命令。这是时间轴模型带来的解耦收益 —— 上一版"`wait_for: finish` 挂起等事件"的整套复杂度消失了。

对话 UI 仍按 [18](18_技术施工_UI与对话系统.md) §10 保持独立，可脱离剧情单独验收。

## 9. 内容边界

- <span style="color:#1565C0">**[用户设计]** 本次建立系统，不擅自改写主线剧情。</span>
- v0.2 先建立**剧本表结构、播放器、适配器与触发器**，内容只做最小垂直切片（首次进入 98 层 / 首次进入某房间）。
- 对话文本、角色关系、章节和结局由后续主设计内容冻结；技术层不得把占位文本当成最终故事。
- **玩法事件与剧情事件必须区分**：`MapFateTriggers`（命运卡）保持独立实现，不复用其骨架，也不合并成"统一事件系统"。
- <span style="color:#1565C0">**[用户设计]** 隔离间"无法返回、未拾取物永久丢失"属于关卡强制系统提示，**不得等待剧情队列、被剧情跳过或因剧情系统故障而消失**；剧情只能在其前后追加氛围内容。</span>
- **标记不进存档（2026-09-23 部分修订）**：`flow.mark` / `grant.flag` 仍是**本局内存态**；但 `once = "run"` 的**消耗记录已落档** —— `BaseData.narrative_history`（业主：「剧情的桥段跟着存档走」）。
  - 唯一写入权在 `BaseManager.commit_narrative_completion()`，导演在 `_finish()` 里调用；**只有完整收口**（`duration` / `flow.end` / `skip`）才写，被抢占与 `abort:*` 不写（= "未达成条件的桥段下次仍会触发"）。
  - 裁决 = **本局内存态 ∪ 跨局档案**（`_try_fire`）：内存管这一局，档案管跨局。
  - 复位存档走 `BaseManager.reset_game_save()`（`data = BaseData.new()`）⇒ 档案一并换新 ⇒ 新档能重新看到开场；老档缺字段 = 空历史（已看过的 `run` 剧情重播一次，属接受项）。
  - 🚫 **不通过 autoload 单例读跨模块常量**（实测会让导演节点编译期整体失效、剧情全部不起播）。
- **新档边界（2026-09-21 补）**：本局内存态的**归零点** = `BaseManager.game_save_reset_completed`（复位存档成功的唯一出口，`NarrativeDirector.reset_run_state()` 接）。不进存档 ≠ 不归零 —— 复位档走 `change_scene_to_file`、autoload 存活，若不归零，`once = run` 的冷启动开场剧本只会播一次，「复位存档 → 重新开始」就再也看不到开场。

### 13.4 相机运镜的构图判据（可测量，不靠肉眼）

镜头接管是**绕玩家竖轴的方位平移**（相机与它的朝向被同一个 `orbit` 刚性旋转），
所以焦点**恒在玩家身上**，队列的构图位置只由「方位角 + 队列侧向距离」决定。
`camera.pan` 的正负号语义：**正角 = 相机位姿绕到玩家右手边 = 视线向左摆**；
要让视线**向右**摆（把玩家右侧的东西纳入画面）必须用**负角**。

验收用**画面水平偏角**（与分辨率 / FOV 无关，headless 也测得准）而不是像素：
`角度 = atan2(视线右轴·目标向量, 沿视线深度)`。第二条剧本实测：

```text
camera.pan yaw_deg = -62  →  队列偏角  0.7°（正中，且与角色重叠）  depth 13.1m   ✗
camera.pan yaw_deg = -26  →  队列偏角 16.3°（画面右侧，与角色分离） depth 10.7m   ✓
反向对照：把符号写成 +26  →  队列偏角 36.7°（贴近画面边缘）        depth  6.9m   ✗
```

⇒ 调运镜不要靠肉眼试；改 `yaw_deg` → 重跑验收 → 读 `C2 构图采样` 那一行。

### 13.5 开场剧本的真机缺陷与修复（2026-09-21 晚）

<span style="color:#791F1F">**背景：`verify_narrative_timeline` 当时 80 项全绿，真机一跑开场却四个问题。**</span>
根因是**验收世界与真机世界的差**：`TowerDescent3D._install_main_entry_screen()` 在
`test_mode / headless` 下**直接 return**，所以假世界验收里**根本不存在开场页** ——
而四个缺陷全部出在「剧情 × 开场页 × 玩家」的三方争用上。

| # | 真机症状 | 根因 | 修复 |
|---|---|---|---|
| 1 | 一开场玩家就能操控，没被锁死 | 剧本 01 挂 `room_entered`，在场景 `_ready` 里就起跑；开场页 `present()` / `_finish_transition()` 随后把 `input_locked` 写回 `false` | 剧本 01 改挂 `gameplay_started`（`TowerDescent3D` 新增该信号，排到 `transition_finished` 之后；无开场页时 `call_deferred`）—— §4.4 |
| 2 | 镜头不"从上往下压" | `_apply_camera_pose()` 只沿「玩家→相机」轴缩放距离 = 纯 dolly；实测俯角全程 **69.4° 零变化** | 新增 `elevation_deg` 通道 + `_camera_elevation_pivot()`（绕水平轴转那条轴）；`camera.focus` / `camera.pan` 都支持 —— §5.2 |
| 3 | 中间"错乱"（左右张望只朝一边、鼠标一抖就顶掉） | ① `actor.face` 的 `relative` 按**当前值**累加，`+32/−32` 退化成单向漂移；② 开场页在剧情期间仍逐帧写近景机位；③ `_update_aim_from_mouse()` 不看 `input_locked`，鼠标能随时改写朝向 | ① face 序列改用**序列基准** `_facing_base_yaw` 锚定；② 开场页 `_process` / `_finish_transition` 让位 `_narrative_holds_presentation()`；③ `Player3D._update_aim_from_mouse()` 让位 `is_actor_facing_overridden()`；④ 姿态相位过渡走完必须 `clear_narrative_pose()`，否则角色僵在倒地剪辑第一帧、待机不播 |
| 4 | 第 4 步完成后没交回键盘，鼠标能转但不能开枪 | 收口把"接管前的快照"写回 —— 那个快照是**开场页刚写进去的 `true`** | 归还改为交回独占权 + `Dungeon3D.refresh_player_input_lock()` 重新裁决 —— §6.1 |

**为什么必须新增一个真机验收**：上面四条**没有一条会报错**，假世界也一条都测不到。
`verify_opening_script_runtime` 的做法是把开场页实例**提前塞进塔楼自己的 `_main_entry_screen`**，
于是塔楼走它自己的 `_defer_gameplay_started()` **真接线**，时序与冷启动逐帧一致：

```text
开场页 present()（锁输入、钉近景）→ 点开始 → 转场 1.15s → transition_finished
  → gameplay_started → 开场剧本起跑 → 收口归还
```

实测判据（`_scratch/nar_diag/probe2.log`，25 项全绿）：

```text
[A] 点开始之前 展开 剧情未起跑（挂 room_entered 会在这里就空跑）
[B] 874 帧逐帧 input_locked == true，违例 0
[B] 俯角 69.4° → 34.0°（降幅 35.4°，剧本写的就是 34.0°）
[C] 收口后 input_locked=false、相机 / 免疫 / 朝向全部归还、开枪四道闸门全通
[D] 剧情演到一半硬把开场页 present 起来 → 相机仍在叙事俯角 30.0°（近景机位是 24.6°）
```

**三项反向对照**（改坏 → 必须变红 → 还原后逐字节一致）：

| 改坏什么 | 变红的判据 |
|---|---|

| `_camera_elevation_pivot()` 退化成单位阵（= 老实现） | `镜头真的从上往下压：69.4° → 69.4°（降幅 0.0°）` 等 3 项 |

<span style="color:#1565C0">**遗留提醒**：`elevation_deg` 的绝对数值依赖房间几何与玩法镜头构图，本版 `34.0°` 是对着 `floor_01_exit`
实测调的。换房间 / 换镜头参数后应当重跑 §13.5 的探针读实测降幅，**不要照抄角度**。
镜头"从上往下压"的**观感**最终仍需在编辑器里亲眼确认一次 —— 本探针证明的是角度真的在变、且落到剧本值，不是"看着好看"。</span>

### 13.6 98F 和平区的「钥匙」生存面修正（2026-09-22）

§13.5 修的是剧情；这一节修的是同一片区域（98F 区块00）的**玩法生存面**两处人报。

| # | 人报症状 | 根因 | 修复 |
|---|---|---|---|
| 1 | 「98 层每个房间都有钥匙」——门明明不消耗钥匙 | `_try_open_room_door()` 读的是 `_door_policy_for_edge()`（硬编码 `requires_clear/requires_key/triggers_fate` 全 `true`），**完全没读** `DungeonRoom3D.door_policies` 里那份由 `authored_layout_peaceful` 算出的放行策略 ⇒ 「门只做普通开关」是空承诺，且**运行时零报错** | 新增 `_door_policy_towards(room_id, target_room_id)`：用 `room.door_targets` 把目标房反查回门方向 → 优先读房间声明，缺失才回落旧函数（**非和平区逐值不变**） |
| 2 | 门不要钥匙了，**地上还躺着一颗「房间钥匙」** | 钥匙闸口 `_ensure_room_key_reward()` 只查 `room.cleared` / 房型 / 已发过，**不判断「本房的门要不要钥匙」**，也不看调用方给的 `spawn_key` 形参。而 `_on_room_entered()` 的**重进已探索房间**分支（`L1956`）是**无条件**调它的 ⇒ 和平区首次进房走 `_mark_room_cleared(room, false)`（不发钥匙），玩家**回头再进同一间**就掉一把 | 新增 `_room_produces_room_key(room)` 并放进闸口守卫：`authored_layout_peaceful` 直接 false；否则只要该房**任一**方向的声明策略 `requires_key == true` 就算产出。**闸口自检、不信调用方形参** |
| 3 | 门不要钥匙、地上也没钥匙，HUD 却写着「搜索剩余物资，**用钥匙开门**选择路线」 | `_journey_objective()` / `_expedition_objective()` 只看「我有没有钥匙」（`_get_total_room_keys() <= 0`），**不看这扇门要不要钥匙** | 同一声明 `_room_produces_room_key(room)` 前置一档：不消耗钥匙的房间返回「区域已肃清 · 直接开启下一扈门」 |

<span style="color:#791F1F">**两点值得记住：**</span>

1. **和平区的"不发"必须写在唯一的产出闸口上。** 把 `spawn_key = false` 交给调用方传参是靠不住的 ——
   同一个闸口还有别的调用方（重进房、修进度兜底），它们**不带**这个语义。判据要能自证。
2. **反向对照实测**：把闸口那一行摘掉 → 98F 四房**各掉 1 颗、全层 4 颗**，
   与人报截图逐项吻合（`failures=6`：四间房各 1 条 + 全层计数 + 源码守卫）。
   装回后 `verify_opening_script_runtime` **86 项全绿**、`_scratch` 无残留。

**顺带验证的可见面**（F 段新增）：门**节点**上也确实落到了放行策略 ——
实测四房各门提示语是 `[E] 开启通道`，不是 `[E] 使用房间钥匙`。
另外 H 段把 **HUD 目标文案**也盯住了：和平区的 `_journey_objective()` 实测返回「区域已肃清 · 直接开启下一扇门」，不再提钥匙。
（`RoomDoor3D.set_access_policy()` 会 `_refresh_prompt()`，所以策略与提示语同源，不会各说各话。）

<span style="color:#1565C0">**一句话**：这不是剧情问题，是「区域声明」与「产出闸口」之间的一条**没接上的线** ——
和 §13.5 的四个缺陷同类：**全部零报错，只有人报才会发现。**</span>

### 13.7 开场的交互与武装口径（2026-09-22）

|---|---|---|
| 1 | 锁死移动与鼠标**动作**，但**鼠标还能转视角** | **已有口径，不动代码**：`Player3D.set_input_locked(true)` 只拦移动 / 射击 / 换弹 / 冲刺 / 交互，**不拦鼠标瞄准**（源码注释原话「input_locked 不拦瞄准」）。⚠️ 唯一例外是 `actor.face` 占用朝向期间（`_narrative_holds_aim()`）——那是 §13.5 缺陷③的修复，防止玩家晃鼠标把剧本摆好的「左右张望」顶掉 |

| 5 | 开场**身上没有枪、但保留备弹** | `TowerDescent3D._reset_new_game_opening_loadout()` 用 `Player3D.clear_all_equipped_weapons()` 收回。**只动「新游戏开场」这一条分支** —— 天台出生 / 死亡返城 / 撤离返航照旧白送枪（那些路径靠 `start_with_weapon` 的默认值）。保底备弹 `GUARANTEED_LOADOUT_AMMO_ROUNDS = 300` 本来就与「有没有枪」解耦 |
| 6 | 他原本那把枪放在办公室**靠右近门**的地上 | 收回函数的**返回值**就是他那一把的原样实例（含已装命运改造），直接落地 —— 不重新造一把。落点 `NEW_GAME_OPENING_DROP_OFFSET`（房间局部）；真机实测办公室东门在局部 `(7.5, 0, -2.5)` ⇒ 本值 = **离门 2.2m、出门方向（+x）右手侧 1.8m** |
| 7 | 起身后对着枪说「那是主人留下的礼物。。」**再**解锁 | 剧本 01 尾段：`actor.face`（`to_point_room` + `to_point_offset` 指那把枪）→ `actor.say` → `flow.end` @18.0s。占用法保证说完之前朝向不弹回 |

<span style="color:#791F1F">**三个只在真机上才露头的点：**</span>

1. **掉落物有确定性散布。** `_spawn_loot_items()` 会按「第几件」把落点推出去
   （实测 index 0 = `(cos0.45, 0, sin0.45) * 0.7` ≈ **偏 0.70m**）。单件、且落点要被剧本的
   `actor.face` 精确引用时，散布会让「指的那个点」与「枪实际在哪」**差 0.7m**（转身指偏）。
   已给该函数加 `spread := true` 形参（默认不变，其余三个调用方一字未动），开场那把枪传 `false`。
2. **备弹发放被 `test_mode` 挡住。** 真机路径是 `if not test_mode: _grant_guaranteed_loadout_ammo()`，
   而真机探针本身跑在 `test_mode` 下 ⇒ 探针里备弹恒为 0。所以探针改为**显式调一次发放**，
   验真正关心的那条关系：**把枪收回之后，备弹照样能进包**（实测 0 → 300），
   外加源码守卫：发放条件只能是「非 test_mode」，**不能被「有没有枪」挟持**。
3. **`.gd` 源码是 CRLF，探针里跨行 `contains` 会永远为假。** 源码守卫用 `\n` 去搜
   `"if not test_mode:\n\t\t_grant..."` 这种两行片段**必然搜不到** ⇒ 守卫变成「永远红」。
   守卫读源码后必须 `.replace("\r\n", "\n")` 再用。
   （同一条也适用于写这类守卫本身：它红了先怀疑它自己。）

**验收**：`verify_opening_script_runtime` 从 87 → **105 项**（新增 I 段 17 项 + F 段门节点 1 项）。
`verify_narrative_timeline` 仍是 **105 项**（C1 台词改两句、C2 台词改词、假世界补一个「办公室」房
供新 `actor.face` 的房间相对目标点解析）。

### 13.8 开场判据修正：天台下线不得被当成「新游戏开场」（2026-09-23 · 真机 bug）

<span style="color:#791F1F">**症状**</span>（业主真机报告）：新开档走完前期剧情、走到 100F 天台、在**天台边缘下线**，再上线 ⇒ **回到「游戏初始状态」且身上没有武器**。

**根因（两处缺陷叠加）**

| # | 缺陷 | 位置 |
|---|---|---|
| 1 | `_should_open_new_game_in_master_office()` 最后一行直接 `return _should_start_on_rooftop_for_entry()`，而后者在「基地快照 `scope=="base"` 且 `current_room_id=="start"`」（= 上次在 100F 天台）时为真 ⇒ **每一次天台下线都被当成全新存档**：落 98F `floor_01_exit`，并由 `_reset_new_game_opening_loadout()` 收走身上的枪 | `TowerDescent3D.gd` `_should_start_on_rooftop_for_entry()` / `_should_open_new_game_in_master_office()` |
| 2 | 开场地上的那把枪是运行时临时节点，**不进任何存档** ⇒ 没捡就走的话，上线后手上地上都没有枪（`equipped_weapon_items` 落盘为 `[{}, {}]`） | `_drop_new_game_opening_weapon()` / `Dungeon3D.build_runtime_save_snapshot()` |

**headless 隔离实测（改前）**：快照 `scope=base / room=start` ⇒ `should_open_master_office=true`、落点 `(−32.5, −23.97, 5.0)`（98F 办公室）、`weapon0/1` 均为空 —— 与真机现象逐项吻合。

**修法**

1. `_should_open_new_game_in_master_office()` **不再复用**「从天台开始」的判据，改为
   **教程未完成（`BaseManager.should_start_on_rooftop()`）且本档没有任何运行时快照**。
   用「没有快照」而不是新增「开过场」标记：**零新增存档字段**，且复位存档会清空快照 ⇒ 复位后重新开始仍看得到开场（与 1848 的归零需求一致）。
   副作用（已接受）：教程未完成但已经开过场的档不再重演开场 —— 这是本次要的。
2. `_should_start_on_rooftop_for_entry()` 的基地快照分支改为返回 `should_start_on_rooftop()`：
   **非战局内下线（100F 天台与 99F 基地都算）一律回 99F 基地固定出生点**；
   `ROOFTOP_LOGOUT_SPAWN` 只剩「教程未完成的新手期出生」一个用途。口径变更已同步 `docs/v0.1/09` §10.1。

**验收**：`verify_block00_floor98_assembly` 新增 **K2 段**（5 组判据：天台下线 / 基地下线 / 塔内续局 / 全新档必须仍走办公室开场 / 教程未完成但已开过场不得重演），断言数 230、失败 0。
**反向对照三组**（逐次注入后跑，每次文件逐字节还原）：① 只把开场判据改回旧实现 ⇒ **恰好 1 条红**（「教程未完成但已开过场仍重演开场」）；② 只把落点判据改回旧实现 ⇒ **恰好 1 条红**（「天台上线没有回 99F 基地」）；③ 两处同时回旧（= 真机原状）⇒ **恰好 3 条红**（含「天台上线被判成新游戏开场」）。
回归：`verify_game_entry_flow` OK、`verify_opening_script_runtime` OK（105 项）、`verify_pause_game_save_reset_flow` OK、`verify_narrative_timeline` OK（107 项）。

**遗留（未做，待业主选）**：缺陷 2 —— 开场地上的枪不进存档。修好判据后正常玩家不会再被误收枪，但**真新档玩家若没捡枪就下线**仍会丢。三个候选见 `design/2026-09-23_剧情触发语义规范与跨局历史_方案.md` §D.2（推荐：把地面枪写进 `active_run_snapshot` 的 `world_drops[]` 并在上线时重建）。
