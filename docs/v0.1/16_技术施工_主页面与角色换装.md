# 技术施工｜主页面与角色换装 v0.1

更新日期：**2026-10-14**

## 1. 启动主页

2026-09-22 用户参考图修订（ENTRY-AVATAR r2）：主页采用左侧白青标题与品红数字、切角霓虹按钮，右侧角色的基地实景构图。`MainEntryScreen3D`是展示状态唯一所有者，新增独立Camera3D、独立CameraAttributesPractical和相机专属Environment，不改玩法镜头资源、全局画质、世界时间或基地灯开关。

展示点位于99F全息平台南侧，背后使用真实基地发光设施；角色是当前已装配外观与武器的只读网格快照，不实例化第二个Player3D，不复制玩法脚本、碰撞、库存或存档。真实玩家保留原出生位置，展示锁定输入；无基地的独立测试场景退回原角色附近取景。只读视觉快照替代旧版“不复制角色视觉”的限制，不能据此改变98F新游戏出生契约。

镜头初始垂直FOV 34°，近景景深关闭、远景柔化，仅该相机持有；冷白主光、暖面光、青蓝与品红轮廓光均只照展示层。主页菜单包含开始和设置，按钮提供入场、呼吸流光、悬停/手柄焦点位移和按下反馈。设置复用PauseMenu3D画质/操作页，暂时提升到主页层，不暴露脱困/复位档案动作。开始使用1.15秒遮黑交接，再恢复原current camera、HUD、输入；开始、跳过、重复调用及意外卸载统一清理展示节点。世界场景不切换、玩法位置与存档不重置。

验收入口：`verify_main_entry_cinematic_flow`（真实渲染、资源隔离、位置不变、按钮/设置与清理），既有入口分流及外观持久化回归仍保留。

### 1.1 入口语义与唯一触发规则

`TowerDescent3D`同时承载开始展示、99F基地和塔楼行动，因此“加载了主场景”不等于“进入开始界面”。`GameEntryFlow`是进程级唯一入口意图所有者：第一次进入主场景默认为`cold_start`；局内场景切换必须在切换前登记一次性意图，由新场景消费后立即清除。

| 入口原因 | 入口类型 | 入口覆盖层 | 出生契约 |
|---|---|---|---|
| 进程冷启动 · **全新存档** | `main_entry` | `OpeningMovieScreen3D` 开场影片 | 98F办公室 |
| 进程冷启动 · **已有存档** | `main_entry` | `MainEntryScreen3D` 主页菜单 | 按存档进度 |
| 明确点击“返回开始界面” | `main_entry` | 同冷启动，按存档形态二选一 | 按存档进度 |
| 复位存档后重新开始 | `main_entry` | `OpeningMovieScreen3D` 开场影片 | 98F办公室 |
| 死亡结算返回 | `gameplay` | 无 | 强制99F基地中点 |
| 成功返航/撤离 | `gameplay` | 无 | 99F基地 |
| 有效战局读档／重载 | `gameplay` | 无 | 重建保存楼层后出生于该层入口安全房间中心 |
| 无可续局快照的冷启动／重载 | `gameplay` | 无 | 按最后基地快照的100F／99F固定出生点；旧档再回退新手进度 |

主页不得再由`_ready()`、场景路径、角色坐标、楼层或死亡UI自行猜测是否打开。以后新增“返回开始界面”按钮时，必须先调用`GameEntryFlow.request_main_entry()`，再切换到主场景；切换失败必须撤销该请求。

塔楼固定相机更新在主页或衣柜持有镜头期间暂停；覆盖层关闭后恢复既有相机链。

### 1.2 全新存档开场影片（ENTRY-AVATAR r3）

全新存档不再先给主页菜单，而是**开场影片 → 无缝进入玩法**：loading 结束后播 `assets/movie/opening_mv.ogv`（20.06 s，赛博朋克末日前史，含音轨），播完渐黑交接，玩家直接站在 98F 主人的办公室里开始主线开场 01。已有存档照旧走主页菜单，见 §1.1 表。

**互斥与判据。** `MainEntryScreen3D`（主页菜单）与 `OpeningMovieScreen3D`（开场影片）是同一个入口的**两个互斥出口**，由`TowerDescent3D._install_main_entry_screen()`二选一，共存于同一槽位`_main_entry_screen`（公共父类`CanvasLayer`）。塔楼只按三个契约调用它们 —— `prepare_gameplay_hud()` / `is_camera_override_active()` / `transition_finished` 信号 —— 不按具体类型分支。

分流判据`TowerDescent3D._should_play_opening_movie()`**复用**`_should_open_new_game_in_master_office()`，不另立一套：“播影片”与“98F 办公室开局”必须是同一个判据，否则会出现「播了影片却落 99F 基地」这种只在真机复现的错位。复用同时白送三道否决 —— `is_expedition()`（远征没有 98F 办公室）、`spawn_target == base_99f`（死亡返城／撤离返航显式落 99F）、`_returning_to_tower03`。此外“已有 runtime 快照”必然否决，与`REASON_RUNTIME_RESTORE`入口天然互斥，故**续档重进永不重播开场影片**。

**所有权交接。** 影片层不切场景、不复制角色、不读写存档，与主页同一套写法：展示期间锁玩家输入、隐藏`HUD`，播完按`FADE_IN_BLACK(0.45s) → 交还 → FADE_OUT_BLACK(0.70s)`两段渐黑收口，全黑时才归还输入与 HUD，结束后`queue_free()`自己并发一次`transition_finished`。塔楼据此才发`gameplay_started`，开场剧情（`nar_tower_opening_01_wake`）挂那一发 —— 这条时序在主页那里已经踩过坑，影片层沿用同一约定。跳过可接受任意键／鼠标点击／手柄键；`_exit_tree()`同样收口，异常卸载不留半接管状态。

**loading 阶段（`StartupLoadingScreen`）随后台预加载走真实进度。** 该页从`change_scene_to_file()`同步切换改为`ResourceLoader.load_threaded_request(TARGET_SCENE, "", true)`后台预加载（`use_sub_threads = true`，否则只预载 PackedScene 壳、实例化时照样同步卡），进度条读真实进度，`已完成`与`最短展示 1.10 s`两者都满足才切（两值取大、单调不减，不会回跳）。阶段文案随之由**按时间分段**改为**按进度分段**。若预加载不可用或失败，退回同步切换，由目的场景自己报错 —— 不新增失败态。理由：主场景真实存档下启动实测 8～12 秒（见`MODULE_INDEX`启动卡顿诊断），同步切换会让进度条停在 100% 冻住十几秒再硬跳，而开场影片正接在这段之后，玩家会误判成“卡死了、动画没了”。

**音频。** 影片音轨随`Music`总线（旁白／配乐属音乐域），无`Music`总线时退回`Master`。

**资源与限制（两条硬约束）。**

1. **运行格式必须是 Ogg Theora**：Godot 4.x 的`VideoStreamPlayer`只支持`.ogv`。源文件归档在`art_source/movie/opening/`（不入包），运行资产在`assets/movie/`（`assets/`不在导出排除列表内，会进包；计入包体约 +10.9 MB）。
2. **Windows 上只有部分 FFmpeg 构建能产出可播的 Theora**：Godot 论坛已确认“gyan.dev 构建的 Theora 编码器是坏的，产出的视频是垃圾”，必须用 BtbN 构建。坏构建的症状是：ffmpeg 自己解码都报`error in unpack_block_qpis`，Godot 里表现为整屏彩虹噪点（画面结构尚在、颜色全错）；该症状与编码质量`-q:v`、分辨率是否 16 倍数**均无关**，不要往这两个方向排查。

   已在本机留了一份可用构建：`I:\工作项目\shellstrom2\ShellStorm2-work\scratch\ffmpeg_btbn\ffmpeg-master-latest-win64-gpl\bin\ffmpeg.exe`。本轮实际使用的转码命令：

   ```
   ffmpeg -i <源>.mp4 -c:v libtheora -q:v 7 -c:a libvorbis -q:a 6 -vf "fps=30" <输出>.ogv
   ```

   转完**必须自解一遍**再落位（`ffmpeg -v error -i <输出>.ogv -f null -` 应零输出），否则会把坏码流带进工程 —— 坏码流用 ffmpeg 仍能放出画面，只有 Godot 会花屏，靠肉眼看 ffmpeg 的播放结果**验不出来**。

**headless 铁律。** headless 下`load()`一个`.ogv`会让**整个 Godot 进程挂死**（不报错、不返回，只能超时杀掉；`ResourceLoader.exists()`正常）。因此影片层在`test_mode / headless`下**连`VideoStreamPlayer`节点都不创建**，直接走自我交接；`TowerDescent3D._install_main_entry_screen()`原有早退也继续生效。自动验收只允许验证「资源存在且非空」「分流判定」「headless 自我交接」三件事，**真实播放与画面无缝性必须走真实渲染验收**。

验收入口：`verify_opening_movie_entry_flow`（资源存在／分流判定／headless 交接），真实窗口播放与交接时序走渲染探针。

## 2. Avatar槽位

当前正式衣柜使用六个纯表现槽：`body / head / hand / feet / hat / glasses`。每个槽至少有3个合法变体；目前使用程序材质变色和现有角色组件验证完整链路。选择外观只调用`PlayerAvatar3D`既有装配入口，不改变角色碰撞、属性、武器、背包或动画所有权。

`glasses` 在衣柜显示为“面饰”，同时容纳眼镜、护面与 `electronic_mask` 电子面具。电子面具为新建角色及缺失/非法面饰ID的默认值；已经保存的合法选择（包括 `none`）保持原值。面饰通过 `HeadJoint/FaceAccessorySocket` 跟随既有头部动作，在原换装入口选中、卸下和保存；使用女仆头时沿用面饰防穿插隐藏规则，保留选择以便切回兔头。面具归属角色组件，Blender 集合为 `01_部件/眼镜/眼镜__electronic_mask`，与兔耳的“部件/样式”两级分类一致。复制当前兔头前侧曲面并轻微前移制作黑色亮面壳，原头部网格、材质和源文件保持原样；蓝色方块眼睛为面具自身视觉几何。独立 GLB 和 PackedScene 使用稳定无版本路径；版本保存在源Blend、清单和台账中。新配件不修改原角色骨架、动作、碰撞或武器。

电子面具 v002 每眼使用5×14颗10.8mm方块，眼睛约66.8×192.8mm；独立模型/动作双母版保留同一共享骨架签名。面具的 `ExpressionPlayer` 默认循环 `mask_idle`（12秒），包括两次眨眼和两段短闪；另提供 `mask_blink`（0.26秒）与 `mask_flicker`（0.42秒）单次剪辑。Blink形态键留在GLB，Blender创作的线性闭眼/亮度曲线经JSON中转为Godot AnimationLibrary；GLTF不携带发光强度动画，因此局部表现适配器直接消费曲线值。每实例独立发光材质；不新增玩家状态，不使用程序生成角色姿势。版本、三段剪辑及文件哈希登记在角色账本和[验收记录](development/2026-10-01_bunny_electronic_mask_v002.md)。

v003扩展为8个独立网格表达组件：平静、开心、难过、红色生气、惊讶、爱心、疑问和警示。它们只替换显示网格，不改变面饰配置。`CharacterExpressionSystem`独立拥有表情ID、随机与保持时间；`PlayerExpressionStateAdapter`消费`Player3D.presentation_state_changed`并暂时随机调用；面具显示端只消费事件并播放原局部动画。系统初始平静，4秒后开始背景随机，后续3–6秒切换且不连续重复；状态变化也可调用，明确指定的表情可保持。符号不压缩眨眼。完整接口、拒绝和生命周期见[独立表情系统设计](design/character_expression_system.md)，制作与验收见[交付记录](development/2026-10-01_character_expression_system.md)。

v004按追加参考移除全部嘴部网格，放大加粗眼睛/爱心/?/!，颗粒11.8mm、间距14mm；默认平静每侧6×15颗。保留8种ID与独立选择/随机/状态调用，继续使用原局部眨眼/闪烁。原11网格、骨架与v001–v003双母版不变，子资产各升级v002并更新既有账本行，见[无嘴部深化验收](development/2026-10-01_character_expression_mouth_free.md)。

v005将8种表情材质自发光从5降至1.25，弱化光晕、保持方块和色彩清楚；双母版与稳定GLB同步，闪烁仍按原相对亮度曲线。父面具v005、子组件v003，详见[自发光减弱验收](development/2026-10-01_character_expression_soft_emission.md)。

衣柜界面保持实际角色居中：左侧为当前穿搭，右侧为分类和140×140方形物品框。关闭或每次选择后，将稳定变体ID写入`BaseData.avatar_customization`；再次进入主页面、衣柜或读档时应用同一记录。

死亡返城、成功撤离和普通场景恢复不会实例化`MainEntryScreen3D`，因此不能再依赖主页或衣柜顺便恢复外观。`Dungeon3D._ready()`在正式玩法初始化时直接通过`AvatarCustomizationPersistence`把`BaseData.avatar_customization`应用到当前真实`Player3D`；自动化`test_mode`不读取开发者档案。这样热返99F与冷启动使用同一外观事实源，退出重进不再成为“修复外观”的必要步骤。

换装不建立独立存档文件，继续随`BaseData`总档一起原子保存。存档封套使用`canonical_json_v3`：写盘前递归将所有Dictionary键规范为JSON字符串键，并完成一次内存JSON往返后再摘要，解决武器装配枚举槽位或高精度数值与换装共同保存时的校验差异；`BaseManager.save_base()`只有在写盘后重新读取、校验成功且revision一致时才返回成功，因此衣柜的“已保存”表示该档确实可以重新加载。旧`canonical_json_v2`整数武器槽位缺陷档优先按旧校验值精确迁移；其他v2档仅在封套与载荷的revision、原因、时间戳完全互证且核心BaseData类型完整时迁移。迁移后立即重存为v3，截断、非SHA-256格式或元数据不一致的损坏档仍拒绝。

## 4. 基地衣柜设施与脱困

`avatar_wardrobe`通过现有`BaseFacility3D → BaseFacilityCatalog → TowerDescent3D/BaseWorld3D`菜单链打开，不新增第二套交互系统。

ESC返回基地中心是安全脱困，不是战局撤离：仅角色处于99/100层基地安全体积且无过渡事务时可用，目标为既有`facility`中心出生点；战局中按钮禁用并显示原因。

同一ESC暂停页复用`UI-SCREEN-PAUSE-3D`增加“复位游戏存档”。按钮始终经过二次确认；确认后由`BaseManager.reset_game_save()`停止旧行动快照提供者、写入并回读校验一份全新`BaseData 2.0`封套，再清除旧`.bak`，最后重置世界时间、关卡选择与局内命运状态并返回正式主场景。复位范围包括基地、蓝图、物品、外观、时间和当前行动；独立`graphics_settings.cfg`明确保留。写入或回读失败时保留原内存档与磁盘回退链，不允许只清内存后继续运行。

## 5. 验收

- [ ] 主页以99F基地纯视觉代理（非Player逻辑）接管：独立Camera3D、独立CameraAttributes与相机专属Environment，不改动真实玩家、玩法镜头或世界位置。
- [ ] 主页使用视觉快照代理（uses_visual_snapshot）与独立展示摄像机（dedicated_camera）/独立attributes（dedicated_attributes），真实玩家yaw不被主页修改；展示锁定南向，摄像机固定于角色南侧正面。
- [ ] 主页灯光限定为展示层专用（presentation_lights_only）：PortraitKey、FaceFill(能量1.3)、CyanRim、MagentaRim四盏独立OmniLight，只照展示层、不产生展示外阴影；开始过渡过半后释放rig，过渡结束确认无展示rig残留。
- [x] 启动页只响应冷启动、新档重启或显式返回主页；死亡返城、撤离和普通重载不触发。
- [x] 死亡结算返回时即使新手标记异常，也依入口契约强制落在99F基地，不改送100F天台。
- [x] 六类外观均至少3项，方形物品框与当前穿搭区可读。
- [x] 外观只影响表现并进入同一基地存档。
- [x] 死亡、撤离或普通场景恢复直接返回玩法时，无需经过主页或重启即可恢复六类已保存外观。
- [x] 带整数武器装配槽位的总档可保存六类换装并在模拟重启后恢复。
- [x] 写盘成功必须通过回读校验和revision核对，旧v2整数槽位缺陷档可定向迁移。
- [x] 衣柜关闭后恢复相机与输入锁。
- [x] 脱困只在基地安全体积内可用，战局中不可使用。
- [x] ESC复位存档具备二次确认、写后回读、旧备份清除和主场景全新启动；画面设置保留。
