# 11 远征03｜场景工坊布局与陈设流程

适用：工程0.1.0；FeatureID：WORLD-PLAN、ASSET-PIPELINE，工具关联TOOL-SCENE-EDITOR。来源：用户关于唯一房间文件、固定陈设、参考图美化、墙边柜架与易碎设施的明确要求。本页维护制作流程，具体设计以[远征03主设计§7.5.2–7.5.4](design/远征关卡03设计.md)、[可交互物件设计](design/场景可交互低模物件设计.md)为准；运行结果写独立开发记录。

## 1. 适用边界与调用

Skill名：`11-expedition03-scene-workshop-layout`；显示名：**11 远征03｜场景工坊布局与陈设**。

调用示例：

```text
使用 $11-expedition03-scene-workshop-layout，挑选远征03一间房间，
丰富墙边书架和柜子，并增加非通道角落的易碎设施，完成游戏内验收。
```

仅用于`block_id=expedition / level_id=expedition_03`。不是远征关卡通用模板，不替换00–04通用房间Skill，不作用于远征01的房间、白盒、尺寸、组件源、拓扑或关卡配置。共享组件可复用，不代表跨关卡同步布置。

默认任务是布局、照明、组件实例与验收。需要新增几何时按现有组件生产/02b导入流程办理；需要修改门墙/地砖配方、关卡生成、刷怪、掉落、门状态、存档或导航时，先报告具体原因和影响，作为独立程序范围处理，不能借本流程修改通用机制。

## 2. 唯一文件与状态所有者

```text
GameDesignConfig / 当前关卡计划
  → 场景工坊scene_index.game_rooms()查询当前有效资源
  → RuntimeRoomArtSource匹配正式TSCN
  → 工坊打开/保存这同一份TSCN
  → 游戏加载作者陈设、灯光与设施
  → 关卡按本局种子布局房间世界位置及合法门位
```

| 内容 | 所有者 | 制作要求 |
|---|---|---|
| 房间拓扑、世界摆位、连接、门位与门状态 | 关卡结构与运行装配器 | 只读取，不在美术流程改规则 |
| 当前底层地砖/门墙 | 现有ManorShellPlan与装配器 | 游戏会重建；静态地砖不是持续作者覆写入口 |
| 房内组件实例、父子变换、启用、作者灯光 | 正式房间TSCN | 用Godot/工坊维护，原路径保存 |
| 模型、材质、原点、组件定义与Prefab碰撞 | 共享组件 | 不在房间里复制几何或为尺寸强行缩放 |
| 作者易碎件身份 | 正式TSCN稳定节点名→房间认领ID | 同名不要跨组任意重排导致ID漂移 |
| 已碎/方向与恢复 | 房间breakable_clutter状态账 | broken信号接线、流送和读档沿现有机制 |
| 布局路径、数量、SHA追溯 | 场景账本《房间运行登记》 | 不是游戏读入的数据源 |

当前池为18份正式资源，这是资源统计，不是单局房间数量。一个正式资源可能供同一局多个实例或不同种子复用；文件名仍有历史指纹也不代表要生成新种子副本。每次以查询结果为准，不根据旧目录里全部TSCN的数量推断运行池。

## 3. 开工与范围冻结

先读场景账本《房间运行登记》的制作状态、维护策略与保留日期。入口15×15、事件25×25、大堂45×40已登记本轮完成、默认保留；自动选房、美化、批量摆放和烘焙须跳过，仅用户明确指定返修时修改。笼统的继续任务不覆盖此约定。验收SHA与当前保留快照SHA分列，后续变化待核对，不自动覆盖或回填。

1. 读项目AGENTS、文档规范、ART_SOURCE_LAYOUT和本次主设计。明确房间路径、用途、参考图、禁止改动项及当前已有手改。
2. 用`scene_index.game_rooms()`及运行引用确认目标。运行Skill内`check_room_scope.py`，它拒绝03目录外文件及metadata不属于03的资源；它不替代运行匹配查询。
3. 改前记录Git状态、文件SHA及节点/灯光快照；在工程外`ShellStorm2-backup/<日期_主题>/before_edits/`备份。并发手改只比较和保留，不能用旧备份整份覆盖。
4. 过程脚本、测试工程、日志/图片走`scripts/workspace_paths.py`的`work_path()`。正式房间仍在稳定runtime路径，不新增整屋GLB或版本目录。
5. 核查目标组件来源、稳定Prefab、GLB哈希及已有独立优化/保真记录。LFS指针只能比OID，不能宣称源已实际重开；Prefab历史哈希若仅为CRLF/LF差异应明确核对，不批量回填无关哈希。

## 4. 空间设计与陈列

### 4.1 先通行，再功能区与视线

读房间真实尺寸、走行面及全部合法门位。以主通道、横向交通带、战斗/事件设施空间为骨架，再划会客、接待、藏品/档案、休息等区域。效果图提供色彩与构图关系，不强制把卧室、卫浴、楼梯分隔复制进既有单间。

公馆语言：深木护墙、石材基底、暗红金边织物、黄铜、暖光、绿植。家具保持人尺度，默认单位缩放；不靠放大家具填满大房，也不靠增亮整屋抹掉层次。

### 4.2 墙边丰富度

- 高柜/书架作为竖向锚点，窄桌、画框、台灯形成低位段，盆栽收口；重复组合之间留空，避免整面等密度复制。
- 柜体与书架放无门墙段、墙角和接待/会客外围；不能盖住门洞，也不能用一排柜子切断横向通路。窗墙与高柜的关系在真实镜头里判断，优先把低桌用于需要保留视线的段落。
- 桌、椅、文件、花器、灯具分别引用已有组件，组成接待台/会客岛/档案陈列；视觉组合不自动获得新的交互能力。
- 现有房间灯光默认保留。新增照明以局部暖光池组织重点，检查灯罩过曝、阴影遮挡、雾中读图和暗处可辨性。灯饰几何与真正Light3D分开统计；不要假设视觉灯自带可交互开关。

### 4.3 易碎设施

使用套件“共享 / 易碎陈设”：罐、花瓶、书本堆、椅、木箱五种正式Prefab。主要在墙边和非通道角落成组，穿插于书架、柜体旁；当前用户倾向约90%外围、中部少量。比例用于本类美术方向，不是所有房型不可调整的程序参数。

数量服从真实可用空间、门口与射击角度。角落可以丰富，但后排不能被前排或柜体永久封住。组件间避免穿插重叠，摆放时用完整包络与物理射线验证；不能为“可打碎”而删碰撞或改子弹穿透。

易碎件本身不挡玩家：layer4受击，PlayerContact负责接触破碎。仍须保留门前视觉净空和主要行走线，避免玩家刚出门就无意撞掉一排物件。首选落地；现有碎片相对物件底面落定，放高台需要另验高度，不能直接搬到桌面后假定碎片会落回地面。

### 4.4 地面和标高

底层地砖遵循现有运行配方，本轮通常用地毯、跑毯和家具岛做固定区域层次。地毯表面高于实际地砖顶面，避免被覆盖或共面闪烁。当前公馆地砖顶面约0.10m，仍须按当前文件/运行实测；旧测试夹具标高0不适用于所有房间。

## 5. Godot正式编辑与保存

已有正式TSCN即直接编辑。可以使用工坊或Godot节点实例化/属性编辑，保存为原路径PackedScene。不要执行整屋烘焙器从旧清单重生成；不用临时JSON成为第二个持续布局真源。

推荐分组：原有`ArtComponents/AuthoredSalon`保留；追加墙边陈列可用`WallCollections`，易碎设施可用`AuthoredDestructibles`。组名是当前案例的组织方式，不要求重命名其他作者节点。只给新组件实例根设置room owner；新增作者碰撞/灯光正确持有owner，Prefab内部Visual、Mesh、HitReceiver不展开复制。

正式保存前检查：

- 全部合法门位净空来自`RoomArtLayoutContract`，不手抄门槽公式、不只避开样本门。
- 其`furnishing_conflicts()`只检查layer1阻挡。易碎layer4要另用实际footprint对`door_boxes()`查询，不能因函数返回空就认为易碎摆位合格。
- 实测包络、完整父链变换、单位缩放、房界、地面、家具互穿、射击起点/弹路。区分家具碰撞、易碎受击体与结构承重，不因去重破坏各自职责。
- 原节点/灯光保留情况有可比对差异；授权删改、新增、并发修改分列。新布局不包含QA过程的已碎状态。

## 6. 运行验收与用户数据隔离

### 6.1 先准备独立测试工程

使用Skill内`prepare_isolated_project.py`，例如：

```text
python3 <skill目录>/scripts/prepare_isolated_project.py --project-root <工程根> --session room-layout-yyyymmdd --case native --renderer gl_compatibility
```

它将完整原配置复制到工程外，并**显式插入**`config/use_custom_user_dir=true`和唯一`config/custom_user_dir_name`；创建指向工程外数据目录的独立用户目录链接。每个case使用不同命名空间，已有case拒绝覆盖。未修改正式project.godot，不启动游戏。资源目录使用链接而非强制只读副本；测试若需要写资源，fixture输出须另指工程外，不能通过res链接覆盖正式文件。

按照输出`guard_args`启动一次Godot：guard必须退出0，打印的`OS.get_user_data_dir()`及`BaseManager.save_path`必须指向本case。只有通过guard才继续测试。缺缓存、符号链接权限、路径不符或脚本错误时停止本case并处理，不回退正式工程执行。`test_mode`、仅设置APPDATA、创建目录、对缺失字段做replace都不能替代此检查。

不结束用户游戏或其他会话进程。若误写默认存档，停止自己的进程、保留当前数据和日志、明确告知用户；没有可确认原备份时不猜测回滚。默认目录存在其他并发进程时，SHA变化不能单独归因于某一测试。

### 6.2 逐层验收

| 层 | 必须证明 |
|---|---|
| 静态资源 | 正式TSCN能加载、组件引用稳定、原布局保留、数量/分布/单位缩放/包络正确 |
| 装配 | 游戏真用此文件；跨种子作者摆位与灯光保持，门墙跟本局端口；所有合法门前通行 |
| 易碎命中 | 真实Projectile3D撞HitReceiver、命中方向与broken信号入账；不能直接shatter冒充枪击 |
| 原生操作 | 每个目标房的玩家当前武器开火、真实玩家接触、破碎前/飞散/落定及完整布局画面 |
| 生命周期 | 破碎幂等、本体隐藏、受击层关闭、碎片落定无阻挡；作者件detail流送常驻、随机件重建 |
| 恢复 | 房间账序列化后回灌全新房间，同稳定ID恢复已碎；未打碎物仍完整 |
| 性能 | 数量及最大碎片量记录；目标设备预算另测，功能通过不冒充性能通过 |

现有入口与具体注意事项见Skill的`references/verification.md`。门口净空/持久化可以headless；画面与玩家输入必须原生渲染。观察相机与原游戏HUD视角注明区别，保留真实环境/雾/灯；不把展示补光的画面当游戏内结果。

## 7. 登记与交付

通过`assets/registry/ledger_index.json`定位场景分账本及《房间运行登记》。只更新受影响房间数量、SHA、备注、域日志和布局页摘要；其他房间逐项保留。共享组件没改，不修改其AssetID/版本/哈希或资产主表公式。陈设总数可以包含易碎设施，但家具阻挡碰撞不能把易碎受击体/Area混入。

更新独立开发记录及MODULE_INDEX，列出退出码、预期故障、非预期脚本/渲染ERROR、未执行项、用户数据事故。运行文档、关卡解耦、运行资产命名与账本所需检查；既有失败单列，不批量接受哈希漂移或放宽阈值。Skill/文档整理不升级工程版本，不改变整关partial状态。

Skill正本为用户级WorkBuddy `~/.workbuddy/skills/11-expedition03-scene-workshop-layout/`，按本项目镜像约定同步至：用户级Codex `~/.codex/skills/`、项目`.codex/skills/`、项目`.workbuddy/skills/`及项目`skills_drafts/`下的同名目录。当前工作区根为仓库根，不向父级另建WorkBuddy工作区。

本Skill全部文件保持CRLF并逐文件SHA一致。用`python3 scripts/check_expedition03_layout_skill.py --installed`核查五处；仅clone项目时省略--installed核查项目三处，不要求其他机器存在本用户全局安装。只同步此目录，不全量覆盖其他Skill；本地同步脚本不存在或有硬编码旧机器路径时不照抄。Skill内项目路径使用“相对工程根”的文本；Skill自带验证参考使用同包相对链接，以免多安装深度造成链接失效。

Codex和WorkBuddy中的文件已落盘不等于当前会话已刷新发现列表；需要时刷新Skill列表或重开会话。不要为安装新Skill重启正在运行的游戏。
