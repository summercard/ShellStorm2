上级文档：[游戏设计文档](README.md)  
数据库文件：[ShellStorm2_游戏内容数据库_v010.xlsx](data/ShellStorm2_游戏内容数据库_v010.xlsx)

## 1. 文档职责

游戏设计文档定义规则，技术施工文档定义实现方式，本数据库定义可批量编辑的具体内容。名称、数值、价格、稀有度、掉落位置、技能参数和背景说明不得长期散落在设计段落、场景备注或临时代码字典中。

本版数据库先导入当前工程能够确认的内容，并为主设计者的新设定建立稳定条目。它不是自动覆盖代码的配置源；在数据管线完成前，代码与表格之间的差异必须进入 [全游戏完成度清单](12_全游戏完成度清单.md)。

## 2. 三色状态

- <span style="color:#2E7D32">**[已实装]** 当前正式代码或正式 3D 场景中存在的内容。</span>
- <span style="color:#1565C0">**[用户设计]** 主设计者已冻结、尚未在游戏中呈现的条目或规则。</span>
- <span style="color:#EF6C00">**[Codex补充]** 为补齐名册、背景、字段、体验或施工闭环而新增的内容。</span>

Excel 内的“状态来源”和“背景来源”使用同样的字体颜色。一个功能已实装但背景由 Codex 补充时，两个单元格分别标色，不用一种颜色覆盖整行事实。

## 4. 稳定 ID 规则

1. ID 使用小写蛇形英文，发布后不因中文名称调整而改变。
2. 内容定义 ID 与运行时实例 ID 分离。例如 `fate_overclock` 是内容 ID，某局抽到的卡片实例另有运行时 ID。
3. `weapon_content_id` 表示枪型定义；每一把实际生成的枪另有永久唯一 `weapon_instance_id`。同型枪不能共享实例 ID，也不能只靠背包格或显示名区分。
4. 精英 ID 永久绑定同一个体；同名显示文本不是唯一性判断依据。
5. Boss 下行钥匙固定为 `item_boss_descent_key`，门用途固定为 `boss_descent_gate`，不得复用普通 `item_room_key`。
6. 删除条目时先标记 `deprecated` 并保留迁移目标，不能直接让旧存档失去引用。

## 5. 各表维护规则

### 5.1 武器

- 枪身保存伤害、射速、弹丸数、扩散、换弹、弹匣和可选蓄力参数。
- 子弹保存附加伤害、速度倍率和行为标签。
- 配件只保存自己提供的修饰，最终武器数值由装配系统计算。
- “产出与掉落”来自物品注册表的权重键；表格不把权重解释为百分比。
- 枪身的可拾取成品与蓝图碎片可以共享装配 ID，但必须保留不同物品 ID。
- 枪型表保存 `fate_slot_base` 与类型/稀有度覆盖规则；普通枪械基础值为 8，未冻结的容量修正不得写死在代码中。
- 内容表不保存玩家拥有的枪械实例；运行时和存档中的 `WeaponInstance` 必须引用枪型内容 ID，并携带自己的永久命运槽、子弹模块与配件快照。

### 5.2 命运卡

- 每张卡必须有稳定 ID、类型、品质、目标规则、效果参数、UI 描述和验收说明。
- 每张卡必须同时声明 `scope=WEAPON / CHARACTER / WORLD`。效果类型说明怎么执行，作用域决定由谁持有，两者不能互相替代。
- `WEAPON` 卡占用目标枪械的下一个永久命运槽；`CHARACTER` 与 `WORLD` 卡不占武器槽。
- 背景介绍是内容层文本，不得承担未实现效果的说明责任。
- <span style="color:#2E7D32">**[已实装]** 48 张当前命运卡已经改用稳定内容 ID；运行时抽取记录不得重新生成顺序号写入长期存档。</span>
- 环境触发卡与可直接选择卡必须在“获得方式”中明确区分。

### 5.3 怪物与 Boss

- 当前正式数值以 `Enemy3D.PROFILES` 为基线；旧 2D 的 10–40 HP 基线只用于换算楼层/主题倍率，不再写入玩家可见数值。
- “刷新位置”同时写房间类型和楼层深度，不能只写“随机”。
- Boss 的阶段技能、专用钥匙和下行门解锁属于同一验收链，但数值与门逻辑分属不同系统。

### 5.4 精英怪

- 名册固定 12 行，不能通过复制行扩充为第 13 只而不修改主设计。
- “当前档案状态”是运行时存档值，不回写内容定义表。
- 每只精英必须有一个核心战术、一个成长方向、一个夺械转译规则和一个辨识特征。
- 当前已有两只兼容原型；其余 10 只名称与玩法是 Codex 补充，后续主设计者可以在不改变 12 只唯一规则的前提下调整。

### 5.5 掉落物品

- 价格 `0` 表示不可出售或未定价，不能自动解释为免费商品。
- 产出位置使用注册表权重键，权重之间只在同一个掉落池内比较。
- 任务钥匙、Boss 专用钥匙等进度物不进入普通商店，不允许被随机消耗逻辑选中。
- 武器成品 `stack_max=1`；物品记录必须携带 `weapon_instance_id` 与完整构筑快照，交易和集合转移按实例 ID 去重。
- 7 枪身、8 子弹模块、6 配件逐条填写 `功能UI提示 / 武器或战斗表现 / 表现状态`；不能用一条通用说明代替。
- 48 张命运卡逐条填写 `选择/槽位提示 / 触发或世界表现 / 表现状态`；作用域、天体专名、目标、槽消耗和失败文案必须与实际规则一致。

## 6. 数据变更流程

```text
设计者修改数据库条目
→ 标记来源、版本与变更原因
→ 内容校验：ID唯一、字段完整、引用存在
→ 技术实现或导入
→ 对应系统自动化测试
→ 游戏内验证数值、表现、掉落与存档
→ 将实现状态改为“正式3D已验证”
→ 更新完成度清单与变更记录
```

## 8. 数据验收标准

<span style="color:#2E7D32">**[本轮完成]** `武器`、`命运卡` 和 `总览` 工作表已同步本轮施工状态；公式错误扫描为 0，并完成 7 张工作表渲染复核。逐内容专属 VFX/音效列仍标记为部分完成。</span>

- 所有内容 ID 唯一且非空。
- 所有枪械实例 ID 唯一；同一实例不能同时位于装备、背包、地面、商店或保险柜。
- 命运卡作用域非空；武器卡具有槽规则，角色卡和世界卡明确不占槽。
- 所有武器与命运卡条目具有非空 UI 和表现定义；页面、HUD、模型、弹道、命中或世界反馈至少覆盖规则所需层面。
- 五张内容表均能从主设计和对应施工文档定位。
- 当前代码已注册内容无遗漏；新增设计不伪装成已实装。
- 数值字段为数值，列表和字典以可读文本保存，不混入公式错误。
- 来源、实现状态、事实源和备注齐全。
- 数据库没有 `#REF! / #DIV/0! / #VALUE! / #NAME? / #N/A`。
- 新内容进入游戏前具有最少一个可复现验收用例。
