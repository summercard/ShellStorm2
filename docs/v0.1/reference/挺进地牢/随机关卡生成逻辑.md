## 零、一句话

**它不是"随机撒房间再连线"，而是"先在一张手画的房间关系图上随机，再把关系图落到真实几何上"。**

随机只发生在三处：

1. 抽哪一张 **flow**（手作骨架）
2. 往节点里**注入**什么特殊房
3. 给每个节点挑哪个**房间模板**

房间怎么摆、门往哪开，是后面几段用**确定性算法**解出来的。

## 一、总体管线

| 段 | 输入 | 做的事 | 随机点 |
|---|---|---|---|
| 1 选骨架 | 每层 4～8 张 flow 文件 | 随机抽一张 | ★ |
| 2 变换图 | flow 图 | 替代链 / 二选一支路 / **注入** / 选房间模板 | ★★ |
| 3 拆复合对象 | 带环的图 | 把最小环一个个切出来，剩下的是树 | — |
| 4 分别拼装 | 单个复合对象 | 树用 DFS 摆、环从两端往中间合 | 部分（出口对选择） |
| 5 总装 | 一堆已摆好的复合对象 | 按"连接最多的房间"出发，把它们拼回一张图 | 部分（出口对选择） |

**关键点：第 2 段结束时，所有房间都定了、但一个坐标都没有。**

## 二、逐段细节

### 1. 骨架是手画的，而且很少

flow 是**图结构**：存房间之间的关系，不存位置。连接**有方向**——从根节点长成一棵树，然后
**额外连接把树打断成环**。所以环不是自然长出来的，是**手工指定的**，每个环都有明确的头和尾。

**实测：全部 28 张 flow，分布在 5 层**（本机解包统计，见 `10A_flow清单.csv`）：

| 层 | 内部代号 | flow 张数 | 平均房间数 |
|---|---|---:|---:|
| 1 Keep of the Lead Lord | `CASTLEGEON` | 6 | 17.0 |
| 2 Gungeon Proper | `GUNGEON` | **8**（最多） | 18.9 |
| 3 Black Powder Mine | `MINEGEON` | 5 | 21.8 |
| 4 Hollow | `CATACOMBGEON` | **4**（最少） | 20.2 |
| 5 Forge | `FORGE` | 5 | 21.6 |
| 合计 | — | **28** | — |

> Boris 原文"最深那层最少只有 4 张、Gungeon Proper 最多 8 张"——和实测完全对上，
> 而且能确认他说的 "Hollow" 就是内部代号 `CATACOMBGEON`（第四层）。

### 2. 变换：四种操作

| 操作 | 作用 | 用在哪 |
|---|---|---|
| 替代链 | 某个节点被替换成**随机长度的一串房间** | 图上表现为 `NORMAL (2 - 3 rooms)` 这种标签，只在后期层出现 |
| 二选一支路 | 某些段有备选路径，随机选一条 | **全游戏只用两次** |
| 注入 | 往图上插特殊节点 | 用得最狠，见第四节 |
| 选模板 | 给每个节点挑具体房间 | 第一层约 **300 个模板**，尽量不重复用同一间 |

`NORMAL (x - y rooms)` 这种写法在 flow 图里是**真的函数**，不是注释：
F3 起大量出现（`CONNECTOR (1 - 3 rooms)`、`NORMAL (1 - 4 rooms)`），正好对应
"替代链只用在后期更大层"这条。

**连接器（CONNECTOR）节点的房间是最后才选的**——它们的房间要等几何长出来才能定，
因为它们通常是"长而窄的房间"，**朝向必须对上**，否则接不上。

### 3. 拆复合对象：先切最小的环

循环执行：**找图里最小的环 → 整块切出来当一个复合对象 → 重复到没有环**。

切完剩下的都是**树**（无环连通块），外加复合对象之间的连接关系。

每个复合对象**在自己的独立坐标系里摆**，互不干扰。

### 4. 分别拼装：树和环两套算法

**树 —— 深度优先 + 回溯**

1. 第一间房随便放。
2. 从树上取下一个房间，选一对**出口**（一个在新房间上，一个在已放好的结构上）粘上去。
3. 只接受"不与已有房间相交"的出口对；一般**偏好离已有房间远的出口**。
4. 放不下就**回溯、重抽房间选择，最多重试 3 次**。

**环 —— 两端往中间合**

1. 从环上依次往**两侧**加房间。
2. 前期出口对随机选，**偏好相对的两面墙**（东西或南北）。
3. 做到一半后，改成**优先选能把两个开口端拉近的出口对**。
4. 全部放完后，最后一个点在两端之间补一条连接：能塞就塞一间**小矩形房**，
   塞不下就**寻路生成一条走廊**。走廊长度 **4～30 单位**（矿坑层放宽到 50）。

> 设计取舍：**先把环的两端拉开，再往中间收**。这保证环不会自己缠在一起，
> 也不用做全局碰撞检测。

### 5. 总装：从最"忙"的房间开始

1. 找到**连接数最多**的房间作为起点。
2. 逐个连接各复合对象；每次连接同样要选一对出口。
3. 两块图在不同位置就把局部**对齐**凑短路；对不齐就**寻路**补走廊。

Boris 的总结最到位：

> **"他们先造地图里最复杂/最重要的部分（中部那些窄环和短走廊），再拿其余部分去适配它们。"**

## 三、房型词表（游戏内部枚举）

mod 文档直接写出了枚举名 `PrototypeDungeonRoom.RoomCategory`，**flow 图上的标签就是这些值**：

| flow 标签 | 枚举 | 含义 | 实测每张 flow 的数量 |
|---|---|---|---|
| `Gungeon Entrance` / `Floor_02_Gungeon_Entrance` / `Elevator Entrance` | `ENTRANCE` | 起点 | **恰好 1** |
| `Exit_Room_Basic` / `Exit_Room_Forge` | `EXIT` | 下一层入口 | **恰好 1** |
| `Boss Foyers` / `Boss Foyer (final)` | `SPECIAL` | Boss 前的整备间 | **恰好 1** |
| `BOSS` | `BOSS` | Boss 房 | **恰好 1** |
| `REWARD` | `CONNECTOR`* | 奖励房（宝箱房） | **2**（矿坑有两张是 3） |
| `Shop Room Table` | — | 商店 | **1**（第五层为 0，见下） |
| `HUB` | `HUB` | 枢纽房，多出口 | 1.4 ~ 1.8 |
| `CONNECTOR` | `CONNECTOR` | 无敌人连接房，常带环境危险 | 0.6 ~ 2.4 |
| `NORMAL` | `NORMAL` | 普通战斗房 | **7.5 → 11.0** |
| `Blacksmith_TestRoom` | — | 铁匠房（第五层独有） | 2（第五层） |
| `EndTimes_Chamber` | — | 第五层终局房 | 2（第五层） |

\* 奖励房在 flow 里被归为 CONNECTOR 类，因为它的房间模板是从"奖励房表"另外取的（`overrideTable`）。

### 三条可以直接拿去用的硬规律

**规律一：固定开销先扣掉，剩下的才是战斗房。**

```
总房间数 N = 固定开销 + NORMAL + HUB + CONNECTOR
固定开销 = 入口1 + 出口1 + Boss前厅1 + Boss房1 + 商店1 + 奖励房2 = 7
（第五层再加铁匠房与终局房 = 9）
```

验算：第一层 `7 + 7.5 + 1.7 + 0.8 = 17.0` ✓ ／ 第五层 `9 + 11.0 + 1.8 + 0.8 = 21.6` ✓

**规律二：难度增长全部压在 NORMAL 上。**

第一层到第五层，房间总数只从 17.0 涨到 21.6（+4.6 间），
但 NORMAL 从 7.5 涨到 11.0（**+3.5，占全部增量的 76%**）。
HUB / CONNECTOR / 奖励房几乎不动。

> 也就是说：**它没有靠"加房型"做后期层，靠的是"同样的房型多塞几间"。**
> 这是很克制的做法——玩家学一套房型语言，从第一层用到第五层。

**规律三：入口的类型泄漏了层结构。**

- 第一层：`Gungeon Entrance`
- 第二层：`Floor_02_Gungeon_Entrance`
- 第三～五层：`Elevator Entrance`

**第一层没有电梯入口，第二层还叫"Gungeon 入口"，第三层起才接电梯。**
这正好解释了官方 Wiki 那条"第一层是唯一没有电梯房"——不是漏配，是**入口节点类型就不同**。

### 一处存疑（别当结论用）

第五层的 5 张 flow 里**完全没有 `Shop Room Table` 节点**，而其它四层每张都有 1 个。
可能：① 熔炉商店是注入进去的；② forge 的商店挂在别的表里；③ 图导出时该节点被折叠。
**本次没有证据判定，标为待核。**

## 四、注入（injection）：整套系统真正的设计接口

**几乎每一个特殊房间都是"注入"进来的**，不是 flow 里画死的。

mod 文档暴露了注入在代码里是**两层**：

```csharp
m_CachedFlow.flowInjectionData   = new List<ProceduralFlowModifierData>(0);  // 本 flow 专属
m_CachedFlow.sharedInjectionData = new List<SharedInjectionData>() { ... };   // 全层共享
```

| 层 | 类型 | 谁持有 | 用途推测 |
|---|---|---|---|
| 单 flow | `ProceduralFlowModifierData` | 每张 flow 自己 | 只在这张骨架里生效的注入（该骨架特有的岔路、房间） |
| 全层共享 | `SharedInjectionData` | 层（Dungeon）持有，所有 flow 共用 | 隐藏房、商人、牢房、壁炉、电梯这类"每层都该有"的东西 |

**这个分层很关键**：如果所有注入都挂在 flow 上，加一层就要重复配 N 遍；
做成共享层之后，**"每层必须有 1 个商店"这种规则只写一次**。

### 注入规则的四要素

```
{ 注什么类型, 注在哪, 概率, 前置条件 }
```

Boris 列举的前置条件：**是否已拿到 Master Round、诅咒是否偏高、某个 NPC 是否已被救出。**

### 已知的注入对象

| 对象 | 落点 | 概率 / 条件 |
|---|---|---|
| **普通隐藏房** | 通常**死胡同**；有 **1/5** 概率挂到任意房间 | **每层 90%**，无前置条件 |
| **NPC 隐藏房** | 独立于普通隐藏房 | 见下"跨层预留" |
| 商人（主商店除外） | 注入指定 | 按条件 |
| 监狱牢房 | 注入指定 | 按条件 |
| **壁炉房** | 注入指定（死胡同） | 按条件 |
| **电梯房** | 注入指定 | 按条件 |
| 秘密帮手房 | `SecretHelpers_RoomTable`（第二层 flow 01 里可见） | 按条件 |

### 隐藏房的两套抽取：一个很值得抄的手法

wiki.gg 的 `Secret_Rooms` 页把这两套写清楚了：

**普通隐藏房：每层独立抽**
- 每层 90% 出现
- 房间从权重表里抽，权重高的更容易中：
  `Secret_Room_Random_001`、`basic_secret_room_001~003` 权重都是 **15**（含随机宝箱 / 1-2 个拾取物）
  `basic_secret_room_004~010` 权重是 **1**
  `basic_secret_room_011` 是 **0.5**
  `high_dragunfire_room_001` 是 **0.2**（只在第二层，且需已杀过 High Dragun）
- 选择公式：`P(某房) = 该房权重 ÷ 所有可选中房的权重和`

**NPC 隐藏房：开局抽一次，预留给未来某一层**
- **每局开始时**从 NPC 房表抽**一个**，分配给将来的某一层
- `EMPTY` 权重 **0.8**，抽中它就是这局没有 NPC 隐藏房
- 具体 NPC 房权重都很低（0.01 ~ 0.05）
- NPC 房**与普通隐藏房互不占用**，可以同层共存

> **设计手法：跨层预算（run-level pre-roll）。**
> 不是"每层独立决定要不要给 NPC 房"，而是"开局就决定这一局会不会有、留给第几层"。
> 好处：**不会出现五层连着都没刷到的极端局**，也不会一层里堆两个。
> 这是把"随机"从层内提到 run 级的典型做法，做 roguelike 很值得直接抄。

### 这条机制解释了本地资料里三个"怪现象"

| 已有结论 | 生成机制的解释 |
|---|---|
| 第一层是**唯一没有电梯房**的层 | flow 入口节点类型就是 `Gungeon Entrance`（不是 `Elevator Entrance`）；电梯房的注入条件在这层不成立 |
| 壁炉房**通常在死胡同** | 和隐藏房同一类落点偏好——死胡同是"注入挂点"的默认位置 |
| 同一 Boss 有多套房间皮肤 | flow 的 Boss 节点固定，但**房间模板是从池里挑的** |

## 五、地图之外的玩法约束（为什么它"看起来像设计过的"）

Boris 开篇给的观察，其实是被写进骨架里的：

| 现象 | 怎么做到的 |
|---|---|
| Boss 房总在合理距离外 | Boss 节点在 flow 图上的**深度**就是固定的，只是横向位置随机 |
| 战斗房总被"喘气房"隔开 | HUB 与 CONNECTOR 在骨架里是固定夹层 |
| **宝箱房藏在单向环的末端** | flow 图里的箭头 = **单向边**。REWARD 节点被放在环的收尾位置，且出口指向来路——你只能绕一圈过去 |
| 大量宝箱要"多走路" | 每层固定 2 个 REWARD，位置由 flow 决定，不由随机决定 |

**单向环（one-way loop）是这套设计里最便宜的一招**：只要在 flow 图里把闭环画成有向的，
玩家就必然要绕路，而这个"绕"**不需要任何额外房间**，成本为零。

## 六、最小可复刻形态

要落地，只要五张表 + 一根管线：

```
tables/
  flows.json        # 每层 4~8 张：节点列表 + 有向边 + 环闭合边 + 节点房型
  rooms.json        # 每间房：房型、尺寸(W×H)、出口位置、可行朝向
  injections.json   # {type, anchor, weight, condition, scope:"flow"|"shared"}
  room_pools.json   # 按 (层, 房型) 分桶的模板池
  place_rules.json  # 回溯上限3、走廊长度4~30、朝向权重、最长重试
```

管线（伪代码）：

```python
flow = pick(flows[chamber])                      # 1 选骨架
for node in flow.nodes:                          # 2 变换
    for inj in shared_injections + flow.injections:
        if inj.match(node, state) and rand() < inj.p:
            flow.insert(inj.type, node, inj.anchor)
for node in flow.nodes:
    node.room = pick_by_weight(room_pools[chamber][node.type])
composites = cut_min_loops(flow)                 # 3 拆
for c in composites:                             # 4 分别拼装
    layout_dfs(c) if c.is_tree else layout_loop_both_ends(c)
assemble(composites)                             # 5 总装
```

**最小验证顺序**：先只做"树 + 直走廊"，能拼出一张能走通的图；
再加环切分；最后做注入。注入放最后，因为它是唯一依赖前四步全部正确的环节。

**如果只想抄一条**：抄 `N = 固定开销 + 战斗房` 这个预算式，和"跨层预算"。
前者让你的第 1 层和第 5 层自动拉开差距，后者让稀有内容不会整局缺席。

### 顺带一个数值参照（来自 `GameLevelDefinition` 的默认字段）

mod 文档里新建楼层时填的 `GameLevelDefinition`，这几个字段说明**难度是层级的全局乘数**：

| 字段 | 例值 | 含义 |
|---|---:|---|
| `enemyHealthMultiplier` | 2 | 敌人血量倍率 |
| `priceMultiplier` | 1.5 | 商店价格倍率 |
| `secretDoorHealthMultiplier` | 1 | 隐藏房墙血量倍率（要打几枪才裂） |
| `damageCap` | **300** | 普通敌人单发伤害上限 |
| `bossDpsCap` | 78 | Boss 的 DPS 上限 |

`damageCap = 300` 与 Wiki 的"单发伤害上限 300"完全一致，互相印证。
`bossDpsCap` 是**另一个独立上限**——之前 `09_刷怪设计.md` 只记了 300，漏了这个维度：
**普通怪看单发上限，Boss 看 DPS 上限**，两套规则并行。
