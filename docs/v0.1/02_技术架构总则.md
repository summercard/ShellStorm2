## 1. 目标

七大核心系统必须能够独立开发、测试、替换表现和迁移数据。正式玩法只保留一条事实链；旧 2D、演示场景和兼容代码可以用于参考与验证，但不能与正式 3D 同时拥有同一规则。

## 2. 三色状态

- <span style="color:#2E7D32">**[已实装]** 正式 3D 已使用的结构。</span>
- <span style="color:#1565C0">**[用户设计]** 尚未呈现、但已冻结的设计目标。</span>
- <span style="color:#EF6C00">**[Codex补充]** 为解耦、可测试和可迁移提出的施工约束。</span>

## 3. 正式运行边界

| 类别 | 正式事实源 | 兼容或原型 | 规则 |
|---|---|---|---|
| 主入口 | `TowerDescent3D.tscn` | 旧 2D 主场景 | 新功能必须先接正式入口 |
| 玩家 | `Player3D` + 独立状态类 | 旧 `Player` | 视觉根不拥有玩法碰撞 |
| 武器 | `BlueprintRegistry` + `WeaponAssemblyTree` + `WeaponModel3D` | `WeaponPresets` 等平行配置 | 内容 ID 和数值只保留一个正式来源 |
| 投射物 | `Projectile3D` 与对象池 | 旧 2D 子弹 | 命中上下文统一 |
| 关卡 | 目标为 `FloorPlanGenerator` + `FloorPlan` + `Dungeon3D/TowerDescent3D` 场景适配 | 当前固定楼层表、`RoomGameMode` / 旧房间生成 | 安全屋触发生成，布局一次冻结，流送不改坐标 |
| 怪物 | `Enemy3D` + `EnemyAvatar3D` | 旧怪物 Actor | 正式数值以 3D Profile 为基线 |
| 基地 | `BaseWorld3D` + `BaseManager` | `BaseWorld` | 存档只经服务层 |
| 精英 | 目标为正式 3D 全局名册服务 | `EliteArchiveModule` 原型 | 原型迁移后才能标为完成 |

## 4. 五层结构

```text
内容数据层
  稳定ID、数值、权重、文案、资产引用
        ↓
领域规则层
  玩家状态、伤害、生成、精英唯一性、设施、剧情、结算
        ↓
运行编排层
  单局会话、整层布局事务、房间流送、事件总线、存档事务
        ↓
场景适配层
  Godot Node、碰撞、导航、相机、灯光、输入、UI桥
        ↓
表现资产层
  Mesh、材质、动画、VFX、SFX、HUD
```

- <span style="color:#2E7D32">**[已实装]** 玩家、怪物和武器大体具有玩法根/视觉根分离。</span>
- <span style="color:#1565C0">**[用户设计]** 所有功能系统都要独立管理，避免功能代码混写。</span>
- <span style="color:#EF6C00">**[Codex补充]** 新代码按上面五层归属；禁止 UI 改数值、场景节点写存档、内容表保存节点路径作为运行状态。</span>

## 5. 模块契约

每个系统必须声明以下六项，缺一项即不进入“正式完成”：

1. 所有者：哪个服务拥有最终事实。
2. 输入命令：外部可以请求什么。
3. 输出事件：外部可以观察什么。
4. 数据定义：稳定 ID、配置和存档字段。
5. 失败语义：失败是否回滚、如何向 UI 说明。
6. 验收证据：自动化测试、场景复现或数据检查。

## 6. 事件边界

建议领域事件使用过去式并携带稳定 ID，例如：

| 事件 | 生产者 | 消费者示例 |
|---|---|---|
| `player_state_changed` | 玩家系统 | HUD、动画、剧情 |
| `weapon_assembly_changed` | 战斗系统 | 武器表现、属性 HUD |
| `weapon_instance_changed` | 战斗/物品事务 | 武器表现页、背包、HUD、存档 |
| `weapon_effect_triggered` | 战斗系统 | HUD 短提示、武器/弹道/VFX/音频表现 |
| `floor_layout_committed` | 关卡系统 | 流送、小地图、验证器 |
| `room_revealed` | 关卡系统 | 刷怪、剧情、地图 |
| `encounter_spawned` | 怪物系统 | 房间清理、UI、精英档案 |
| `boss_defeated` | 怪物系统 | Boss 钥匙、剧情、存档 |
| `elite_escaped` | 精英系统 | 成长、档案、剧情 |
| `facility_command_completed` | 基地设施 | UI、存档 |
| `run_settled` | 结算系统 | 基地、统计、剧情 |

事件只描述已经发生的事实，不承担跨系统同步调用。需要原子结果的行为使用命令和返回值，例如 Boss 钥匙开门事务。

## 7. ID 与版本

- 内容 ID：跨版本稳定，用于数据库和存档。
- 枪械实例 ID：跨场景、跨背包和跨存档稳定，绑定一把可交易的具体枪械及其完整构筑。
- 战斗实例 ID：单局唯一，用于节点、攻击、投射物、敌人和房间实例。
- 布局 ID：由 `run_seed + floor_id + floor_rule_version` 派生。
- 事务 ID：用于生成、掉落、结算和存档重试去重。
- Schema 版本：每个存档域独立版本，但统一写入存档清单。

<span style="color:#EF6C00">**[Codex补充]** 任何存档字段改名必须提供从上一正式版本迁移的方法；不允许通过“取不到就默认空”静默丢失唯一精英、带出物或剧情状态。</span>

<span style="color:#1565C0">**[用户设计]** 装备位、背包、地面物、商店、保险和存档移动的是同一个 `WeaponInstance` 所有权记录；任何场景适配器都不得通过枪型 ID 重建枪械后搬运旧构筑。</span>

<span style="color:#2E7D32">**[已实装并验收]** `WeaponInstance` 已成为枪械持久化边界，装备、背包、地面、商店、保险、带入、撤离和 `BaseData 1.2` 共用同一份序列化结构；各集合按 `weapon_instance_id` 拒绝重复实例。</span>

## 8. 依赖方向

允许：

```text
场景适配 → 领域接口 → 数据定义
UI → 只读查询 / 用户命令
剧情 → 订阅领域事件 / 请求剧情动作适配器
存档 → 读取各领域快照 / 恢复领域状态
```

武器表现页只能读取统一的 `WeaponPresentationSnapshot`，其中包含实例身份、所有权位置、基础/最终属性、来源拆分、命运轨道、装配槽和触发链。背包、工坊、商店、地面比较和命运选卡复用该快照与组件，禁止各自重新计算一套武器结果。

禁止：

- 怪物脚本读取基地菜单节点。
- 房间脚本直接创建某个具体精英并写精英档案。
- 玩家脚本硬编码掉落价格。
- UI 直接增加资源、解锁门或标记 Boss 已死。
- 动画回调成为唯一伤害事实源且没有超时收口。
- 兼容 2D 和正式 3D 同时写同一个长期存档字段。

## 9. 失败与回滚

| 事务 | 成功条件 | 失败收口 |
|---|---|---|
| 整层生成 | 房间、门、走廊、楼梯可达且不重叠 | 丢弃整层计划，用同种子确定性重试或安全模板 |
| 敌群创建 | 敌对房至少有有效计划或合法空房原因 | 记录诊断并允许房间清理，不能永久锁门 |
| 精英生成 | 全局预约成功、实例创建、档案绑定 | 释放预约，不复制同名精英 |
| Boss 门开启 | Boss 已死、专钥匙存在、目标楼梯有效 | 不消耗钥匙，不只开视觉不改碰撞 |
| 掉落结算 | 生成来源、权重和物品 ID 有效 | 跳过无效条目并报告，不生成空气碰撞 |
| 存档 | 临时写入、校验、备份、提升均成功 | 保留旧主档和错误日志 |

## 10. 兼容代码治理

<span style="color:#1565C0">**[用户设计｜未实装]** `FloorPlanGenerator` 必须是不依赖 Godot 场景树的领域模块：输入楼层边界、结构占位、资产外框、种子与楼层规则，输出纯数据 `FloorPlan`。面积计算、不少于 10 房的主路、支路、每 5 层 Boss、楼梯禁建区和钥匙流验证都在该模块中完成。</span>

<span style="color:#EF6C00">**[Codex补充]** `TowerDescent3D` 不再自行编排房间坐标；它只负责 `floor_seed_gate` 交互、请求/提交编排、实例化组件、流送与领域事件转发。小地图、刷怪和存档通过 `layout_id/room_id/edge_id` 只读引用同一计划。</span>

- <span style="color:#2E7D32">**[已实装]** 工程中仍有 2D 与 3D 两套场景适配代码。</span>
- <span style="color:#EF6C00">**[Codex补充]** 兼容目录中的功能只允许修复阻断性缺陷，不再添加新玩法；迁移完成后先断开正式入口引用，再执行删除。</span>
- <span style="color:#EF6C00">**[Codex补充]** `WeaponPresets`、旧怪物图鉴数值、`RoomEventHandler`、精英原型等平行来源必须逐项确定“迁移、适配或废弃”，不能长期保持双权威。</span>

## 11. 通用验收标准

- 每个系统有唯一事实所有者。
- 每个跨系统操作都能找到命令、返回结果或领域事件。
- 正式 3D 主入口能独立运行，不依赖旧 2D 场景节点。
- 内容 ID、实例 ID 和存档 ID 不混用。
- 生成、精英、Boss 门和存档具备失败回滚。
- UI 和表现可以替换而不改变规则结果。
- 数据库、代码和文档对同一数值只有一个正式口径。
- 每项已完成功能至少有一个自动验证或明确复现场景。
