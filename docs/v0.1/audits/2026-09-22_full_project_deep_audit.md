## 1. 结论总览

| 问题 | 结论 | 等级 | 关键证据 |
|---|---|---:|---|
| 工程架构是否按功能解耦 | **部分成立**。已有 19 个工程模块和五层目标架构，但塔楼、远征房间、玩家、基地等主类仍是大型编排器，场景/UI/服务存在私有字段和共享数据直连 | 黄/红 | `TowerDescent3D.gd` 6076 行、`Dungeon3D.gd` 5622 行；多个模块直接访问 `BaseManager.data` 或对象私有字段 |
| 数据串联是否通畅 | **正常主链可运行，但没有完全闭环**。内容 ID、运行实例、存档与 UI 已能串联；奖励切流、结算原子性、工坊事务、剧情文档同步仍有断点 | 黄 | `REWARD-SERVICE` 已实现但尚未切流；运行存档/总档仍由场景编排多步提交 |
| 资产模块与制作链路 | **框架完整、当前健康度不合格**。7 个分账本、426 条资产、多个专项 Skill 和验证器已存在；但账本有 231 项问题，负责人全部待分配 | 红 | 199 个 SHA 漂移、24 个路径不存在、5 个非法状态、1 个缺 SHA、主索引 Skill 漂移 |
| 文档中心开发 | **大体建立，执行不一致**。37 个功能均进入模块索引，但只有 15 个功能 ID 能在开发记录中精确追溯；模块索引已有实现事实过期 | 黄 | 剧情已存在实现和测试，索引仍写“系统本体不存在”；runner 已隔离用户目录，索引仍写“无隔离” |
| 验收机制 | **数量充足、当前基线不绿、注册不完整** | 红 | 208 个验证场景；smoke 6 项中失败 3 项；47 个 `verify_*.tscn` 未注册到 runner |
| 命名与目录体系 | **有中心规范，但历史债务大** | 黄/红 | 运行资产命名新增门禁通过；仍有 289 文件、13 目录、1 备份的版本号债务；`_scratch/` 被 Godot 扫描 |
| 可精简内容 | **至少 790 个 Git 跟踪文件可进入第一批确认清理；本地另有约 4.6 GB 可重建/迁出的生成数据** | 黄 | 7 份用户快照共 776 文件、约 691 MiB；根目录 14 个日志/探针文件；`.godot/` 2.7 GB、`outputs/` 1.9 GB |

总体判断：项目已经形成较成熟的“设计—实现—资产—验收”骨架，但尚不能称为每个功能都可独立维护。当前最需要的不是继续增加平行框架，而是收口四类债务：**主场景编排器瘦身、跨域数据访问、文档状态同步、账本与验证基线恢复**。

## 2. 本次采用的工程原则

依据 [项目文档入口](../README.md)、[文档规范](../../DOCUMENTATION_STANDARD.md)、[模块索引](../MODULE_INDEX.md) 和各主设计，审计按以下原则判断：

| 原则 | 合格判据 | 当前情况 |
|---|---|---|
| 唯一状态所有者 | 每项状态只有一个权威写入者，其他模块通过命令/查询/事件访问 | 部分成立；基地与存档集中度较高，但 UI、场景和服务仍直接读写共享数据 |
| 清晰边界 | 功能具备输入、输出、ID/schema、失败语义与回滚 | 纯数据算法、换装事务、HUD 映射较好；塔楼生命周期、工坊、结算不足 |
| 分层 | 内容数据 → 领域规则 → 运行编排 → 场景适配 → 表现资产 | 目标明确；大型场景脚本仍同时跨越多层 |
| 正式接入 | 新服务不只存在，还替换旧运行链 | 奖励服务、部分 VFX 和后处理存在“已建但未完全切流” |
| 独立验收 | 有可单独启动的验证入口，正常与故障路径均可判定 | 验证数量多，但注册、预期故障声明和当前通过状态不完整 |
| 设计先行 | 功能主设计与契约先于改变规则的实现 | 多数模块具备；剧情/runner 当前事实未及时回写索引，部分 UI/后处理缺独立契约 |
| 证据可追溯 | 功能 ID → 主设计 → 代码/数据 → 开发记录 → 验收 | 模块索引已搭框架；37 项中仅 15 项有精确功能 ID 开发记录命中 |

## 3. 系统、玩法与游戏流程模块

### 3.1 模块清单与独立维护能力

本项目当前可识别 **19 个工程模块**。下表的“独立”表示可通过稳定输入输出和替身维护，并不要求脱离 Godot。

| 类别 | 模块 | 权威链路/主要入口 | 独立性 | 数据串联 | 主要阻塞 |
|---|---|---|---:|---:|---|
| 角色 | PLAYER | `Player3D` → 状态类 → `PlayerAvatar3D`；交互控制器 → 门/设施 | 部分 | 通 | `Player3D` 1983 行并持有装备、背包接口、动作和全局依赖；动作库读取大量私有字段 |
| 战斗 | WEAPON | 内容注册 → `WeaponInstance` → 装配树 → 武器模型/弹体 | 部分 | 通 | 命中上下文、实例所有权与生命周期未形成统一账本 |
| 战斗 | INVENTORY | 背包/保险格位 → `EquipmentTransactionService` → 玩家装备槽 | 部分；换装事务较独立 | 通 | 场景仍负责卸装、快捷栏、掉落和部分回滚 |
| 战斗 | FATE | 牌组内容 → `FateCardEngine` → 玩家/武器/世界持有者 | 部分 | 通 | 世界执行器依赖 Dungeon；48 张运行卡与 78 张目标牌组需持续区分 |
| 世界流程 | WORLD | `FloorPlanGenerator` → `RoomGraphRuntime` → Dungeon/Tower 装配；基地入口 → 读取页 → 远征场景 | 计划/查询独立，生命周期不足 | 基本通 | `TowerDescent3D`、`Dungeon3D`、`DungeonRoom3D` 合计约 1.49 万行；开门、卸载、快照仍由场景编排 |
| 敌人 | ENEMY | `Enemy3D` + `MonsterAIManager` + 视觉/光照查询 | 部分 | 通 | 物种行为集中于 1744 行 `Enemy3D`；管理器读取场景私有状态 |
| 敌人 | ELITE | 精英目录 → `EliteRosterService` → `BaseData.elite_archive_records` | 部分 | 通 | 服务直接写 `BaseManager.data` 并调用私有初始化；12 名册仅 1 个正式投放 |
| 敌人 | BOSS | Boss 内容 → `Enemy3D` 阶段 → 塔楼下行权限 | 部分 | 有偏差 | 设计中的钥匙实体与当前计数式授权未完全一致 |
| 基地 | BASE | 设施目录/服务 → `BaseManager` → `BaseData` → UI/场景适配 | 规则局部独立，事务不足 | 通 | `BaseManager` 1379 行，同时承担存储、交易、能源、外观与运行档；工坊仍多步保存 |
| 存档流程 | SAVE | 运行快照 → `ProfileSaveService` → `AtomicJsonStore` → `BaseManager` | 序列化独立，业务提交不足 | 基本通 | 结算、故障恢复、多写者互斥、领域通知未统一为事务 |
| 叙事 | NARRATIVE | 触发声明 → 时间轴 JSON → `NarrativeDirector` → 八域适配器 → 对话 UI | 部分 | 已有运行链 | **文档状态过期**：索引称未实现，但当前已有 `src/narrative/`、Autoload 与验证；需补正式接入审计 |
| 世界规则 | TIME | `WorldTimeDomain` → `GameTimeManager` → BaseData → 太阳/HUD/能源 | 算法独立，接入部分 | 通 | 配置仍偏代码常量，联动和持久化验收归属不够清晰 |
| 世界规则 | POWER | 基地能源服务/BaseManager；玩家手电/物品处理器 | 两条链可独立验 | 通 | 基地灯光和设施负载尚未进入统一电网事件链 |
| 入口流程 | ENTRY | `GameEntryFlow` → 主页/塔楼 → 玩法；外观持久化 → BaseData | 部分 | 通 | 塔楼仍装配主页和设施 UI；作者包、运行包装、用户装配版本边界需强化 |
| 表现 | PRESENTATION | HUD Presenter、UI 组件、VFX 池、音频和音乐管理器 | HUD/音乐较独立，VFX 部分 | 基本通 | UI 仍参与业务事务；新旧 VFX 池并行；`InventoryUI.gd` 1611 行 |
| 性能 | PERFORMANCE | 画质设置、后处理、运行时性能管理器 → 场景/渲染 | 部分 | 通 | 调参越过设置服务；节点预算当前失败；真实 GPU/长测未执行 |
| 工具玩法 | TRAINING | 独立训练场 → 只读武器注册 → 共用玩家 → 会话统计 | **独立** | 通 | 当前核心验证显示 59 组合矩阵失败，需恢复基线 |
| 资产 | ASSET | 分账本 → Blender/源文件 → GLB → PackedScene → 正式场景 | 标准完整，运行闭环不足 | 有漂移 | 账本 231 项异常、负责人缺失、旧总账访问未退役 |
| 工具链 | TOOLING | verification 场景/runner/检查脚本 → 日志与退出码 | 部分 | 不完整 | runner 已隔离用户目录，但复用 `.godot` 缓存；47 个验证场景未注册；文档说明过期 |

结论：**TRAINING 是唯一在索引中明确达到完整独立启动与验收的功能模块**。WORLD 的纯计划/查询、装备交换、时间计算、HUD 映射等“内核”可独立维护；其余多数模块已有边界但仍依赖全局 Autoload、大型场景脚本或共享 BaseData。

### 3.2 关键数据流是否闭合

| 数据流 | 当前链路 | 状态 | 审计意见 |
|---|---|---:|---|
| 启动到玩法 | `GameEntryFlow` → 主页面/塔楼 → 基地设施或战局 | 通 | 24 个 Autoload 提供集中入口，但全局依赖数量偏高 |
| 远征入口 | `BaseFacilityCatalog` → `RogueMapSelectMenu` → `ExpeditionLoadingScreen` → 远征场景 | 通 | 有专项验证；入口生命周期仍不是独立服务 |
| 战斗与拾取 | 内容注册 → 敌人/武器 → 旧 `LootModule/ItemRegistry` → 背包/地面物 | 通但双轨 | 新 `RewardService` 已实现和测试，运行消费点尚未切换，存在双轨语义风险 |
| 装备交换 | Inventory/Insurance → `EquipmentTransactionService` → 玩家实例槽 | 较好 | 已有可替身验证边界；场景侧仍保留部分流程 |
| 行动存档 | Dungeon/Tower 快照 → `RunPersistenceService` → 总档封套 | 基本通 | 开门/卸载可能先于落盘成功；自动存档与重启恢复验证没有进入核心套件 |
| 结算回基地 | 撤离/死亡 → Settlement → `BaseManager` → UI/场景切换 | 正常路径通 | 多次写入尚未形成单一原子事务，故障后恢复语义不足 |
| 基地交易 | UI/设施适配 → Base 服务/Manager → BaseData → 存档 | 部分通 | 普通商店已有冲突/失败回滚；工坊扣款与解锁仍非一次事务 |
| 剧情 | 触发源 → 时间轴 → `NarrativeDirector` → 系统适配器/DialogueUI | 已实现，文档未同步 | 需先做当前实现契约复核，再把索引从“未实现”改为真实状态 |

## 4. 资产体系审计

### 4.1 资产域、账本、Skill 与流程

资产总账已拆为 7 个分账本，共 **426 条资产记录**。结构设计是清晰的，但所有域负责人目前仍为“待分配”。

| 资产域 | 条目 | 独立账本 | 主要 Skill/链路 | 制作链成熟度 | 当前账本问题 |
|---|---:|---:|---|---:|---|
| characters | 31 | 是 | 角色契约 → Blender 双母版 → 导出中转 → Godot 包装 → 状态绑定 → 专项验收 → 账本 | 高 | 18 个 SHA 漂移；域负责人未分配 |
| enemies | 12 | 是 | 通用角色链 + 普通怪专项链 | 中高 | 4 个 SHA 漂移；内容投放与角色链责任边界需登记 |
| scenes | 236 | 是 | `scene-full-pipeline`；房间种类 → 组件拆解 → 房间布局 → 运行装配；Blender/Godot 专项标准 | 高 | 138 SHA、17 路径、5 非法状态、1 缺 SHA、1 非规范文件名 |
| props | 20 | 是 | 道具契约/Blender → GLB/PackedScene → 代码接入 | 中高 | 8 SHA、7 路径不存在；通用道具链与 05–08 项目链映射需统一 |
| weapons | 36 | 是 | 武器模型链；项目 05–08 资产到代码接入链 | 高 | 19 个 SHA 漂移 |
| vfx | 17 | 是 | `vfx-combat-effect-authoring` → Prefab/池 → 战斗接入 → 生命周期验证 | 中高 | 6 个 SHA 漂移；JSON 索引已换新 Skill，总账 Skill 单元格仍旧 |
| media | 74 | 是 | 当前统一指向模型导入标准 | 低/不匹配 | 6 个 SHA 漂移；UI/音频混在一个域，缺少匹配媒介的独立生产 Skill |

统一链路应为：

`AssetID/设计契约 → 原始源文件 → 可转移中间产物 → Godot 稳定路径 PackedScene/资源 → 运行引用 → 分账本状态与 SHA → 独立验证`

当前有 21 个脚本仍读写旧单体账本，另有 49 个账本文件引用悬空；因此“分账本已经建立”尚不等于“旧链已经退役”。

### 4.2 资产门禁实测

| 命令 | 退出码 | 结果 |
|---|---:|---|
| `python3 scripts/check_asset_registry.py` | 1 | 426 条资产，231 项问题：199 SHA 漂移、24 路径不存在、5 非法状态、1 缺 SHA、1 非规范文件名、1 主索引 Skill 不一致 |
| `python3 scripts/verify_ledger_split.py` | 1 | baseline 424 / 当前 426；缺 2、增 4、20 项拆账基线失败，说明拆账基线没有随受控变更升级 |
| `python3 scripts/check_asset_runtime_naming.py` | 0 | 没有新增债务，但历史 debt 仍为 289 文件、13 目录、1 备份；版本化引用仍有 GDScript 23、TSCN 93 |
| `python3 scripts/check_ledger_refs.py --allow-pending` | 0 | “允许待迁移”模式通过；仍报告 21 个旧总账访问脚本、49 个悬空引用、176 个历史 JSON + 14 个文本记录 |

结论：资产端已经有良好的**制度和工具框架**，但目前不是健康绿线。优先级应是逐域确认漂移来源，而不是批量接受当前文件哈希。

### 5.2 明确的文档漂移

1. [模块索引](../MODULE_INDEX.md) 仍以 `31ed360` 为审计基线，当前 HEAD 已是 `380a15a`。
2. NARRATIVE 行写“实现未建立、全仓 narrative 零命中”，当前已有 `src/narrative/` 8 个脚本、`NarrativeDirector` Autoload 和时间轴验证。
3. TOOLING 行写“无统一运行前存档隔离”，当前 runner 已复制临时 `project.godot` 并使用自定义用户目录；真实问题变成它仍复用工作区 `.godot` 缓存。
4. `RUN-REVIVE` 仍只有目标，无策略实现与验收。
5. `GRAPHICS-POSTFX` 缺独立设计；`verify_postfx_overlay_runtime` 仅有脚本而无 `.tscn` 入口。
6. `BASE-WORKSHOP` 只有相邻覆盖；`RUN-MERCHANT` 只被综合流程覆盖，故障边界不独立。

结论：文档中心架构已经成立，但“每个功能都以独立设计和开发记录为核心”尚未成立。当前最有效的治理动作是把 37 个功能行升级为机器可核对的五联表：`FeatureID / 主设计 / Owner / 开发记录 / 注册验收入口`。

## 6. 验收机制与当前实测

### 6.1 验收资产

| 层级 | 当前能力 | 缺口 |
|---|---|---|
| 静态文档 | 链接、索引、功能与测试引用检查 | 当前有 2 个失效资产入口链接（本审计同步修复） |
| 代码静态 | `class_name` 唯一性、资源路径、资产命名 | 多数有效；旧场景/工具仍有 37 个资源引用命中，分布于 14 个文件，需人工排除注释/故障测试后清理 |
| 功能验证 | 208 个 `verify_*.tscn`、216 个验证脚本 | 47 个验证场景未注册进统一 runner；“文件存在”不等于发布门禁覆盖 |
| Smoke | 6 项 | 刷新导入缓存后仍 3 失败 |
| Core | runner 注册约 78 项 | 本次结果见下表；当前不是绿线 |
| Visual | 20 项、真实渲染要求 | 本次未执行 |
| 长测/硬件 | 30/60 分钟、目标 GPU/移动端 | 本次未执行 |

## 10. 对六个问题的直接回答

1. **系统与玩法模块**：当前共 19 个工程模块、37 个功能条目。系统之间已有主数据链，但只有训练场和若干纯逻辑内核达到明确独立；大型场景、共享 BaseData 和全局 Autoload 使多数模块仍为“部分独立”。
2. **资产模块**：共 7 个资产域、7 个分账本、426 条资产。场景、角色、武器链最完整；media 域的 Skill 不匹配。框架清楚，但 231 项账本异常和无人负责使当前链路不能判绿。
3. **设计与开发记录**：37 个功能都有索引入口或明确待建状态，但仅 15 个能通过精确功能 ID 找到开发记录；剧情、工具链状态已经与实际工程不一致，所以尚未做到“所有功能均以独立设计/日志为中心”。
4. **验收机制**：每层都有工具，但统一门禁覆盖不完整且当前实测失败。208 个验证场景中 47 个未注册，smoke 只有 3/6 通过。
5. **命名和目录**：有完整中心文档与资产规范，新增运行资产版本号门禁有效；历史版本号债务、`_scratch/`/`output/` 混入工程、旧场景悬空引用仍需治理。
6. **精简空间**：第一批可高置信度移除 790 个 Git 跟踪文件、约 691 MiB；另有 14,765 个本地生成/用户数据文件、约 4.6 GB 可重建或迁出。其余约 1548 个候选需先复核，不能整目录删除。
