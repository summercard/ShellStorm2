# 星星命运卡：节点、挂点与功能一致性评估

日期：2026-10-16；FeatureID：`FATE-RULES`，关联 `WEAPON-COMBAT / WEAPON-OWNERSHIP`；工程版本：0.1.0。

范围：只检查星星卡，太阳/月亮暂缓。本轮为源码追踪、隔离运行探针和设计评估，未修改玩法代码或模型。用户最新明确要求：**先处理节点与挂点的构筑关系；枪上挂副枪必须在枪身上真实出现对应副枪，功能与这个装配结构关联。** 下文接口/改造方案为建议，不能视作已实现。

## 1. 结论

**当前是“有逻辑装配树，但多数运行效果汇总为属性字典，由单个主枪模型统一执行”。不满足完整的节点式实体构筑。**

星星共36张：8张大阿尔卡那 + 14张权杖已有运行预设，14张宝剑待施工。实测运行池星星数为22。已有执行器不等于外观、挂点、子枪运行状态、顺序和存档身份全部完成；本轮不将任何一张标成“满足新要求且全链验收”。

魔术师的缺口最清楚：数据树能增加一个副枪，但没有把来源枪模型装上去，副枪从主枪枪口发射。战车与炮台也存在“功能有了、对应实体没有建”的同类缺口。

## 2. 按构筑操作重新分种类

这里是设计整理，不是修改现有CardType枚举。每张牌只按主要操作归一组，附属效果可跨组。

| 类别 | 数量 | 卡片 |
|---|---:|---|
| 实体挂载 | 3 | 魔术师、战车、权杖·三 |
| 节点属性与尺度 | 6 | 力量、权杖·王牌、权杖·二、权杖·国王、宝剑·王牌、宝剑·三 |
| 弹体行为与形态 | 9 | 星星、权杖·四/五/六/七/八、宝剑·二/六/王后 |
| 发射方式与分支 | 3 | 恶魔、权杖·九、宝剑·八 |
| 元素载荷 | 3 | 权杖·十、权杖·侍从、权杖·骑士 |
| 事件、计数与资源 | 10 | 命运之轮、死神、高塔、权杖·王后、宝剑·五/七/九/十/侍从/国王 |
| 姿态条件 | 2 | 宝剑·四、宝剑·骑士 |

并非每张卡都必须加一个可见零件：倍率可以是目标节点的修饰器；**凡承诺“挂上、携带、生成炮台、环绕弹”的牌，必须有对应实体。** 所有牌都应能回答：改哪个节点、在哪个挂点、影响哪个发射器/弹体、在什么事件执行。

## 3. 最关键的实现缺口

### E1：逻辑树只有简化节点，来源完整结构被压成属性

- `FateCardEngine._apply_attach_gun_to_gun()` 在主枪MOUNT新增GUN_BODY；这层并非完全没做。
- `_make_attached_gun()` 使用 `source.get_computed_stats()`，新建同名枪节点并复制标签，但没有复制来源的BULLET、配件和挂载子树。实测副枪后代数为0。
- `FateCardGameBridge._resolve_source_targets()` 能验证真实来源归属；但魔术师目标固定为root，另外两张固定为root.BULLET。**来源选择不等于目标节点/挂点选择。**
- 默认选目标：无target_rules则root，有规则则按遍历取匹配节点，很多执行器只用targets[0]。玩家无法稳定指定“这次改副枪B的子弹”。
- 每节点只有一个MOUNT。第二张魔术师在默认路径仍打主枪槽，实测报 `Main gun mount slot already occupied`；不能据此声称已支持递归挂枪构筑。

证据：[FateCardEngine](../../../src/weapons/FateCardEngine.gd) 的 `_auto_select_targets`、`_apply_attach_gun_to_bullet`、`_apply_attach_gun_to_gun`、`_make_attached_gun`；[FateCardGameBridge](../../../src/game/FateCardGameBridge.gd) `_resolve_source_targets`。

### E2：表现没有按装配树递归实例化，副枪没有自己的枪口

- `WeaponModel3D._rebuild_visual()` 只选择根gun_id的模型。
- `_add_imported_attachment_visuals()` 检查root.MOUNT非空后，只在ScopeSocket位置画 `InstalledMount` 方块。没有把来源枪PackedScene实例化成副枪，没有专门的命运挂枪定位契约。
- `_socket_position()` 只取position；装配装饰通常被加到_visual_root，而非挂点下。现有根资产为单位变换时可能碰巧对齐，但没有传递完整挂点旋转/缩放，不能支持任意方向接枪。
- `_secondary_guns` 是属性字典数组；`_fire_secondary_gun()` 最后仍取主 `_muzzle.global_position`。子枪射击方向是瞄准方向加散布，不来自某个子枪的实际世界朝向。
- 子枪fire_rate虽然保存，枪上子枪由主枪每次射击调用；它自己的发射时钟、弹匣、装填、枪口火光/抛壳并未独立建立。可设计为共享供弹或同步触发，但必须显式定规则，不让字段名暗示另一种行为。

证据：[WeaponModel3D](../../../src/combat3d/WeaponModel3D.gd) `configure_from_tree`、`_fire_now`、`_fire_secondary_gun`、`_rebuild_visual`、`_socket_position`、`_add_imported_attachment_visuals`。

### E3：存在顺序效应，但不是完整的结构与处理顺序

**不能说当前顺序完全没作用。** 实测以本枪为来源：力量→魔术师，副枪伤害倍率0.75；魔术师→力量，副枪倍率0.5。原因是副枪保存创建时的来源属性快照，后来强化主枪不会回写副枪。

同时存在三种尚未统一的语义：

1. 结构挂载读取当时的汇总属性，造成快照差异。
2. 多数行为直接写同名字段，例如bounce_count、chain_count、copy_fire；同类重复经常后写覆盖，不会形成逐卡处理节点。
3. 弹体碰撞后的炮台/返航/穿透/爆炸靠固定if分支，不能由刻印顺序表达。“先炮台后返航”与“先返航后炮台”在命中时都先变炮台。

权杖九的动作名是COPY_NODE，但只写copy_fire；实测逻辑后代1→1，没有复制节点或子树。它实现了第二波开火，不应被解释为节点复制已完成。

证据：[AssemblyNode](../../../src/weapons/AssemblyNode.gd) `get_computed_stats/_combine_stats`；[FateCardEngine](../../../src/weapons/FateCardEngine.gd) `_apply_copy_node/_apply_mutate_to_bounce/_apply_mutate_to_chain`；[Projectile3D](../../../src/combat3d/Projectile3D.gd) `_hit_target/_hit_surface`。

### E4：携枪子弹、炮台和寄生配件缺少对应视觉实体

- 携枪弹：运行有attached_gun字典，但只生成弹种VFX与碰撞体；子射击从母弹global_position加方向偏移产生，没有附着枪的枪口。
- 炮台：`_become_turret()` 让弹体速度归零、关碰撞、隐藏拖尾并放大原视觉；没有炮座、转轴、枪身、枪口。移动炮台只是移动该弹体。
- 寄生配件：命中/换弹触发确有消费者，但参数取整树；未在Projectile3D创建配件模型。
- 追踪“长眼睛”、返航“长腿”：执行器写visual_has_eyes/legs，WeaponModel3D传入字典；实际弹体视觉配置只传颜色、缩放、几何context，未读这些造型标记。

证据：[Projectile3D](../../../src/combat3d/Projectile3D.gd) `_apply_fate_on_hit/_build_visual/_apply_visual_configuration/_become_turret/_fire_attached_gun/_spawn_child_projectile`。

### E5：刻印记录保存顺序，缺少可持久化的目标节点与挂点身份

`WeaponInstance.append_fate_upgrade()` 保存slot_index、卡ID、正逆、参数和事务ID；没有该次操作的target_node_id、socket_id或来源子树关联。装配快照确实保存现有父子结构与参数，因此**不能说读档会丢光构筑**；但 `_serialize_node()` 不保存node_id，恢复时重新生成节点ID，无法用稳定ID追踪“第3张牌改的是哪把子枪”。

这会阻碍精确预览、迁移、重放、定位失败与跨显示场景的一致性。建议给装配节点稳定实例ID，把操作目标与来源明确记录，不能靠可变node_name或遍历顺序恢复意图。

证据：[WeaponInstance](../../../src/weapons/WeaponInstance.gd) `append_fate_upgrade/_serialize_node/_deserialize_node`。

### E6：触发状态集中在整枪，多发射器尚未隔离

成长、击杀暴击、配件触发冷却等存在WeaponAssemblyTree；WeaponModel3D有单套开火/换弹计数。这对单枪能工作，对枪上枪、多分支子弹则容易形成“某个子节点击杀，全枪获得收益”。具体跨节点共享可以是设计，但必须明示，不能被属性合并方式决定。

证据：[WeaponAssemblyTree](../../../src/weapons/WeaponAssemblyTree.gd) `record_projectile_kill/consume_shot_damage_bonus/record_growth_result/claim_attachment_trigger`。

### E7：宝剑14张仍是设计内容

本轮在src与data检索14张fate_sword_*稳定ID未找到实现；`FateCardPresets.playable_presets()`与`TarotFateCatalog`没有这些运行预设/双向定义。结合运行池实测22张星星，宝剑14张应标“待施工”，不能评成“已实现但表现较弱”。

## 5. 节点先行的设计建议

### 5.1 把“位置结构”和“事件处理”分别定义，并关联到同一节点身份

物理结构决定谁装在谁身上、从哪里朝哪里射；事件链决定何时开火、命中后先做什么。这两者有关联，但不能把时间先后简单当成空间父子关系。

```text
枪实例A
└─ 枪身A（稳定节点ID）
   ├─ 主枪口 → 发射器A → 弹体模板A
   ├─ 命运挂点01 → 枪身B（来源快照形成的构筑子节点）
   │  ├─ 子枪口 → 发射器B → 弹体模板B
   │  └─ 命运挂点01 → 后续可挂节点
   └─ 可更换配件槽
```

**术语必须区分：** 装备栏“副武器”是另一把可切换的武器实例；“挂载副枪”是当前枪实例内部的构筑节点。沿用当前明确的来源只读复制规则，不因可见副枪而擅自消耗玩家原来的副武器。是否复制整套来源子树、允许哪些嵌套仍需冻结，至少不能把保留结构的承诺实现成仅拷贝伤害数字。

同一装配数据负责驱动：手持模型、背包/工作台预览、掉落枪模型，以及实际发射器。表现是结构的投影；伤害不能从Mesh推算，但发射位置必须读取该发射器绑定的真实枪口变换。

### 5.2 每次刻印至少明确这些信息

| 信息 | 用途 |
|---|---|
| 目标枪实例、目标节点稳定ID | 区分主枪、挂枪和不同弹体分支 |
| 操作类型、应用顺序、牌实例与正逆快照 | 区分加子节点、改参数、加事件处理器 |
| 父节点ID、逻辑槽ID、资产挂点名、本地变换 | 逻辑挂载与表现定位一一对应，完整传递位置/旋转/缩放 |
| 来源身份和已批准的子树快照 | 正确复制来源造型与功能，避免原来源后来变化影响已刻印枪 |
| 影响范围与继承规则 | 只改当前节点、现有后代，还是未来生成物；不能默认一锅汇总 |
| 发射器ID、事件阶段、独立/共享状态规则 | 计数、弹药、冷却和伤害来源不串线 |

每个可挂模型应有明确连接锚点；对齐用父挂点完整世界变换与子连接锚点的逆变换，不能只复制position，更不能拿ScopeSocket充当所有挂枪的位置。挂点不存在/被占用/不兼容时应在购买前给可理解提示，提交失败则整笔回滚。

### 5.3 顺序示例要先明确目标，再谈结果

- A挂B后，选B施加放大：应只把B及其按规则继承的子节点变大；A外形不应被整树汇总误改。
- 先放大A再从A复制B：是否复制放大效果，由来源快照范围明确决定；当前已有这个快照差异，但缺少可读预览。
- A挂B后再挂C：应由玩家选择A剩余挂点或B挂点。若只允许一条递归链，UI就展示下一合法连接；若允许多挂点，就明确容量。不能静默挂第一匹配项。
- 给B弹体加追踪：B发出的弹体追踪，A不受影响；追踪视觉附着到B的弹体模板。
- “复制发射”与“复制结构”应是不同操作。保留权杖九为第二波发射可以，但卡面、节点树必须显示它是发射处理器，不伪造额外枪身。
- 炮台与返航都请求弹体转态时，给出明确互斥/顺序组合，如“先返航，返航结束落地变炮台”；若不支持该组合，刻印前明确拒绝。不能只让一个标志永远被另一条if吞掉。

## 6. 建议施工顺序

1. **先做魔术师最小闭环**：真实来源 → 确定目标挂点 → 子枪完整必要结构 → 实例化对应模型 → 绑定它自己的枪口 → 按明确供弹/触发规则发射 → 换枪/存档恢复一致。
2. 再做战车与权杖三，让弹体实例能带着对应子结构；接炮台的真实模型、转轴和枪口。
3. 建立节点修饰与事件作用范围，迁移已存在的22张；尤其重复卡覆盖、父级/子级缩放、元素叠加、发射/命中计数。
4. 用实际节点树支持目标选择、预览及顺序提示，最后接宝剑14张。无需先做一轮无结构依据的数值平衡。

这不是要求为每张牌复制一个执行器。应统一新增节点、挂载、局部修饰和事件处理接口；卡片只声明操作，避免表现层和战斗层各自解释一套卡义。

## 7. 验收标准应补什么

- A挂B后，结构中有B、画面能认出B、B模型的枪口可定位；A/B射击分别从各自枪口世界位置发出。
- 旋转或缩放父挂点后，B位置/朝向、枪口火光、弹源一起更新；不能只移动模型。
- 指定B修改，不误改A；A的主弹体与B的弹体各有身份。
- 来源含子弹模块和配件时，按已冻结的复制范围保留；不支持的来源应明确拒绝，不静默丢部件。
- 正/逆位发射节奏来自同一发射器结构，视觉与功能一致；明确同步模式是否使用子枪射速。
- 刻印顺序、同类重复、事件冲突分别有手写预期；不能仅断言“字段存在”或“子弹总数多了”。
- 挂点占用、缺模型、缺枪口、深度超限、构建失败必须回滚金币、槽位和装配；视觉构建不能成功提示后才发现缺件。
- 手持、地面物、背包图标、工作台预览及读档后保持同一构筑；不要求每种视图使用相同多边形数，但结构与挂点含义一致。
