## 1. 职责与边界

本系统拥有存档清单、原子写入、版本迁移、行动快照、死亡/撤离结算、保险与复活策略。玩家只报告死亡并接受复活结果；基地、精英、剧情等系统提供可序列化快照，不自行写文件。

## 2. 生命周期分层

| 生命周期 | 示例 | 是否跨场景 | 是否跨局 |
|---|---|---:|---:|
| 房间运行态 | 当前敌人实例、门动画、临时 VFX | 否/按需 | 否 |
| 行动运行态 | 已提交FloorBundle、活动Boss区段、房间清理、普通背包格、已装备背包、动态容量、保险格、角色/世界命运状态、Boss钥匙、隔离门事务 | 是 | 结算前否 |
| 长期档案 | 基地、蓝图、完整枪械实例、带出物、精英、剧情、95→94唯一电梯状态 | 是 | 是 |

不能把运行时 Node、Callable、临时实例 ID 或场景路径当作长期事实保存。

<span style="color:#1565C0">**[用户设计]** `weapon_instance_id` 不是临时节点实例 ID。它永久绑定具体枪械，必须随装备、背包、地面、保险、撤离和存档保存。</span>

### 3.1 正式存档时机

| 时机 | 保存内容 | 规则 |
|---|---|---|
| 启动游戏/返回基地 | 读取长期档案并校验 envelope、schema、revision、checksum | 主档无效时只允许回退有效 `.bak`；不能用空档覆盖损坏档 |
| 基地购买、出售、设施升级、保险柜转移 | 资源点、物品所有权、交易 ID、设施等级 | 强一致事务；内存变化与一次原子写入同时成功，否则全部回滚 |
| 预选命运、准备下局带入 | 稳定卡 ID、物品实例及来源集合 | 成功写盘后 UI 才显示完成 |
| 行动开始、FloorBundle生成、区段卸载 | 当前运行态及后续行动快照 | FloorBundle生成/验证后先同步落盘再开到达门；隔离卸载先保存提交意图再删节点；写盘失败保持门/旧段并允许重试 |
| 成功撤离、死亡、Boss 后隔离提交 | 结算变更、永久遗失集合、统计、清理行动档 | 事务 ID 幂等；重复请求不能重复发放或扣除 |
| 暂停、切后台、正常退出 | 仅刷新已经通过验证的脏快照 | 不把半生成楼层或正在执行的交易强行保存 |
| ESC确认复位游戏存档 | 停止旧快照提供者，写入并回读全新封套后删除旧`.bak` | 写盘失败保留原档；独立画面设置不清除；成功后回正式主场景 |

<span style="color:#2E7D32">**[E03已修复｜2026-09-12]** `BaseManager.spend_extraction_points(amount)`只接受正数；余额不足直接拒绝。合法扣款先修改当前事务对象，只有`save_base("spend_extraction_points")`写入并回读成功才返回`true`；写盘失败时恢复原余额和修订元数据。若保存因磁盘已有更高revision而拒绝，保留`save_base`重新加载的权威档案，不用旧实例余额覆盖。专项`verify_extraction_points_spend_transaction`覆盖正常提交、强制失败回滚、非法输入和旧实例冲突。该修复先收口单次普通扣款接口；工坊“扣款+解锁”与撤离／死亡结算后续已分别由`upgrade_blueprint`与`commit_run_settlement`收口，见2026-09-23 P1记录与§5。</span>

玩家位置的逐帧变化、瞄准、弹道、怪物逐帧位置、门动画进度、悬停和临时 UI 状态不逐帧写长期档。背包、装备、弹药、生命、手电和局内货币变化只标记运行态为脏；在 450ms 合并窗口结束时抓取并写入最后状态。房间切换和应用生命周期边界绕过合并窗口，重新抓取最新状态并同步提交。

### 3.2 玩家运行态自动存档（2026-08-10）

`BaseManager` 是唯一磁盘写入者，活动场景通过弱引用注册 `build_runtime_save_snapshot()` 提供者。实现采用“事件标脏、尾沿合并、关键边界强制提交”，不为背包另开第二个存档文件：

| 触发 | 策略 | 性能与一致性 |
|---|---|---|
| 基地内背包/保险格变化、装备或卸下主副枪/背包、快捷栏变化 | 标脏并重启 450ms 单次计时器 | 连续拖拽和整理只产生一次 JSON 序列化与原子磁盘提交 |
| 战局内拾取、丢弃、换装、开枪、受伤、魂或手电状态变化 | 同一合并窗口 | 高频信号不立即写盘；计时器触发时只抓取最后完整状态 |
| 玩家真正进入新房间 | 立即重新抓取并原子提交 | 每次过门都有可恢复边界，不依赖之前的延迟任务 |
| 应用暂停、窗口关闭、场景卸载 | 同步重新抓取并提交 | 即使仍处于 450ms 窗口也不会丢最后变化；使用主档/`.tmp`/`.bak` 原子链 |
| 启动并完成场景生成 | 先读快照种子，再恢复运行态 | 恢复期间关闭变化监听，避免默认装备或空背包覆盖旧快照 |

`runtime_player_state_v2` 当前保存：`scope / run_seed / current_room_id / current_floor_index / player_position / player_rotation_y / player_hp / inventory_capacity / inventory_slots[] / insurance_slots[] / equipped_weapon_items[2] / active_weapon_slot / equipped_backpack_item / flashlight_module_id / flashlight_charge_ratio / quick_item_slots[2] / quick_item_ids[]兼容索引 / room_key_count / run_value / kills / run_currency / edge_states / world_state / runtime_map_id`。`scope=base`覆盖100F天台与99F基地：不续用旧玩家坐标，固定回99F，但恢复同地图的世界与携带物；`scope=combat`才按行动入口安全房续局。快捷槽保存完整物品与堆叠数量，旧ID引用档恢复时从背包原子迁移；枪械条目使用完整 `WeaponInstance` 物品字典，因此当前弹药、永久实例 ID、命运槽和装配不会因重启重建成默认枪。

2026-09-24 增量：局内商人行动快照另含 `merchant_stock = {schema:"run_merchant_stock_v1", stocks:{merchant_id:[{offer_id,item}]}}` 与 `trade_extraction_unlocked / trade_extraction_room_id`。`merchant_id` 是稳定房间ID，临时UI会话ID不进存档；首次展示前先同步提交货架，成交时货架移除、魂、背包和交易撤离条件同次提交。旧档缺 `merchant_stock` 视为未开商人，字段存在但校验不通过则拒绝交易，不默默重抽。具体所有权和失败契约见[局内商人](04.1_玩法系统_局内商人.md) §4.2。

`tower_world_state_v1` 保存已提交楼层索引、每层 `layout_id`、房间访问/清理/钥匙/事件进度、垂直到达门和首段封门状态。恢复顺序固定为：读取 `run_seed` → 纯数据规划同一楼层 → 对照 `layout_id` → 顺序提交 `FloorBundle` → 恢复门与房间进度 → 选择该楼层入口安全房间中心 → 放置玩家。有效`combat`行动快照不再恢复战斗房内的精确坐标；布局校验失败时拒绝旧世界并回退99F，不能把角色投放到空世界。

### 新档 98F → 基地 → 远征的存档交接（2026-09-23）

| 边界 | 唯一 Owner 与输入 | 命令/查询/事件及持久化 | 失败/重试与落点 |
|---|---|---|---|
| 首次启动 | `GameEntryFlow` 给入口意图；`TowerDescent3D` 以教程未完成且无行动快照判断新档 | 一次提交 98F `FloorBundle`，落办公室；剧情 `gameplay_started` 触发 `scene.spawn_item`，奖励服务解析正式物品，`Dungeon3D` 创建地面实例 | Bundle 失败回退安全出生点；剧情动作失败不得写完成历史；不由塔楼代码补刷第二把枪 |
| 地面物与下线 | `Dungeon3D` 独占房间地面物和 `_segment_runtime_state`；`BaseManager` 独占档案原子写入 | `build_runtime_save_snapshot()` 收集房间 `ground_items[]`（完整物品字典、世界坐标）及剧情刷物键；离房、后台、退出写 `active_run_snapshot.world_state` | 写盘失败不得假称已保存；同一刷物键重复执行只能有一件；拾取后该键仍保留，避免中途退出重播时复制 |
| 基地重登 | `TowerDescent3D` 读 `scope=base` 且地图 ID 匹配的快照 | 只用其世界进度和携带物，不用旧玩家坐标；重建已提交 98F、房间地面物，在 99F 固定点落位 | 旧档无这些字段视为空；布局不匹配拒绝旧世界，玩家仍落 99F；远征地图 ID 不得被塔楼接收 |
| 战局续局 / 远征 | `GameEntryFlow` 按 `runtime_map_id` 路由；`Dungeon3D` 恢复 `scope=combat` | 同一 `run_id`、种子、布局 ID、房间地面物和携带物；战局位置退到楼层入口安全房 | 地图不匹配不续局；失败不得把玩家投进未提交楼层；结算后不可再次续已结算行动 |

剧情刷物键是剧本中显式 `spawn_key`（同一档内稳定，如 `nar_tower_opening_01_wake:starter_weapon`），由剧情适配器传给地牢；它只用于幂等，不替代 `weapon_instance_id`。旧剧本不传此键时保持原有可重复刷物语义。`narrative_history` 只记录完整收口，不能代替刷物/拾取所有权账本；两者分别由 `BaseManager` 与 `Dungeon3D` 写入各自域。开场未拾取枪不得因玩家在 99F 下线而丢失，也不得因中断剧本重放复制。新档独立门禁必须覆盖未拾取、已拾取、中断重播、基地重登和远征地图隔离。

<span style="color:#2E7D32">**[E11已完成｜2026-09-12]** 运行快照明确分离四类字段：`schema`只表示结构版本；`run_id`表示一次行动；`checkpoint_id`表示该行动的检查点身份；`layout_id`表示当前楼层布局。新行动即使复用同一玩法种子也生成不同`run_id`，恢复时沿用原值。旧快照把`runtime_player_state_v1/v2`误写进身份字段时，`RunPersistenceService`按`run_seed + current_floor_index + floor_layout_ids`迁移生成稳定兼容身份。精英遭遇使用`run_id + room_id`，不再把schema或检查点字段当作行动ID。</span>

楼层规划种子是可保存、可复现的正式事实。`FloorPlanGenerator` 使用 `run_seed ^ (floor_number << 17) ^ (sequence_index << 9) ^ (attempt * 7919)` 派生每次候选 RNG；入口方向与 Boss 标记也是规划输入。同一工程规则版本、行动种子和楼层语义必须生成相同房间树、类型分配和 `layout_id`。专项性质测试覆盖1000种子×4层共4000份计划，并在真实98F磁盘重载恢复中再次比对布局 ID。

这里的“实时保存”指每次合法状态变化都会进入自动存档队列，并在最长约 450ms 后落盘；不等于每个输入事件都同步写磁盘。关键边界始终同步保存。强一致的购买、出售、保险柜转移和设施升级仍沿用原事务的一次立即原子写入，不经过合并窗口。

敌人逐帧位置、弹道、VFX和门动画百分比不保存；未清房间按稳定内容规则重建战斗，已清房间不会重复生成首波或钥匙。98F 剧情地面枪的完整实例、位置和拾取后互斥所有权已进入房间快照并通过跨重启专项；一般地面掉落与战斗中敌人当前HP/位置的全场景完整性仍待更广覆盖。FloorBundle开门与区段卸载已改为§5.4/§5.5的同步提交边界；这仍不等于逐帧冻结整个战斗世界。

### 3.3 存档封套与交易日志

长期基地档采用版本化封套：

```text
SaveEnvelope
  manifest_version
  profile_schema
  revision
  saved_at_unix
  reason
  payload_checksum
  payload: BaseData

BaseData
  completed_transaction_ids[]  # 有界幂等日志，当前保留最近128笔
  active_run_snapshot           # 玩家运行态/行动检查点共用槽；必须带 schema、valid 与 checkpoint_id
```

`payload_checksum` 对规范化 JSON payload 计算 SHA-256。读取顺序固定为主档、备份；解析成功但 checksum 不匹配也视为无效。旧 `BaseData 1.2` 裸 JSON 首次读取时迁移到封套，不丢失原字段。

当前 `BaseManager.save_base(reason)->bool` 是唯一长期档写入口：写前读磁盘 revision，发现较新档则拒绝并重载权威档；否则递增内存 revision，原子写盘并回读校验，失败恢复本次 revision/时间/原因元数据。它目前**没有通用 `save_committed/save_failed` 领域事件**；正式信号只覆盖个别域（例如蓝图 Tier、重置结果），调用方必须读取命令返回值。各领域事务须分别证明在“强制写盘失败”和“磁盘 revision 冲突”时不把旧对象回滚值写进已重载的新权威档，普通 `spend_extraction_points` 专项通过不能外推全部事务。

## 5. 结算事务

### 5.1 成功撤离

1. 冻结行动快照并停止新掉落/交互。
2. 校验普通背包格、已装备背包及其动态容量、保险格、任务物、完整枪械实例及角色/世界临时命运状态。
3. 生成带出物变更、统计、精英与剧情变更。
4. 在内存副本应用并验证。
5. 原子保存所有长期域。
6. 成功后清理行动档；失败保留可重试快照。

<span style="color:#2E7D32">**[E05已完成｜2026-09-12]** `BaseManager.commit_run_settlement()`已将行动统计、击杀、成功撤离魂、待领取战利品、幂等事务ID与行动档清理合并为一次原子保存。`TowerDescent3D`和`Dungeon3D`只在提交成功后发送完成事件及返航；写盘失败恢复长期数据并保留本次场景事务ID以便重试。相同ID在当前进程或重载后重放均不会再次累计统计、魂或战利品。</span>

塔楼普通撤离点属于“成功返航”，不得复用死亡或98F反向撤退的清空逻辑，也不得通过重载 `TowerDescent3D` 回到100层天台。结算完成后只清理本轮战斗楼层、敌人、未拾取世界物与门状态；玩家当前 `InventoryModule`、主副武器槽、装备背包、快捷栏和保险格保留原实例，随后传送到99层 `facility` 基地房间。带出物不能同时再复制到 `extraction_loot`。

<span style="color:#2E7D32">**[2026-09-21 实装｜撤离信号塔带物返航]** 上一句「不得复用塔楼带物返航」约束的是**塔楼的场景内复位**（`_reset_initial_loop_world_after_retreat()` 会按塔楼 98F 重建世界，把整张远征地图换成只剩一间白盒房），**不是允许丢物品**。此前实现把它读成「成功路径整条交给 `Dungeon3D._finish_run(true)`」，后果是携带物被复制进 `extraction_loot`、运行检查点被清空、场景重载 ⇒ 玩家回 99F 时身上复位成初始状态；而该待领取栏的唯一消费者是 `BaseMenu`（`scenes/BaseMenu.tscn`），`BaseFacilityCatalog` 的 99F 设施目录里没有它，物品等于被封存在存档里（业主实机报告，`extraction_loot` 里躺着 15 件）。现改为 `TowerDescent3D._finish_expedition_successful_extraction()`：结算仍走 `Dungeon3D` 的事务边界（`extraction_loot` 传空，同一运行时实例不复制到待领取栏），随后写一条带 `successful_extraction_carry` 标记的所有权交接快照（`scope=base`、`current_room_id=facility`、`current_floor_index=1`、`runtime_map_id=""`、世界与坐标清空），由落点场景（99F 塔楼）的 `Dungeon3D._restore_carried_ownership()` 只恢复背包 / 主副枪 / 装备背包 / 快捷栏 / 保险格。**标记必须显式存在才恢复**，因此这条交接与「可续局行动快照」互斥、可安全重放（玩家回落点时若已恢复，再恢复一次不会产生第二份实例）。门禁 `verify_expedition_extraction_carry_return`（已注册 `core` 套件）含「去掉标记就不得装回」的反向对照。</span>

<span style="color:#1565C0">**[用户设计｜2026-09-19 远征关卡主动退出战局门]** 上句“不得调用98F反向撤退的清空物品步骤”只约束**撤离信号塔与死亡**两条结算路径；远征关卡出生安全房那扇无目标抵达侧门（运行时节点名 `ExpeditionExitWarning`，门提示“`[E] 退出战局`”）是**主动弃局**入口，其物品契约与塔楼 98F 首门反向撤退**完全一致**（背包、装备枪、装备背包全部丢失；保险格按契约）。两条语义的差异只在落点：塔楼落回场景内 99F 基地房，远征关卡没有 99F 基地房，必须登记 99F 出生契约并 `change_scene_to_file(return_scene_path)` 回正式基地。**禁止**对远征关卡复用 `TowerDescent3D._reset_initial_loop_world_after_retreat()`：它会按塔楼 98F 重建世界，把整张远征关卡地图换成只剩一间无美术白盒房（实测 65 间房 → 1 间 `floor_01_entry`，且玩家物品被清空却没有任何结算）。**该门在两条入口下都必须成立**：刚传送进图按门、以及“关卡内重新上线 → 安全房 → 按门”。反向约束：撤离信号塔与死亡**不得**改用这套清空物品。门禁由 `verify_expedition_level01_flow` 的 `_verify_expedition_exit_contract` 组断言盯着。</span>

### 5.2 死亡

1. 玩家发出唯一死亡请求。
2. 查询复活策略；若存在合法复活来源，进入复活事务。
3. 无复活则按保险和损失规则生成死亡结算。
4. 结算精英逃脱/成长、剧情和统计。
5. 原子保存长期域并结束行动。

<span style="color:#2E7D32">**[E06已完成｜2026-09-12]** 死亡规则仍由`DeathSettlementModule`计算，长期交接统一由`BaseManager.commit_run_settlement()`一次提交失败行动统计、保险格中转、幂等日志与行动档清理。保存失败时`Dungeon3D`恢复结算前的普通背包、快捷栏和保险格，不发完成事件、不切换场景；保存成功后才清空运行时保险格并返回99F。</span>

保险格的“保留”必须具有长期落点，不能只留在即将销毁的运行时 `InsuranceModule`。保险槽自身保存 `物品实例 + 堆叠数量`；死亡结算将条目按原 `insurance_slot / item_instance_id / weapon_instance_id / count / 完整构筑` 写入专用 `pending_insurance_slots`，提交成功后才清空本局保险格；写盘失败则保险格保持原状并允许重试。99F基地启动时不要求玩家去另一个界面领取，而是把中转条目恢复到原金色格；只有包含这些格的新 `runtime_player_state_v2` 与清空中转集合同次原子写入成功，才算完成所有权交接。保险物取回背包必须整笔成功，空间不足时回滚，不能部分加入后复制。未保险背包物继续按死亡损失比例处理。

<span style="color:#1565C0">**[用户设计｜保险格位置契约]** 保险格不是物品锁。物品当前位于随身保险格时，不受战场离场损失影响：死亡时由专用持久中转恢复到99F的原保险格，98F反向撤退时保持在保险格，普通撤离成功时随当前行动物品完整保留。玩家仍可主动把它移动到背包、兼容装备槽、快捷栏或当前房间地面；转移成功后物品立即按新位置的普通规则处理，不再享受保险格保护。目标无效、容量不足或落地失败时整笔回滚，继续留在保险格。楼层流送、区段清理、场景重建和失败结算不得擅自移动或删除仍在保险格内的物品。</span>

### 5.3 Boss 专钥匙

`item_boss_descent_key` 属于行动进度物：默认不带出、不出售、不进入普通掉落池。开门时作为关卡事务的一部分消耗；保存行动快照时必须保留其阶段来源，防止加载后打开错误 Boss 门。

<span style="color:#777">**[历史口径｜用户确认2026-09-12，已被2026-09-23 P1工程修复替代]** 原允许FloorBundle生成后不等快照即开门；深度审计将其确认为恢复断点，现不再作为当前工程事实。</span>

### 5.5 隔离间区段提交与永久遗失

<span style="color:#777">**[历史口径｜用户确认2026-09-12，已被2026-09-23 P1工程修复替代]** 原隔离间先卸载再等后续快照；审计证明崩溃可让已永久遗失的旧段重现，因此不再是当前口径。</span>

<span style="color:#2E7D32">**[当前工程口径｜2026-09-23 P1]**</span> 前门交互时先构造“Boss后侧路线关闭 + `unloaded_segment_floor_indices`已提交”的预期快照并同步落盘。只有保存成功才实际`queue_free`旧房间并继续开前门；保存失败会回滚预期标志，保留旧段和活动隔离间以便重试。若进程在“保存成功”与“场景删除完成”之间终止，恢复会消费已存的卸载索引重放删除。

当前世界快照保存与该链路有关的以下事实：

```text
committed_floor_indices[] / floor_layout_ids{}
vertical_arrival_open{}
unloaded_segment_floor_indices[]
room_progress{} / segment_runtime_state{}
```

- 玩家必须处于`_active_airlock_room_id`对应隔离间；交互前门时`_finalize_airlock_commit()`先保存预期状态，成功后才关闭Boss后侧边并调用`_unload_completed_segment()`。
- 卸载遍历旧区段楼层，释放房间、地面物、楼层Stage、电梯和运行缓存，并记录已卸载楼层索引；装备、背包和保险格不属于这些场景节点。
- 当前以“快照中的完整卸载楼层集”作为幂等事实，还没有独立`segment_commit_id`或逐实例稳定销毁清单。
- 保存失败阻断前门和卸载；保存成功后运行时删除失败，下次恢复仍会按已提交索引重放。

### 5.6 基地自动贩卖机事务

<span style="color:#1565C0">**[用户设计]** 基地自动贩卖机允许购买固定货架商品，并出售随身背包或保险柜中的枪械/道具。早期初始集合为三把基础枪械、2格初级背包、治疗药水；当前正式货架已扩为[07 §5.6](07_技术施工_基地设施.md)登记的七类（含小型电池），以正式 `ItemRegistry` 上架定义为准。</span>

商品静态配置只来自内容数据库 `基地商店`，通过 `物品ID` 映射 `ItemRegistry`；存档只保存交易结果与独立物品实例，不复制一份价格表。

`ShopTransaction` 是原设计的数据字段清单，**当前没有同名运行对象或统一事件 schema**。现行正式命令是 `BaseManager.purchase_base_shop_item(item_id, transaction_id="", target_owner="loadout")`、`purchase_base_shop_item_to_inventory(item_id, inventory, transaction_id="")`、`sell_base_shop_item(item_instance_id, transaction_id="", source_owner="vault")`、`sell_runtime_inventory_item(inventory, slot_index, transaction_id="")`。基地货架 `shop_entry_id` 只用于内容上架与排序，命令接收 `item_id`；运行背包出售用格位索引，长期集合出售用物品实例 ID。调用方不能把 `shop_entry_id` 当作命令参数，也不能假设所有入口都以实例 ID 锁定来源。

| 当前字段/返回 | 实际语义 |
|---|---|
| `transaction_id` | 可由调用方提供；空值由 `BaseShopService` 生成。已完成 ID 保存在 `BaseData.completed_transaction_ids`，返回 `{success:true,duplicate:true,transaction_id}`；日志最多保留最近 128 个 ID，不能宣称无限期跨局幂等。 |
| `item_id / item_instance_id / weapon_instance_id` | 内容 ID 定义商品；成功购买生成完整物品实例 ID，武器再带永久武器实例 ID。`BaseShopService` 只管纯数据规则，`BaseManager` 负责资源、集合与写盘。 |
| 成功/失败结果 | 成功返回 `success` 和交易/物品/价格或价值字段；失败当前主要返回中文 `reason`，**没有统一机器错误码或已实现的成交事件**。UI 成功提示以命令结果为准。 |
| `save_revision` | `BaseManager.save_base()` 对磁盘较新 revision 拒绝旧写者并重载权威档；普通扣款专项覆盖该路径。商店各事务的 revision 冲突后完整域回滚尚无逐入口专项，不把普通扣款通过直接外推为商店全部通过。 |

- 数据字段 `extraction_points` 的玩家显示名统一为“魂”；不迁移字段名，以保证旧档兼容。拾取的局内魂在成功撤离时进入这一同一持久化余额，基地、塔楼主 HUD 与贩卖机读取它。
- 购买前校验商品上架、购买价、魂与目标背包容量；99层设施目标是 I 键正在使用的运行时 `InventoryModule`，独立主基地目标才是 `pending_loadout_items`。成功后生成独立 `item_instance_id`，枪械同时生成永久 `weapon_instance_id`；可堆叠物品优先合并，商店库存永不递减。
- 出售的**当前接口**分两种：长期 `vault/loadout` 集合按“来源集合 + 稳定实例 ID”定位；99F 当前 I 键背包按格位索引读取当时的完整条目。售价都重新读取 `ItemRegistry.base_sell_price`，不相信物品存档中可被篡改的价格。若要求跨UI旧快照安全地以实例 ID 锁定运行背包出售，需要另补命令与拒绝专项，当前不假称具备。
- 同一仍保留在最近128条完成日志内的 `transaction_id` 重放返回已完成，不再次扣资源、发物或增加资源；更长期的外部幂等账本尚未实现。
- 强制写盘失败的购买/出售专项已覆盖资源与物品集合回滚；`revision` 并发冲突的所有商店分支仍需逐入口核验。UI 只能在命令报告成功后刷新“购买成功/出售成功”，不能把底层 `save_base()` 的 `false` 忽略。
- 枪械出售必须显示枪型、实例短 ID、命运槽和装配摘要，并采用二次确认；普通道具同样按实例或堆叠记录成交。

### 5.7 保险柜格子转移事务

- `vault_items` 是长期保险柜，容量为基础 `20` 格加设施等级；99层右栏使用当前行动 `InventoryModule`，必须与 I 键界面对象同一；`pending_loadout_items` 仅用于没有行动库存的独立主基地和下局准备。基础容量是派生规则，旧档不需要迁移数组结构。
- 点击和拖拽调用同一个双集合转移事务：先保存两个集合快照，再移除来源、合并或占用目标格，最后只写盘一次。
- 目标无空格且无可合并堆叠时拒绝；保存失败时两侧集合同时回滚。独立枪械/装备不堆叠，消耗品仅在 `id` 相同且 `stack_max > 1` 时合并。

## 6. 复活策略

- <span style="color:#EF6C00">**[Codex补充]** 建立 `RevivalPolicy` 接口，但不在本版默认改变“死亡结束行动”的当前规则。</span>
- 合法复活来源必须显式配置：来源 ID、每局次数、消耗、复活点策略、生命比例、无敌秒数、敌人状态策略和战利品惩罚。
- 复活点只能来自当前仍存在且已经提交的安全锚点，例如本房入口、最近清理房或95→94唯一电梯的合法一侧；不能简单使用死亡位置，也不能把角色送回已经由隔离提交销毁的旧区段。
- 复活事务先预约并扣除来源，角色成功恢复后提交；恢复失败则回滚扣除并进入普通死亡结算。
- <span style="color:#1565C0">**[用户设计]** 具体复活次数、成本和剧情含义由后续设计决定；技术接口不得提前锁死免费复活或付费复活。</span>

## 7. 幂等与恢复

- 撤离、死亡、Boss 钥匙、精英结算、物品转移均携带事务 ID。
- 楼层生成使用 `layout_id + generation_transaction_id` 幂等；重复提交同一事务只返回原计划，不新增房间或重置门状态。
- 区段卸载依赖活动隔离间ID和当前场景状态防止普通路径误触；当前没有持久化`segment_commit_id`或跨重启幂等承诺。
- 枪械实例转移使用 `weapon_instance_id + transaction_id` 幂等；同一实例在一次提交后只能有一个所有权位置。
- 重试同一事务返回同一结果，不重复发物、扣钥匙或增长统计。
- 主档损坏时读取 `.bak` 并展示恢复提示；不能静默创建空档覆盖旧档。
- 版本迁移先备份完整旧域，迁移失败保留旧档和诊断。

### 10.2 死亡表现与确认

致命伤害先锁定移动、开火和交互，再依据最后受击方向施加水平击飞与向上速度；角色受重力落地后弹起一次，最终侧倒。完整表现时长1.35秒。动画完成后才出现全屏模态对话框，玩家点击“返回99层基地”后执行一次失败结算和场景返回；点击前不得自动切场景或重复结算。

本文档中“死亡返基地”是“结束当前行动后在基地重建玩家”，不等于第6节所述的局内`RevivalPolicy`复活。两者不得共用启动页作为中转节点。

`death_animation_finished`只表达表现完成，`Dungeon3D`负责对话框与结算，`BaseManager`只负责长期档和出生标记，三者保持解耦。
