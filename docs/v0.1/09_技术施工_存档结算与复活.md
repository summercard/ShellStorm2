# 技术施工｜存档、结算与复活 v0.1

系统编号：7  
上级设计：[游戏设计文档 §12](README.md#12-核心系统七存档结算与复活)  
相关内容表：`精英怪`、`掉落物品`

## 1. 职责与边界

本系统拥有存档清单、原子写入、版本迁移、行动快照、死亡/撤离结算、保险与复活策略。玩家只报告死亡并接受复活结果；基地、精英、剧情等系统提供可序列化快照，不自行写文件。

## 2. 生命周期分层

| 生命周期 | 示例 | 是否跨场景 | 是否跨局 |
|---|---|---:|---:|
| 房间运行态 | 当前敌人实例、门动画、临时 VFX | 否/按需 | 否 |
| 行动运行态 | 已提交FloorBundle、活动Boss区段、房间清理、普通背包格、已装备背包、动态容量、保险格、角色/世界命运状态、Boss钥匙、隔离门事务 | 是 | 结算前否 |
| 长期档案 | 基地、蓝图、完整枪械实例、带出物、精英、剧情、95→94唯一电梯状态 | 是 | 是 |

不能把运行时 Node、Callable、临时实例 ID 或场景路径当作长期事实保存。

<span style="color:#1565C0">**[用户设计]** `weapon_instance_id` 不是临时节点实例 ID。它永久绑定具体枪械，必须随装备、背包、地面、保险、撤离和存档保存。</span>

## 3. 当前能力

- <span style="color:#2E7D32">**[已实装]** `AtomicJsonStore` 先写 `.tmp`、备份旧档为 `.bak`，再提升为主文件；读取可回退备份。</span>
- <span style="color:#2E7D32">**[已实装]** `BaseData` schema 已升级为 `1.2`，包含统计、设施、蓝图、资源、保险柜、预选命运、带入和撤离战利品；旧枪械物品会补齐唯一实例、命运槽与装配快照。</span>
- <span style="color:#2E7D32">**[已实装]** 死亡结算默认处理未保险物品损失，单局保险格保留；成功撤离结算当前主/副枪、普通背包内容、已装备背包本体和保险物，整枪构筑一并写入撤离战利品。98F撤退会清除已装备背包并把容量复位为基础12格。</span>
- <span style="color:#2E7D32">**[已实装原型]** 精英档案使用独立 `elite_archive.dat`，尚未进入统一正式 3D 存档清单。</span>
- <span style="color:#1565C0">**[用户设计]** 存档和复活属于独立核心系统，不能依赖死亡 UI 或房间脚本拼接。</span>

## 4. 目标存档清单

<span style="color:#EF6C00">**[Codex补充]** 根清单至少记录以下内容。</span>

```text
save_manifest_version
profile_id
last_transaction_id
domains:
  base: {schema, checksum, file}
  inventory: {schema, checksum, file}
  elite_roster: {schema, checksum, file}
  narrative: {schema, checksum, file}
  progression: {schema, checksum, file}
active_run: {schema, checksum, file, resumable}
migration_history[]
```

`inventory` 与 `active_run` 中的武器记录至少保存：`weapon_instance_id / weapon_content_id / schema_version / rarity / fate_slot_capacity / fate_upgrades[] / bullet_module_id / attachment_slots{}`。

可以继续使用多个文件，但所有文件的版本与提交必须由同一事务清单协调，不能一个成功、另一个失败后仍显示完整保存。

## 5. 结算事务

### 5.1 成功撤离

1. 冻结行动快照并停止新掉落/交互。
2. 校验普通背包格、已装备背包及其动态容量、保险格、任务物、完整枪械实例及角色/世界临时命运状态。
3. 生成带出物变更、统计、精英与剧情变更。
4. 在内存副本应用并验证。
5. 原子保存所有长期域。
6. 成功后清理行动档；失败保留可重试快照。

### 5.2 死亡

1. 玩家发出唯一死亡请求。
2. 查询复活策略；若存在合法复活来源，进入复活事务。
3. 无复活则按保险和损失规则生成死亡结算。
4. 结算精英逃脱/成长、剧情和统计。
5. 原子保存长期域并结束行动。

### 5.3 Boss 专钥匙

`item_boss_descent_key` 属于行动进度物：默认不带出、不出售、不进入普通掉落池。开门时作为关卡事务的一部分消耗；保存行动快照时必须保留其阶段来源，防止加载后打开错误 Boss 门。

### 5.4 已提交 FloorBundle

<span style="color:#1565C0">**[部分完成｜持久化未实装]** `floor_seed_gate` 成功后已冻结 `layout_id`、房间坐标/尺寸、连接器和提交原因，并可由 `get_tower_snapshot()` 读取；尚未写入磁盘行动快照，跨场景/跨重启恢复仍是P0缺口。</span>

快照至少保存 `layout_id / floor_rule_version / floor_id / floor_number / segment_id / generation_transaction_id / entry_anchor / exit_anchor / vertical_connector_id / next_floor_entry_anchor / next_entry_safe_room_shell / room_records / edge_records / structural_reservations / critical_path / branch_records / boss_route / validation_hash`。已实例化 Node、导航对象或场景树引用不进入快照。

到达门状态必须与FloorBundle快照同事务：只有FloorBundle及N→N-1楼梯、N-1入口壳体均通过校验并持久化后，才保存到达门为已开启。加载时若发现“门已开但FloorBundle缺失/校验失败”，必须恢复门为关闭并重试生成，不能让玩家进入空层。

### 5.5 隔离间区段提交与永久遗失

<span style="color:#1565C0">**[用户设计]** 玩家完整进入区段隔离间且后门关闭后，旧区段所有未拾取物永久丢失，旧楼层运行世界释放，且不能通过读档返回提交前。</span>

区段提交保存以下最小事实：

```text
segment_commit_id / source_segment_id / source_floor_range
isolation_room_id / rear_gate_locked / committed_at
owned_weapon_instance_ids[] / carried_item_instance_ids[] / insured_item_instance_ids[]
destroyed_world_item_instance_ids[] / destroyed_unclaimed_reward_ids[]
next_segment_id / next_floor_bundle_id / next_entry_anchor
unload_completed / validation_hash
```

- 点击确认和踏上楼梯不提交；只有玩家完整入内、隔离后门确认关闭锁定且下一FloorBundle纯数据计划已验证才写 `segment_commit_id`。
- 提交前冻结拾取、丢弃、容器领取和物品转移，以稳定实例ID划分玩家所有与世界遗留集合。
- 装备、背包、保险格中的物品保留；地面掉落、玩家主动丢弃物、已生成未拾取容器物和未领取房间奖励进入永久销毁清单。
- 同一 `segment_commit_id` 重放必须返回同一销毁清单，不得复制枪械、重复统计损失或再次发放奖励。
- 区段提交成功后，行动档只保留摘要和销毁清单，不保存98–95F可恢复运行快照；主档/备份恢复也不得回到不可逆边界之前。
- 下一FloorBundle在不可逆提交前验证失败时，取消过渡并允许重新打开后门返回，且不产生永久损失。提交后若实例化或旧区段卸载收尾失败，玩家安全留在双门关闭的隔离间；事务可续跑或使用已验证安全模板，但不能打开后门、撤销销毁清单或恢复旧区段。

## 6. 复活策略

- <span style="color:#EF6C00">**[Codex补充]** 建立 `RevivalPolicy` 接口，但不在本版默认改变“死亡结束行动”的当前规则。</span>
- 合法复活来源必须显式配置：来源 ID、每局次数、消耗、复活点策略、生命比例、无敌秒数、敌人状态策略和战利品惩罚。
- 复活点只能来自当前仍存在且已经提交的安全锚点，例如本房入口、最近清理房或95→94唯一电梯的合法一侧；不能简单使用死亡位置，也不能把角色送回已经由隔离提交销毁的旧区段。
- 复活事务先预约并扣除来源，角色成功恢复后提交；恢复失败则回滚扣除并进入普通死亡结算。
- <span style="color:#1565C0">**[用户设计]** 具体复活次数、成本和剧情含义由后续设计决定；技术接口不得提前锁死免费复活或付费复活。</span>

## 7. 幂等与恢复

- 撤离、死亡、Boss 钥匙、精英结算、物品转移均携带事务 ID。
- 楼层生成使用 `layout_id + generation_transaction_id` 幂等；重复提交同一事务只返回原计划，不新增房间或重置门状态。
- 隔离提交使用 `segment_commit_id` 幂等；旧区段永久遗失集合、卸载状态和下一入口不得因重载重新随机。
- 枪械实例转移使用 `weapon_instance_id + transaction_id` 幂等；同一实例在一次提交后只能有一个所有权位置。
- 重试同一事务返回同一结果，不重复发物、扣钥匙或增长统计。
- 主档损坏时读取 `.bak` 并展示恢复提示；不能静默创建空档覆盖旧档。
- 版本迁移先备份完整旧域，迁移失败保留旧档和诊断。

1. 枚举全部长期域和现有写入点，建立统一清单。
2. 把撤离、死亡、保险与基地物品转移改为事务变更集。
3. 把精英档案接入清单并编写迁移。
4. 为剧情、95→94唯一电梯、Boss区段提交和稳定命运卡ID预留版本化域。
5. <span style="color:#2E7D32">**[本轮完成]** 新增 `WeaponInstance` schema，并迁移装备、背包、保险柜、带入和撤离战利品中的枪械记录。</span>
6. 实现不改变当前玩法的 `RevivalPolicy` 空策略与测试桩。
7. 完成损坏、断电式中断、重复提交和旧档迁移测试。

## 9. 验收标准

- [ ] 所有长期存档域可由清单列出并校验版本/校验值。
- [ ] 撤离重复提交不会复制物品、资源或统计。
- [ ] 死亡重复信号只产生一次损失和精英结算。
- [ ] 保险柜、保险格、带入和撤离物之间转移具备事务 ID。
- [x] 换枪、地面物、出售、保险、撤离和加载后，同一枪械实例 ID 唯一且完整构筑不变；主动丢弃的独立操作菜单仍可作为交互增强，不影响实例落地与拾取链。
- [x] 永久命运槽顺序、效果版本与配件快照能够跨 JSON 存档恢复。
- [ ] Boss 专钥匙在行动快照恢复后仍只匹配原阶段门。
- [ ] `floor_seed_gate` 提交后的楼层边界、不少于 10 房的主路、支路、房型、下行楼梯锚点和 Boss 路线可跨场景/跨重启原样恢复。
- [ ] 到达门已开启的存档一定包含有效FloorBundle、真实N→N-1楼梯与下一入口壳体；不允许“开门后空层”。
- [ ] 隔离间提交前读档可返回当前Boss区段；提交后任何主档、备份或复活路径都不能恢复已销毁区段。
- [ ] 未拾取物永久销毁集合按稳定实例ID结算；装备、背包和保险格中的完整枪械实例不误删、不复制。
- [ ] 精英、基地和剧情任一域写入失败时不会提交半套档案。
- [ ] 主档损坏能从备份恢复，恢复失败不覆盖旧文件。
- [ ] 从 `BaseData 1.1` 迁移到 `1.2` 的枪械集合已完成；旧精英档案尚待纳入统一清单后做跨域数量验收。
- [ ] 复活空策略保持当前“死亡结束行动”的体验不变。
- [ ] 未来任一复活来源可通过同一接口配置并在失败时安全回滚。
