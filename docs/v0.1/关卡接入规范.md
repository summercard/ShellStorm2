# 关卡接入规范

生效日期：2026-10-18
适用范围：所有远征关卡（`expedition_0N`）及后续新增关卡
接入状态与验收分开：`expedition_01`已有13房正式路径，2026-11-11原节奏/奖励接线已实现待验收；room03/04/06/09/10现行全部触发即封门计时60秒，第2秒首批、清批0间歇、模板走完重复各自末批；主线程已同步五房数据，沿用通用截止关闭/HUD能力，未实到在截止丢弃，残怪清零后才允许出箱解封（09另需终端结算），不自动推开门板；死路反向回退仍按原设计与待施工边界处理，真实整关仍在联调，不能标“完整通过”；`expedition_02`原数据白盒缺口以其设计及当前专项为准；`expedition_03`的flow生成器、场景与情报室入口已接入，不再是“仅设计源/runtime_enabled=false”，具体权限与未验项见[模块索引](MODULE_INDEX.md)及[远征03设计](design/远征关卡03设计.md)。

> **这份文档解决一个问题**：新增关卡时，改哪里、不许改哪里、怎么证明没弄坏旧关卡。

---

## 1. 一句话原则

**通用机制按「能力」分支，关卡专属内容按「ID」分支。两者不许混。**

混的后果不是代码难看，是**死分支**——2026-10-18 解耦前就有一例：

```gdscript
# configure_expedition_fate_economy（配置环节）
if level_id != "expedition_01": return          # 02 不被配置
# _fate_price（消费环节）
if map_id == "expedition_01" and is_configured() # 02 永远为假
```

这是一条**永远走不到的路径**：02 因为前半句不被配置，因为不被配置所以后半句恒假。全部测试都是绿的，因为没有任何用例跑 02 的经济。这种缺陷只能靠规范防，不能靠测试防。

---

### 各关共用的性能入口

登记的新远征通过正式读取页进入。读取页从本局房间、刷怪盒和导航面取输入，按能力准备资源和可复用网格；规则层保持实际房间揭示、占位复核和出箱时序。房间承担导航缓存的生命周期。碰撞布局、尺寸或端口变化必须重新生成；导航区域只在正式细节需要时入树。

用 `python3 scripts/profile_expedition_events.py <登记的关卡ID> --godot <Godot可执行文件>` 走正式读取页、真实渲染器和独立档案。开发记录同时列出预热覆盖、事件调用耗时、窗口最慢帧、真实扣血与已覆盖房间。按关在目标机器复核，每个种子记录实际经过的房型。绕开远征读取页的独立入口单独验收。

## 2. 两层结构：数据层 vs 核心层

| 层 | 位置 | 并行开发冲突 | 谁维护 |
|---|---|---|---|
| **数据层** | `data/level_plans/<level_id>/`、`scenes/ExpeditionLevel0N_3D.tscn` | **零** | 各关卡独立 |
| **核心层** | `src/world3d/Dungeon3D.gd`、`src/world3d/TowerDescent3D.gd`、`src/map/FloorPlanGenerator.gd` | 有 | 共享，改动需走 §5 流程 |

**结论：新关卡 90% 的工作在数据层。只要不改核心层，任意多关卡可以并行开发、互不冲突。**

## 3. 通用机制：禁止按关卡 ID 分支

### 3.1 属于「通用机制」的清单

以下能力**所有关卡共享同一套实现**，新关卡不得在代码里出现自己的 ID：

| 能力 | Owner | 判定方式 |
|---|---|---|
| 命运卡发放与稀有度池 | `Dungeon3D._gate_expedition_fate_offer` | `uses_dynamic_fate_economy()` |
| 命运卡逐门定价、报价区间、冻结报价 | `FateEconomyService` | 同上 |
| 命运经济配置 | `Dungeon3D.configure_expedition_fate_economy` | `plan` 非空即配置 |
| 关卡级怪物数值与 AI 参数 | `Dungeon3D.set_monster_rules` | `monster_rules` 段是否非空 |
| 关卡级掉落表 | `RuntimeRewardCoordinator.configure_level_drop_table` | `monster_drop_table` 段；`legacy_fallback=false` 时允许空 `rows`（= 普通怪不掉物品，只留金币），`variant_legacy_fallback=true` 让强化怪仍回退通用公式（2026-11-10，远征01 在用） |
| 强化怪概率升级与按房间禁用 | `MonsterInjector._strong_variant_chance` / `set_active_room_id`（由 `Dungeon3D._spawn_room_enemies` 包装设置） | `monster_rules.strong_variant.chance` 与 `suppressed_rooms`（room_id 数组；2026-11-10） |
| 货币分档 | `RuntimeRewardCoordinator.configure_level_currency` | `monster_rules.currency` |
| 房间流送、清理、封门 | `Dungeon3D` | 房间类型 / 房间数据 |
| 房间级追加指定精英 | `Dungeon3D._commit_room_waves` | 房间的 `elite_id` 非空 |
| 门策略（清房 / 钥匙 / 命运卡） | `TowerDescent3D._door_policy_for_edge` | `door_policy` 段是否非空 |
| 房间钥匙经济开关 | `TowerDescent3D._room_key_economy_enabled` | `economy.room_keys_enabled`（缺省 true） |
| 清房 / Boss 掉落 | `Dungeon3D.configure_clear_drops` + `ClearDropService` | `clear_drops` 段是否非空 |
| 存档与恢复 | `RunPersistenceService` | `runtime_map_id` |

### 3.1.2 门策略、钥匙经济、清房掉落（2026-11-06）

这三段是**能力段**：任何关卡写同样的字就得到同样的行为，代码里不出现关卡 ID。
不写（或写空）的关卡逐字保持接入前的行为 —— 塔楼现在走这条。

当前使用情况：

| 关卡 | `door_policy` | `economy` | `clear_drops` | 备注 |
|---|---|---|---|---|
| `expedition_01` | 清房门槛 + 免钥匙 + 不弹卡 | 钥匙退役 | 内容房100%普通箱 / Boss高级箱；逐房小包与追加枪分账 | 2026-11-11已实现待验收，非整关通过 |
| `expedition_02` | ✅ 清房门槛 + 免钥匙 + 不弹卡 | ✅ 钥匙退役 | ⛔ **刻意不配** | 本关没有金币来源（无 `monster_rules.currency`）⇒ 上宝箱会把保底压成 0 元白送卡，见设计页 §13 L02-14 |
| `expedition_03` | ⛔（走 flow 内置口径） | ✅（flow 覆写） | ⛔（宝箱来自数据摆位 `treasure_chests`） | — |
| 塔楼 | ⛔ | ⛔ | ⛔ | 三项全按原行为 |

```json
"door_policy": { "requires_clear": true, "requires_key": false, "triggers_fate": false },
"economy":     { "room_keys_enabled": false },
"clear_drops": {
  "schema": "shellstorm2.battle.clear_drops",
  "content_room": { "chest_chance": 1.0 },
  "boss": { "chest_count": 1, "min_quality": "rare" },
  "chest": { "quality_weights": {...}, "reward_pool_id": "loot_floor_1_2",
             "drop_count": 2, "fate_card_per_open": 0,
             "mimic": { "chance": 0.2, "monster_kind": "egt_mimic" } },
  "fallback_pool": [ { "item_id": "item_health_potion", "count": 1, "weight": 40.405 } ]
}
```

| 项 | 规则 |
|---|---|
| `door_policy` 的优先级 | 固定交通接口（楼顶→99F、98F 楼梯间、远征入口门、楼层种子门、气密室）**先返回**，本段管不到它们；之后本段优先于 flow 默认 |
| `door_policy` 影响的边 | 本关**所有** `_door_policy_for_edge` 查询。远征01 用它把 `requires_key` / `triggers_fate` 整关关掉，只留 `requires_clear` |
| `economy.room_keys_enabled=false` 的连带效果 | 开局不发初始钥匙；`_room_produces_room_key()` 不再产钥匙；状态栏不再写「钥匙已掉落」；命运卡池剔除 `grant_room_key` 类空卡 |
| `clear_drops` 掷骰 | `(run_seed, room_id)` 稳定哈希，**不是运行时 RNG** ⇒ 同局同房读档 / 流送重建前后恒定 |
| `clear_drops` 的两档结果 | `chest`（掉一只宝箱，走与 `chest_placements` 同一套实例与房间账）或 `item`（走正常地面掉落通道）；二者互斥 |
| Boss 箱 | 不看 `chest_chance`，`boss.chest_count > 0` 即保底一只；挂在「首领阵亡」而非「房间肃清」；`min_quality` 只提下限不改权重 |
| 运行期宝箱的存档 | 房间账 `treasure_chests[chest_id]` 记 `spawned/config/offset`，detail 重建时按账重造；**漏记 = 走远再回来箱子消失** |
| 与钥匙的关系 | 两者**互斥**：配了 `clear_drops` 就不该再开 `room_keys_enabled`，否则同一间房发两份清房奖励 |
| `clear_drops` 的房型边界 | 只对**有敌群可清**的房结算：Boss 房（首领箱另挂）、非内容房、**无怪房** `authored_layout_peaceful` 一律早退。判据用标志**不用房型名** —— flow 关走廊 `room_type` 是空串、商店 `MERCHANT`、前厅 `UPGRADE`、宝箱房 `STORAGE`，全不在 `NON_CONTENT_ROOM_TYPES` 里。2026-11-09 前每间通道房白送一只箱（远征03 报障） |
| `room_guarantees`（2026-11-09） | **关卡保底段**：`[{id, candidate_rooms, weapon_choices?, weapon_grade?, weapon_count?, items?}]`。每局按 `run_seed + id` 的稳定哈希在 `candidate_rooms` 里挑**恰好一间**，那间的宝箱额外必掉 `weapon_choices` 二选一（品质写 `weapon_grade`）与 `items`。是**额外追加**，不替换该箱的正常奖励；条目接在 `_unit_grants()` 之后，数量不会被拍成 1 |
| `room_guarantees` 的边界 | 候选房必须真有 `clear_drops` 生成的箱子，否则保底无处落地（固定 `chest_placements` 房、无怪房、Boss 房都不吃这条）；写了不存在的房号只静默不命中，由关卡专项门禁抓漂移 |

```json
"room_guarantees": [
  { "id": "exp01_opening_weapon_or_ammo",
    "candidate_rooms": ["room_01", "room_02"],
    "weapon_choices": ["weapon_shotgun", "weapon_rifle"],
    "weapon_grade": "blue", "weapon_count": 1,
    "bullet_module_id": "mod_bullet_standard",
    "items": [ { "item_id": "item_ammo_pack", "count": 100 } ] }
]
```

### 3.1.3 十三房流程扩展的共同能力边界（2026-11-11）

以下扩展仍归既有 `WORLD-PLAN`、`ENCOUNTER-EVENT`、`REWARD-SERVICE/WORLD-LOOT`、`FATE-RULES`、`NARRATIVE-TRIGGER` 和 `SAVE-RUN`，不另建“远征01框架”或FeatureID。目标规则只在[远征01设计](design/远征关卡01设计.md)、[触发器刷怪](design/触发器刷怪设计.md)及[奖励设计](design/战斗奖励与物品流转设计.md)定义，此处仅规定接入交接。

| 能力段/交接 | Owner与边界 |
|---|---|
| `encounter`阶段与限时循环 | `duration_sec=0` 的显式有限stages继续表示无截止，但远征01五房room03/04/06/09/10均显式启用固定窗口：触发即封门并计时，`duration_sec=60/preparation_sec=0/freeze_player_sec=0/start_delay_sec=2/intermission_sec=0`、`deadline_behavior=close_dispatch_and_clear`、`repeat_last_stage=true`。第2秒首批、清批0间歇，各房模板走完重复各自末批；模板/cap保持03 5/7/8 cap8、04 6/6 cap6、06 8/9/13 cap10、09 12/16/20/24 cap16、10 10/12 cap10，波数/总量不定。截止先丢全部未实到（含active pending及本事件预约/延迟），保留实体/休眠敌人，存活清零才完成；出箱解封仍走原清房链（09另需终端结算），不自动开门板；HUD只读battle/cleanup。Owner按能力分支，精确队列与恢复契约见[触发器§10.5.2](design/触发器刷怪设计.md#1052-固定窗口循环与精确关闭派发2026-11-12) |
| `max_alive/min_player_distance_m` | 由Host落实实体/休眠/预约/延迟容量与真实空间筛选；派发开放时临时无合法点返回可重试、保留pending、不重掷，不用房心或非法点假成功；显式close截止后不再补发，精确撤回本事件未实到队列；硬失败停止派发 |
| `light` | Host调用房间正式 `set_room_light_on()`；失败与事件终态分别报告。该接口已存在，不再登记为未实现 |
| `clear_drops.room_overrides` | 新计划由ClearDropService一次冻结为房间 `clear_drop_plan`；`grants`清房小包、`additional_weapon`追加枪、`chest`箱子分别消费并沿原交付账幂等；旧局缺字段不补造 |
| 箱子与命运凭据 | 箱快照保留来源/档位/池/保底/拟态/概率及普通报价标记；凭据沿地面与快照传递 `source_room_id/source_chest_id/fate_common_offer`。新报价按源房映射价格、过滤后补普通候选，再冻结；旧offer不重算 |
| `flow_barks` | 只订阅进入/遭遇/清房并复用原bark；已触发ID随世界快照保存。`first_run_only`当前由对应主线钥匙“未取得”判断，首通前失败重试仍提示，不是严格第一次尝试；不改主线时间轴或钥匙领取后8秒返航 |

`room_guarantees.candidate_rooms`必须匹配生成器输出的运行时房间ID（远征01为 `room_01/room_02`，不是设计源旧 `f00_room_*`）。无奖励概率覆盖时保留普通30%/高级100%默认；02/07的100%是替代、不是再叠一次。07追加紫枪与教学蓝枪的标准弹绑定不改变普通随机枪的弹种权重，也不迁移旧枪卡片。

新增专项仅登记，不等于通过：奖励/集成场景归manual并用专用外部Runner在Autoload前隔离；Python数据检查、安全刷点/容量检查按既有command schema登记。full目录扫描也须排除这两个专用Runner场景。结果、待验项和主线程回填位置见[开发记录§4](development/2026-11-11_expedition01_flow.md#4-验证结果主线程回填区)，真实整关与视听不能由静态/服务fixture代签。

### 3.1.1 房间级追加指定精英（`elite_id`，2026-11-03）

`floors/floor_00.json` 的**任意房间**可声明：

```json
{ "key": "room_01", "content_type": "COMBAT", "elite_id": "elite_arms_taker" }
```

语义是**追加**：本房原有编成（普通刷怪 / 盒子 / 授权编成）全部照旧，
生成完再额外落一只点名的 `EliteContentCatalog` 精英。空/缺省 = 不追加，未声明关卡行为逐字不变。

| 项 | 规则 |
|---|---|
| 生效房型 | **普通战斗房**。`ELITE` / `BASEMENT` 已出精英、`BOSS` 自带精英随从，这三类声明无效（避免出两只） |
| 楼层窗口 | **不查**。走 `EliteRosterService.reserve()` 点名指派，绕过 `eligible_floor_numbers` 的三选一 |
| 唯一性 | 仍受「同 ID 全局单例 / 预约唯一性」约束 —— 已被别处占用时生成失败并 `push_warning` |
| 与 `spawn_placements` 的区别 | 后者是「只认盒子」，会**替换**本房编成 |
| 与 `encounter` 的区别 | 后者是触发式遭遇，同样**替换**本房编成 |
| 与改成 `ELITE` 房型的区别 | 那会让整房变成精英房，普通战斗消失 |

**跨文件契约（缺一环 = 静默失效，不打日志）**：

| # | 落点 | 作用 |
|---|---|---|
| 1 | `art_source/.../<level>/v<NNN>/data/floors/*.json` | 设计源声明（`data/level_plans/` 只是投影） |
| 2 | `LevelPlanLoader.normalize_floor` | **白名单重建**，登记 `elite_id` |
| 3 | `FloorPlanGenerator.room_from_source` + flow 装配白名单 | 出口白名单，登记 `elite_id` |
| 4 | `Dungeon3D` / `TowerDescent3D` 的房间 `configure` | 透传到 `DungeonRoom3D.elite_id` |
| 5 | `Dungeon3D._commit_room_waves` | 消费：追加进第一波（唯一提交点） |

> **不要放在 `_spawn_room_enemies` 的房型分支里**：那个函数有四条早退
> （触发遭遇 / 和平区 / 只认盒子 / 无盒子不刷），走任意一条都到不了追加代码。
> 实测 `room_01` 就走盒子路径。

门禁：`verify_expedition99_pre_boss_elite`（契约）+ `probe_expedition99_pre_boss_elite`（真实场景出怪）。

### 3.2 唯一的合法写法

**定义一个语义化判据方法，全文件只在这一处判断，其余地方调用它。**

范例（`Dungeon3D.uses_dynamic_fate_economy`）：

```gdscript
## **唯一判据**：本局是否使用关卡级动态命运经济。
## 只看能力，不看关卡 ID。
func uses_dynamic_fate_economy() -> bool:
	return _fate_economy.is_configured()
```

消费方一律：

```gdscript
if uses_dynamic_fate_economy():
	...
```

### 3.3 明确禁止的写法

```gdscript
# ❌ 禁止：关卡 ID 出现在通用机制里
if get_runtime_map_id() == "expedition_01": ...
if get_expedition_level_id() == "expedition_02": ...
if level_id != "expedition_01": return
match get_expedition_level_id():
	"expedition_01": ...
	"expedition_02": ...
```

**加关卡时如果发现需要往通用机制里加 `== "expedition_0N"`，先停手，问一句：这是能力差异还是内容差异？**

- 能力差异（这关有没有这个系统）→ 用能力判据，或让数据段留空
- 内容差异（这关的数值/美术/布局不同）→ 走 §4

### 3.4 校验方式

新增关卡前跑一次：

```
grep -n 'expedition_0[0-9]' src/world3d/Dungeon3D.gd
```

**只应命中注释。** 命中活代码即视为违规，拒绝提交。

## 4. 关卡专属内容：允许按 ID 分支，但必须收口

### 4.1 属于「关卡专属内容」的清单

| 内容 | 现落在 | 现状 |
|---|---|---|
| 出生点偏移 | `TowerDescent3D._expedition_entry_spawn_offset` | 01 / 03 = 房心；其余 = 朝前门偏 4 m |
| 关卡整体朝向 | `_expedition_rotation_for_checkpoint` | 01 = 180°（北向版），其余 0° |
| 检查点布局校验 | `_expedition_checkpoint_layout_matches` | 仅 01 校验旋转 |
| 相机档案 | `_expedition_02_camera_profile_for_spec` | 02 专属 |
| 氛围（远景暗部） | 建氛围时 `expedition_02` 分支 | 02 专属 |
| 静态布局归属判定 | `_bind_shared_edge_doors` 附近 | 02 专属路径 |

这些是**真实的内容差异**，不是缺陷。每关的出生点、朝向、相机、氛围本来就应该不同。

### 4.2 三条硬约束

| # | 约束 | 理由 |
|---|---|---|
| **C1** | 每个分支必须有注释说明**为什么这关特殊**，以及**新关卡默认走哪一支** | 否则下一个人不知道是"默认值"还是"忘了" |
| **C2** | 分支必须**收口在单一函数**内，不许散落在调用点 | 分散 = 加第三关时要找 N 个地方 |
| **C3** | 必须提供**明确默认分支**，新关卡未声明时落到默认，不许报错或空值 | 否则加关卡要先改代码才能跑 |

范例（合规）：

```gdscript
## 各远征关卡的入口出生偏移。
## 01 / 03 = 房心（安全房的中央那批固定陈设已按需求拿掉，落点不再与它们重叠）。
## 其余关卡（含后续新增）= 朝前门方向偏 4 m —— 这是**默认值**，新关卡不写即可用。
func _expedition_entry_spawn_offset(entry_room: DungeonRoom3D) -> Vector3:
	if get_expedition_level_id() in ["expedition_01", "expedition_03"]:
		return Vector3(0.0, 0.05, 0.0)
	return { ... }.get(front, Vector3(0.0, 0.05, 0.0))
```

### 4.3 中期目标（不必现在做）

把 §4.1 的表从 `if/else` 迁成**数据驱动**：关卡在 `level_plan.json` 里声明 `presentation` 段（出生偏移、朝向、相机档案 ID、氛围 ID），代码只读数据。

在那之前，按 C1–C3 收口即可。**不要为了架构漂亮先做大重构**——这些分支目前只有 6 处，收口成本远低于迁移成本。

## 5. 新增关卡的标准流程

### 第 1 步：建数据层（零冲突）

```
data/level_plans/<level_id>/
├── level_plan.json          # 必须含 generation_policy.runtime_enabled = true
├── floors/floor_00.json     # 房间表
├── room_templates/
└── validation/
scenes/ExpeditionLevel0N_3D.tscn   # 声明 expedition_run_id / expedition_plan_id
```

`level_plan.json` 的必备段：

| 段 | 缺了会怎样 |
|---|---|
| `level_id` | 加载器找不到目录 |
| `generation_policy.runtime_enabled: true` | 回退内置房表，你的设计源被忽略 |
| `floors[]` | 无房间 |
| `monster_rules` | 全部回退全局常量（不报错，但你这关没有专属数值） |
| `monster_drop_table` | 无本关掉落表 |
| `monster_rules.currency` | 无货币掉落（不报错） |

### 第 2 步：补齐终局

**这是远征 02 当前的缺口，也是最容易被漏的一步。**

远征关卡必须有：

| 房间类型 | 作用 | 缺失后果 |
|---|---|---|
| `SAFE_ROOM` | 入口 | 出生点无处可放 |
| `COMMON_ROOM` × N | 内容 | — |
| `BOSS_ROOM` | 终局挑战 | **打完无处可去，关卡没有终点** |
| `EXTRACTION_ROOM` | 撤离 | 无法结算离场 |

校验方式：

```
python -c "import json;d=json.load(open('data/level_plans/<id>/floors/floor_00.json',encoding='utf-8'));print({r['room_type'] for r in d['rooms']})"
```

输出必须同时含 `BOSS_ROOM` 与 `EXTRACTION_ROOM`。

### 第 3 步：确认不用改核心层

对照 §3.1 清单逐项检查。**能靠数据段留空 / 填值解决的，不许改代码。**

### 第 4 步：登记

| 文件 | 动作 |
|---|---|
| `docs/v0.1/design/远征关卡0N设计.md` | 关卡设计页 |
| `docs/v0.1/12_全游戏完成度清单.md` | 追加条目 |
| `docs/v0.1/MODULE_INDEX.md` | 追加功能行（若新增 FeatureID） |
| `docs/v0.1/development/CHANGELOG.md` | 交付记录 |
| 场景账本 | 新增房间静态布局资产时登记 |

### 第 5 步：验收

必须跑，缺一不可：

| 验收 | 证明什么 |
|---|---|
| `verify_expedition_level0N_flow` | 本关能起、布局合法 |
| `verify_fate_economy_service` | 逐门定价通了（**证明 §3 的解耦没有失效**） |
| `verify_expedition_level01_flow` | **旧关卡没被弄坏**（新增关卡必须跑） |
| `check_documentation_contracts.py` | 文档链接与功能行完整 |

## 6. 并行开发的分工边界

三条线同时开工时的文件归属：

| 文件 | 允许谁改 | 冲突处理 |
|---|---|---|
| `data/level_plans/expedition_01/**` | 01 线 | 独占，零冲突 |
| `data/level_plans/expedition_02/**` | 02 线 | 独占，零冲突 |
| `src/world3d/Dungeon3D.gd` | **共享** | 改不同函数可自动合；改同一函数必须串行 |
| `src/world3d/TowerDescent3D.gd` | **共享** | 同上 |
| 天台/基地资产与 `TowerFloorStage3D.gd` | 天台线 | 与远征线零交集 |
| 登记文件 5 个 | 共享 | 末段一次性补，或按 §7 拆 |

**`Dungeon3D.gd` 是 398 KB 的单文件，是并行开发的主要风险点。** 约定：

- 01 线改**房间装配段**（约 L2600 起）
- 02 线改**经济与配置段**（约 L1500–1600）
- 谁要改对方的段，先在这一轮交付说明里写一句
