## 1. 问题陈述：四处断层

### 1.1 真源倒置 —— 白盒是代码的派生物

| 证据 | 位置 | 说明 |
|---|---|---|
| `"source": "src/map/FloorPlanGenerator.gd"` | `.../battle_level01/v003/data/unit_plan.json:2` | 白盒清单自述来源是运行时代码 |
| `ROOM_LAYOUT = {...}` | `scripts/blender/build_battle_level01_whitebox_v003.py:44` | 手抄一份 `{key: {center, size}}`，与 `FloorPlanGenerator._normal_rooms()` 的 `position/dimensions` 重复 |
| `CONNECTIONS` | 同文件 `:66` | 再抄一份父子边，与 `_room(..., parent_key)` 重复 |
| `"Mirror TowerDescent3D's 5m lane choice for same-axis room links."` | 同文件 `_nearest_runtime_lane()` docstring | 门槽算法是**跨语言手工镜像**，无任何断言 |
| `boss_size_override_m / boss_code_size_m / sync_required` | `unit_plan.json:81-93` | 漂移已发生：白盒 Boss `190×90` vs 代码 `90×90`，用三个字段承认 |

**后果：** 任何一侧独立修改都会静默产生不一致；Boss 尺寸冲突已经暴露，且按重建方案 §9.1.2 需上级裁决。

### 1.2 白盒缺「层」与「朝向」维度

- `ROOM_LAYOUT` 只有 98F 的 east 入口 / north_ring 一个朝向（`entry` 中心 `(27.5, 2.5)`）。
- 四层战斗层（98/97/96/95）共用这一份骨架：98F 与 96F 旋转步数均为 0 → **几何完全相同**；97F 是其 180° 旋转。
- 白盒侧无法表达「这一层入口在西侧」，只能等代码旋转后再反推。

### 1.3 白盒缺「房间模板」概念

现有 17 份房间白盒（日志口径：19 文件 = 17 房 + 2 走廊组件）是**按位置逐间做的**。但按尺寸归并后只有 7 类：

| 模板尺寸 | 占用房间位 | 数量 |
|---|---|---|
| 15×15 | entry, exit | 2 |
| 30×25 | hub, main_02/03/04/06/07/10, branch_01/02/04 | 10 |
| 30×40 | main_05 | 1 |
| 35×30 | main_08 | 1 |
| 40×25 | main_09 | 1 |
| 40×35 | branch_03 | 1 |
| 190×90 | boss | 1 |

10 个 30×25 的房间位理论上需要 10 份布局，但美术价值上 3–4 个轮换已足够。当前既没有「模板」身份，也没有「变体池」概念，导致美术量按位置线性膨胀。

### 1.4 消费端硬编码、通用装配器不存在

- `src/world3d/DungeonRoom3D.gd:287-290` 的 `BATTLE_LAYOUTS` 是**硬编码字典**，仅 4 条：`floor_01_hub` / `floor_01_main_02` / `floor_01_main_03` / `floor_01_main_04`。
- 全仓库**不存在** `RoomLayoutAssembler3D`（违反 `00-battle-room-layout-assembler` §7「首次执行必须补齐通用装配基础设施」、§8「禁止把房间特例继续堆入 `DungeonRoom3D.gd`」）。
- 97F/96F/95F 仍走 `DungeonRoom3D._build_tower_wall_v2()` 旧程序化墙体。
- 已实测的连带故障（见审计报告 P02）：seed2 / north_ring 下 hub 计划门为 south+east，固定布局为 north+east，**实际只生成 east 一扇游戏门** —— 固定布局 + 随机变体不匹配的真实断门。

### 1.5 附带事实：文档描述的是另一套算法

`docs/v0.1/05` §5.2「几何生成顺序」写的「在 5m 占用网格上生成自避交主路骨架 / 沿骨架放置 N_main 个实际房间外框」= 程序化生成；§7 写了 `FloorGenerationRequest` / `attempt_salt` / `floor_rule_version`；§11 的 `FloorPlan` 契约含 `corridor_records / structural_reservations / encounter_slots / loot_slots / generation_transaction_id`。

实际实现是常量表 + 镜像/旋转/洗牌，上述字段多数**不存在**。§12 的 `[x]` 验收项沿用旧口径，不代表 §5.2 属实。本次重构需要同时裁定：**是让实现追上文档，还是让文档降级到实现。**

## 2. 目标架构：真源倒置

```text
                 ┌─────────────────────────────────────────┐
                 │  设计真源（新）：白盒版图层               │
                 │  level_plan.json                         │
                 │  floors/floor_NN.json                    │
                 │  room_templates/<template_id>.json       │
                 └────────────┬────────────────────────────┘
                              │  单一事实来源，手写 + 校验
              ┌───────────────┴────────────────┐
              │                                │
              ▼ (A) 美术链路                    ▼ (B) 玩法链路
    房间种类源 → 组件库 → 房间布局        确定性生成器
    → room_layout.json → Godot 重放      → FloorPlan → 房间/走廊/门/存档
    （归重建方案八阶段）                  （归本文 §4–§6）
```

两条链**共享同一份房间身份与门槽契约**（`room_id` / `ports[].lane_m`），由白盒版图唯一定义：

- (A) 只回答「这个模板长什么样」——不决定它出现在哪一层、哪个位置。
- (B) 只回答「这一层用哪些模板、怎么连」——不决定模板内部的组件摆位。

**判据：** 任一方向不得反向写回。生成器不得改写白盒 JSON；美术布局不得添加白盒未声明的门。

## 3. 白盒版图规范

### 3.1 三层文件与所有权

```text
source/art/whitebox/tower_zones/battle_level01/v###/data/
├─ level_plan.json                     # L1 关卡级：层清单、生成规则版本
├─ floors/floor_98.json                # L2 层级：房间表 + 连接 + 保留区（新增，取代手抄 ROOM_LAYOUT）
├─ floors/floor_97.json
├─ ...
├─ room_templates/<template_id>.json   # L3 房间模板：尺寸 + 可开门墙 + 槽位 + 变体登记
└─ component_packages/**/asset_manifest.json   # 既有：白盒组件包（保留，L3 引用它）
```

| 层 | 所有权 | 禁止 |
|---|---|---|
| L1 | 关卡设计 / 玩法 | 出现具体房间坐标 |
| L2 | 关卡设计 / 玩法 | 出现组件 ID、材质、视觉描述 |
| L3 | 场景美术 | 出现层号、层内位置、连接目标 |

```json
{

  "core": { "size_m": [65.0, 65.0], "center_m": [2.5, 2.5] },
  "floors": [
    { "floor_number": 98, "floor_index": 2, "sequence_index": 1,
      "rule": "normal", "plan": "floors/floor_98.json" },
    { "floor_number": 95, "floor_index": 5, "sequence_index": 4,
      "rule": "boss", "plan": "floors/floor_95.json" }
  ],

  "generation_policy": {

    "target_occupancy_ratio": 0.42,
    "reference_room_cost_m2": 1450.0,
    "enforce_area_budget": true
  }

```

`generation_policy` 里**逐关可覆写**的两个键（缺省即塔楼口径，行为与不写时逐位一致）：

- `target_occupancy_ratio`：覆盖面积预算的占用率上限（`LevelAreaBudget.TARGET_OCCUPANCY_RATIO`）。越界值（`≤0` 或 `>1`）落回常量。
- `enforce_area_budget`：**可否决面积判定**。置 `false` 时 `LevelPlanValidator` 不再报 `area_budget_exceeded` —— 数字照算并落进 `plan.area_budget`（多一个 `area_budget_enforced` 键），只是不判定。**专供单层独立关卡**（远征01 用，见其设计页 §4.7）：单层没有「塔楼层数 × 每层面积」的平衡诉求，房型由设计页一一定死，总面积上限反而会卡住合法版图。塔楼各层**不得**置 `false`。

`room_type_targets` 吸收现有 `room_type_art_targets.json`；该文件保留但降级为 L1 的派生视图（或直接由 L1 生成，二选一，不得两处并存）。

### 3.3 L2 `floors/floor_NN.json`（核心）

这是**取代手抄 `ROOM_LAYOUT` + `CONNECTIONS` 的那一份**。

```json

  "schema_version": 1,
  "level_id": "battle_level01",
  "floor_number": 98,

  "sequence_index": 1,
  "entry_side": "east",

  "rooms": [
    {
      "key": "hub",
      "room_type": "COMMON_ROOM",
      "role": "hub",
      "parent_key": "entry",

      "template_variant": "a",

        { "port_id": "P2", "target": "main_02", "side": "east",  "lane_m": 0.0 }

      "enemy_spawn_plan": {
        "waves": [
          { "monsters": [ { "type": "melee_chaser", "count": 2 },
                          { "type": "ranged_caster", "count": 1 } ] }

      }

    {
      "key": "boss",

      "center_m": [0.0, 0.0],
      "size_m": [35.0, 35.0],
      "ports": [
        { "port_id": "P1", "target": "hub", "side": "north", "lane_m": 0.0 }
      ]
    }
  ],
  "main_path": ["entry", "hub", "main_02", "..."],
  "edge_policy": [
    { "a": "boss", "b": "boss_exit", "allow_zero_length": true,
      "reason": "boss arena shares a wall with the exit lobby" }
  ]

```

**关键点：**

1. `ports[].lane_m` 是**数据不是算法**。GDScript 侧只校验不推导（见 §3.5），从根上消除 `Mirror TowerDescent3D's 5m lane choice` 这类跨语言镜像。
2. `room_id` 由 `floor_index` + `key` 规范化生成，规则唯一（见 §7.1）；白盒不写运行时 ID，避免路径与显示层号混用。
3. `edge_policy` 把现行代码里的唯一特例（Boss→stair_exit 共墙 0 长度，`FloorPlanGenerator._edge_is_buildable()` 第 388-392 行）从代码搬进数据。
4. `reservations` 把现行 `_stair_reservation_rect()` 的 `20×30m`（`STAIR_RESERVATION_OUTWARD_M` / `_TANGENT_M`）显式化。
5. **房间级刷怪计划 `enemy_spawn_plan`（可选）。** 写了就由设计源全量接管**这一间房**的
   波次数 / 每波数量 / 怪物组合；不写 = 该房继续走引擎全局公式，这是默认行为。
   单只怪的**数值**（血量 / 伤害 / 速度）仍由 `MonsterInjector` 出，设计源只写「要谁、几只」，
   避免两份数值真源。硬上限：波数 ≤ 6、单波总数 ≤ 24、全房总数 ≤ 64。
   `monsters[].type` 只能取 `MonsterInjector.BASE_ENEMY_TYPES` 去掉 `boss` 的 6 个值
   （`melee_chaser` / `ranged_caster` / `summoner` / `shielded` / `exploder` / `ambusher`）。
   **房型限制走唯一口径 `GameDesignConfig.is_spawn_plan_authorable_room(content_type)`**
   —— 即房型属于 `ROOM_TYPES_WITH_HOSTILES` **且不是 `BOSS`**。填在永不调用刷怪入口的房上报
   `enemy_spawn_plan_on_non_hostile_room`；填在 Boss 房上报 `enemy_spawn_plan_on_boss_room`
   （Boss 房不是「不刷怪」，而是**不归设计源管**：写在这里会让刷怪入口跳过 boss 生成，
   表现为「Boss 房没有 Boss」并可能锁死下楼门）。
6. **房间级首领指派 `boss_content_id`（可选）。** 只指定本 Boss 房出场的**是哪一个**首领，
   其余全部由名册 `BossContentCatalog` 决定（显示名 / 正式模型 / 竞技场 / 阶段技能袋 / 强调色）
   —— 设计源**绝不**写竞技场或技能袋，否则会与名册形成两份真源。
   当前可填 3 个：`boss_abyss_archivist_95`（95F）/ `boss_furnace_warden_90`（90F）/
   `boss_hollow_choir_85`（85F）。
   **解析走唯一口径 `BossContentCatalog.resolve_profile`：** ①写了就用它，层号取内容**固有层号**；
   ②没写则按房间所在层号取名册条目（塔楼 95/90/85 照旧）；③两层都取不到（**单层关卡没写**）
   → **本房不出 Boss**，这是**合法空房**，运行时清房放行、不报错；
   ④写了但名册里没有 → **什么也不出，且绝不静默换人**（静默替换会让作者看到自己没指定的首领）。
   校验错误码：`boss_content_id_on_non_boss_room`（填在非 Boss 房上）、
   `boss_content_id_unknown`（指向名册外内容）。
   **「Boss 房」判定口径是 `GameDesignConfig.is_boss_room(content_type, role)`** ——
   `content_type == "BOSS"` **或** `role == "boss"` 都算：生成器会把 `role == "boss"` 的房间
   钉成 `type = "BOSS"`，只写 `role` 的房间运行时照样是 Boss 房。
   ⚠️ 本字段**不进 `layout_id`**（`layout_id` 是存档指纹），故改它不会让既有存档失配。

### 3.5 门槽 lane 规范（必须写成公式）

现行规则（`build_battle_level01_whitebox_v003.py::_nearest_runtime_lane()` 与 `TowerDescent3D._door_lane_candidates()` 同构）：

```text
count      = round(wall_length / 5)                    # 墙上 5m 槽段数
candidates = [ -L/2 + 5*(i + 0.5) for i in range(first, last+1) ]
  first = 1            if count >= 3  else 0           # 首尾各留一段不贴角
  last  = count - 2    if count >= 3  else count - 1
nearest    = argmin(|candidate|)
```

实测结果（复核通过，与 03 skill 第 11 条一致）：

| 墙长 | count | 候选槽 | 最近槽 | 有无 0m 槽 |
|---|---|---|---|---|
| 15m | 3 | `0` | `0` | 有 |
| 25m | 5 | `-5, 0, +5` | `0` | 有 |
| 30m | 6 | `-7.5, -2.5, +2.5, +7.5` | `-2.5` | **无** |
| 35m | 7 | `-10, -5, 0, +5, +10` | `0` | 有 |
| 40m | 8 | `-12.5, -7.5, -2.5, +2.5, +7.5, +12.5` | `-2.5` | **无** |
| 190m | 38 | `…, -2.5, …` | `-2.5` | **无** |

**新规范约定：**

- `lane_m` 必须是上表候选值之一，且必须与目标房间对侧墙的候选值**共同满足同轴**（两侧 lane 决定同一条走廊中心线）。
- 运行时不再自行推导 lane，只读 `ports[].lane_m`；推导只发生在 L2 生成/校验工具里。
- 跨语言一致性由一条断言盯住：`tools/` 下的校验器读 L3 `wall_lane_table`，GDScript 侧读同一文件比对——**不允许两边各有一份实现**。

### 3.6 房间模板可拼性约束

要让生成器自由拼接，模板必须满足：

1. `size_m` 的两个分量都是 5m 整数倍。**现有全部满足**（15 / 25 / 30 / 35 / 40 / 90 / 190）。
2. 门只能开在 `openable_walls` 声明的墙上，`lane_m` ∈ 该墙 `wall_lane_table`。
3. 模板不得依赖「另一侧是谁」；门侧与 lane 由 L2 的 `ports` 决定，模板只提供候选集合。
4. `template_rotation_deg ∈ {0, 90, 180, 270}`；奇数步旋转时 `size_m` 的两个分量交换，L2 必须写交换后的实际尺寸。
5. 内部布局随 `template_variant` 变化，但 `wall_lane_table` 与 `door_contract` 在变体间必须一致——否则该变体应升级为一个新模板。

### 3.7 走廊与保留区

**走廊不进入白盒声明**，由两端房间中心与尺寸推导，约束（沿用现行，写成公式）：

```text
corridor_clear = |Δalong| - (size_a.along/2 + size_b.along/2)   ≥ 5.0
lateral_offset = |Δlateral|                                     ≤ 5.01   # 必须同轴
segments       = round(door_to_door_distance / 5)                        # 必须整数
```

唯一例外（Boss→exit 共墙，`corridor_clear == 0`）必须写在 L2 `edge_policy`，不得写死在代码分支里。

保留区（不可建房）：
- 场地外边界：`|x| ≤ 125, |y| ≤ 125`（`MAP_SIZE_M = 250`）
- 核心区：65×65，中心 `(2.5, 2.5)`，安全房与楼梯大厅**不占用**但可位于其外
- 楼梯预留：`20×30m`（`STAIR_RESERVATION_OUTWARD_M=20` × `STAIR_RESERVATION_TANGENT_M=30`）
- 地面洞、门厅净空、角区：由 L1 `generation_policy` 的 `stair_and_utility_reserve`（现行 6500 m²）统一扣除

## 4. 生成范式（D1 已裁决：方案 3）

现状是「固定版图 + 表观随机」。三条重构路线：

### 方案 1 — 手绘版图库

白盒 = 一批手绘整层版图（如 8 张），生成器只做挑选 + 镜像 + 旋转。

| | |
|---|---|
| 优点 | 每张图都经过人工质量担保；走廊必为直线；房间美术可逐位定制；实现最简单 |
| 缺点 | 肉鸽感 = 版图张数；每加一层要重做一遍美术；10 个 30×25 房间位要 10 份布局 |
| 成本 | 美术量线性增长（每层 ≈ 17 房布局） |
| 适配现有资产 | 高（现有白盒直接可用） |

### 方案 2 — 纯程序化生成

生成器在 5m 网格上随机游走生成主路骨架，房间按尺寸从模板池取，走廊按真实门槽解析。

| | |
|---|---|
| 优点 | 真随机拓扑，重复度最低；房间美术量与层数解耦 |
| 缺点 | 需要模板覆盖所有「尺寸 × 门位组合」；走廊长度非整数、房间错位、面积超支都要靠重试收敛；调试成本最高 |
| 成本 | 美术量固定（7 类模板 × 变体池），但生成器实现与验证成本高 |
| 适配现有资产 | 中（模板已有，但门位需参数化） |

### 方案 3 — 白盒约束下的受约束随机（**推荐**）

L2 白盒**不写死某一层的房间位置**，而是写「这一层的骨架约束」：主路长度、支路区间、可用模板池、入口方位、保留区。生成器在这个约束内随机生成房间位置与连接。

折中做法：**保留 L2 为「手绘默认版图」**（保证最低质量与确定性验收），同时允许 `mode: "constrained"` 的层由生成器在约束内生成，两者产出**同一 schema**，走同一套校验。

| | |
|---|---|
| 优点 | 保留现有白盒作为「保底版图」不浪费；随机只在已声明约束内发生，不会生成不可玩布局；7 类模板覆盖 17 个房间位，美术量与层数解耦；`layout_id` 仍可确定性复现 |
| 缺点 | 生成器与校验器都要实装；需要同时维护「手绘默认图」与「生成图」两条路径的验收 |
| 成本 | 一次性的生成器 + 校验器投入；之后每层美术成本 ≈ 0 |
| 适配现有资产 | 高 |

**推荐理由：** 现有 17 份白盒的表达能力已经是「尺寸 + 门槽 + 槽位」，只差把「位置固定」改成「位置由约束生成」。方案 3 等于把现有白盒从「版图」升格为「模板池 + 约束」，增量最小、可回退（出问题就把 `mode` 退回 `"authored"` 走手绘版图）。

## 5. 受约束随机的作用域

**随机（可复现，种子 = `run_seed ^ (floor_number << 17) ^ (sequence_index << 9) ^ (attempt * 7919)`）：**

| # | 随机项 | 自由度 | 备注 |
|---|---|---|---|
| 1 | 支路接入点位置 | 主路 20%–80% 区间内选点 | 取代现行固定 `main_03` / `main_09` |
| 2 | 支路条数与长度 | 2–5 条 × 1–4 房 | 受面积预算约束 |
| 3 | 房间模板变体选择 | 池内均匀 | 决定视觉重复度 |
| 4 | 房间模板旋转 | 0/90/180/270 | 受模板 `openable_walls` 与门位约束 |
| 5 | 内容类型分配 | 现有 `CONTENT_TYPES` 洗牌 | 保留现行行为 |
| 6 | 房间中心 ±1 格抖动（可选） | -5/0/+5 m | 必须过 5m 整数、不重叠、走廊整数段校验 |

**不随机（硬约束）：**

- 层数、层号、`floor_index`、入口/出口方位
- 主路内容房下界 ≥ 10（`min_main_content_rooms`）
- 面积预算：占用率 0.42、参考成本 1450 m²/间、内容房目标数 clamp 14–16
  （占用率可被 L1 `target_occupancy_ratio` 覆写；**单层独立关卡**可置 `enforce_area_budget: false` 整体放开，见 §3.2 —— 塔楼各层不得放开）
- Boss 层规则（`floor_number % 5 == 0`）、Boss 不可绕过、整备房与 Boss 之间无钥匙锁
- 楼梯/电梯唯一性（95→94 唯一电梯）
- 保留区与核心区不可占用
- 走廊同轴性与 ≥5m 净距

**重试语义修正：** 现行实现里几何不读 rng，24 次重试实际只有镜像两种几何（另外 22 次是重复）。新生成器下重试将真正在不同拓扑间试探；`attempt` 必须先减少支路数与大型房数量，再降低随机抖动幅度，**不得降低 10 房主路下界**。

## 7. 房间身份、确定性、兼容与迁移

### 7.1 `room_id` 规则（必须统一，现状混乱）

现状：`FloorPlanGenerator._normal_rooms(sequence_index)` 用 `prefix = "floor_%02d" % sequence_index`，`sequence_index = 99 - floor_number`；而 `physical_floor_index = sequence_index + 1`。

```text
98F → sequence_index 1 → room_id "floor_01_hub"  → floor_index 2   ← 名字里的 01 与实际层索引 2 不一致
```

`BATTLE_LAYOUTS` 的 `floor_01_*` 正是这个错位的产物。

**新规范：** `room_id = "f%02d_%s" % [floor_number, key]`，例如 `f98_hub`、`f97_main_02`。`floor_number` 是显示层号（98/97/96/95），无歧义。

**兼容：** 旧档按 `room_progress` 的 room_id 字符串索引（`TowerDescent3D.gd:4795-4814`）。改 ID 规则会使旧档房间进度全部丢失。处置见 §7.3。

### 7.2 `layout_id` 公式冻结

现行：`layout_id = "floor_%d_%s" % [floor_number, str(abs(hash(layout_identity)))]`，`layout_identity = "seed:floor:attempt:entry_side:boss|normal:variant"`。

存档按 `floor_layout_ids[floor_index]` 与 `layout_id` 比对，**不一致直接 `return false` 整档恢复失败**（`TowerDescent3D.gd:4786-4792`）。

**新规范：** `layout_id = "f%02d_%s" % [floor_number, sha256(canonical_plan_json).substr(0, 16)]`，其中 `canonical_plan_json` 只含语义字段（room key / template_id / variant / center / size / rotation / ports），**排除时间戳与哈希顺序**。同一 L2 + 同一种子必须得到同一 `layout_id`。

`floor_rule_version` 一并进 `layout_id`，使规则升级后的档可识别而非静默失败。

### 7.3 迁移策略（推荐：兼容读 + 新写）

| 层 | 策略 |
|---|---|
| 存档 | 读旧档时按 `floor_rule_version` 缺失 = `1`（旧公式）解析；新写一律 `2`。旧档不迁移、不重算，读入后按旧 layout_id 校验通过即继续 |
| `room_progress` | 读旧档时按 `floor_01_hub` → `f98_hub` 的**显式映射表**转换（映射表是常量，可单测）；不做模糊匹配 |
| 美术布局（(A) 链路） | 现有 4 个 `floor_01_*` 布局按新 ID 重新登记，不重建源文件 |
| `BATTLE_LAYOUTS` 硬编码 | 由 `RoomLayoutAssembler3D` + 注册表取代（`00` skill §7），注册表由 L3 `variants[].room_layout` 生成 |
| 旧塔楼路线 | **冻结**，继续规划到 85F，继续走旧 `_build_tower_wall_v2()`；新链路只服务远征关卡 |

### 7.4 远征关卡单层化（已落地 2026-09-19）

`docs/v0.1/05` §12.1 原登记待施工项「独立关卡为单层，只生成一层完整关卡，不向下逐层」**已完成**。落地形态与本规范 L1 表达一致：只列一层，`mode = "expedition"`、`terminal_mode = "extraction_room"`，不生成下行楼梯与 95→94 电梯；终局由撤离房间 + 唯一不可拾取撤离信标承担。

### 7.5 远征关卡运行时包络与「干净场景」契约（已落地 2026-09-19）

单层关卡的唯一层 `floor_index` 也是 0，天然与 100F 天台撞号。因此运行时有两道**必须显式声明**的开关，缺一即回归成「房间没有阻挡」或「隐形挡墙」：

| 开关 | 载体 | 取值 | 漏掉会怎样 |
|---|---|---|---|
| `force_standard_map` | `TowerFloorStage3D.configure()` 第 5 参 | 远征恒 `true` | 继承天台窄轮廓 `Rect2(-50,-35,90,80)` + 99F 中庭洞 + 0.75m 女儿墙 → 6/7 房无承重楼面与外墙，玩家踩空 |
| `content_bounds` | `configure()` 第 6 参 | 远征 = 7 房包围盒外扩一格（5m）并对齐 5m 网格，实测 `Rect2(-10,-50,135,70)`（27×14 格） | 楼面/外墙铺满 250×250，远处空地上立着一圈没有内容的墙；地砖数与节点数虚高（2500 → 369 地砖、2744 → 1544 节点） |

外圈墙**可视高度必须等于碰撞高度**：`_outer_visual_transform()` 的 0.5 纵向缩放只允许挂在 `_uses_rooftop_profile()` 上（真正的 100F 天台女儿墙 1.50m → 0.75m）。裁决值写入快照 `outer_visual_scale_y`，门禁断言远征恒 `1.0`。

「干净场景」= 只保留基础玩法逻辑与关卡本身。远征必须做到：

1. `Blocks/Base/Art`（99F 基地美术，约 1200 节点）**整棵从场景树移除**（`remove_child` + `queue_free`），不是 `visible = false` —— 后者碰撞体仍留在 y≈0 的行走平面上；同时清空 `Blocks/Base` 声明的 `asset_ids` / `source_blends`。
2. 水平走廊挂 `Blocks/Expedition`（经 `_connector_block()`），不挂塔楼的 `Blocks/Battle`。
3. `Blocks/Rooftop|Base|Battle|Stairs` 在远征中**子节点为 0**（空容器保留：`_block()` 依赖它们存在，删除会波及塔楼共用代码）。
4. 垂直楼梯走廊**不**改走 `_connector_block()`：它只在塔楼生成，而该方法在塔楼返回 `Blocks/Battle`，改了会把楼梯走廊挪出 `Blocks/Stairs`。

门禁：`verify_expedition_level01_flow` 的 `_verify_level_enclosure()`（包络）+ `_verify_clean_scene()`（干净场景），判据 `EXPEDITION_LEVEL01_FLOW_OK`。

> ⚠️ **本节数值随房型表变化 —— 改版图必须连改。** `content_bounds` 的实测值 `Rect2(-10,-50,135,70)` 是按**当前 7 房包围盒**外扩一格算出来的；[远征关卡01 设计](design/远征关卡01设计.md) 的 9 房型包络为 **210×170m**，一旦落设计源，这个 `Rect2` 与门禁快照 `outer_visual_scale_y` 都要重算并同步。`force_standard_map=true` 与「外圈墙可视高度 = 碰撞高度」两条与该尺寸无关，继续有效。

### 8.1 S2 取证发现：S1 导出的门侧曾整体反向（已修复）

S2 的断言第一次跑起来就抓到一个真缺陷：**`battle_level01/v004/data/floors/floor_98.json`
里 7 处南/北门侧全部写反**，东西向门侧与全部 `lane_m` 都是对的。

根因是 `RoomDoorLane.port_pair()` 的南北约定写反：

```text
平面 +y  →  世界 +z  →  south（南）      ← 唯一正确约定
```

依据：`TowerDescent3D._plan_world_position()`（`Vector3(x, -层高, y)`）
+ `Dungeon3D._direction_between()`（`delta.z >= 0 → "south"`）。
原实现写作 `delta.y >= 0 → "north"`，与这两处都相反。

**为什么当时没被发现：** 门侧写反**不会让任何几何校验失败** —— `lane_m`、房间矩形、
走廊净距全部照旧通过。S1 导出时 `port_pair` 没有消费者，所以这份错数据安静地落了盘，
直到 S2 把它与几何推导摆在一起比对才暴露。

**处置：** 修正 `RoomDoorLane.port_pair()` 的南北分支，重跑 S1 导出工具重生成 v004
（`FLOOR_PLAN_WHITEBOX_EXPORT_OK floors=1 rooms=16 lanes_ok=30 templates=6`）。
重生成后 15 条父子边与推导零失配。**运行时不受影响** —— 运行时自己用
`_direction_between()` 判方位，不读白盒 `ports[].side`。

> 这条正是 §1.1 想根治的病：同一件事有两处实现（导出脚本 vs 运行时），
> 两侧无断言盯住，就可以长期静默分叉。现在 `port_derivation_mismatch` 是那条断言。

### 8.2 S3 取证发现：功能房的类型曾整批丢失（已修复）

给 S3 的接缝补护栏时，把「按设计源生成」与「内置生成器」的产出摆在一起逐字段比对，
抓到第二个隐形缺陷：**功能房（入口 / 出口楼梯厅 / 撤离房 / Boss）的 `type` 全被产成空串。**

| role | 内置房表写死值 | 数据驱动路径曾产出 |
|---|---|---|
| `stair_entry` | `STAIR_LOBBY` | 空 |
| `stair_exit` | `STAIR_LOBBY` | 空 |
| `extraction` | `EXTRACTION` | 空 |
| `boss_prep` | `UPGRADE` | 曾被误赋 `BOSS` |

连带一处计数错误：`content_room_count` 曾算成 6（内置远征硬编码 `EXPEDITION_ROOM_COUNT = 5`），
因为它只排除了 `stair_entry` / `stair_exit`，漏排 `extraction`。

**根因：** `type` 在内置路径里是 `_room()` 调用时**写死的常量**，只在 `_shuffle_content_types()`
里对「内容房」做覆盖 —— 功能房的类型从来不来自洗牌，而是房表常量。数据驱动路径只实现了
「洗牌 + 排除功能房」，没有实现「功能房的类型缺省值」，于是这些房间失去了身份。

**为什么静态校验抓不到：** 这几个 `type` 既不在设计源 schema 里（设计源的 `content_type` 是
可选覆盖字段，缺省为空是合法状态），也不参与任何几何校验。实测此缺陷下
`LEVEL_PLAN_VALIDATE_OK` 照样全绿、生成器也照样 `valid = true`。

**处置：**
1. `FloorPlanGenerator._default_type_for_role()` 新增功能房 role → type 的缺省映射，
   口径与内置房表**逐值一致**；设计源显式写了 `content_type` 时仍以设计源为准（钉死优先）。
2. `FUNCTIONAL_ROLES` 常量集中定义，`content_room_count` 改为排除全部功能房。
3. `tests/verification/verify_level_plan_design_source.gd` 新增**运行时产出护栏**
   （`_verify_runtime_outputs`）：直接调生成器，逐房断言功能房 type 命中期望值、
   内容房 type 非空且不是功能类型、尺寸非零、`content_room_count` 与实际相符。

**判据：** `LEVEL_PLAN_RUNTIME_GUARD_OK levels=2 rooms=23 checks=2`

> 该行此后已扩为带**样本计数**的形式：
> `LEVEL_PLAN_RUNTIME_GUARD_OK levels=N rooms=R checks=K plans=P boss_ids=B rewards=W`
> —— 分别统计设计源里真的填了 `enemy_spawn_plan` / `boss_content_id` / `reward_plan`
> 的房间（或槽位）条数。任一计数为 0 时另打一行 `LEVEL_PLAN_RUNTIME_NOTE` 声明
> 「该字段暂无可比样本」，**避免 0 样本伪装成通过**；这类字段（当前没有关卡的
> 数据里写它）的透传由 `verify_test_level_99_flow` 的手写 patch 探针单独覆盖。

**负向测试已做：** 把 `_default_type_for_role("extraction")` 改成返回空串，
护栏立刻红掉 —— `LEVEL_PLAN_RUNTIME_ERROR expedition_01 floor 0 room extraction:
role=extraction 的 type 应为 EXTRACTION，实为 <空>`，而同一轮 `LEVEL_PLAN_VALIDATE_OK`
仍然通过。这恰好是本节的论点：**静态自洽 ≠ 产出可用**。

> 与 §8.1 同源：又是一条「不在 schema 里、过不了几何校验、只能靠断言盯住」的隐形契约。
> 凡是「运行时靠它认东西、但设计源不写它」的字段，都必须有一条会失败的断言。
