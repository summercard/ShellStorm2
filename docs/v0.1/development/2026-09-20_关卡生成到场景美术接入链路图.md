# 关卡生成 → 场景美术接入 · 全链路图

> 状态：`LEVEL-TO-ART-PIPELINE r2`（2026-09-20 · 增补设计段）
> 适用范围：ShellStorm2 塔楼战斗区块房间、远征单层独立关卡
> 目的：把「关卡怎么生成」「设计怎么定形」「房间怎么长出来」三条链画在一张图上，标出它们在哪衔接、在哪合体、以及哪些段已经落地、哪些还只是纸面设计。
> 上游文档：`docs/v0.1/development/2026-09-18_战局房间美术制成与导入链路.md`（讲 B 段的原口径）、`docs/v0.1/development/2026-09-17_3D资产正式制成链路总表.md`（只讲资产制成）。
> 对应 Skill：`scene-full-pipeline`（阶段 0–2 ＝ 本文 C 段）、`09-level-plan-authoring`（A 段）、`00`–`04` + `godot-model-asset-import-standard`（B 段）。

---

## 0. 一句话结论

**三段链、一处衔接、一处合体。**

| 链 | 回答的问题 | 输入 → 输出 | 唯一真源 |
|---|---|---|---|
| **A · 关卡生成** | 这间房**在哪、多大、几扇门、门开哪边、刷什么怪、出哪个 Boss** | 设计表 → 运行时计划 | 设计源 JSON（L1/L2/L3）+ `FloorPlanGenerator` |
| **C · 设计定形** | 这间房**该长成什么样子**（风格 / 材料感 / 构成密度） | 白盒 → 概念图 → Blender 源 | 概念图（定方向）+ 白盒（定尺寸） |
| **B · 场景美术接入** | 这间房**怎么变成可复用的运行资产** | Blender 源 → 稳定 PackedScene | 共享组件库 + 房间布局清单 |

- **A → C 衔接点** = 白盒。关卡数据在此脱掉玩法，只剩几何与视觉需求。
- **C → B 交接口** = **Blender 源文件**。分界线很清楚：**C 段管「想做成什么样」，B 段管「做成能反复用的资产」。**
- **A+B 合体点** = `DungeonRoom3D`（房间实例）。A 链给**入参**，B 链给**外观**。

> 为什么把设计单独拎成一段：它是**唯一一个「白盒给约束、概念图给方向、两者必须同时满足」的环节**。混进 A 段会把「尺寸来源」与「观感来源」搅在一起 —— 而这两者的真源本来就是分开的（见 §4 与 §8 红线 8）。

## 2. A 段 · 关卡生成链（09-level-plan-authoring）

| # | 动作 | 产物 / 落位 | 唯一真源 | 门禁判据 |
|---:|---|---|---|---|
| 1 | 发设计表，用户填第一部分 | 对话内 | `docs/v0.1/design/新关卡设计表.md` | — |
| 2 | 落 L1/L2/L3 | `source/art/whitebox/tower_zones/<level_id>/v001/data/` | 规范 `05.2` §3 | `LEVEL_PLAN_VALIDATE_OK` |
| 3 | 取门槽（**禁止手算**） | `PORT_JSON` 逐行输出 | `src/map/RoomDoorLane.gd` | `port_derivation_mismatch` |
| 4 | 静态校验 | `LevelPlanValidator` | — | `LEVEL_PLAN_VALIDATE_OK levels=1 rooms=…` |
| 5 | 生成运行时计划 | `FloorPlanGenerator.room_from_source` | — | `LEVEL_PLAN_RUNTIME_GUARD_OK … plans=N boss_ids=B rewards=W` |
| 6 | 登记为可玩关卡（仅单层） | `GameDesignConfig.EXPEDITION_LEVELS` | **唯一登记点** | `verify_<level>_flow` |
| 7 | 建独立场景 | `scenes/ExpeditionLevel<NN>_3D.tscn`（父 `scenes/Dungeon3D.tscn`，覆写 `script = TowerDescent3D.gd`；`Blocks` 下**只挂 Expedition**） | — | 场景断言 |
| 8 | 实例化房间 | `TowerDescent3D._instantiate_dynamic_room` → `DungeonRoom3D.configure` | — | `room.<字段>` 非空 |
| 9 | 刷怪 | `Dungeon3D._spawn_room_enemies()` | **唯一刷怪入口** | 逐值断言波次/数量 |

**L2 房间级可选字段（三个，都默认不填）：**

- `enemy_spawn_plan`：波次 / 每波数量 / 怪物组成。不填 → 走引擎全局公式（`desired = 4 + floor*2`、房型波次表、主题权重池）。上限：波数 ≤6、单波 ≤24、全房 ≤64。只能填在 `is_spawn_plan_authorable_room(content_type)` 为真的房上（BOSS 房不算）。
- `boss_content_id`：**只指定「是哪一个」首领**，其余归 `BossContentCatalog`。不填 = 塔楼按层号取（95/90/85）、**单层不出 Boss（合法空房）**。拼错 → 什么也不出，绝不静默换人。
- `reward_plan`：键 = 触发点（`clear` / `search` / `kill`），值 = 槽位引用（`{pool_id[,draws][,chance]}` 池简写 / `{spec_id}` 命名规格 / `{entries[,fallback]}` 内联，**三种写法只能选一种**）。不填 → 逐级回退（房间 > 关卡 > 怪物表 > 全局默认公式）。校验只强制 `kill` 的房型约束（`is_spawn_plan_authorable_room`，Boss 房禁止）；`clear` / `search` 写在永不触发事件的房上**不报错但等于白写**，见 `docs/v0.1/design/新关卡设计表.md` §1.9 的房型对照表。同时暴露为运时的 `plan.reward_slots[]`（`{slot_id, room_id, trigger, spec_id, ref}` 纯投影，**不进 `layout_id`**）。

**A 段必守的三条口径：**

1. 房间级字段是**四道白名单**，漏一道静默丢字段：`LevelPlanLoader.normalize_floor` → `FloorPlanGenerator.room_from_source` → `TowerDescent3D._append_plan_room_record` → **两处** `DungeonRoom3D.configure({...})`（`Dungeon3D._generate_layout` 与 `TowerDescent3D._instantiate_dynamic_room`）。
2. 远征关卡运行时**按字面量认房**：入口恒 `start`、撤离房恒 `extraction`、主路恒 `room_01…room_0N`。`f%02d_<key>` 是**塔楼层**的命名，套到远征会静默失效。
3. 功能房 `type`（`STAIR_LOBBY` / `EXTRACTION` / `BOSS` / `UPGRADE`）**不在设计源里**，由 `FloorPlanGenerator._default_type_for_role()` 给，靠 `LEVEL_PLAN_RUNTIME_GUARD_OK` 兜。

## 3. 桥 · 白盒反导出（A → C 的接口）

| 项 | 内容 |
|---|---|
| 工具 | `tools/whitebox/export_floor_plan_whitebox.gd` + `.tscn` |
| 性质 | **纯只读取证**：不改运行时文件，只在白盒目录写 JSON |
| 输入 | `FloorPlanGenerator` 的运行时版图 |
| 输出 | `source/art/whitebox/tower_zones/battle_level01/v004/data/` |
| 复用真源 | 门槽走 `RoomDoorLane`、网格对齐走 `TowerGeometry3D`、墙厚/层高/门洞契约读既有白盒 manifest（**不手抄几何常量**） |
| 判据 | `FLOOR_PLAN_WHITEBOX_EXPORT_OK floors=1 rooms=N lanes_ok=K templates=T` |
| 取证 | `docs/v0.1/development/2026-09-19_S1白盒版图反导出取证.md` |

这一层是**关卡数据变成美术输入**的唯一转换点：美术拿到的是白模（尺寸 / 门洞 / 连接 / 可走面），不是关卡规则。白盒同时也是 C 段第一步「出概念图」的构图底图，以及 C 段第二步「做 Blender 源」的尺寸真源。

## 4. C 段 · 设计定形（白盒 → 概念图 → Blender 源）

**这一段回答「这间房该长成什么样」，它不产出任何运行资产。** 出口是 Blender 源文件。

对应 `scene-full-pipeline` 的阶段 0（效果图 / 场景需求）、阶段 1（读取白模）、阶段 2（Blender 正式美术资产）。

### 4.1 第一步 · 白盒 → 概念图

| 项 | 内容 |
|---|---|
| 输入 | 白盒：`source/art/whitebox/tower_zones/<level_id>/v###/data/`（尺寸 / 门洞 / 连接 / 可走面）+ `renders/` 顶视图与**同机位无文字顶视图** |
| 再输入 | 需求文字、风格关键词、外部参考图 |
| 生成 | `$imagegen`（`scene-full-pipeline` 阶段 0 指定）。白盒顶视图作为**构图约束**喂进去，不是让模型自由发挥 |
| 输出 | 概念图 / 效果图：主全景 1 张 + 关键立面与近景各 1 张 + 1 张与顶视图同机位的构图对照 |
| 门禁 | ① 房型、门位、开间必须与白盒一致（数门、数墙段、量开间）；② 全程固定挂钩齐备：`block_id` / `floor_range` / `design_scope` / `scene_design_docs` / `asset_ledger` |

**红线 · 概念图不承载尺寸。**

尺寸的唯一真源是白盒与运行时探针，概念图只定**观感与构成**。这条口径在房间源 README 里已经写死（安全房 v007 原话："来源：运行时探针实测，非从旧模型或效果图反推"）。概念图与白盒冲突时，**永远改图、不改尺寸**。

### 4.2 第二步 · 概念图 → Blender 源

| 项 | 内容 |
|---|---|
| 输入 | **双输入**：概念图（定方向）+ 白盒（定尺寸）。两者都必须满足，冲突以白盒为准 |
| 产物 | 房间种类源；具体房间布局源在 B 段 03 做 |
| 落位（设计规范） | 房间种类：`assets/art/environments/tower_zones/<block_id>/source/room_types/<room_type>/v###/`<br>具体房间：`…/source/room_instances/<room_id>/v###/` |
| 落位（项目现状） | `room_types/` 目录尚未建立，历史落在兼容目录 `room_instances/entry_safe_room/v006,v007`、`main_room_02/v003` |
| Skill | `blender-game-prop-standard`（经 `01-battle-room-type-art-authoring` 实例化） |
| 交付 | 版本化 `.blend` + 房间 / 种类 manifest + `renders/` + 可拆解对象清单 + 范围锁定签名 + 美术验收记录 |

**渲染图命名惯例（项目实测）：**

```text
renders/
├─ 00_同镜头制作前.png        ← 可选，白盒 / 程序化状态同机位对照
├─ 01_参考全景.png            ← 概念图的落点，作为制作的参照
├─ 02_完整结构顶视.png
└─ 0N_<部位>近景.png          ← 逐部位近景（如 03_北墙柜组与核心近景）
```

**沿概念图制作时必须守住的三条：**

1. **尺寸与门洞由白盒给，不从概念图反推。** 墙中线、净空、门洞净宽净高、层高全部照白盒 / 探针。
2. **一个单元服务所有槽位与所有朝向。** 同族组件（实墙 / 门墙 / 门扇）的装饰在**槽位自身局部帧**里必须逐值相同，否则后续无法用「一个组件铺满一圈」。先例：安全房 v007 的 `qa/component_slot_uniformity.json`。
3. **材质四共享角色 + PaletteUV + 公共色盘外链**（`assets/art/shared/palette/设施低亮多巴胺色盘_10x10_512.png`）。展示相机、灯光、参考辅助对象不得进入游戏输出集合。

### 4.3 为什么这一段必须独立

| 若并入 A 段 | 若并入 B 段 |
|---|---|
| 会把「玩法规则」与「观感方向」混进同一份设计源，而二者的真源与变更节奏完全不同 | 会让「一次性视觉决策」提前固化进资产流水线；方向错了才发现，返工要重走导入与台账 |

独立成段后，**C 段的产物随时可推翻重做**（只影响美术，不动关卡数据、不动已导入资产），这正是概念阶段该有的自由度。

## 5. B 段 · 场景美术接入链（02–04 + godot-model-asset-import-standard）

> 入口 = **C 段的出口**（通过验收的房间种类 Blender 源 / 具体房间源）。原大纲里的阶段 0（效果图）与阶段 1（房间种类源）已上移到 C 段，见 §4。

| 阶段 | 输入 | 产物 | 落位 | Skill |
|---|---|---|---|---|
| 2 | 房间种类源（已验收） | 共享组件源 + `component_catalog.json` + 各组件 `asset_manifest.json` | `…/source/common_components/v###/` | `02-battle-room-component-decomposer` |
| 3 | 组件 Blender 源 | GLB（稳定路径）+ PackedScene + 台账登记 | `…/components/<slug>/*.glb`、`…/runtime/common_components/<slug>/*_root_top3d.tscn` | `godot-model-asset-import-standard` |
| 4 | 具体房间白模 + 组件源 | 具体房间布局源 + `room_layout.json` | `…/source/room_instances/<room_id>/v###/` | `03-battle-room-instance-layout-authoring` |
| 5 | 布局清单 **或** 白盒 | 运行时房间 | `…/runtime/room_instances/<room_id>/` | `04-battle-room-runtime-assembler`（双分支） |

**阶段 5 的双分支：**

```text
分支 A  blender_layout_replay   : room_layout.json + 组件 AssetID 注册表 → 按 position/rotation/scale 重放
分支 B  whitebox_direct_assembly: 白盒尺寸/门洞/连接 + 组件 PackedScene → 生成基础结构布局
```

**B 段三条硬纪律：**

1. 组件只生产一次。房间文件**只存实例**（`instance_id` / `component_id` / 位置 / 旋转 / 启用），禁止 Append 复制共享 Mesh、禁止房间专用整屋 GLB。
2. `components/` 与 `runtime/` 路径**不带版本号**；替换 = 覆盖同路径同名文件。`v###` 只出现在 `source/`。
3. 任何新增环境 GLB：色盘 PNG **不嵌在 GLB 里**，`.import` 不绑 `tools/asset_pipeline/scene_facility_shared_palette_post_import.gd` → 白板且**不触发门禁**。判据：探针 `albedo_null=0`。

## 6. 合体点 · `DungeonRoom3D` 房间实例

这是三条链真正交汇的地方，也是排障时最该先看的一个类。A 链给**入参**；外观由 C 段定形、再经 B 段转成稳定 PackedScene 后送进来。

| 侧 | 提供什么 | 来源 |
|---|---|---|
| A 链（入参） | `room_id` / `room_type`(`content_type`) / `dimensions` / `ports`（门侧与 lane） / `enemy_spawn_plan` / `boss_content_id` | 运行时计划 record |
| C→B 链（外观） | 壳体 prefab 常量、房间包清单、设施与灯 | C 段的 Blender 源 → B 段的 `preload` 常量 + 包件安装 |

**壳体分支判据（写错会静默退化）：**

```text
room_type == "STAIR_LOBBY" 且 _can_build_safe_room_shell(dimensions)
  → 恰好 2 扇互相垂直的门 → _build_safe_room_shell()   ← v007 正式美术
  → 否则                 → _build_tower_wall_v2()      ← 程序化白盒，不报错
```

**运行时细节两层：**

- **壳体**（墙 / 门 / 地板 / 触发器）永久在场。
- **`RuntimeDetail`**（家具、危险区、地面标线、**灯与灯开关**）只在 `STREAM_ACTIVE`（= 玩家当前房）建，`DATA_ONLY` 时整棵 `queue_free`。⇒ 全场任何时刻只有 1 个灯开关；隔着门口看邻房永远看不到开关。

**已知的「静默退化」风险点（都不报错，只能靠断言盯）：**

| 风险 | 后果 | 盯着它的是 |
|---|---|---|
| 删掉远征「抵达侧封闭气门」（`door_targets` 里 `target=""`） | 安全房凑不满「2 扇互相垂直的门」→ 静默退化成程序化白盒 | `verify_expedition_level01_flow` |
| 房间级字段少接一处 `configure` | 房实例上字段为空 | 专属门禁断言 `room.<字段>` 非空 |

## 7. 现状对照：设计 vs 已落地（2026-09-20 实测）

| 环节 | 设计要求 | 项目现状 | 证据 |
|---|---|---|---|
| A 段 关卡生成 | 设计源 → 校验 → 运行时可玩 | ✅ **已落地** | `verify_level_plan_design_source` / `verify_expedition_level01_flow` / `verify_test_level_99_flow` 均在 `run_verification_suite.sh` 的 `core_scenes` |
| 白盒桥 | 运行时版图反导出白盒 | ✅ **已落地** | `tools/whitebox/export_floor_plan_whitebox.gd`；`battle_level01/v004/data/` 已导出 |

| C 段 · 概念图 → Blender 源 | 双输入（概念图 + 白盒）→ 房间源，落 `source/room_types/<room_type>/v###/` | ⚠️ **已发生，但落位偏离设计** | 安全房 `room_instances/entry_safe_room/v006,v007`、数据机房 `main_room_02/v003` 均已通过美术验收；`source/room_types/` 目录**未建立** |
| 02 共享组件库 | `source/common_components/v###/` + catalog + 包 manifest | ✅ **已落地** | `v001`–`v008` 均有 `component_catalog.json` + `component_packages_v###`（`v009` 为空目录） |
| 阶段 3 组件导入 | 稳定 GLB + PackedScene + 台账 + 色盘注入 | ✅ **已落地（6 类件）** | `runtime/common_components/`：`wall_standard_5m` / `wall_door_5m` / `door_5m` / `floor_tile_5m` / `floor_tile_r01_c01` / `floor_tile_r01_c02` |
| 03 具体房间布局清单 | `room_layout.json` | ❌ **全仓 0 个** | `find -name room_layout.json` 无结果。布局实际以 Blender 源 + `qa/slot_table.json` 形式存在 |
| 04 运行时装配器 | `RoomLayoutAssembler3D` 读布局重放 | ❌ **src 无此类** | 仅有文档与白盒导出工具提到；实际由 `DungeonRoom3D` 用 `preload` 常量 + `SAFE_ROOM_WALL_SLOTS` **手工抄表**接入 |
| 阶段 5 双分支路由 | `blender_layout_replay` / `whitebox_direct_assembly` | ⚠️ **纸面** | 两个 route 名无运行时实现；当前实际只有「常量直连」一条路 |

**结论：**

- **A 段 + 白盒桥 = 真实闭环**：有校验器、有产出守卫、有取证文档，三条门禁都在 `core_scenes` 里。
- **C 段 = 过程真实存在，产物不在档**：概念图只在对话里、不落盘；房间源确实做出来并通过了美术验收，但落位在兼容目录；这一段也是三段中唯一**没有门禁脚本**盯着的。
- **B 段 = 「常量直连」快车道**：美术件以稳定 PackedScene 存在、也被运行时消费，但 03 的 `room_layout.json` 与 04 的通用布局重放器都没落成；摆位写在 `DungeonRoom3D.gd` 的常量表里（先例：安全房 v007 的 `SAFE_ROOM_WALL_SLOTS`，逐项源自 `qa/slot_table.json`）。

⇒ 两个后果：

1. **概念图这一环不留档** ⇒ 同一个房间换人接手时，只能从 `.blend` 反推当初想做成什么，观感决策不可追溯。建议：概念图随房间源落位（`renders/00_概念图.png`，或在房间版本目录下另开 `concept/`）。
2. **布局清单不存在** ⇒ 新增一间「有正式美术的房间」目前必须改 GDScript 常量，而不是新增一份数据文件。要让 B 段数据驱动，缺的就是 03 的清单文件 + 04 的装配器这两块。

## 8. 跨链红线（写错不报错，必须靠断言）

| # | 红线 | 写错的代价 |
|---:|---|---|
| 1 | 房间级字段四道白名单 | 字段静默丢失，四道门禁全绿 |
| 2 | 远征房间编号按字面量（`start`/`room_0N`/`extraction`） | 出生点与撤离信标静默失效 |
| 3 | 门槽 / 走廊公式唯一实现 = `RoomDoorLane` | 第二份实现必然与运行时漂移 |
| 4 | 色盘 PNG 不嵌 GLB，靠 `.import` 绑脚本注入 | 白板，且**不触发门禁** |
| 5 | `generation_policy.runtime_enabled` 默认 `false` | 打开会改 `layout_id`（存档指纹）→ 该关旧档失效 |
| 6 | `layout_id` 是存档指纹，**不加字段** | 既有存档失配 |
| 7 | 资源路径稳定、`v###` 只在 `source/` | 换版本即断引用 |
| 8 | **把概念图当成尺寸来源** | 墙位 / 门洞按图偏移，而几何校验照样全绿 —— 白盒与探针才是尺寸真源，概念图只定观感 |
| 9 | 同族组件未做「槽位局部帧逐值相同」检查 | 一个组件铺不满一圈，被迫按方位复制资产。历史教训：安全房 v006 自持 7 个方位化装饰包，v007 才并回通用组件 |

## 9. 门禁命令速查

### C 段（设计）· 目前没有自动化门禁，靠人工逐项确认

1. 概念图与白盒对齐：房型、门位、开间逐项数过（**不是**目测像不像）。
2. 材质四共享角色 + PaletteUV + 色盘外链唯一。
3. 同族组件的**槽位局部帧一致性**（先例 `qa/component_slot_uniformity.json`）。
4. 展示相机、灯光、参考辅助对象**未**进入游戏输出集合。
5. 尺寸全部可追溯到白盒或运行时探针，**没有**任何一项是从概念图量出来的。

> 这一段的产物（概念图、Blender 源）目前没有门禁脚本盯着，所以它是三段里**最容易在无人察觉时跑偏**的一段 —— 一次人工核对的价值高于事后返工。

