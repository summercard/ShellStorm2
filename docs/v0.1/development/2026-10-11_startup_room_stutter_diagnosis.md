# 启动慢与开门、进房、刷怪卡顿诊断（2026-10-11）

FeatureID：ENTRY-AVATAR / PERFORMANCE-RUNTIME / WORLD-BLOCKS / ENEMY-AI / SAVE-PROFILE。
工程版本0.1.0，Git基线 `5ab18194`。来源：用户反馈Godot点运行后很久才出现游戏画面，开门、进入新房间、刷怪时卡顿。
设计依据：`13_技术施工_性能优化与热管理.md`、`05_技术施工_关卡生成与爬楼.md`、`09_技术施工_存档结算与复活.md`。

## 结论

两个症状都有主线程同步工作的证据。启动存在Autoload提前拉入表现资源、固定计时假进度、先加载塔楼再恢复远征、远征结构一次性装配。事件卡顿存在首次敌人模型加载、重复外观构建、重复扫描刷怪碰撞和同步保存检查点。降低云海画质不能消除本次已经测得的这些CPU阻塞。

## 启动实测与原因

Godot4.6.3、RTX4060Ti、真实Forward+窗口1280×720，保留当前画质配置。使用当前真实存档副本，当前档有远征续局意图。四次有效启动观察到目标远征场景的时刻分别为8.384、9.369、8.412、11.985秒（引擎ticks计时，非点击编辑器按钮到首个显示像素的外部计时）。以下拆分以第一、第二次为代表，不能将嵌套区间相加。

| 阶段 | 本轮观察 | 原因与定位 |
|---|---:|---|
| 读条场景进入帧循环 | 启动后约2.4～3.2秒 | Autoload初始化在启动页之前；存在对Player3D/Enemy3D及武器、图标等表现资源的编译依赖 |
| 启动读条 | 代码固定1.10秒 | StartupLoadingScreen只按_elapsed更新进度，之后才同步change_scene_to_file，不反映资源加载进度 |
| 首次塔楼资源加载 | 2.132 / 2.330秒 | StartupLoadingScreen固定目标TowerDescent3D，加载塔楼、基地、跨塔路线、云海及脚本preload依赖 |
| 恢复远征 | 塔楼_ready识别检查点后再次转场 | 先加载并实例化塔楼，才在_ready中判断目标是ExpeditionLevel01_3D；资源工作在判断之前已经发生 |
| 远征楼层提交 | 0.786 / 0.801秒 | _commit_floor_bundle→_ensure_structural_shells_resident，同步加载/实例化全部已提交房间的静态结构 |
| 玩家动作库绑定 | 第二轮168毫秒 | CharacterMotionLibrary3D.bind同步解析13,795,797字节JSON（约13.2MiB），该进程只需首次解析一次 |

当前远征进入后的节点数约24,981～24,993。这是现有正式装配的实测规模，不能只凭节点总量认定某个慢帧来源。结构永久驻留是既有遮光、承重与碰撞合同，优化时不得直接关闭整片结构来跑分。

Autoload对照：原版BlueprintRegistry构造完成至FateCardGameBridge构造完成约1.465秒；只在诊断副本将两处`Player3D.is_fate_snapshot_number`换成完全相同的局部数字校验，桥接器区间降到约104毫秒，但后续MonsterAIManager构造前增加约1.45秒。首个Autoload_ready总时刻由2.388秒变为2.468秒。说明这些静态脚本依赖确实提前拉入较重依赖链；只移走桥接器的一处引用会把成本移到其它Autoload，不能当成总启动时间修复。

## 开门、进房、刷怪实测

沿远征start→room_01…room_05做受控动作，调用正式流送与进房方法。首轮使用测试开边入口绕过清房/钥匙/抽卡前置，仅测它下游的正式_update_room_streaming、波次生成与_on_room_entered；不能将其签署为真实鼠标/键盘开门输入验收。

首轮已复现：

- 第一次普通近战怪模型`load()`：259.391毫秒；同帧对应进房函数513.081毫秒、帧间隔609.829毫秒。
- 第一次胖子怪模型`load()`：326.508毫秒；延迟刷怪批次330.042毫秒、对应帧间隔468.803毫秒。
- 首批模型加载结束后，同种资源再次加载通常约1～2毫秒。重启后的第二轮首用降至65.668 / 14.435毫秒，说明缓存状态影响很大。未清空驱动或OS缓存，不能称作严格冷启动，也没有把全部load时间细分归因到磁盘或Shader编译。

首轮与第二轮手动进房后，物理RoomTrigger又在下一帧报告同一进房，重复执行了一次保存。这是探针直接调用与物理通知并存造成的测量干扰，不据此认定真实游戏必有重复进房bug。第三轮关闭RoomTrigger监测，用一次脚本调用代替物理通知，保留正式进房、存档与流送代码。第三轮仍复现以下耗时：

| 受控操作 | 主线程函数耗时 | 对应帧间隔 |
|---|---:|---:|
| 进入room_02，流送邻房首波 | 317.516毫秒 | 358.438毫秒 |
| 揭示room_04下游流送 | 87.765毫秒 | — |
| 揭示room_05下游流送 | 155.373毫秒 | 169.826毫秒 |
| 进入room_05 | 126.696毫秒 | 145.968毫秒 |
| 再次进入room_03，恢复细节/实体 | 159.369毫秒 | 181.661毫秒 |

60FPS单帧预算为16.67毫秒。以上函数耗时与帧间隔是不同口径；帧间隔还包含本帧其它逻辑、渲染等待和限速，不能相加。

原因链与代码：

1. `Dungeon3D._update_room_streaming`对可见房调用_prepare_revealed_hostile_room，首波生成在同一个调用栈内。`EnemyAvatar3D._load_formal_normal_model`、configure_elite_content、configure_boss_content都直接同步load表现场景；没有将这次首次使用工作移到进入战斗前。
2. `_spawn_enemy_batch`先add_child(enemy)触发Enemy3D._ready→apply_profile默认近战外观，再configure_from_enemy_data→apply_profile实际类型。EnemyAvatar3D.configure每次_rebuild，无同类型复用；胖子和精英也先构建随后抛弃默认近战外观。此项有确定重复工作证据，未独立消融测出其净收益。
3. `_collect_spawn_blockers`从房间父节点find_children扫描所有CollisionShape3D，并逐件计算包围盒。spawn_points_in_box及resolve_spawn_box_center_local都会调用它，同帧多盒重复扫描同一已驻留层。首轮单次最大46.485毫秒，第二轮最大65.212毫秒；room_04/05整波生成包含多次约7～16毫秒扫描。应按布局、碰撞变更建立失效缓存，并在一批落点计算内复用。
4. `_on_room_entered`先同步flush_runtime_checkpoint("room_transition")再做流送；BaseManager.save_base读旧revision、生成校验封套、原子写盘、回读复验，均在主线程。三轮直接保存约30～33毫秒，路线上的检查点保存约30～60毫秒。当前原档约59KB，不能继续把10月4日17KB副本约12毫秒的结果当成本次存档开销。周期world_time_interval本轮约43毫秒，同样会造成事件之外的小顿。
5. DATA_ONLY阶段会卸载细节/怪物；返回房间仍需构建内容和恢复实体。第三轮返回room_03的流送95.333毫秒、保存60.053毫秒，说明不是仅有首用资源加载这一种卡顿。

## 修复顺序建议

1. 把敌人表现资源和必要材质首次使用准备纳入真实加载阶段，保持资源引用；每只敌人按最终类型构建一次，按帧预算准备即将揭示房间的波次。后台只做允许的资源读取；节点树、实体/碰撞提交仍在主线程，保留开门后首波可见和波次预检/失败原子性合同。
2. 对静态刷怪障碍建立失效缓存，一批落点共享一次结果；家具、门与碰撞状态变化时失效，保留合法落点与共墙判定。
3. 优化保存的重复解析/校验，再以单一串行后台写入者处理快照。保留检查点恢复、revision冲突、bak回退、写入失败和退出等待；不能用call_deferred代替后台工作或直接关闭存档。
4. 启动阶段提前从已读取的入口意图选择目的场景，避免为远征续局加载塔楼视觉实例；拆开Autoload领域代码与表现依赖，用真实进度覆盖资源加载及分帧装配，处理动作库大JSON的解析成本。仅把同步load改成线程读取，不会自动消除instantiate/_ready装配阻塞。

本轮未实施上述正式修改，不能承诺修复后的秒数/帧率。尚未对完整旧版本、同存档和同路线做历史A/B；未锁定“最近哪一次提交”是唯一回归起点。
