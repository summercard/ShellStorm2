## 2. 2026-08-05 实机现场检查

检查设备为 Apple M1、8 核 CPU、8GB 内存的 MacBook Pro。检查时正式调试游戏已经停止，Godot 编辑器进程约为 `0.7% CPU / 38–47MB RSS`，不是当时的主要热源。

发现 14 个已脱离父进程的 Godot 无界面诊断实例：

```text
Godot --headless --path . -s tools/diag_wall_v2.gd
Godot --headless --path . -s tools/diag_test.gd
```

现场事实：

| 指标 | 结果 |
|---|---:|
| 残留诊断进程 | 14 个 |
| 父进程 | 全部为 PID 1，原启动器已经退出 |
| 已持续时间 | 约 4 天 21 小时 |
| 五次采样合计 CPU | 约 71% |
| 两个最高实例 | 各约 25%–28% CPU；早期采样曾达到 38%–40% |
| 合计 RSS | 约 131MB |
| 内存压力 | `kern.memorystatus_vm_pressure_level = 2`，压缩页较高 |
| macOS 热警告 | `pmset -g therm` 未记录系统热/性能警告 |

结论：当前机器明显发热的首要原因是诊断进程泄漏，而不是已经停止的游戏窗口。macOS 尚未触发系统热警告不代表没有持续功耗和外壳升温。

<span style="color:#2E7D32">**[P0｜已清理]** 用户确认后已按上述 14 个精确 PID 发送 `TERM`，没有使用 `killall`，没有关闭编辑器或改动项目文件。清理后残留诊断进程为 0；核心套件结束后再次检查，仍只有原 Godot 编辑器，约 `0.7% CPU / 31MB RSS`，没有测试子进程残留。</span>

此前文档中的约 `6.88ms` 是未显式限帧时 `await process_frame` 的墙钟间隔，不能代表60FPS发布节拍。短场景性能预算明确把16.67ms主动等待计入墙钟，并以18ms作为调度容差；30怪真实渲染长测按Metal+VSync的55FPS墙钟门槛采用P95≤22ms，同时用 `RenderingServer.viewport_get_measured_render_time_cpu/gpu` 独立阻断8ms/12ms预算并记录Draw Call。

最终回归另修复两项生命周期边界：受光传感器在typed太阳缓存中遇到freed placeholder时会先做有效性判断，再进入Light3D helper；统一测试看门狗收到TERM/INT/EXIT时会同步回收内部`sleep`。专项证明释放太阳后暗点查询不报类型错误，15秒看门狗回归实际2秒退出且遗留sleep为0。
