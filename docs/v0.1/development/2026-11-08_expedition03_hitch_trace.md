# 远征03「一顿一顿」的落点：卡在跨门那一帧，不在稳态

日期：2026-11-08（第二轮）。功能：PERFORMANCE-RUNTIME。
关联：[帧预算归因](2026-11-08_expedition03_frame_budget.md)、[性能优化与热管理](../13_技术施工_性能优化与热管理.md)、[关卡进入与冷启动预热设计](../design/关卡进入与冷启动预热设计.md)。

上一轮（同日）修掉了 24 盏零能量灯仍在投阴影，稳态 GPU 19.0 → 13.1 ms。
业主反馈仍是「很卡，一顿一顿」。这一轮**不预设还是同一个问题**，改成
「走遍全图 + 逐帧记录 + 把长帧对到具体事件」，看它到底卡在哪一帧。

---

## 零、结论

1. **稳态是健康的**：p50 **10.4 ms**、p95 16.4 ms、GPU p50 10.2 ms、draw 1385。
   上一轮的阴影修复确实生效了，不需要再往稳态帧时上投。
2. **卡顿全部落在跨门那一帧**：p95 **354 ms**、max **1175 ms**；第二次走同一间房
   p95 仍有 **191 ms**、max 234 ms。每跨一道门就是一次肉眼可见的停顿。
3. 跨门的钱分三份：`_update_room_streaming()` 同步段 31~149 ms、**下一帧 79~217 ms**、
   首次进入额外 0.4~0.9 s（资源首次载入）。
4. 开火（持续 300 帧、draw 2155）p50 10.7 / p95 20.0 —— **战斗本身不卡**。

所以「一顿一顿」= 跑图时每隔几秒撞一次 200~350 ms 的同步停顿，不是持续低帧。

---

## 一、口径

上一轮的教训全部继承：先 `set_verification_frame_budget_override(0)`，再 `Engine.max_fps = 0`；
`Performance.TIME_PROCESS` 不用；720p / Forward+ 高档 / `--disable-vsync` / 真渲染。

新增 `tools/_exp03_hitch_trace.tscn`（只读）：

```
godot --path . res://tools/_exp03_hitch_trace.tscn --disable-vsync --resolution 1280x720 --quit-after 16000
```

它做四件事：① 装配后解限帧；② 采 150 帧基线；③ BFS 逐门打开、把玩家送到每间房中心、
每房停 60 帧；④ 清空全图敌人再测 120 帧，然后**反向再走一遍**。逐帧写
`.workbuddy/tmp/exp03_hitch_trace.csv`（墙钟 / `render_gpu` / `render_cpu` / draw / 房 / 敌人数）。

⚠ 这台机器上并行跑第二个 Godot 会话会污染数据：同一探针首轮读到 p50 16.1 ms / p95 72.8 ms，
干净复跑是 10.4 / 16.4。**测量期间不要并行跑其它渲染用例**。

## 二、数据

### 2.1 分阶段（3594 帧，干净复跑）

| 阶段 | n | 墙钟 p50 | p95 | max | GPU p50 | draw p50 |
|---|---:|---:|---:|---:|---:|---:|
| baseline（入口房） | 150 | 16.6 | 18.1 | 52.3 | 16.6 | 2052 |
| 房内稳态（第一遍） | 1500 | **10.4** | 16.4 | 881.8 | 10.2 | 1385 |
| 房内稳态（第二遍） | 1500 | **10.8** | 17.1 | 51.3 | 10.5 | 1331 |
| 开火 300 帧 | 300 | 10.7 | 20.0 | 124.6 | 10.1 | 2155 |
| **跨门（第一遍）** | 75 | 29.7 | **354.6** | **1174.7** | 11.8 | 1395 |
| **跨门（第二遍）** | 75 | 21.8 | **190.6** | 233.6 | 12.0 | 1345 |

稳态最差的三间房 p50 也只有 12.7~14.4 ms；只有入口 `start` 房 16.6~17.2 ms 贴着 60 fps 线。

### 2.2 长帧的构成：主线程在等，不在画

所有跨门长帧的 `render_gpu` 都只有 **8~14 ms**、`render_cpu` 只有 **1.4~3.1 ms**，
墙钟却是 200~1175 ms ⇒ 阻塞在渲染之外。逐个测出来是这样：

| 段 | 量级 | 说明 |
|---|---:|---|
| `_unload_runtime_detail()` | **0.6~2.7 ms** | 只是 `remove_child`，真正释放落帧末 |
| 释放帧（下一帧） | 9~18 ms | `queue_free` 的实际析构 |
| `ensure_detail_built()`（资源已热） | **12~97 ms**（均值 30） | 陈设/碰撞/灯/导航面 |
| 构建后一帧 | 8~85 ms | 物理空间与渲染侧同步 |
| `_update_room_streaming()` 整条 | **31~149 ms** | 含降级旧房、敌人休眠、快照回灌 |
| 其上再一帧 | **79~217 ms** | 新内容进物理/渲染 |
| 首次进入额外 | **380~1175 ms** | glb 首次 load + 着色器编译 |

`shop` 房的 `ensure_detail_built()` 是 88~101 ms（最贵的一间，65 个节点）。

### 2.3 「第一次」比「以后」贵一倍多

同一间房第二遍跨门 p95 191 ms vs 第一遍 355 ms，max 234 vs 1175。
差额是**资源首次载入与管线编译**，不是每次都要付。但这笔钱偏偏付在玩家第一次
踏进那间房的那一刻 —— 加载页只预建了 `start` 房与开门邻房（11-07 的决定），
其余 20 间房的陈设是走到才 load。

## 三、判断

这条和上一轮不是一回事：上一轮是「每帧都在浪费」，这一轮是「每几秒撞一次墙」。

- **不该动稳态**：p50 10.4 ms，余量 6 ms。再压稳态（降画质、合批）对「一顿一顿」没有帮助。
- **该动的是跨门那条同步链**：它一次干了三件重活（释放旧房、建新房、刷首波怪），
  而且是在玩家跨过门框的那一帧。
- 首次载入的 0.4~0.9 s 属于**加载页欠账**，可以在读取界面一次付清，不改变玩家看到的东西。

## 四、候选修法（未实施，等业主拍板）

| # | 做法 | 收益 | 代价/风险 |
|---|---|---|---|
| A | 加载页把全场房间**各渲染一帧**（不是 load 资源，见下） | 跨门 p95 368→257 ms、max 1724→1254 | 加载页 +1.17 s —— **2026-11-09 已实施**，见[逐房渲染预热](2026-11-09_loading_room_render_warm.md) |
| B | `ensure_detail_built()` 拆帧（每帧 8~10 ms 的预算） | 剩下那 250 ms 的顿挫摊成 20~30 帧的轻微抖动 | 改动最大：建造中途房间不可交互，要处理玩家立刻进门/开火/开箱 |
| C | 首波怪从「进门同帧整批」改成「进门后 2~3 帧分批」 | 每房再省几十到几百毫秒 | 会改怪出现时机（上一轮业主未接受最小 50 ms 延迟通道） |
| D | 门框预触发：玩家距门 3 m 时提前激活目标房 | 顿挫被藏进走路的 0.5 s 里 | 要定「预触发但玩家没进去」的回滚口径 |

⚠ **A 的方向修正**：本节最初写的「加载页预载陈设资源」是错的。实测跨门那一帧
`OBJECT_RESOURCE_COUNT` 恒在 3928~4276、draw call 不变、GPU 仅 7.7 ms —— 资源早在
装配期就随壳体 load 完了。真正要挪的是**渲染管线首次编译**，只有"画一次"能挪。

推荐下一步做 **B**：A 只消掉管线编译，剩下的 `RuntimeDetail` 重建 + 释放旧房 + 物理同步
仍是一次 250 ms 的顿挫，只能靠拆帧。

## 五、验收口径（若实施）

- 同一探针复跑：跨门 p95 从 354 → 目标 ≤ 80 ms，首进额外 ≤ 100 ms。
- 稳态不得劣化（p50 ≤ 11 ms、draw ≤ 1500）。
- 加载页时长增量如实记录，不能靠「反正加载页本来就长」掩盖。
- `probe_expedition03_entry_chain` 与 `_exp03_shadow_budget_probe` 必须仍全绿。
