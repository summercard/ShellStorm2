## 3. 取证发现

比对口径：v004 房间与 v003 白盒 manifest 按**房间中心坐标**配对（不使用命名约定），共 14/16 配对成功、2 个因坐标差异未配对。下表差异即取证结论。

### 3.1 发现一：既有白盒的门槽从未经过 5m lane 合法性约束

**10 处门槽差异，全部同源：**

| 房间 → 目标 | 侧墙长度 | v004（运行时口径） | v003（既有白盒） | 该墙有无 0m 槽 |
|---|---|---|---|---|
| `entry → hub` | 15m | `0.0` | `2.5` | 有（且只有 0） |
| `exit → main_10` | 15m | `0.0` | `2.5` | 有（且只有 0） |
| `main_03 → main_04` | 30m | `-2.5` | `0.0` | **无** |
| `main_04 → main_03` | 30m | `-2.5` | `0.0` | **无** |
| `main_04 → main_05` | 30m | `-2.5` | `0.0` | **无** |
| `main_06 → main_05` | 30m | `-2.5` | `0.0` | **无** |
| `main_09 → main_10` | 30m | `-2.5` | `0.0` | **无** |
| `main_10 → main_09` | 30m | `-2.5` | `0.0` | **无** |
| `main_03 → branch_01` | 30m | `-2.5` | `0.0` | **无** |
| `branch_01 → main_03` | 30m | `-2.5` | `0.0` | **无** |

**为什么 `0.0` 是非法槽位。** 墙长 L 的候选槽为：

```text
count      = round(L / 5)
candidates = [ -L/2 + 5*(i + 0.5) for i in range(first, last+1) ]
  first = 1          if count >= 3  else 0
  last  = count - 2  if count >= 3  else count - 1
```

- `L = 30` → `count = 6`，候选 `-7.5 / -2.5 / +2.5 / +7.5`，**不含 0**。
- `L = 15` → `count = 3`，首尾各留一段后只剩索引 1，候选**恰好只有 `0`**。

所以 `30m 墙用 0.0` 与 `15m 墙用 2.5` 两种写法都落在候选集之外。这正是 `03-battle-room-instance-layout-authoring` 第 11 条明文禁止的情形（“如 30m 墙取 `-2.5m`，不是 `0m`”）。

**根因。** `build_battle_level01_whitebox_v001.py:91-98` 的 `side_and_offset()` 只做几何推理，没有 lane 约束：

```python
if abs(dx) >= abs(dy):
    return ("east", dy) if dx >= 0.0 else ("west", dy)
return ("north", dx) if dy >= 0.0 else ("south", dx)
```

同轴相邻（`dx == 0` 或 `dy == 0`）时偏移直接为 `0.0`。v003 脚本虽然补了 `_nearest_runtime_lane()`（`:94-100`），但 **v003 的 manifest 里 ports 仍是 `0.0` / `2.5`**（已逐包核对 `main_03` / `main_04` / `main_05` / `entry` / `exit`），说明 v003 的 ports 沿用了 v001 的结果，lane 修复没有回写。

**判定：v004 正确，v003 错误。**

### 3.2 发现二：两间房的版图坐标不在 5m 网格上

| 房间 | 尺寸 | 版图坐标（v003） | 运行时吸附后（v004） | 差 |
|---|---|---|---|---|
| `main_05` | 30×40 | `y = 37.5` | `y = 40.0` | 2.5m |
| `main_08` | 35×30 | `y = 87.5` | `y = 90.0` | 2.5m |

吸附公式（`TowerGeometry3D.snap_component_axis`，`src/world3d/TowerGeometry3D.gd:47-49`）：

```text
snap(c, s) = snappedf(c - s/2, 5) + s/2
```

- `main_05`：`snap(37.5, 40) = snappedf(17.5, 5) + 20 = 20 + 20 = 40.0` → 边界由 `[17.5, 57.5]` 校正为 `[20, 60]`。
- `main_08`：`snap(87.5, 30) = snappedf(72.5, 5) + 15 = 75 + 15 = 90.0` → 边界由 `[72.5, 102.5]` 校正为 `[75, 105]`。

运行时会记录 `grid_position_adjusted = true`，但白盒没有这条信息，因此白盒版图与服务端实际坐标差 2.5m。

**判定：运行时正确（网格对齐是硬约束），v003 白盒缺少吸附。**

### 3.3 发现三：门的位置有两条互不相干的来源

| 房间 | 门位来源 | 实际值（30m 墙） |
|---|---|---|
| 有 Blender 布局的房（98F `hub` / `main_02` / `main_03` / `main_04`） | 布局里的 `door_wall` 实例 → `DungeonRoom3D._build_battle_layout_doors()` | 按 v003 白盒口径制作 → `0.0` |
| 无布局的房（97F / 96F / 95F 及其余房间） | `TowerDescent3D._shared_door_lane()` 现算 | `-2.5` |

**同一张版图，98F 的门在 `0m`，97F 的门在 `-2.5m`。** 两条路径没有任何交叉校验，这就是 2026-09-18 审计记录 P02「seed2/north_ring hub 计划 south+east，固定布局 north+east，实际只生成 east 游戏门」的机制解释：计划门位与固定布局门位不一致时，布局重放路径只会生成布局里存在的那一扇。

这也解释了为什么 `verify_tower_grid_component_alignment` 与 `probe_safe_room_v007_integration` 都是 PASS：它们校验的是「运行时门位 == 布局门位」，而两条路径各自内部自洽。**自洽不等于正确。**

## 4. 结论与后续

### 4.1 结论

1. 运行时口径（v004 导出结果）是权威；既有白盒 v003 的 `ports` 与两处房间坐标是错的。
2. 但**不能直接修改 v003 的 manifest**：v003 的 Blender 房间源与 `room_layout.json` 是按错误口径做出来的，只改 manifest 会让 manifest 与布局互相矛盾，属于「用一份错误替换另一份错误」。
3. 三类错误都由同一个原因产生：**白盒是代码的派生物，且派生过程经过了一次有损转换（v001 的 `side_and_offset`）**。反向导出（本次 S1）之所以能发现它们，是因为导出直接调用运行时实现，不经过任何中间口径。
