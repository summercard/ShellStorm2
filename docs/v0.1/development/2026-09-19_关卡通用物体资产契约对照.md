# 关卡通用物体资产契约对照（地板 / 墙壁 / 墙壁门 / 门 / 门扇 / L 墙角）

- 日期：2026-09-19
- 范围：`DungeonRoom3D` 生成关卡时使用的通用物体
- 性质：**现状取证 + 契约对照 + 统一实施记录**。第 1–7 节是实施前的取证口径（保留原样以便回溯），第 8 节起是本次实际落地内容、实测数据与仍未决项。
- 取证方式：源码走读 + Godot headless 实测。探针日志 `_scratch/prefab_probe_before_20260919.txt`（判据 `PREFAB_PROBE_OK`，升级前口径）。
- 门禁目标数：**6 件**（地板 / 墙壁 / 墙壁门 / 女儿墙 / 门扇 / L 墙角）。门扇是第 8.5 节、L 墙角是第 8.6 节新入册的第五、第六件。

## 1. 结论

原始四类物体**都已经不是裸程序几何，都已经是 PackedScene（prefab）**。程序生成的是**布局**——哪一格摆哪一段墙、门开在第几段、地砖铺几行几列；物体本身来自 prefab。

所以「能不能变成 prefab 资产」这个问题不成立。需要解决的是另一个更具体的问题：

> 同一类物体存在**两套并行资产**，契约不一致。制作模块化资产时按哪一套做，直接决定替换会不会炸。

**2026-09-19 补充结论（实施后）**：四类物体的**装配策略不能统一**，但**契约可以统一，且已经统一**。

- 统一的是**契约层**：同一套 metadata 字段 + 同一个视觉解析入口 + 同一条碰撞责任规则 + 一个会失败的断言门禁。
- 不能统一的是**装配层**：墙与地砖**必须**继续走 MultiMesh 批渲染。逐 prefab 实例化会把节点数推爆硬门禁——实测 `initial_world` 余量只有 205 节点，而实墙逐实例化净增 2038、地砖净增 45026（第 8.2 节有完整数据）。
- 因此新增 `metadata/runtime_instantiation` 字段，把「批渲染 vs 逐实例」这个差异**显式写在资产上**，而不是藏在代码里。美术替换时看这一条就知道该不该保留 `visual_node_name`。

> **第五件（门扇）的补充结论（8.5）**：门扇**反向**验证了上面这条分界——它是「可以逐实例化、且值得逐实例化」的那一类。
> 每门只 +2 节点（38 门共 +76），代价可接受；而把它硬塞进批渲染（换 `ProceduralDoorPanel` 的 `mesh`）
> 反而要多绕一层「资产解析」的间接，收益为零。

> **第六件（L 墙角）的补充结论（8.6）**：它是**第一件自带碰撞**入册的通用物体（`visual_only=false`），因为它的两个
> `StaticBody3D` 名字（`WallCollisionLong` / `WallCollisionShort`）是 `DungeonRoom3D` 镜头下压逻辑的**运行时契约**。
> 它同时带来**第四个原点契约 `bottom_corner`**——原点必须落在转角，把几何重新居中会让每个房间的四个角错位；
> 门禁为此新增了 `bottom_corner` 识别（结构盒 X 起点 = 0、Z 起点 = −size.z）。

> **门墙的补充结论（8.7）**：门墙**本来就是六件之一**，所以这次换 v004 **不增加件数**（门禁仍是 `count=6`）——
> 它不是新入册，而是把六件里**最后一件还挂着旧塔楼程序生成方块**的资产换成正式美术（前四件在 8.1/8.4/8.5/8.6 已换完）。
> 它也是四件塔楼通用件里**唯一不能照搬实心墙优化策略**的一件：门墙有门楣，门楣底面朝下，照实墙那样「全剔朝下面」
> 会让玩家仰头看穿墙体，因此改成**只剔贴地那一层**（见 8.7）。

> **门墙双面的补充结论（8.8，v005）**：门墙会**连着走廊**——它两侧都会被玩家看到。v004 只有房内侧（`+Z`）有装饰，
> 走廊侧（`−Z`）是一块平整结构背，玩家站在走廊里看过去是素板。v005 把装饰面**绕基准面镜像**一份到背面，做成双面。
> 关键约束有两条：① **只能镜像装饰面，不能镜像整物体**——门洞隧道与背壳横跨基准面，整物体镜像会与保留几何共面闪烁、
> 并把门洞复制成两条；② **镜像对称性不能用面「色心」去比**——镜像顶点以 float32 存盘，色心会差约 `1e-5`，
> 任何逐项比对都会误报（见 8.8）。门禁口径也随之改向：`probe_door_wall_visual` 从「房内侧能量 ≫ 外侧」改成
> 「两侧都达装饰级、且比值回到 1 附近」。

### 3.2 装配方式

墙与地是**「prefab 当 mesh 容器」**：

```
prefab.instantiate()  →  _find_first_mesh()  →  塞进 MultiMesh  →  source.free()
```

代码位置：`_get_tower_solid_wall_mesh()` (1328)、`_get_tower_floor_tile_mesh()` (1127)、`_find_first_mesh()` (1350)。

后果：prefab 的**节点结构、节点名、材质槽、子节点、碰撞体全部被丢弃**，只有「第一个被递归找到的 MeshInstance3D 的 mesh」进入运行时。

Y 对齐全靠 AABB 反算：`wall_transform.origin.y += -mesh.get_aabb().position.y`（1262）。

门墙与门则是**整 prefab 实例化**（1171、2007），相对安全。

### 3.3 已知缺陷（2026-09-19 已全部处理，保留原记录）

1. **首 mesh 已实际漂移。** 探针实测 `prp_tower_wall_door_5m.tscn` 的 `_find_first_mesh` 返回 `MOD_WALL_DOOR_5M_U01_DoorLeaf_OPEN`——一片 `visible=false` 的门扇，而**不是墙体**。当前门墙走整 prefab 实例化所以没爆；一旦有人把门墙也改成 mesh 复用，立刻取错。
   → **已处理**：`_find_first_mesh` 全部退役，改由 `TowerGeometry3D.resolve_visual_mesh()` 按 `metadata/visual_node_name` 声明解析；断言门禁第 2 项盯住「不得靠回退命中」。漂移本身仍被记录（门禁会打印 `[记录] 首网格漂移`），但不再有取错路径。
   → **另：漂移源头也已消失**（8.7，2026-09-19 当日）：换 v004 后，门墙资产子树里唯一的网格节点就是 `ENV_TOWER_WALL_DOOR_5M`，那片隐藏门扇随重导出彻底不存在（见 8.7「门扇」节）。这属于「把缺陷资产换掉」而不是「把缺陷藏起来」——旧的 `DoorLeaf_OPEN` 覆盖节点也从 prefab 里删了。
2. **该 prefab 漏声明 `visual_only`。** 其余三个都声明了 `visual_only=true`，只有它没有；`collision_owner` 也与其他三个写法不同。
   → **已处理**：补 `visual_only=true`，`collision_owner` 统一为 `DungeonRoom3D`；并移除了 prefab 内那份与脚本代理逐值重叠的 `WallCollision`（门柱 2 + 门楣 1）。
3. **材质覆盖靠单个 metadata 开关。** `preserve_authored_palette` 为真才豁免；未声明就会被 `material_override` 换成主题材质，美术成果被盖成单色。
   → **已处理**：四件套全部声明 `preserve_authored_palette=true`；门禁第 7 项断言「声明了保留色盘就不得存在任何 `material_override`」。

## 5. 跨套互换的四个坑

| # | 坑 | 机制 | 症状 |
|---|---|---|---|
| 1 | **朝向反 180°** | A 套 `+Z` / B 套 `-Z`。塔楼 north 墙用 `rotation_y = 0`，换成 B 套后装甲壁板朝房外 | 墙看不见装饰，像换了套皮 |
| 2 | **碰撞双份或全缺** | A 套是 `visual_only` + 脚本代理（`_add_tower_wall_collision` / `_add_tower_solid_run_collision` / `_add_corner_aware_solid_run_collision`）；B 套自带。直接换 → 同位置两套；删代理却没生效 → 穿墙 | 角色卡门或直接穿墙 |
| 3 | **地砖不是同一规格** | 5.0 × 0.3005 厚板（居中，运行时 −0.15 对齐）vs 4.94 × 0.056/0.081 薄砖（靠各自 snap 偏移）。铺法也不同：整板满铺 vs 3×3 棋盘交替 | 地面高低不平、棋盘节奏丢失 |
| 4 | **首 mesh 无断言保护** | `_find_first_mesh` 只递归找第一个 `MeshInstance3D`，已被实测证明会漂移 | 换资产后取到装饰件或隐藏件，几何错位 |

> 4 号坑**已封堵**：`_find_first_mesh` 全部退役，改为按 `visual_node_name` 声明解析 + 断言门禁第 2 项盯住回退。1–3 号坑仍未跨套解决（属于「要不要割接到 B 套」的独立议题）。

## 6. 制作模块化资产的检查清单

按统一契约做，逐条对齐即可安全替换（完整字段表见第 9 节）：

- [ ] 结构尺寸对齐 `TowerGeometry3D`：网格 5.0、层高 12.0、**视觉墙高 11.9**（顶部留 0.1）、门洞净空 2.2 × 2.5
- [ ] 原点：墙 / 门 / 门扇 = 底面中心；地板若沿用 A 套 = 板厚居中；若走 B 套薄砖 = 底面中心 + 声明 `snap_to_walk_plane_offset_m`；**L 墙角 = `bottom_corner`（原点在转角，两臂向 +X / −Z 伸出，禁止重新居中）**
- [ ] 声明 `forward_axis`，且与实际装甲面一致（塔楼 A 套 = `+Z`）
- [ ] 声明 `preserve_authored_palette = true`，否则被主题材质盖掉
- [ ] 声明 `visual_only` 与 `collision_owner`，且与装配侧策略一致（二者只能有一个负责碰撞）
- [ ] **声明 `visual_node_name`**，指向承载模块几何的节点。不声明就会回退到「子树里第一个可见 MeshInstance3D」，在带装饰/带隐藏件的资产上会取错（门墙与滑升门都有这个坑）
- [ ] **同时声明 `bounds_size_m`（结构）与 `visual_bounds_size_m`（可视）**。装饰件（如门墙门框）会让两者不同；混成一个字段，改美术时装配基准就会漂
- [ ] **声明 `runtime_instantiation`**：`batched_multimesh` 要求「只有 1 个 MeshInstance3D可用」，因为批渲染只吃单一 Mesh 资源；`per_instance_prefab` 无此限制
- [ ] 门扇：底边中心原点，垂直升起（改 `DoorPanel.position.y`），不要做绕铰链旋转；**不得自带任何碰撞**（`visual_only=true` + `collision_owner=RoomDoor3D`）
- [ ] **若零件带门楣 / 悬挑结构**（任何「朝下且高于地面」的面）：派生时**不得**整体剔朝下面，只剔贴地那一层（`|z| ≤ GROUND_BAND_M = 0.05`），并断言门楣底面仍在。**门墙就是这条**——照实墙全剔会让玩家仰头看穿墙体（见 8.7）
- [ ] **换资产后审一遍「描述旧资产缺陷」的断言**：例如「子树里必须存在隐藏门扇且不可见」。旧资产修好后这类断言会变成**假失败**，应退役或反向（门墙 8.7 把它反成「不得存在任何 `DoorLeaf` 节点」）
- [ ] 门扇可视底边允许略高于结构底面（本资产为 8mm，关闭的门不擦地），但要声明 `panel_bottom_clearance_m`
- [ ] 同步更新 prefab 的 `metadata/asset_version` 与 `source_glb`，不要改运行时稳定路径
- [ ] 改完跑 `verify_tower_module_prefabs.gd`，判据 `PREFAB_CONTRACT_OK count=6`

## 7. 取证与门禁（2026-09-19 已补上门禁）

`assets/art/props/dungeon_3d/qa/verify_tower_module_prefabs.gd`

升级前**只 print，不是断言门禁**——`failures` 仅在 prefab 加载失败时 append，因此即使像「首 mesh 指向被隐藏门扇」这种明确错误，判据依然是 `PREFAB_PROBE_OK`。

**现已升级为断言门禁**，判据 `PREFAB_CONTRACT_OK: ... count=N` / `PREFAB_CONTRACT_FAILED count=N`，8 项检查：

（`N` = `TARGETS` 数组长度。2026-09-19 8.6 之后为 **6**：地板 / 墙壁 / 墙壁门 / 女儿墙 / 门扇 / L 墙角。）

1. 统一字段齐全（11 项，见第 9 节）
2. `visual_node_name` 能解析到真实节点，且**不得靠三级回退命中**
3. 根空间可视包络 `==` `visual_bounds_size_m`（容差 0.02m）
4. `origin_contract` 语义成立（`bottom_center` / `centered_slab` / **`bottom_corner`**），且**结构盒 ⊂ 可视包络**
5. `forward_axis` 全集一致（塔楼 A 套 = `+Z`）
6. `visual_only=true` ⇒ prefab 内不得内嵌任何 `StaticBody3D` / `CollisionShape3D`
7. `preserve_authored_palette=true` ⇒ 不得存在任何 `material_override`
8. `runtime_instantiation=batched_multimesh` ⇒ 视觉节点必须是 `MeshInstance3D`（批渲染只吃单一 Mesh 资源）

第 8 项是刻意加的：它把「墙/地砖为什么不能逐实例化」这条**编码依据**钉在门禁里，而不只是写在注释里。

第 6 项对门扇是同一条规则的另一个方向：门扇声明 `visual_only=true` + `collision_owner=RoomDoor3D`，所以**门扇 prefab 里一个碰撞体都不能有**。这不是形式约束——门扇自带静态碰撞的话，它不随升降逻辑启用/禁用，门就永远开不了（B 套 `door_5m` 那个包就带 `DoorCollision`）。

> **L 墙角是第 6 项唯一的反向特例**：它声明 `visual_only=false` + `collision_owner=self`，**必须**自带两个 `StaticBody3D`。
> 原因是碰撞节点名本身是运行时契约——`DungeonRoom3D._configure_corner_camera_collisions()` 按名字 `WallCollisionLong` / `WallCollisionShort`
> 只把「属于南墙的那一条臂」标为 `camera_lower_wall`，镜头下压行为依赖它。所以门禁第 6 项对它是**豁免**而非通过：
> 判据形态是「`visual_only=true` ⇒ 碰撞数必须 0」，`visual_only=false` 时不触发该条。改名 / 删碰撞体不会让任何数值门禁失败，只有画面会变。

另有第 4 项的边界：`origin_contract` 描述的是**结构**原点，不是可视包络底面。门墙装饰门框下探到楼面下 0.14m，这不违反 `bottom_center`——所以判据用「结构盒 ⊂ 可视包络」而不是「可视包络底面 == 0」，并在命中时打印 `[记录] 装饰件低于结构底面`。

> 门扇的同类情况：它的可视底边在结构底面**上方** 8mm（美术意图，见 8.5），也不违反 `bottom_center`——同一条「结构盒 ⊂ 可视包络」判据覆盖两个方向。

#### 摆位：两条臂由同一个 bake 坐标系生成

两臂都先做同一段 `bake = yaw(180°) @ recenter(−(4.0, −58.344406, 0.0))`（8.4 的跨套迁移范式），再刚性摆放：

| 臂 | Blender 摆位 | Blender 覆盖 | Godot 结果 | 装饰面朝 |
|---|---|---|---|---|
| 长臂 | `T(+2.5, 0, 0) @ Rz(+180°)` | X 0..5 | 沿 Godot `+X` 0..5 | Godot `−Z`（房内） |
| 短臂 | `T(0, +2.5, 0) @ Rz(+90°)` | Y 0..5 | 沿 Godot `−Z` −5..0 | Godot `+X`（房内） |

> **房间内侧 = 两臂之间的凹象限（局部 `+X`/`−Z`）**，这是运行时口径，不是几何直觉：
> `_spawn_room_corner()` 的注释写明两臂从角点沿房间两条边**指向房内**（`SW` 角 `long=+X`、`short=−Z`），
> `_build_corner_aware_wall_run()` 里南墙 `rotation_y=PI`、西墙 `+PI/2` —— **A 套直墙的装饰面永远朝房内**。
> 所以 L 的两条臂也必须朝房内：长臂 = 当南墙用（180°）、短臂 = 当西墙用（90°）。
>
> 于是每条臂都是通用墙的一次**刚性偏航**（180° / 90°），两条装饰面在房间内角相交于
> Godot `(X +0.3175, Z −0.3175)` —— 正是玩家走到跟前的那条竖棱。
>
> 顺带澄清 `forward_axis=+Z`：它是 **A 套家族标签**（跨套混用会整体反 180°，六件必须一致），
> 不是「本件的装饰面朝 +Z」。L 形有两条臂，实际朝向是长臂 `−Z` / 短臂 `+X`，prefab 里用
> `forward_axis_note` 记了这条差别。

#### Stage 1 / Stage 2 分离——这是「一模一样」的实现方式

派生脚本**刻意分两段**（顺序有原因，见下）：

- **Stage 1** 在 bake 坐标系里把通用墙**优化一次**：`triangulate → remove_downward_faces(nz < −0.5)`，断言 `optimized_triangles == 5319`。
- **Stage 2** 对优化结果**刚性复制两次**摆成 L，逐臂断言 `triangles == 5319`，L 合计 `10638 == 2 × 5319`。

> **为什么不能在摆位后再合并 cull**：初版就是那样写的，结果断言直接报
> `CORNER_NOT_TWO_WALLS: L has 10631 triangles, expected 2×5319 = 10638`——差 7 个面。根因是摆位后又做一次 `transform_apply`，
> float 四舍五入让 7 个临界朝下面翻转（长臂 1082 / 短臂 1087，而墙是 1081）。改成分离两段后数学等价但消除了非确定扰动，
> 每条臂正好 5319。**这条断言抓到的就是真问题**：没有它，「差不多像」会被当成通过。

#### 第四个原点契约：`bottom_corner`

其余五件是 `bottom_center` 或 `centered_slab`；L 墙角的原点**必须落在转角**（两臂交点、底面 Y=0），两臂从原点向 `+X` 与 `−Z` 伸出。

`DungeonRoom3D._spawn_room_corner()` 直接把模块摆到房间角点，再按 `NW/NE/SW/SE` 用 `rotation_y` 区分朝向。
**把几何重新居中会让所有房间的四个角错位**——所以门禁为此新增 `bottom_corner` 识别：结构盒 X 起点 = 0、Z 起点 = −`size.z`。

#### 碰撞留在 prefab——六件里唯一的例外

L 墙角声明 `visual_only=false` + `collision_owner=self`，prefab 内保留两个 `StaticBody3D`
（`WallCollisionLong` / `WallCollisionShort`，各 12m 高 × 0.30m 厚）。

**节点名是运行时契约**：`DungeonRoom3D._configure_corner_camera_collisions()` 按**名字**只把「属于南墙的那一条臂」
标为 `camera_lower_wall`，镜头下压行为依赖它。改名或删碰撞体**不会让任何数值门禁失败**，只会让画面行为悄悄变。

这也让门禁第 6 项对它是**豁免**而非通过：判据是「`visual_only=true` ⇒ 碰撞数必须 0」，声明为 `false` 时不触发该条。

#### 同日修订：长臂装饰面原先朝外（当日重派生 + 重导出）

首版 v001 的长臂是**纯平移**（`T(+2.5,0,0)`，无偏航），于是它保留了 bake 后的装饰面朝向
Godot `+Z` —— 那是 L 的**外侧**。短臂当时是对的（`+X`），所以只有一条臂反了。玩家看到的现象是：
站在房间里面对长臂，那一面是**平整的结构背**（白板感），装饰面朝着没人看的凹角外侧。

**根因不是几何，是「哪一侧算房间内」被写错了**：prefab 注释与探针都把凹侧标成 `−X/−Z`，
而两臂沿 `+X` 与 `−Z` 伸出时，**两臂之间的凹象限是 `+X`/`−Z`**。
当时的朝向判据也是照这个错标号写的（`verify_glb` 断言「长臂装饰面在 Godot +Z」），

| 项 | 改法 |

| 几何 | 长臂补 `Rz(+180°)`（与南墙同款）；短臂不变 |
| 断言 | 新增 `ARM_FACING_GODOT`：逐臂断言自身 AABB 的**离面轮廓**（装饰面凸 0.3175 / 结构背 0.15），任一臂反了即 `CORNER_ARM_FACING_WRONG` |

#### ⚠️ 本件唯一不能照搬实墙的地方：门楣底面**必须保留**

实墙的优化是「全剔朝下面」（`triangulate → remove_downward_faces(nz < −0.5)`，8.4 第 3 条约束）。
**门墙不能这么做**：它有一道门楣，门楣的**底面正朝下、且位于门洞净高 2.5m 处**——那是玩家站在门里
抬头唯一能看到的一个朝下面。照实墙全剔，门洞上方会被**打穿**，玩家仰头能直接看到墙体内部/楼板。

所以门墙改判据为**只剔贴地那一层**：

| 项 | 值 |
|---|---|
| 带判据 | `abs(face.center.z) <= GROUND_BAND_M`（`GROUND_BAND_M = 0.05`，派生坐标系 z = 高度轴） |
| 被剔 | **116** 个贴地封口面（批次源里带的、任何机位都看不到的底面） |
| 被保留 | **1376** 个高于地面的朝下面（含门楣底面） |
| 断言 | 派生脚本内建 `lintel underside was culled: N downward faces above the floor band`（保留数掉到 0 即报错），导出阶段第二道复核 `no downward faces above the floor band: the lintel underside is gone` |

> 顺序约束照旧：**先三角化、再剔面**。n-gon 存的法线是顶点法线的平均，先剔会漏判——

### 8.8 门墙改双面装饰（v005，装饰面镜像到背面）

2026-09-19 追加。用户原话：「我发现这个墙会连着走廊，做成两面都有效果的，直接复制一个镜像一下，在blender里头制作，完成后重新导入。」
范围经确认**只做门墙**——实心墙与 L 墙角保持单面不动（它们本来就不夹在走廊两侧）。

这不是「把缺陷藏起来」，是把「一面是素板」这个视觉缺陷从资产层消除。**不增加件数**：门禁仍是 `PREFAB_CONTRACT_OK count=6`。

#### 问题定性：v004 只有房内侧有装饰

v004 的装饰面只活在结构面前侧（Blender `y = −0.15` 以前），走廊侧（Godot `−Z`）是平整结构背。
门墙夹在**房间与走廊之间**，两侧都会被玩家看到，所以走廊侧那块素背板是真实可见的缺陷。
8.7 当时的画面探针就已经把它量出来了，只是判据写成了「房内侧能量 ≫ 外侧」（比值 4.247）——
**当时是在给缺陷留位置，不是在验收合格**。

#### 做法：镜像**只复制装饰面**，绝不镜像整物体

在派生脚本（`export_env_tower_wall_door_5m_v005.py`）里新增 `mirror_decoration()` 阶段，
位置在 **yaw 烘焙与三角化之后、朝下剔面之前**：

1. 复制网格 → 在新的装饰副本上删掉 `y > −(0.15 + 0.002)` 的面，只留结构面前侧的装饰面；
2. 在副本上加 **Mirror 修改器**，绕 `y = 0`（网格中心线，即基准面）翻转，`use_axis=(False, True, False)`、
   **`use_mirror_merge = False`、`use_clip = False`**，应用后与原网格 `join`。

三条硬约束：

- **整物体镜像不可行。** 门洞隧道与背壳横跨 `y = 0`，整物体镜像会让镜像面与保留几何**共面**（z-fighting），
  并且把门洞复制成两条。所以必须先按结构面切掉，只翻装饰那一份。
- **Mirror 不能开合并/裁剪。** `use_mirror_merge=True` 会把跨平面的面粘到基准面上；`use_clip=True` 会把它们钉死在平面上。
  两项都关掉之后，修改器**自己会翻转绕向**，镜像面法线朝外，不需要手工 `flip_normals`。
- 切割阈值取 `−(0.15 + CUT_GUARD_M)`，`CUT_GUARD_M = 0.002`——2mm 容差保证结构面本身不会被切到。

上轮（v004）用来把「+Y 装饰面」搬到 Godot `+Z` 的那次 180° yaw 烘焙**保持不变**：
`mirror_decoration()` 排在它之后，所以镜像是在**已经对齐塔楼 A 套 `+Z` 约定之后**发生的，
镜像结果是**真镜像（z → −z）**，而不是旋转 180° 复制一份。

#### 门洞绝不能被镜像面堵死：射线三向复测

镜像有可能把门洞盖住，所以门洞判据从两向扩到**三向**（`measure_aperture()`）：

| 射线 | 方向 | v005 实测 | 说明 |
|---|---|---|---|
| `±X` | 门洞内部水平 | 命中于 `x = ±1.1` | 净宽 **2.2** |
| `+Z` | 门洞内部向上 | 命中于 `z = 2.5` | 净高 **2.5**（门楣底） |
| `±Y` | **贯穿厚度** | `plus_y = null`、`minus_y = null` | `clear_through_thickness = true` |

第三条是本轮新增的：`null` 表示射线一路打出去没有任何面 —— **门洞在厚度方向上是通的**，
镜像面没有横在门洞里。净宽 / 净高与 `TowerGeometry3D.DOOR_CLEAR_WIDTH_M` / `DOOR_CLEAR_HEIGHT_M`
以及 `DungeonRoom3D._add_tower_wall_collision()` 的脚本碰撞代理**逐值一致**，因此**未改任何运行时代码**。

#### ⚠️ 镜像对称性**不能**用面的「色心」去比（float32 陷阱）

这是本轮踩得最深的一个坑。第一版对称断言把面按「色心（顶点均值）」排序后逐项 `zip` 比对，报了 **911 条不对称**；
改成容差桶贪心匹配后仍然报 **29 条**。逐条对拍后发现：**两侧顶点位置的多重集完全相同（差异为 0）**，
那些「未匹配」的行的最近邻 `dpos = 0.000000`。

根因是 float32：

- 镜像后的顶点存盘为 **float32**，色心与法线会与「原面」差约 **1e-5**；
- 只要差值在 5 位小数处翻转，**排序后的逐项 zip 就会整体错位**（不是真的不对称）；
- 容差桶的贪心匹配本身**不保证传递性**，遇到本来就存在的完全相同的孪生面时会假阳性。

最终改用**两个对 float32 逐位稳定的不变量**：

| 不变量 | 定义 | 为什么稳定 | v005 实测 |
|---|---|---|---|
| 顶点位置键多重集 | 把每个面的顶点位置打包成键，比较两侧多重集 | 镜像只翻 `abs(y)`，键**逐位精确** | `mirror_position_key_mismatches = 0` |
| 向量面积相对偏差 | 比较两侧面**向量面积和**（有向） | 绕向反号会直接暴露 | `mirror_vector_area_relative_delta = 0.0` |

第二条专门抓「面反了」：如果镜像时绕向没翻正，法线会指向墙体内、背面渲染不可见，但面积绝对值一样，只有**有向**面积能抓到。

#### ⚠️ 退化面会让「朝下面」计数在存盘/重载之间翻转

源文件里含 **24 个零面积面**（`area < 1e-9`）。零面积面的**法线是数值垃圾**，
用「法线朝下」去分类时，这些面在存盘/重载之间会来回跳——实测「朝下面」计数在 **1367 / 1368** 之间摆动，
让门楣保留断言偶发假红。

处理：

- 新增 `DEGENERATE_AREA_M2 = 1e-9`，所有朝下统计**跳过退化面**并单独报告 `degenerate_zero_area_faces = 24`；
- 门楣保留断言的计数差加容差 `DOWN_FACE_COUNT_TOLERANCE = 4`。**门楣是否存在不靠计数证明**——
  由门洞射线直接测出 `clear_height_m = 2.5` 精确证明（没有门楣底面就测不到这个高度）。

## 9. 统一契约字段表（就是「同一规格」的可执行定义）

六类通用物体必须全部声明：

| 字段 | 含义 | 门禁断言 |
|---|---|---|
| `asset_id` / `asset_version` | 稳定身份 | 存在 |
| `origin_contract` | `bottom_center` / `centered_slab` / **`bottom_corner`**（L 墙角：原点 = 转角） | 结构盒语义 + 被可视包络包含 |
| `forward_axis` | 正面朝向；塔楼 A 套 = `+Z` | 全集一致 |
| `bounds_size_m` | **结构/碰撞**包围盒（玩法用） | 用于求结构盒 |
| `visual_bounds_size_m` | **并入美术后的实测可视**包围盒 | == 根空间实测（容差 0.02m） |
| `visual_node_name` | 视觉/包络载体节点名 | 必须解析到真实节点，不得回退 |
| `visual_only` | 视觉专用 | 为真 ⇒ 内嵌碰撞数必须为 0 |
| `collision_owner` | 碰撞责任方 | 与装配侧策略一致 |
| `preserve_authored_palette` | 保留美术自带色盘 | 为真 ⇒ 无任何 `material_override` |
| `runtime_instantiation` | `per_instance_prefab` / `batched_multimesh` | 批渲染 ⇒ 视觉节点是 `MeshInstance3D` |
| `double_sided` | **条件字段**：该件两侧都会被玩家看到（如门墙连着走廊）时为真 | 为真 ⇒ 可视包络关于基准面对称（`|z_min| ≈ z_max`），且 prefab 必须显式声明 `double_sided=true` |

## 10. 仍未决 / 已知债务

1. **台账无损基线（`ledger_split_baseline.json`）无法从当前状态重建**。8.5 新增门扇行后，`verify_ledger_split` 报
   `missing=0 extra=1`，extra 就是新行本身。根因：`--baseline-only` 需要**源账本仍持有《资产主表》**，而总目录分账后已无资产行，
   工具链里**没有**「从 7 个分账本合并重建基线」的路径。后果是基线永久停留在分账时刻，此后**每一次有意新增资产都会让这条门禁永远报 extra**，
   久而久之这条门禁会被当成噪声忽略（它现在另有 472 条派生列公式红项，见下）。
   两条出路，需主人拍板：(A) 给 `split_asset_ledger.py` 加**合并式基线重建**（读 7 个分账本 → 归一化成全集指纹 → 刷新基线），
   语义从「分账前真值」变成「当前快照」，但仍能挡住后续静默丢/改行；(B) 让基线只覆盖**集合**（AssetID 列表 + 逐行指纹），
   显式允许新增（`extra` 不判失败），只对 `missing` / `row_content_mutated` 报红。

   > **8.6 追加的两个实测事实**（都是这条基线债的直接后果）：
   > (a) **「重复登记」不会被新增行掩盖**。先按「新增行」处理 L 墙角时，门禁直接报 `duplicate_asset_id`
   > ——因为 `ENV-TOWER-CORNER-L-5M` 已作为第 69 行存在。这条门禁仍然有效，它挡住了一次真会发生的重复登记。
   > (b) **每一次有意变更恰好 +1 条红项**，不连带、不级联：8.5 新增门扇行是 +1（`asset_not_in_baseline`），
   > 8.4 改墙第 55 行是 +1（`row_content_mutated`），8.6 改第 69 行同样 +1（`row_content_mutated`，473 → 474）。
   > 所以「增/改几件资产 = 多几条红项」是可预测的，判据「红项 ⊆ 基线 ∪ 本次有意变更」不会失控。
