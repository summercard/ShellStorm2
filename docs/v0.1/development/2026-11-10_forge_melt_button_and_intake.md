# 2026-11-10 熔炼按钮禁用理由 + 投料表现（补齐前半段）+ 闸门台面剧透

功能 ID：`RUN-FORGE`。设计主源：[07.2 玩法系统｜武器改造台](../07.2_玩法系统_武器改造台.md)。

## 业主口径

> 「把熔炼这块按钮修了。过一遍设计文档和项目框架。然后把熔炼的表现也一起做了。整套流程要完整。」

起因是业主在 99F 改造台投了 3 把枪 + 一堆材料，判为「融合」、费用 432、`COINS 0`，**按钮是灰的点不动，界面没有任何地方说为什么**。

## 一、按钮：禁用理由不可见

### 病根

`_refresh_readout` 里禁用条件是对的：

```gdscript
var affordable := cost <= _coins()
_forge_button.disabled = _busy or not affordable
```

但**只做了禁用这一个动作**：按钮变灰、`FEE` 转红，状态栏仍停在默认速记「任意物品可作材料…」。
玩家拿到的唯一信息是"这个按钮点不动"，而原因要自己反推。

更关键的是 `_execute_forge` 里那句：

```gdscript
if cost > 0 and not _spend_coins(cost):
    _set_status("金币不足：需要 %d，持有 %d。投入物一件未动" % [cost, _coins()])
```

**这是不可达代码。** 按钮已经禁用了，正常路径上玩家永远点不到这一行；能走到它的只有验收直接调 `_execute_forge`、或未来的快捷键/自动化绕过表单。禁用理由只能在**禁用那一刻**由读数刷新给出。

### 改法

1. 状态栏写出**带差额**的原因：`金币不足：需要 432，持有 0，还差 432。投入物一件未动`。
   玩家要的不是"你钱不够"，是"还差多少"。
2. 凑够钱后必须**回收**这句 —— 否则攒够回来还看到"金币不足"。
3. 顺手补齐同一类问题：配方不成立时状态栏也要写**可操作的原因**
   （`insufficient_fuel` → 「燃料熔炼值不足 3 点（3 件白装，或 1 件稀有材料）」），
   而不是只把按钮灰掉。
4. `_execute_forge` 里那条保留，注释改成"最后一道账目保险"，不再假装它是主路径。

### 一个必须小心的边界

状态栏是**多来源共用**的：拖拽失败的即时反馈（「这个位置放不下：需要 4×2 格」）、
熔炼结果文案、目录页完成度汇总都往这里写。读数刷新是高频的（每次拖动都跑），
无条件覆盖会把即时反馈抹掉 —— 玩家拖歪一格，提示闪一下就没了，会以为拖成功了。

所以加了 `_is_readout_status()`：只覆盖**自己写过**的两类（默认速记、以及
「钥匙还差 N 个」软提示）。用文本前缀判断而不是加布尔标记 —— 后者要同步改所有
写入方（拖拽 / 目录页 / 结算），漏一处就静默失效。

**空盘是刻意的例外**：那是文档 §7 规定的"空白态"，三条配方速记就是它的正式文案。

### 踩到的坑：软提示被自己的判据挡回去

`_refresh_status_hint`（"钥匙还差 N 个"）内部的守卫是"只在状态栏还是默认速记时才写"。
第一版把拒绝原因写在软提示**之前**，于是状态栏已被改成「燃料熔炼值不足…」，
软提示回头一看"不是默认速记"就自己放弃了 —— **软提示被自己人的改动静默吞掉**。

改成先软提示、后拒绝原因。这类顺序 bug 不会报错、也不会让验收变红（除非专门断言），
只有把两句提示的优先级想清楚才发现。

## 二、投料表现：补上流程缺的前半段

2026-10-19 做的是**后半段**（兔子闸门）。前半段一直是空的：点下熔炼直接
`SynthesisGateVeil.play()`，盘面上一动没动 —— 玩家看不到"我放进去的东西被吃掉了"，
只看到画面突然被一块板盖住。业主这次要的"整套流程要完整"，缺的就是这一段。

新增 `src/ui/ForgeMeltVeil.gd`（纯表现层）。演出变成**两段串行**：

```
_execute_forge（事务已全部落地）
  → ① ForgeMeltVeil      投料 + 炉心充能  1.45s
  → ② SynthesisGateVeil  兔子闸门         5.00s
  → _finish_forge（一次性刷新 + 结果文案 + 发信号）
```

### 为什么物品不能从盘面读

事务在进演出之前就 `_tray.clear()` 了。投料段若读当前盘面，读到的是空的 ——
吸入物会一个都建不出来。所以在 `_execute_forge` 清盘**之前**加了
`_capture_melt_layout()` 存下锚点 + 物品 + 转数，由 `plan` 的投入清单复原矩形。
这是"表现要跟事务解耦"的具体代价：**表现层读事务前的事实，不是事务后的状态**。

### 配方配色为什么是这四色

全部落在既有调色板上，不新增常量（避免"炼炉有自己一套色"）：

| 配方 | 色 | 依据 |
|---|---|---|
| 重铸 | `PRISM_ACCENT` 蓝 | 枪身不变，重掷品质 → 低烈度，冷色 |
| 融合 | `PRISM_EPIC` 紫 | 介于冷与暖之间（与史诗品质色同源） |
| 合成 | `SOUL_GOLD` 金 | 凭空造枪，与产物的贵重感一致 |
| 定向 | `NEON_MINT` 翠 | "已知目标"，复用既有的成功/确认色 |

四色互不重复 —— 玩家靠颜色辨认"这次熔的是哪一类"，撞色就失效。进验收。

### 视觉上必须说清的三件事

炉心要同时表达"这是一个口""它在吃""它吃饱了"，缺一件就读不懂：

- **暗膛**（吃掉光的洞）+ **收束刻度环**（24 段断弧，留缺口才读得出"在转"；
  实心圆环读起来只是装饰）+ **反向内环**（两圈反向才像两个部件在咬合）；
- **辉光梯度**（5 层同心圆，透明度按 1/layer 衰减）+ **亮核提亮到近白**
  —— 没有梯度，蓝光/金光会脏成一个暗点（与闸门兔子眼睛同一套做法）；
- 位移用 **ease-in-cubic**：起步慢、末端快 = 被炉心拉住；线性位移读起来像自己均匀飘过去。

### 截图看出来的两个问题（都不是想出来的）

**一、投料铭牌压在盘面说明文字上。** 第一版锚在炼炉栏**底部**，那里正是
「拖回右侧＝取回　·　盘内拖动＝调整位置」那一行，截图里「合成　·　6 材料」
和它叠成一团。改成锚在**盘面内部**底边（`_board_rect` 由面板传入，
不在表现层猜列高行高），并给铭牌加一条窄幅暗底衬 + 上下 1px 亮线 ——
盘面内部可能正有被吸走的图标经过，没底衬照样会叠。

**二、吸入影子的帧。** 第一版的 `forge_melt_intake` 帧里，物品已经缩到很小，
看起来像"凭空没了"而不是"被吸走"。调整后 0.40s 时替身还有约 0.83 尺度、
位置明显偏向右下（正被拉向盘心），读得出方向。

## 三、闸门台面剧透（过框架时发现的，比按钮问题更严重）

`SynthesisGateVeil.play()` 第一行就 `_fill_stage()` 且 `_stage.modulate.a = 1`，
而闸门此刻 `progress = 0`（还在矩形上方）。

**意味着点下熔炼的第一帧，答案就已经亮在台面上了** —— 先亮 0.60 秒，
闸门才盖住它。之后 3 秒的等待全是空转。闸门变成"盖住已经揭晓的答案"，
而不是"盖住之后才揭晓"。

`2026-10-19_synthesis_gate_veil.md` 里"防剧透"那一节只堵了**页脚**与**背包**
（封条），漏了台面本身 —— 而它是最直接的一处。这正是那份记录自己命名的
"做了动画但没做表现"的形态，只是换了个位置复发。

改法：`play` 时 `_stage.modulate.a = 0`，到 `PHASE_OPENING` 段 **35% 之后**
才开始拉到 1（闸门刚抬起一条缝就摆出产物，等于开门那一瞬直接跳到答案）。
`get_snapshot()` 新增 `stage_alpha`，验收据此断言。

## 验收

`verify_synthesis_gate` 扩展（`core`）：

- 投料段在闸门段**之前**播完（材料还没被吃掉就先落闸即失败）；
- 投料层 `actors > 0`（吸入替身真的建出来了，不是空播）；
- 三段时间合计恰为 1.45s，且 `INTAKE_SECONDS < 1.0`；
- 四条配方配色互不重复；
- `abort` 不发 `finished`；
- **防剧透三处**：闸门未开到底前 `stage_alpha == 0`、背包封条可见、状态栏不含「熔炼完成」。

`verify_weapon_forge` 扩展（`core`）：

- 金币不足时状态栏写「金币不足：需要 X，持有 Y，还差 Z」，含费用与差额两项；
- 钱给够后**回收**该句，回到默认速记；
- 空盘保持默认速记（空白态文案）；
- 1 件白装当燃料 ⇒ 状态栏写出「燃料熔炼值不足」。

`capture_synthesis_gate` 实拍扩到 6 帧（1280×720，Vulkan Forward+）：

| 帧 | 时刻 | 看到什么 |
|---|---|---|
| `forge_melt_intake` | 0.40s | 材料离位缩向盘心、炉心半亮、铭牌「定向合成 · 6 材料」 |
| `forge_melt_charge` | 1.25s | 材料已消失，炉心全亮（充能满的定格） |
| `synthesis_gate_closed` | 闸门 1.0s | 闸门闭合、兔子双眼全红、**台面无任何产物**、背包封条 |
| `synthesis_gate_revealing` | 闸门 3.45s | 闸门升起约六成，豌豆手枪露出上半身 |
| `synthesis_gate_revealed` | 闸门 4.30s | `SYNTHESIS COMPLETE` + 豌豆手枪 + 「蓝 · 标准子弹模块」 |
| `synthesis_gate_done` | 闸门 5.20s | 台面淡出，盘面清空，背包里那把枪仍在 |

`synthesis_gate_closed` 这张帧就是防剧透判据的可视证据：闸门关着，台上什么都没有。
改动之前这一帧会显示「豌豆手枪 蓝 · 标准子弹模块」。

另加一张独立的实拍 `capture_forge_unpaid_reason`，复刻业主截图那个场景
（3 把枪 + 材料、判融合、`COINS 0`）：`forge_unpaid_reason.png`。
实测输出 `fee=124 coins=0`，状态栏「金币不足：需要 124，持有 0，还差 124。投入物一件未动」，
`FEE` 转红、按钮置灰 —— 这就是改动前后唯一可见的差别。

结果：`WEAPON_FORGE_OK` / `SYNTHESIS_GATE_OK` / `SYNTHESIS_CATALOG_OK`，exit 0。

### 回归时发现的两个环境问题（与本次改动无关，未处理）

跑 `verify_workbench_menu_entry` / `verify_fate_integration_completion` 时两条变红，
都不是本次改动引起的：

1. **`src/world3d/TreasureChest3D.gd` 在 17:57 被并行会话改动后带解析错误**
   （`Cannot infer the type of "chest"` 等），套件的 import 门禁直接 `VERIFICATION_IMPORT_LOG_FAILED`。
   该文件本次一行未碰。它会连带让 `verify_workbench_menu_entry` 报
   「99F 不应再实例化 monster_archive」「z=-4.72」—— 那是基地设施位点的事，也在我的改动面之外。
2. **`verify_fate_integration_completion` 要求 `APPDATA` 含 `fate_completion_20261008/integration`**，
   而标准 runner 建的隔离目录名是 `ShellStorm2Verification_<pid>_<ts>`。这个用例需要它自己的
   启动脚本，不在 `run_verification_suite.sh` 里。

绕开这两处（直接用隔离 `APPDATA` 跑三个相关场景）后全部 exit 0。
