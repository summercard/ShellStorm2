# 五件场景可交互易碎小物件的制作与接入

日期：2026-10-29。范围：罐子 / 书本堆 / 花瓶 / 椅子 / 木箱。设计契约见[场景可交互低模物件设计](../design/场景可交互低模物件设计.md)。

## 一、需求与判定口径

用户原话是「一批（4种）」，但名称清单列了五件。**按名称做完五件**，不按字面数字漏做。

| 要求 | 落地口径 |
|---|---|
| 每件不超过 100 个面 | 收紧为**每件不超过 100 个三角面**，以修改器求值后、导出后的实际统计为准 |
| 大小不超过 1 米 | 最大边（X/Y/Z 任一）≤ 1.0m |
| 交互反馈 | 短促缩放/倾斜脉冲 + 方向性破碎 |
| 1 套破碎动画 | 五个组件共用同一套方向破碎逻辑，各 1 套动画 |
| 破碎后停留地面 | 落地后不回收、不淡出、无计时器 |
| 可用粒子，数量≤5 | **不用粒子发射器**：直接 5 块实体碎片，天然满足≤5 且落地可留 |
| 交互态不阻挡 | 受击体只在层 4（子弹 mask=5），玩家移动 mask=1 不与其碰撞 |
| 朝对应方向破碎 | 子弹传真实 `direction`；角色取水平速度，静止回退「角色→物件」方向 |

## 二、组件规划与预算

`component_plan.json` 在正式几何之前冻结（`status = frozen_before_geometry`），5 个唯一定义，预算 50 → 剩 45。五件是五个独立组件，不复用既有书本/座椅/木箱，也不按摆位复制。

花瓶轮廓经两轮门禁收敛：十边 136 面 → 删饰带 116 面 → 八边 92 面。**不是放宽阈值，是改轮廓**。

| 组件 | 三角面 | 最大边(m) | 主题 |
|---|---|---|---|
| breakable_jar | 96 | 0.54 | 八边收肩罐身 + 双耳 + 环形罐沿 |
| breakable_book_stack | 84 | 0.64 | 三本错位叠放 + 双色封面 + 书脊 |
| breakable_vase | 92 | 0.73 | 八边细颈鼓腹 + 环形瓶口 |
| breakable_chair | 96 | 0.86 | 四腿 + 座面 + 双立柱靠背 |
| breakable_crate | 98 | 0.69 | 箱体 + 四角护条 + 盖缝 + 正面斜撑 |

原始源 `battle_interactive_clutter_v001.blend` 与独立优化源 `export/v001/...optimized_v001.blend` 分离保存；导出前重开优化文件、断言源 SHA-256 前后一致，再从优化文件逐件导出 GLB。

## 三、接入路径

- 稳定 Prefab：`runtime/common_components/<slug>/<slug>_root_top3d.tscn`，结构为 `Visual`（GLB 实例）+ `HitReceiver`（StaticBody3D，layer 4）+ `PlayerContact`（Area3D，mask 1）。两者共用同一个 BoxShape3D，尺寸取本体包络。
- `DungeonRoom3D._build_interactive_clutter()` 在 `room_type == "STAIR_LOBBY"` 分支追加五个实例到 `RuntimeDetail`，**不重生成整房**。
- 破碎状态写进 `_pending_detail_runtime_state["breakable_clutter"]`，由 `_restore_interactive_clutter()` 在流送重建后按稳定 `clutter_id` 恢复。

## 四、验收里挖出的三个真故障

### 1. 受击体「在树上」但不在物理空间里

现象：独立 Prefab 的 layer-4 射线能命中，放进 `DungeonRoom3D` 后连全 mask 射线都打空，真子弹直接穿身而过。

探针打出 `PhysicsServer3D.body_get_space(rid) = RID(0)`，而 viewport space 是正常 RID —— 碰撞体根本没注册。根因是 `room.process_mode = 4`（`PROCESS_MODE_DISABLED`）：`set_stream_state()` 只在 `presentation_ready` 时恢复 `INHERIT`，测试直接 `new()` + `ensure_detail_built()` 绕过了这一步。

修法不是改产品代码，而是**让测试走正式入口**：补 `set_stream_state(STREAM_ACTIVE)`。这条值得记住 —— 凡"节点存在、属性正确、物理/信号却无反应"，先查 `process_mode` 与 space 注册，别急着怀疑层值。

### 2. 碎片初版是一条「刀片带」

| 项 | 初版 | 实际观感 |
|---|---|---|
| 横向散布 | ±0.43m（固定值，不看本体） | 五块连成 0.86m 长条，比本体还宽 |
| 碎片厚度 | 0.018m | 贴地后只剩一条线 |
| 配色 | 从 4 个固定色盘格随机取 | 木箱碎出红/蓝/黄，与本体无关 |

三处一起改：散布改为受 `bounds_size` 约束（总半径 ≤ 对角线的 0.9 倍）、碎片改为 12 面凸块且尺寸随本体、配色直接采样**本体各表面的实际 UV 格心**。落地高度按网格最低顶点贴地，不按中心点 —— 否则凸块会一半埋进地板。

### 3. 房间截图全黑

验收场景没有 `WorldEnvironment`，房间自身的顶灯在无环境光时不足以成像，存出来是一张纯黑图。补环境光后**同时断言亮度分桶 ≥ 6**，防止「截了张黑图也算通过」。

## 八、远征03 随机布置（同日追加）

用户追加要求：「随机布置在远征03的房间里，让我测试。」

先核实了远征03 的真实状态 —— 记忆里记的是「flow 生成器与场景未施工 / `runtime_enabled=false`」，
**实际已经是 `runtime_enabled=true`、`ExpeditionLevel03_3D.tscn` 可进图**，`probe_expedition03_playable`
实测 27 房、门全通。按旧记忆办事会得出「没房间可布」的错误结论，这一步必须查而不是猜。

### 8.1 为什么走数据段，不走关卡分支

远征03 是 `mode=flow`，房间由种子现算，没有静态房间场景可改。所以做成能力段：
`level_plan.json` 写 `interactive_clutter`，`DungeonRoom3D` 认这段数据、不认关卡 ID。
`check_level_decoupling.py` 巡检 7 个通用机制容器 `violations=0`。

透传三段都要改，漏一段就是静默失效（`_append_plan_room_record` 不落字段，房间就永远拿不到计划）：

| 层 | 文件 | 改动 |
|---|---|---|
| plan 顶层 | `src/map/FloorPlanGenerator.gd` | 透传 `interactive_clutter`，**不进 canonical**（不影响 `layout_id`、不影响存档） |
| 房间记录 | `src/world3d/TowerDescent3D.gd` | 按 `exclude_room_types` 过滤后落 `record["interactive_clutter"]` |
| 两条建房路径 | `TowerDescent3D._instantiate_dynamic_room` + `Dungeon3D._prepare_layout_rooms` | 两处都透传给 `configure` |

第三条尤其容易漏：读条建房走 `Dungeon3D`，走进房间走 `TowerDescent3D`；只改一处会出现
「读条进去没有物件、走动进入才有」。

### 8.2 三个实现口径

1. **布置挪到 `_build_content()` 末尾**。原先安全房五件是在 `prop_count = 0` 分支里即时摆的；
   随机撒点必须在家具/服务点/危害区全部落位**之后**执行，才能读它们做避让。现在统一在末尾调用，
   入口安全房那五件仍在（走固定摆位分支）。
2. **确定性种子**：`hash([room_seed, "interactive_clutter", room_id])`。用 `randf()` 会让房间重建重抽，
   玩家进进出出看到罐子自己换地方 —— 而那不会让任何「数量断言」变红，属于最难发现的一类缺陷。
   探针逐件比对位置与朝向，实测漂移 0 处。
3. **小房显式跳过**：5×5 十字路口（`cr01_hub_01_n02` 等 10 间）四面都是门，2.4m 门净空会把候选点全清空。
   初版就出现了「9 间房 0 件」—— 现象上和「数据没下发」无法区分。加了 `min_room_size_m=8.0` 显式跳过，
   并在探针里把「尺寸够却没物件」判为失败，两者从此可区分。

## 九、v002：放大 + 破碎重做（业主反馈）

业主原话：**「动画不够明显，散落的范围也不够大…打碎后要散开一些，范围至少高一点，力道足一些。
然后散落的范围也大一些。然后是限制的物体整体都太小了，椅子可以大50% 罐子可以大50% 箱子可以大30% 书本不变。」**

### 9.1 尺寸冲突必须先讲清

「不超过 1 米」是业主 2026-10-28 定的。这次 +50% 让椅子到 **1.29m**，两条指令直接冲突。
按最新指令优先：椅子单件上限放宽到 1.30m 写进 `component_plan.json` 的 `max_dimension_m`，
其余四件仍守 1.0m —— **不是把全局上限一刀切放开**，验收也是按件声明。

纯统一缩放，顶点先乘系数再做底部中心对齐，所以三角面与拓扑与 v001 逐件相同
（96/84/92/96/98），不存在「放大后偷偷减面」。

### 9.2 破碎为什么之前「不明显」

三个叠加原因，任一不改都还是不够明显：

1. **弧高被硬上限锁死**：`arc_height = minf(0.28, ...)` —— 0.28m 的弧顶，在 25m 房间里等于没跳。
2. **时长太短**：0.65s 里要塞完飞行+落地，抛物线只能压扁；改 0.95s 才撑得起 1m 级弧线。
3. **落点没有互斥**：五块各自算出落点，经常落在同一处，肉眼就是「一堆没散开」。

对应改法：弧高改为随本体最长边放大并逐块抖动；时长 0.95s；落点做**最小间隙 0.30m 的 6 轮松弛**。

### 9.3 碎片按材质分三类

业主说「每个不同的东西碎块要不一样」。陶器碎成片子、木头碎成条、书碎成纸 —— 这是材质决定的，
不是配色问题。所以按 `clutter_kind` 走三条几何路径：

| 材质 | 组件 | 形态 | 面数 |
|---|---|---|---|
| 陶瓷 | 罐子、花瓶 | 五边片 + 正反中心鼓起（弧面瓦） | 20 |
| 木质 | 椅子、木箱 | 一端收窄的长条木板 | 12 |
| 纸张 | 书本堆 | 薄片 + 沿 X 单折卷边 | 12 |

配色取本体实际色盘格（木色 (5,2)~(7,2)、罐陶 (6,3)、瓶陶 (2,6)、书页最亮格 (9,9)），
色盘格是用 PIL 逐格采样确认过的十六进制值，不是估的。

### 9.4 过程中踩到的两个坑

1. **书页卷边写成 `curl * |sx|²` 等于整体平移**：四角同时抬高，网格没有负向顶点，
   `end.y = -lowest + 0.004` 就算成负数，五片书页全浮在半空。改成沿 X 单折（一端抬、一端压）才真正弯曲。
2. **陶片断言只认一个色格**：陶片按件在**两格**轮转（罐 6,3 与 8,4），只断言 0.65 行会让 3/5 的陶片误报。
   改成「件自身允许的两格之一」判定。
