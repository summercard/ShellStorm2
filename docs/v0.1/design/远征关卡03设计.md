## 2. 玩法循环

```text
选关 → 读取界面
  → [生成期] 抽骨架 → 注入特殊房 → 切复合对象 → 拼装 → 总装
  → 入口安全房 15×15（唯一弃局门）
  → 内容房（NORMAL / REWARD / HUB / BOSS 前厅）**按本次抽中的骨架排布**
      · **进屋即落门封锁 → 清空敌人 → 门自动重开**（Gungeon 的房间封锁语义）
      · 不弹命运卡、不消耗房间钥匙 —— 本关规则独立（见 §2.1）
  → 宝箱房 ×2（REWARD，其中一间通常在单向环末端）
  → 商店 ×1
  → Boss 前整备房 → Boss 竞技场 50×40
  → 撤离房 25×25（常驻撤离信标）→ 撤离成功 → 结算
```

### 2.1 房门规则（本关独立，2026-10-28 定稿）

业主裁定：**「不需要房间钥匙这个设定。这个关卡的规则独立，不用走远征01 的逻辑。」**

本关的房门语义按 Gungeon 实现，**不复用**远征01 的"按 E 开门 + 钥匙 + 命运卡"三件套：

| 项    | 本关（Gungeon 口径）                                | 远征01/02（既有）                   |
| ---- | --------------------------------------------- | ----------------------------- |
| 门扇   | **有**（宽 2.2m 标准门，`DOOR_CLEAR_WIDTH_M`）        | 有（部分关卡走静态布局烘死）                |
| 门状态 | **可开启 / 不可开启**两种（见 §2.1.0）                    | 开 / 关（位置态）                    |
| 进战斗房 | **自动落门封锁**：出口全部翻成**不可开启**                      | 不封锁（玩家自己按 E）                  |
| 清空敌人 | 出口恢复**可开启**（门板不替你敞开，走近才开）                    | 解封后可开，但仍要按 E                  |
| 房间钥匙 | **不用**（`requires_key = false`）                | 战斗房要钥匙（`requires_key = true`） |
| 命运卡  | **不弹**（`triggers_fate = false`）               | 每扇门后弹（`triggers_fate = true`） |
| 无怪房  | 走廊 / 入口 / 撤离 / 商店 / **宝箱房 / Boss 前厅** 不封锁、门可开启 | 视房型而定                         |
| 房间外  | **不可观察**（只留当前房间是舞台）                           | 相机可越过墙顶看到隔壁                   |

**为什么"无怪房"要单列**：Gungeon 原文把连接房写成
  
"connector rooms, which are enemyless rooms, often with a environmental hazard"。
  
给一间本来没有怪的房间落门，只会把玩家关进空屋子 —— 这不是"难"，是坏掉的手感。
  
所以走廊房（`cr*`）与入口 / 撤离 / 商店 / 宝箱房 / Boss 前厅一律 `authored_layout_peaceful`：
  
不刷怪、门策略全放行、开局即算已清。

**实现落点**（改一处分，三处联动）：

| 文件                                        | 职责                                                  |
| ----------------------------------------- | --------------------------------------------------- |
| `FloorPlanGenerator.FLOW_DOOR_OPENING_M`  | 门宽 2.2m ⇒ `_port_creates_door_leaf()` 会建实体门扇        |
| `FloorPlanGenerator.FLOW_PEACEFUL_KINDS`  | 无怪房清单 ⇒ `authored_layout_peaceful`                  |
| `FloorPlanGenerator.FLOW_KIND_CONTENT`    | `NORMAL`/`HUB` 钉成 `COMBAT`（见下"内容洗牌"）                |
| `TowerDescent3D._flow_rules_active`       | 本层是 flow 规则 ⇒ 门策略覆盖（无钥匙 / 无命运卡 / 留清房门槛）             |
| `TowerDescent3D._stage_flow_room_entry()` | 进战斗房的完整时序（落门延迟 → 封锁 → 静默 → 出怪）                      |
| `TowerDescent3D._sync_flow_room_doors()`  | **门权限唯一推导点**：连通门可开启、封闭抵达门不可开启。见 §2.1.0          |
| `TowerDescent3D.set_room_seal()`（覆盖）   | 封锁 / 解封同步翻门权限 —— 只关板不翻权限 = 「封着但可开启」的漏          |
| `RoomDoor3D.set_proximity_target()`     | 把玩家交给门，门自己按距离开合（近 3.6m 开、远 4.4m 停 0.45s 关）      |
| `RoomDoor3D.set_openable()`             | 权限开关；不可开启时门板留下并拒绝一切自动开启                     |
| `TowerDescent3D._on_room_unsealed()`    | 清房 ⇒ 走 `_sync_flow_room_doors()` 把本房连通门恢复**可开启**（含共享边对端那扇） |
| `TowerDescent3D._build_flow_view_walls()` | 换房重建"房间外幕墙"（四面独立竖直纯黑面，门洞处开口，贴当前房间墙外）          |

#### 2.1.0 门有两个**正交**状态：权限 `openable` × 位置 `is_open`

业主 2026-10-30 二次裁定：

> 「远征-03 的这个门的状态，使用可开启和不可开启。在可开启状态，人走近了会自动打开，
> 然后再关闭。不可开启状态人走近了不会打开。」

于是「开没开」不再等于「能不能过」：

| 状态 | 判据 | 走近 | 画面 |
|---|---|---|---|
| **可开启** | 房间未封锁（连通门） | **自动双扇滑开**；走远超过 4.4m 停 0.45s 自动关上 | 关着：门板在门洞；开着：两扇贴墙 |
| **不可开启** | 战斗封锁中 / 封闭抵达门（退局气闸） | **纹丝不动** | 关着：门板在门洞 |

数值口径（`RoomDoor3D`）：

| 常量 | 值 | 为什么 |
|---|---|---|
| `PROXIMITY_OPEN_DISTANCE_M` | 3.6 | 玩家走到门口约 0.6s，门动画 0.24s ⇒ **人到位门前门已开完**；又略大于交互距离 3.4m，不会先闪一下 E 提示 |
| `PROXIMITY_CLOSE_DISTANCE_M` | 4.4 | 比开阈大 0.8m 形成**迟滞**，站在门槛附近不会反复开合 |
| `PROXIMITY_CLOSE_DELAY_S` | 0.45 | 走远后先留半秒，回头还能赶上 |

**为什么不"清完房直接把门推开"**：那样门只有「敞开」和「关死」两幅画面，
「可开启」这个状态在画面上根本不存在 —— 而业主这次要的正是这两种状态的区分。

| 时机 | 权限 | 入口 |
|---|---|---|
| 装配收尾（带加载圈首次进入） | 连通门可开启、气闸门不可开启 | `_open_all_flow_doors()` → 对每房跑 `_sync_flow_room_doors()` |
| 进未清战斗房 | 延迟落门 → 全部不可开启 | `_apply_flow_room_seal()` → `_stage_flow_room_entry()` → `set_room_seal()` |
| 清空敌人 | 连通门恢复可开启 | `_on_room_unsealed()` |
| 进已清房 / 和平房 | 连通门可开启、气闸门不可开启 | `_apply_flow_room_seal()` 的 `cleared` 分支 |

**为什么第四行必须有**：`_open_all_flow_doors()` 只在
`_complete_expedition_loading()` 里调用，而它要求 `_expedition_loading_active`（有加载圈）。
续局走的是另一条路 —— 装配完直接回灌存档，收尾不跑。少了这一行，玩家下线重进后
回头路的门会停在**不可开启**，等于把已清房变成死路。

**为什么两个状态都不存档**：`openable` 是 `cleared` / 封锁的派生量，
`is_open` 是玩家距离的派生量 —— 存任何一个都会与真相分叉，
那正是「门自己开了、存档又记着关」这类 bug 的成因。
塔楼的 `edge_states` 管的是**路线授权**，本关的连通性由 flow 骨架固定，两者不是一回事。

**共享边必须两头算**：门扇只在一端手里（另一端 `_door_nodes` 里没有节点）。
封锁时若只翻本房那几扇，对端那扇仍是「可开启」—— 玩家能在战斗中用身体把门顶开走出去。
`_sync_flow_room_doors()` 因此在本房取不到节点时，按"通向哪一间"去对端取同一扇。

**封闭抵达门**（`door_targets` 里目标为空串）是**退局气闸**，不是通道：
入口安全屋东墙那扇带 EXIT 牌、点了就退局。它**恒不可开启**，任何批量开门路径都必须跳过。
安全屋没有怪、开局即 `cleared = true`，清房回调会触发 —— 早期实现把 `door_targets`
里所有方向一起推开（含气闸），双扇滑门开到位就是"滑进墙里"，玩家看到的是
「出口的门不见了」（业主 2026-10-30 报单）。

**感应门不接受 E**：`RoomDoor3D.is_manual_interaction_enabled()` 为假 ⇒
`Dungeon3D.get_interaction_candidate()` 直接跳过它，交互圆点与提示都不会亮 ——
玩家走近就开，不需要也不应该再按一次。退局气闸走
`_get_configured_base_door_bindings()` 的独立通道，不受这条影响。


#### 2.1.1 进房时序（业主 2026-10-28 明确要求）

Gungeon 的节奏不是"跨过门槛门就拍在脸上"。本关按三段实现，**时长写在常量里**：

| 段         | 常量                              | 值        | 为什么                                       |
| --------- | ------------------------------- | -------- | ----------------------------------------- |
| ① 进门 → 落门 | `FLOW_ROOM_SEAL_DELAY_S`        | 0.30s    | 门扇落下时碰撞是启用的，贴着门框关会把人夹住；也给玩家两步路看清房间有几扇门    |
| ①′ 贴门洞时多等 | `FLOW_ROOM_SEAL_DOORWAY_WAIT_S` | 最多 0.90s | 玩家还站在门洞里就宁可晚关，不夹人；走出房间则不锁                 |
| ② 落门 → 出怪 | `FLOW_ROOM_SPAWN_PAUSE_S`       | 0.45s    | 这是"落锁"的反馈窗口：门砸下来、房间静一下、敌人才出场。没有它，门和怪挤在同一帧 |

配套的两处**必须**成立，否则时序会被打乱：

- `_prepare_revealed_hostile_room()` 在 flow 关卡**返回 false**：塔楼的做法是门一开就把下一间房的怪预先生成（玩家靠近时它们已经站好），那样 `_spawned_rooms` 会提前置真，真正的进房反而什么都不做。
- `_spawn_room_enemies()` 被覆盖成"排程"而不是"吞掉"：它同时被 `_repair_hostile_room_progress()` 复用（重进未清房时补刷）。若只是吞掉，玩家在落门延迟窗口里快步走出去一次，该房就永远停在**无怪、未清、门也锁不上** —— 一条路过的走廊能把房间永久弄坏。

#### 2.1.2 房间外不可观察

房间壳体是 2.8m 白盒，且 `DungeonRoom3D.set_stream_state()` 明确规定**壳体永久可见**
  
（流送契约，避免房间凭空消失）。相机在约 10m 高、俯角 −60°，视线必然越过墙顶 →
  
站在 A 房能看见 B 房的墙与地砖。

Gungeon 是"一次只有一间房是舞台"。本关用一圈**贴着当前房间墙外墙面的纯黑竖直幕墙**
  
（`FlowViewWalls`，随换房重建）达到同一观感。

| 项    | 值                                                 | 说明                   |
| ---- | ------------------------------------------------- | -------------------- |
| 水平范围 | 房间足迹外扩 `半墙厚 0.14 + gap 0.02`                      | 贴墙外表面，墙顶剖面完整露出       |
| 竖直范围 | `FLOW_VIEW_WALL_BOTTOM_M = −1.0` 到 `TOP_M = 26.0` | 下沿沉地；上沿远高于相机（10.26m） |
| 结构   | 四面各一个 `FlowViewWalls<Side>` 子节点                   | 便于逐面开关排查             |
| 材质   | unshaded 纯黑 + `disable_fog` + 双面 + 不投影            | 见下方坑 ①               |
| 重建时机 | 换房（`_refresh_flow_view_mask`）                     | 幕墙跟着当前房间走            |
| 缺口   | 只在**门洞位置**开口（洞宽/位置读门扇实际几何）                        | 见 §2.1.2.1、§2.1.2.2  |
| 显隐   | **恒显**，不按镜头位置收起                                   | 同上                   |

##### 2.1.2.1 为什么幕墙必须整圈密闭（2026-10-29 三次返工的最终结论）

这一天被来回改了三次，把边界试干净了，结论写死在这里，改动前先读完：

| # | 业主反馈                                      | 当时做法                     | 结果     |
| - | ----------------------------------------- | ------------------------ | ------ |
| 1 | 2026-10-28「顶部横截面可以露出来」/「会漏缝」              | 水平带洞遮罩 → 竖直幕墙            | ✅ 幕墙成立 |
| 2 | 2026-10-29 早「黑色区块硬切太难受了，摄像机会弹一下」          | 门洞留口 + 镜头出门收起整圈 + 去掉房间夹取 | ❌      |
| 3 | 2026-10-29 晚「进门的时候会看到外边的房间，黑色覆盖还是先还原」     | 幕墙回到整圈密闭 + 恒显            | ✅      |
| 4 | 2026-10-29 晚「别改了。这个黑幕是垂直的啊 摄像机碰撞这个别改了。保留」 | 只还原幕墙（垂直密闭恒显），夹取保留       | ✅ 当前   |

**第 2 条为什么必错**（这不是调参能救的）：

- 幕墙只围**当前房间**。镜头一旦离开这个圈，视线就绕到黑墙背后 ——
    
  看到的是隔壁房间、走廊、墙外地面，正是业主第二张截图里的画面；
- 而镜头跟在角色后 `CAMERA_DEFAULT_TRAILING_M = 4.914m`，玩家跨门时它必然还在旧房间，
    
  所以"镜头会出圈"不是偶发，是**每次过门都发生**；
- 门洞留口再加一层漏：洞口对着的就是外面那间，留口等于直接放弃房间边界。

**结论：黑幕只改"还原"，镜头碰撞（房间夹取）保留。**

业主 2026-10-29 晚有两句话，第二句是对第一句的更正：

> 「我只要你把黑幕的出现时机还原……摄像机镜头碰撞这个怎么也给我加回来了。」
>
> 「别改了。这个黑幕是垂直的啊 摄像机碰撞这个别改了。保留。」

所以第 3 条返工只做**幕墙**：改回垂直整圈密闭、恒显。镜头那条 `_clamp_flow_camera_into_room()`
  
**保留**（本来就是对的，之前是我误删）。

最终形态：

```text
幕墙 `FlowViewWalls`：垂直、整圈密闭、恒显，四面各一整块（-1m → 26m），零缺口
镜头 `_clamp_flow_camera_into_room()`：瞬时夹在当前房间足迹内缩 0.55m 内，只动 x/z
```

两者是配套的：幕墙恒显且密闭 ⇒ 镜头贴到房间边界时，看到的是自己这间；
  
镜头不越出房间 ⇒ 不会绕到黑墙背面。

试过并**已撤销**的改法：

| 方案                | 为什么撤                                        |
| ----------------- | ------------------------------------------- |
| 门洞留口 **+ 镜头出圈收起** | 收起那一半才是漏的原因（业主截图）；单留口、不收起是可以的 —— 见 §2.1.2.2 |
| 镜头出圈时收起幕墙         | 收起即无遮挡 ⇒ 看见隔壁房间                             |
| 把夹取改成阻尼（0.5s 收敛）  | 那 0.5s 镜头还在旧框里，过门会拖一段，观感不如瞬时换框              |
| 干脆删掉夹取            | 业主明确「保留」，且删了镜头会跟出房间                         |

校验（`probe_expedition03_playable`）：

| 断言                            | 判据                                           |
| ----------------------------- | -------------------------------------------- |
| `curtain_area == expect`      | 每面三角形面积 == 「整面 − 门洞」，两边都要对：开小了是黑块，开大了是漏      |
| `curtain_door_holes == lanes` | 门洞数 == 墙体门洞数（该开的地方开了没有）                      |
| `covered_bad == 0`            | 每个洞覆盖「门中心 ± 门洞净宽/2」（开够宽，不是一条缝）               |
| `curtain_always_on`           | 镜头强行挪到房间外，幕墙仍然可见                             |
| `camera_clamp outside=0`      | 每间房 × 四角内缩 1.5m 的站位，镜头都不许越出该房足迹（允许半墙厚 0.14m） |
| `camera_clamp height_drift`   | 夹取只动 x/z，高度漂移 ≤ 0.02m                        |

##### 2.1.2.2 门洞处必须开口（2026-10-30）

业主：「想办法把门的位置不要有黑幕」。

上一次（§2.1.2.1 第 3 条）为了修"进门能看见外面房间"，把门洞也一起封了。
  
封完之后门洞里是一块黑 —— 但那块黑其实分两层，只有一层该封：

| 层  | 是什么                       | 该怎么处理               |
| -- | ------------------------- | ------------------- |
| 门后 | 走廊 / 下一间的**实体**，被自己的墙与灯照亮 | 让它透出来（门洞就该透）        |
| 幕墙 | 贴在墙外的一圈纯黑竖直面              | 门洞处**必须开口**，否则它挡在门后 |

关键在于：漏的根因是**镜头跑出房间**（幕墙收起又或者围在别处），
  
不是"幕墙开了口"。只要镜头仍被夹在当前房间内（§2.1.6），
  
门洞开口就只是"门该有的样子"。

三条实现约束：

1. **洞的位置读门扇实际几何，不读 `lane_m` 声明。**
     
   实测一间 25×25 的 `boss_foyer`，`wall_door_lane_south` 声明是 0（墙面中心），
     
   而门扇实际在中心偏 −5m 处。按声明切洞 ⇒ 洞开在空心、门洞正对的那块幕墙原封不动。
     
   现在 `DungeonRoom3D.get_wall_door_lanes(side)` 直接量 `RoomDoor3D.global_position`，
     
   同侧多门也天然覆盖；只有在门扇还没建出来时才退回声明值。
2. **洞的上沿 = 房间墙顶 2.8m，不是门洞净高、也不是幕墙上沿。**
     
   两个边界各被业主退回过一次，都是"上沿放错位置"：
   | 上沿           | 表现                                                                                 | 判定   |
   | ------------ | ---------------------------------------------------------------------------------- | ---- |
   | 2.5m（门洞净高）   | 门洞上方 2.5→26m 是一堵**悬空黑墙**，比墙顶还低 0.3m，露出一圈凭空多出来的黑                                    | ❌    |
   | 26m（挖到顶）     | 洞上方的口子通到天，俯视时视线越过 2.8m 墙顶从口子里穿出去，看到门后那间的墙面 —— 屏幕上一个漏斗状亮梯形（业主 2026-10-30「为什么上面有一块」） | ❌    |
   | **2.8m（墙顶）** | 洞只在"门洞 → 自己房间墙顶"这一段开；墙顶以上与其他三面同一套判据                                                | ✅ 当前 |
   为什么开到墙顶仍能看见门后：相机 10.26m、门洞净高 2.5m，穿过门洞的视线在幕墙
     
   平面（墙外 0.16m）上的高度最大约 `2.5 − (10.26 − 2.5) × 0.16 / 5.5 ≈ 2.28m`，
     
   远低于 2.8m 的洞上沿。实测像素级漏光 **2**（上限 500）。
3. **洞宽要留视差余量 `FLOW_VIEW_DOOR_HOLE_BLEED_M = 0.60m`。**
     
   幕墙在墙外 0.30m 处，门洞在幕墙平面上的投影以镜头为中心放大
     
   `(d + 0.30) / d`；镜头最近可贴到 d = 0.55m ⇒ 门洞半宽 1.1m 在幕墙上要占 1.70m。
     
   洞**偏大无害**（超出部分被墙垛实体挡住），洞**偏小就是一条黑边**。

配套：门后那间 5×5 连通小间原本**一盏灯都没有**（实测 9 间里 8 间为 0），
  
洞开了也是看进一个没光的盒子。`_ensure_flow_passage_lighting()` 按几何判据
  
（`max(x,y) ≤ 8m` + flow 开关，不认 room_id）补一盏窄范围灯：范围 4.5m（小间半对角
  
3.54m，不外溢）、能量 3.0、高 2.35m。

> ⚠️ 范围不能放大：`gl_compatibility` 每物体最多 8 盏灯，9m 范围会让九盏灯盖住
>   
> 隔壁战斗房、把房间顶灯挤出预算，房间反而更暗（实测过）。

**为什么必须竖直、不能是水平面**（这是本关返工最多的一处，两个原因都成立）：**为什么必须竖直、不能是水平面**（这是本关返工最多的一处，两个原因都成立）：

1. **视差**。水平遮罩在 Y = 2.88m、相机在 10.26m，视线穿过平面的交点比地面落点
     
   更靠近相机（约 0.72 倍）。于是"世界坐标的洞"和"屏幕上的洞"永不重合：
     
   洞外扩就露出墙外地面（业主红框那条缝），洞内缩就把墙顶剖面盖黑。
     
   挪相机位置缝宽还会变 —— **这个形状无解**，试过 0.35m 外扩 / 0.05m 外扩 / 0.35m 内缩，都不对。
2. **观感**。业主 2026-10-28：「顶部横截面可以露出来，这样更有顶视角游戏的感觉」。
     
   水平面在墙顶上方 0.08m，正好把房间四周的墙顶剖面整圈盖掉 ——
     
   房间看着像个"顶被掀了的盒子"，反而没有顶视角厚度。

竖直幕墙两个问题都没有：从房间内看向房间外的任何视线都必然穿过它（与相机位置无关），
  
而它是竖直的，俯视时完全不遮挡墙顶水平剖面。

> **为什么之前没发现这条缝**：门板一直挡在门洞里（升降门只抬起 0.32m，视觉上门洞始终被盖住）。
>   
> 门改成双扇对开之后门洞真的通了，缝就从门洞透出来了 —— 这是"改了 A 暴露了 B"的典型。

三条踩过的坑：

- 材质必须 `disable_fog = true`。unshaded **不等于**不参与环境雾，漏了这一步
    
  遮罩会被染成灰蓝，看上去仍然像"墙外有一层远景"。
- **挂载点不能挂在 `Blocks/Expedition` 下**。那是楼层几何容器，`visible` 归楼层流送管，
    
  装配后实测 `is_visible_in_tree()` 为 `false` —— 遮挡跟着一起失效。现在直接挂场景根。
- **换房重建时必须先 `remove_child()` 再 `queue_free()`**。`queue_free()` 是延迟的，
    
  名字要到帧末才释放；紧接着 `add_child` 同名新节点，Godot 会因重名把**新**节点
    
  改成匿名 `@MeshInstance3D@NNN`，于是它既搜不到名字、又被当成"塔楼高墙穿房"报假红。
    
  另外清理要按**名字前缀全树扫描**（挂载点在历史上变过），不能只看当前 parent。

不选"隐藏非当前房间"：壳体可见是流送契约，改它会把走廊、隔壁门扇、相机门代理一起卷进来。
  
不选"加高墙"：业主已确认 2.8m 墙高没问题，这是相机视线问题。

#### 2.1.3 入口安全房的「[E] 退出战局」

入口房那道**封闭抵达门**（`door_targets` 该侧为空串）是主动弃局入口。契约沿用
  
[独立关卡出生安全房离场契约](../development/2026-09-19_standalone_safe_room_exit_contract.md)：
  
背包 / 主副武器 / 装备背包全部丢失，保险格按规则保留，返回 99F 基地场景。

flow 关卡上这扇门原本**没有门扇**：程序化壳体只按端口建门扇，而这扇门不属于任何拓扑边，
  
只在 `doors` / `door_targets` 里登记过 —— `_get_configured_base_door_bindings()` 取
  
`get_door_node(side)` 得到 null，整条交互静默消失（远征01 因为门画在静态美术 TSCN 里，绕过了这个坑）。
  
现在给入口房补一条**无目标端口**（`retreat_<side>`，不参与 `connections`），让它走正常门扇构建路径。

#### 2.1.4 内容洗牌：`NORMAL`/`HUB` 必须钉成战斗房

EGT 骨架已经用 `kind` 指定了每间房的职责，不需要再走塔楼那套"一层里摊开各种功能房"的内容洗牌。
  
漏钉的实测后果：15 间"内容房"里只有 3 间是 `COMBAT`，其余被洗成 TRAP / STORAGE / EVENT / SCAVENGE
  
—— 不刷怪，于是"进房封门、清完开门"几乎从不发生，玩家看到的就是**门从来不关、怪也没有**。

> **走过的一段弯路（记在这里防复发）**：白盒阶段为"没有刷怪、门打不开会卡死"，
>   
> 曾把门洞做成 5m **纯通洞**（`open_passage`，不建门扇）。那是把"缺刷怪"的临时状态
>   
> 固化成了关卡设计。现在刷怪链路是通的（`_spawn_room_enemies` 对任何非无怪房都会
>   
> 刷，且**生成失败时自动放行房间**，不会留锁门），门就该是门。

#### 2.1.5 门扇开合：双扇对开（`slide`）

业主 2026-10-28：「这个门，帮我做成左右打开的。」

本关的门扇**不是升降**，是**两扇向左右滑进门洞两侧墙体**。
  
同一个资产（`ENV-TOWER-DOOR-LEAF-5M`）两种开合方式，由 `RoomDoor3D.set_opening_style()` 选择：

| 方式         | 谁用                               | 表现              |
| ---------- | -------------------------------- | --------------- |
| `lift`（缺省） | 塔楼、基地99F、远征01/02                 | 门板整体垂直抬起 0.32m  |
| `slide`    | **远征03 的 `procedural_shell` 房间** | 两扇各覆盖半个门洞，向左右滑出 |

几何口径（`RoomDoor3D` 常量）：

| 项        | 值                     | 说明                                  |
| -------- | --------------------- | ----------------------------------- |
| 每扇可视宽度   | `门洞宽 × 0.55`（= 1.21m） | 系数 `SLIDE_PANEL_WIDTH_SCALE = 1.10` |
| 两扇中心初位   | ±0.55m（= 1/4 门洞宽）     | 关门态，中间重叠 0.11m                      |
| 开门行程     | 左右各 1.16m             | 门板内缘退到门洞边线之外                        |
| 右扇门厚偏移   | 0.008m                | 重叠区不同 z，避免共面闪烁                      |
| **门板厚度** | **0.18m < 墙厚 0.28m**  | 滑出门洞后整块落在墙体内部 ⇒ 观感是"滑进墙里"           |
| 碰撞       | 单块覆盖整个门洞，不跟门板走        | 开完立即放行；半开时人钻不过去                     |

**门板必须用塔楼门扇（厚 0.18m），不能用基地 99F 的滑升门体（厚 0.88m）**：
  
后者滑到门洞两侧时会凸出 0.28m 墙厚整整 0.31m，玩家看到的是"一整块门体贴在墙外面"
  
（业主 2026-10-28 报的原话就是"门看起来贴在墙外面"）。所以 `_door_panel_visual()`
  
对 `slide` 一律返回塔楼门扇 —— 语义上也对：EGT 的门是普通门，不是气闸。

**为什么可视宽度不是精确的 0.5**：门板美术是「一整扇 2.2m 的门」，四周留了边框内缩。
  
直接压成 50% 时，两扇拼起来的**可见板面**只有约 2.0m —— 中间会露出一条深色竖缝
  
（实测截图能看到，缝宽约占单扇 7%）。放大到 1.10 系数后中间有真实重叠，缝消失。
  
超出门洞的两端（各 0.055m）整块落在墙体内部，被深度测试挡住，不会露出来。

**为什么不用"裁剪一半"**：需要给美术材质加 `discard`，会丢掉 PaletteUV 色盘
  
（`preserve_authored_palette` 的契约），代价大于收益。

**为什么滑出门洞看不见**：门洞两侧是 0.28m 厚的实墙，门扇只有 0.18m 厚，滑出去的部分
  
整块在墙体内部 —— 观感就是"门滑进墙里"，不需要给墙开门槽，也不会与墙面共面打架。

> **关门时中间那条亮线不是缝**：把两扇材质换成纯色无光照后实测 80 列全是纯色、
>   
> 非纯色 0 列 —— 几何完全覆盖。那条亮线是门板美术自带的发光竖条（原本在单扇门中央，
>   
> 压扁后跟着落在每扇中央）。别再调宽度系数"修缝"，那条路是死路。

**落点**：`TowerDescent3D._append_plan_room_record()` 对 `procedural_shell` 房间写
  
`record["door_opening_style"] = "slide"`；其余关卡**不写这个字段** ⇒ `RoomDoor3D` 用缺省
  
升降，行为逐字不变。

#### 2.1.6 相机：不做"墙碰撞后自动复位"

业主 2026-10-28：「摄像机会被自动复位（就是场景墙碰撞后）的那个功能。去掉。」

塔楼原有的镜头避让是：墙进入镜头通道 ⇒ 镜头抬高 0.30m，并把沿后方轴的距离从 3.1m
  
收到 0.15m，离开墙再弹回。玩家感知是「贴墙镜头突然跳到头顶，走开又弹回来」。

本关**完全关掉这条路径**（`_update_camera_lower_wall_lift()` / `_update_camera_stair_slab_drop()`
  
在 `_flow_rules_active` 时把目标锁死在基准值，平滑仍在跑 ⇒ 是"回到原位"而不是"瞬跳"）。

关掉之后镜头严格按「角色 + 后方 4.914m」跟随，贴墙背对房间中心时会落到墙外 ——
  
所以补一条**边界限制**（不是碰撞避让，业主指定保留）：

| 项      | 值              | 说明                              |
| ------ | -------------- | ------------------------------- |
| 约束范围   | 当前房间足迹内缩 0.55m | `FLOW_CAMERA_ROOM_INSET_M`      |
| 改动维度   | **只夹水平 x/z**   | 高度、俯角、跟随距离基准一律不动（实测高度漂移 0.000m） |
| 是否探测墙体 | **否**          | 只按房间地板边界夹取                      |
| 生效时机   | **瞬时**         | 过门那一帧完成；阻尼版实测会拖 0.2~0.5s，已被否    |

业主 2026-10-28 反对的是「墙碰撞就抬升收拢」，2026-10-29 对房间夹取的原话是
  
「摄像机镜头碰撞这个别改了。保留」—— 两者不冲突：**抬升/收拢不要，边界夹取要**。

探针 `camera_clamp` 是这条契约的守卫：每间房四角内缩 1.5m 的站位，镜头全部在足迹内
  
（允许半墙厚 0.14m），高度漂移 0.000m。

### 3.1 房型映射表

| 9 | `CONNECTOR` 连接房 | `CONNECTOR`  | `COMMON_ROOM`     | `TRAP`         | `main`        | 是     | 无专属敌人、常带环境危险         |

**三条映射裁决（改动需重开）：**

1. **`EXIT` → 撤离房，不是下行门。** 远征是单层，没有下一层。Gungeon 的 `EXIT` 是"本层结束、进入下一层"，

   本关把它落在"本层结束、结算离场"，语义位置一致、机制按远征口径。**不得**为对齐名字而新增下行门。
2. **`SHOP` → `MERCHANT`（2026-10-30 落地；此前是"待施工"。）**

   原裁决写的是"复用 `EVENT` 房型 + 商人终端"，理由是 `ROOM_TYPES_WITH_HOSTILES` 与内容类型白名单里都没有 `SHOP`。
     
   那条理由只对了一半：**白名单要的是 `room_type`，而 flow 房间的运行时 `room_type` 取自 `content_type`**
     
   （`room_from_source()` 的 `type` 字段 → `TowerDescent3D._append_tower_record()`），
     
   而 `content_type` 并没有走那份 4 项白名单。所以不存在"必须先改 `GameDesignConfig`"这道门。

   改成 `MERCHANT` 而不是 `EVENT`，是因为 `EVENT` 房的终端走的是
     
   `Dungeon3D._on_service_activated()` 的 `"event"` 分支 → `_resolve_event_room()`
     
   （随机 CURSE / BLESSING / TRADE / GAMBLE / REVEAL / SUMMON），**打开的是随机事件而不是商店**。
     
   只有 `room_type == "MERCHANT"` 才会命中 `"merchant"` 分支 → `_open_merchant()`。

   实证：改之前每张 flow 都有 1 间 `shop` 房，但它的 `content_type` 是空串 →
     
   被 `_assign_content_types_data_driven()` 洗成 `COMBAT` / `STORAGE` / `TRAP`，
     
   于是 `DungeonRoom3D._build_detail()` 里 `if room_type in ["MERCHANT","UPGRADE","EVENT"]`
     
   永远不成立，**服务点一个都没建过，商人 UI 一次都没打开过** —— 且没有任何报错。
     
   症状就是「商店房在、门能进、里面是空的」。
3. **`CONNECTOR` 用 `TRAP` 而不是 `EVENT`。** `TRAP` 在 `ROOM_TYPES_WITH_HOSTILES` 内，

   能带环境危险 + 少量敌人；`EVENT` 是非敌对房、要点终端才结算，语义不符。

### 4.2 单张骨架的读法（以 `flow_01` 为例）

```text
entry ── n01 ── n02 ── hub_01
                        ├─ n03 ── reward_01
                        └─ n04 ─┬─ boss_foyer ── boss ── exit
                                └─ hub_02 ─┬─ n05 ── n06 ── reward_02
                                           └─ n07 ── shop

回连边（单向，箭头即唯一通行方向）：
    reward_01 ──► n01
    reward_02 ──► hub_02
```

- **16 间房 / 17 条边 = 15 树边 + 2 回连边 ⇒ 2 个环**（`E − N + 1`）。
- **两条回连边都是「宝箱 → 回到主干」**：Gungeon 的手法是把宝箱放在**单向环的末端** ——
    
  进去是一条路，出来只能绕一圈，玩家不会走回头路。这与"宝藏放在死路尽头"的区别是
    
  **不需要多建一间房、多铺一条走廊**。
- `hub_01` 有 4 条出边、`hub_02` 有 3 条 ⇒ 它们必须是 `HUB` 房型（多门位），
    
  不能退化成 `std_25x25`。
- 门数分布逐张对照 `第一层房间位清单.csv`，断言在
    
  `scripts/build_expedition03_level_plan.py` 的 `EXPECTED_DEGREES`。

> 每张骨架的**完整节点清单（102 行）**&#x89C1;本页**附录 A**，逐行列 `node_id / kind / 模板 / 尺寸 / 父房`。

### 4.3 环的表达方式

本关采用 Gungeon 的两层拓扑：

| 层 | 字段                                  | 谁读它                                          | 现状                  |
| - | ----------------------------------- | -------------------------------------------- | ------------------- |
| 树 | `parent_key` / `tree_edges[]`       | 摆位器与拓扑                                       | 已支持                 |
| 环 | `loop_edges[]` / 计划里的 `connections` | `EgtFlowAssembler` 组装 + `TowerDescent3D` 声明边 | **已实现**（2026-10-28） |

> **`parent_key` 不能表达环**：它每个房间只有一个父，边数恒等于 `N − 1`。
>   
> 所以 flow 的计划里**另有一份 `connections`（无向边清单，存运行时 id）**，
>   
> 运行时优先按它声明拓扑，再回退 `parent_key`（21 → 原为只读 parent_key，
>   
> 结果 flow 模式 `_declared_edges = 0`、一扇门都不建）。

**回连边的三条硬约束**（违反即拒绝生成，不靠人工审）：

1. **不得成为某个节点的唯一入口。** 回连边的终点必须已有树父房（`check_expedition03_flow_quotas.py` 已断言）。
2. **不得跳过 Boss 前厅或 Boss 房。** 回连边两端必须都在 `boss_foyer` 之前，或都在之后。
3. **必须可几何闭合成环。** 拼装期若两端房间不相邻（无法共用墙或无法铺 ≤30m 走廊），

   该回连边**丢弃并记 `closure_skipped`**，不得为它强行挪房或拉超长走廊。

   丢弃只影响"能不能绕近路"，不影响房间数与主线可达性。

## 6. 注入规则

注入 = 在骨架已经定下来、但还没有坐标的时候，按 `{类型, 锚点, 概率, 条件}` 往图上插节点。

**它只加节点、不改树的边**，所以不影响 §3.3 的房型配额计算基准。

### 6.1 三条规则（本关启用）

| `inject_id`           | 类型        | 锚点                     |                  概率 | 作用域      | 条件 |
| --------------------- | --------- | ---------------------- | ------------------: | -------- | -- |
| `inj_secret_room`     | 普通隐藏房     | **死胡同优先**；1/5 概率挂到任意房间 |             **0.9** | 每层共享     | 无  |
| `inj_npc_secret_room` | NPC 隐藏房   | **开局预抽**（run 级）        | 0.2（`EMPTY` 权重 0.8） | **整局一次** | 无  |
| `inj_fireplace`       | 壁炉房（藏层入口） | 死胡同优先                  |                 1.0 | 每层共享     | 无  |

### 6.2 两条来自 Gungeon 的关键机制

**① 隐藏房分两套抽，互不占用。**

普通隐藏房每层独立掷 90%；NPC 隐藏房**整局开局抽一次**、预留给将来某一层，`EMPTY` 权重 0.8。

结果：不会出现"五层连着都没刷到"的极端局，也不会一层堆两个。**本关单层，所以 `run` 级规则退化为一次掷骰。**

**② 概率与锚点的分工。**

概率回答"有没有"，锚点回答"挂在哪"。死胡同优先这条**同时**解释了 Gungeon 的

「壁炉房通常在死胡同」和「隐藏房通常在死胡同」—— 它们是同一套落点偏好的两个消费方。

### 6.3 本关的锚点定义

| 锚点                  | 定义          | 可用房型                           |
| ------------------- | ----------- | ------------------------------ |
| `dead_end`          | 出边数 = 0 的节点 | 任何 `main` 房                    |
| `any_room`          | 任意节点        | 除 `ENTRANCE` / `EXIT` / `BOSS` |
| `run_level_preroll` | 开局抽定，不随层    | 见 ①                            |

### 6.4 注入房**不计入** §3.3 的配额

隐藏房与壁炉房是**附加**节点，不在 `room_quota` 里，也不进 `flow_*.json` 的 `nodes[]`。

它们的数量期望是：每层 `0.9 + 0.2 + 1.0 ≈ 2.1` 间（含 NPC 隐藏房的整局摊薄）。

⇒ **实际单局房间数 = 16~~18（骨架）+ 0~~3（注入）**。文档与验收断言都必须写这个区间，不要写死 16~18。

## 7. 随机性边界（写清楚"什么变、什么不变"）

### 7.1 每局会变

| 2 | `NORMAL` 用哪个模板      | 4 选 1             | 只改大小，不改数量与拓扑                     |

| 4 | 环能不能闭合              | 能 / 丢弃            | 丢弃记 `closure_skipped`，不挪房        |

| 7 | 易碎小物件撒点（2026-10-29） | 每房 3~6 件、五个品类轮转   | 房内留边 0.9m、离门 2.4m、彼此 1.1m；见 §7.4 |

### 7.3 确定性复现

```text
layout_id = hash(run_seed + level_id + floor_rule_version + flow_id)
flow_id   = hash(run_seed, level_id, 0) % 6
```

同一 `run_seed` 必须复现**完全相同的骨架、模板、坐标与注入结果**。

`layout_id` **包含 `flow_id`** —— 否则两张不同骨架会撞同一个存档指纹（01/02 是单骨架，没有这个问题）。

### 7.4 易碎小物件的随机撒点（2026-10-29）

罐子 / 书本堆 / 花瓶 / 椅子 / 木箱（见[场景可交互低模物件设计](场景可交互低模物件设计.md)）会撒进本关房间。
  
**这不是关卡专属分支**：`level_plan.json` 顶层写了 `interactive_clutter` 段，`DungeonRoom3D` 就按这段数据撒点；
  
任何关卡写同款段效果一致，代码里没有 `expedition_03` 这个字符串。

| 参数                   | 值                    | 为什么                                                |
| -------------------- | -------------------- | -------------------------------------------------- |
| `per_room_min/max`   | 3 / 6                | 少于 3 看不出「这房有杂物」，多于 6 在 25×25 里开始拥挤                 |
| `exclude_room_types` | `STAIR_LOBBY`、`BOSS` | 安全房已摆固定五件；Boss 房有自身构图，不该被杂物破坏                      |
| `min_room_size_m`    | 8.0                  | 5×5 十字路口四面都是门，门净空会把整间房清空 ⇒ **显式跳过**，不让它「碰巧过滤成 0 件」 |
| `wall_margin_m`      | 0.9                  | 留出贴墙设施与玩家擦身空间                                      |
| `door_clearance_m`   | 2.4                  | 不堵门，也不挡清房后的通行                                      |
| `min_spacing_m`      | 1.1                  | 不叠成一堆                                              |

**种子口径**：`rng.seed = hash([room_seed, "interactive_clutter", room_id])`。房间流送卸载重建、读档后位置逐格不变
  
—— 玩家离开再回来不会看到罐子自己换地方。这条由探针 `E3_CLUTTER_DRIFT` 逐件比对位置与朝向，0 处漂移。

实测（种子 100990）：17 间房、75 件、10 间 5×5 走廊房显式跳过、2 间排除；27 扇门仍全通（`blocked=0`，`reachable=27/27`）。

### 7.5 随机家具与可搜索容器（2026-10-30 修正判据）

家具 / 可搜容器**不是**本关配置项，是 `DungeonRoom3D._build_content()` 的人造陈设。
本轮修的是**判据用错了量**，不是"值设小了"：

| 问题 | 修复前 | 修复后 |
|---|---|---|
| 档位 | `_append_plan_room_record()` 一律传 `tower_cell`（15m 格子）⇒ 45×40 的大厅与 5×10 的走廊同档 | flow 房间按真实面积取档（见下） |

（`ROOM_DIMENSIONS`：396 / 832 / 1496 / 2352 ㎡）**相邻两档的几何平均**，
因为面积比才是等距的：

```text
< 574㎡   → small   (3 件)
< 1115㎡  → medium  (5 件)
< 1876㎡  → large   (7 件)
≥ 1876㎡  → arena   (9 件)
```

**只对 flow 房间生效**：判据是 `spec.procedural_shell`（`FloorPlanGenerator` 只在 flow
分支置真）。塔楼模块壳与远征01/02 继续 `tower_cell`，行为逐字不变。

#### 7.5.1 本关已整段关闭（2026-10-30 晚）

业主看完 §7.5 的实测表后要求：「把程序生成的这些箱子每个房间都去掉。」

关法是一条数据段，不是代码里的关卡判断：

```json
"furnishing": {
  "schema": "shellstorm2.battle.room_furnishing",
  "enabled": false
}
```

透传链：`FloorPlanGenerator` plan 顶层 → `TowerDescent3D._append_plan_room_record()`
→ 房间 record `procedural_furniture_enabled=false` → `Dungeon3D` / `TowerDescent3D`
两处 `configure()` → `DungeonRoom3D._build_content()` 把 `prop_count` 归零。
未写本段的关卡沿用缺省 `true`，塔楼与远征01/02 行为逐字不变。

关闭后实测（seed 100990）：29 个房间 **家具 0 件、可搜索容器 0 件**（原 103 / 52）。

| 不受影响 | 原因 |
|---|---|
| 安全房固定五件易碎件 / Boss 房构图 / 服务台 / 撤离信标 | 各自专门分支，不进家具循环 |
| 易碎小物件（§7.4） | 走 `interactive_clutter` 另一段，17 间房 68 件 |
| 宝箱（`chest_placements`） | 走 `_build_treasure_chests()`，与家具无关 |

两条实现上的坑，写下来免得下次重踩：

1. `prop_count += 2`（`STORAGE` / `SCAVENGE` / `BASEMENT`）必须排在关闭判据**之前**。
   第一版排在之后，这两类房各被 `+2` 抵回来 ⇒ `reward_01` / `fireplace_room_inj2` 各剩 2 件。
2. 易碎件数量随开关联动：撒点洗牌消耗的随机数个数 = **候选点数**，去掉家具后候选变多
   ⇒ `wanted = randi_range(3, 6)` 抽到的值随之改变 ⇒ 75 → 68 件，位置也不同。
   这是"家具在/不在"的连带效应，不是漂移（`E3_CLUTTER_DRIFT` 仍为 0）。

## 13. 改本关之前先读这一节

1. **配额是硬契约。** 改 §3.3 任何一个数字，先跑 `check_expedition03_flow_quotas.py`；

   它红着就说明"一一对照"已经断了，此时不要继续改几何。
2. **环只声明、不建门**（阶段 A）。看到 `loop_edges` 出现在数据里，不要以为游戏里已经能绕圈。
3. **注入房不在配额里。** 单局房间数是 `16~18 + 0~3`，任何写死 18 的断言都会误报。
4. **`layout_id` 必须含 `flow_id`。** 六张骨架共用同一份 L2，不含 `flow_id` 会让不同骨架撞档。
5. **`runtime_enabled = false` 是刻意的。** 生成器没施工之前不要改成 `true` ——

   那会让加载器按 `authored` 口径把 `floor_00.json` 当固定版图跑，看起来"能进"，但实际上和本页设计无关。

这一节记根因，防止后人再用同样的方式改回去。

### B.1 进房后刷出 11.9m 的墙和空阻挡

**根因**：塔楼的走廊连接器（`TowerDescent3D._build_tower_horizontal_corridor`）与
  
楼层台座外墙（`TowerFloorStage3D._build_outer_shell`）是 **5m 栅格 + 11.9m 高** 的一套几何。
  
它按 `_room_door_world_position()` 取门位铺墙，而 flow 房间的门位落在**半个模块**上
  
（15m 墙的门在 lane −2.5），塔楼模型表达不了 ⇒ 在房间内部凭空铺出 11.9m 墙，
  
连同 `CorridorWallCollision_*` 一起（就是"空阻挡"）。

**修法**：给"墙体由房间自己生成"立一条判据
  
（`_room_walls_owned_by_static_layout()` 扩展为也认 `room_owns_walls`），
  
命中就**完全不建连接器几何**。静态布局（01/02）与程序化壳（03）共用同一个结论。

**防回归**：`probe_expedition03_playable` 断言「>5m 高的墙不得与任何房间足迹相交」。

### B.2 靠墙边缘闪面

**根因**：房间自带 `Floor`（顶面 Y=0），楼层台座也铺一层通用砖（同样 Y=0）——
  
两套砖共面 z-fighting。原来的可视砖挖洞判据只认 `type == "STAIR_LOBBY"`，
  
而 flow 的入口房 type 是 `SAFE_ROOM`、其余是 `COMMON_ROOM`，一个都命中不了。
  
（01/02 靠静态布局那条路绕开了这个坑，所以只在新的 flow 关卡上暴露。）

**修法**：`_stair_lobby_visual_holes()` 增加一条：`procedural_shell` 房间按
  
`custom_dimensions` **精确挖掉**通用砖。承重碰撞不受影响（它只吃 `_hole_rects()`）。

**防回归**：同一条验收断言「每个房间足迹被地砖洞覆盖 ≥99%」。

### B.3 进房关门 / 清怪开门

**根因**：机制在项目里是齐的（`set_room_seal` / `_mark_room_cleared`），
  
flow 关卡缺三样东西：**门扇没建**（门洞是 5m 通洞）、**没有封门触发**、
  
**清房不自动开门**。

**修法**（见 §2.1 的落点表）。

**防回归**：验收会真的进一间房、断言"已封锁且 0 扇门开着"，再清房、
  
断言"已解封且门自动打开"。

### B.4 房间钥匙

**根因**：`Dungeon3D._door_policy_for_edge()` 的默认值是
  
`requires_clear/requires_key/triggers_fate` 全 true，flow 关卡没有任何覆盖。

**修法**：`TowerDescent3D._flow_rules_active` 为真时返回
  
`{clear: true, key: false, fate: false}` —— 只留"清房"这一条（它是 EGT 的房门语义），
  
钥匙与命运卡都关掉。入口那一跳（entry→room_01）仍按 `_expedition_entry_gate_edges`
  
全放行，开局不会卡。

**防回归**：验收断言「key_locked = 0 且 fate_gated = 0」。

## 附录 C：2026-10-28 报单（第二轮：视野与手感）

业主第二轮报的是**观感与节奏**，不是"能不能走"。三条都只有真的玩起来才看得见。

### C.1 墙外可被观察

**现象**：站在房间里能看见隔壁房间的墙与地砖（截图里红框圈出的就是隔壁房与走廊）。

**根因**：不是墙矮。房间壳体 `set_stream_state()` 明确规定**永久可见**（流送契约），
  
相机在 10m 高、俯角 −60°，视线必然越过 2.8m 墙顶落到别处的地面上。
  
业主已确认 2.8m 墙高没问题 —— 这是**相机视线**问题，不是几何问题。

**修法**：~~`FlowViewMask` —— 一层只给当前房间挖洞的纯黑水平面（Y = 2.88m）~~
  
→ **已废弃，改为 `FlowViewWalls` 竖直幕墙**。水平面有视差（洞外扩就露墙外地面、
  
洞内缩就盖住墙顶剖面），且会把墙顶横截面整圈盖黑。详见 §2.1.2 与附录 E。
  
洞 = 当前房间足迹（含 0.35m 墙厚余量），其余区域全黑；换房时重建（洞跟着走）。
  
判据：相机永远高于遮罩，所以遮罩挡住的就是"墙外的一切"。

两个坑：

1. **`disable_fog = true` 必须写**。unshaded ≠ 不参与环境雾，实测漏掉时遮罩被染成
     
   灰蓝（采样 56,68,78），看上去仍然像"墙外有一层远景"。
2. **洞只能给当前房间**。第一版给所有房间挖洞 —— 等于没做，整层房间全都露着。

不选"隐藏非当前房间"：壳体可见是流送契约，改它会把走廊、隔壁门扇、相机门代理一起卷进来。

**防回归**：`probe_expedition03_playable` 断言「恰好 1 间房（当前房）头顶不被遮，
  
其余全部被遮」以及「当前房不得被遮」。

### C.2 进房时序：落门延迟 + 关门后的静默

业主原话：「包括一些进门后多少时间产生关门，而且我记得还有带一个短暂的停顿。」

| 段       | 常量                              | 值        | 理由                            |
| ------- | ------------------------------- | -------- | ----------------------------- |
| 进门 → 落门 | `FLOW_ROOM_SEAL_DELAY_S`        | 0.30s    | 门扇落下时碰撞启用，贴门框关会夹人；也给玩家两步路看清房间 |
| 贴门洞时多等  | `FLOW_ROOM_SEAL_DOORWAY_WAIT_S` | 最多 0.90s | 宁可晚关也不夹人；走出房间则不锁              |
| 落门 → 出怪 | `FLOW_ROOM_SPAWN_PAUSE_S`       | 0.45s    | "落锁"的反馈窗口：门砸下来、房间静一下、敌人才出场    |

**根因（原来的顺序是反的）**：`super(room)` 里 `_spawn_room_enemies()` 立刻刷怪，
  
而封门在它之后 —— 玩家看到的是"怪先出现、门才落"。

**修法**：flow 关卡覆盖 `_spawn_room_enemies()`，把刷怪推迟到 `_stage_flow_room_entry()`
  
里落门之后再执行（`_flow_spawn_passthrough` 做一次性放行）。
  
同时 `_prepare_revealed_hostile_room()` 在 flow 关卡返回 false —— 塔楼的"门一开就预刷下一间"
  
会提前置真 `_spawned_rooms`，真正的进房反倒什么都不做。

> **一个必须避开的坑**：覆盖 `_spawn_room_enemies()` 时不能只是"吞掉调用"。
>   
> 它同时被 `_repair_hostile_room_progress()` 复用（重进未清房时补刷）——
>   
> 吞掉的话，玩家在落门延迟窗口里快步走出去一次，该房就永远停在
>   
> **无怪、未清、门也锁不上**。必须改成"排程"，让重进房能重新走一遍时序。

**防回归**：验收断言「进房瞬间未封锁」「约 100ms 内封锁」「落门时存活数为 0」
  
「静默结束后存活数 > 0」「清房后门自动全开」。

### C.3 初始房间的「退出战局」

**现象**：入口安全房那道门按 E 毫无反应。

**根因**：flow 关卡走**程序化壳体**，门扇只按 `connection_ports` 建
  
（`_build_door_for_port`）。而这扇"封闭抵达门"不属于任何拓扑边，只在
  
`doors` / `door_targets` 里登记过 → 一个门扇都不建 →
  
`_get_configured_base_door_bindings()` 取 `get_door_node(side)` 得到 null →
  
`[E] 退出战局` 整条交互静默消失。远征01 因为门画在静态美术 TSCN 里，绕过了这个坑。

**修法**：`_append_closed_arrival_door_port()` 给入口房补一条**无目标端口**
  
（`retreat_<side>`，不写进 `connections`），让它走正常门扇构建路径。
  
落门后 `_open_all_flow_doors()` 会把它**显式关掉**（连通门全开、封闭门全关）——
  
它是气闸，开着等于在墙上开个通向房间外的洞。

**契约**不变，见 [独立关卡出生安全房离场契约](../development/2026-09-19_standalone_safe_room_exit_contract.md)：
  
背包 / 主副武器 / 装备背包全部丢失，保险格保留，返回 99F 基地场景。

**防回归**：验收走完整交互链 —— 站到门内侧 1.2m → `get_interaction_candidate()` 必须是
  
`configured_expedition_retreat` → `perform_interaction()` → `HUD/ExpeditionExitWarning` 出现。

### C.4 顺带修好的一条：内容洗牌把战斗房洗没了

`FLOW_KIND_CONTENT` 只钉了入口 / 撤离 / Boss / 前厅四种，`NORMAL` 与 `HUB` 留空，
  
于是走塔楼的内容洗牌。实测 15 间"内容房"里只有 3 间是 `COMBAT`，
  
其余变成 TRAP / STORAGE / EVENT / SCAVENGE —— 不刷怪，"进房封门"几乎从不发生。
  
现在 `NORMAL` / `HUB` 钉成 `COMBAT`：EGT 骨架本来就用 `kind` 指定了职责，不需要再洗一次。

## 附录 D：2026-10-28 报单（第三轮：门与镜头）

业主第三轮两条，都是**手感**：门要左右开、镜头不要被墙弹。

### D.1 门扇改成双扇对开

**做法**：`RoomDoor3D` 新增开合方式（`lift` / `slide`），缺省仍是升降 —— 塔楼、基地99F、
  
远征01/02 逐字不变。远征03 由 `TowerDescent3D` 对 `procedural_shell` 房间下发 `slide`。

**第一次做错的点**：把整扇门按 50% 压扁，两扇拼起来只有约 2.0m 可见板面，**中间露出竖缝**
  
（截图放大可见）。根因是门板美术四周有边框内缩，不是几何算错。
  
改成 `SLIDE_PANEL_WIDTH_SCALE = 1.10`（每扇 1.21m），中间产生 0.11m 真实重叠，缝消失。

**第二个坑**：重叠区两扇同 z 会 z-fighting。右扇沿门厚让开
  
`SLIDE_PANEL_DEPTH_OFFSET_M = 0.008`。

**第三个坑（最花时间）**：改完之后门是"贴在墙外面"的。根因不是开合逻辑，是**门板美术选错**：
  
入口房属于 `authored_layout_peaceful`，`_door_panel_visual()` 原本给它基地 99F 的滑升门体 ——
  
那是"门体"不是"门板"，可视厚度 **0.88m**，而程序化房间墙厚只有 0.28m。滑到门洞两侧时
  
凸出 0.31m，露出一整块蓝色门体。修法：`slide` 一律用塔楼 A 套门扇（厚 0.18m）。
  
验据：`slide_panel_thickness worst=0.180 worst < wall=0.28`。

**一个不是 bug 的现象**：关门时中间有一条亮竖线。把两扇材质换成纯色无光照后实测
  
80 列全是纯色、非纯色 0 列 —— 几何完全覆盖，那条线是**门板美术自带的发光竖条**
  
（原本在单扇门中央，压扁后落在每扇中央）。这条记在这里，避免后人再花一轮去"修缝"。

**数值自证**（探针）：关门态两扇中心 `±0.55m`、开门态 `±1.71m`，行程 1.16m，
  
门板内缘在开门后完全退出 2.2m 门洞；门板可视包络 `0.18×2.49×1.21m`，
  
厚度 0.18m < 墙厚 0.28m ⇒ 开门后整块落在墙内。

### D.2 去掉"墙碰撞后自动复位"的镜头

**关掉的两条**（只在 `_flow_rules_active` 时）：

| 函数                                 | 原行为                              | 现在           |
| ---------------------------------- | -------------------------------- | ------------ |
| `_update_camera_lower_wall_lift()` | 墙进镜头 → 抬高 0.30m + 后方轴 3.1m→0.15m | 目标锁死基准值，平滑归零 |
| `_update_camera_stair_slab_drop()` | 楼板/天花板压镜头                        | 探针一并关掉       |

**为什么不能只删调用**：删掉之后镜头严格跟随，贴墙时会落到房间外 —— 而房间外是黑幕，
  
玩家会看到一片黑。所以补 `_clamp_flow_camera_into_room()`：只夹水平 x/z 到房间足迹内缩
  
0.55m 处，**不改高度、不改俯角、不探测墙体**。这是边界限制，不是碰撞避让。

**验收**（`probe_expedition03_playable` A 段）：

## 附录 E：2026-10-28 报单（第四轮：墙外那条浅带）

### E.1 现象

业主截图：房间边上一圈浅灰蓝的带子，透过它能看到**另一个房间的地板**。红框标在墙根下方。

### E.2 为什么"改门之前没有"

不是门的问题，是**门把缝挡住了**。升降门只抬起 0.32m，视觉上门洞始终被门板盖住 ——
  
墙根那条缝一直存在，只是从门洞透不出来。门改成双扇对开之后门洞真的通了，缝就露出来了。
  
典型的"改了 A 暴露了 B"。

### E.3 根因：水平遮罩有视差，这个形状无解

原来的遮挡是一层带洞的**水平**平面（`FlowViewMask`，Y = 2.88m）。相机在 10.26m、
  
俯角约 −60°，一条射向墙外地面的视线与这个平面的交点，比它在地面的落点**更靠近相机**
  
（约 0.72 倍）。于是"世界坐标的洞"与"屏幕上的洞"永远对不上：

| 洞口相对房间足迹      | 结果                                        |
| ------------- | ----------------------------------------- |
| 外扩 0.35m（原实现） | 墙根外约 0.5m 的地面在屏幕上仍落在洞里 ⇒ **露出隔壁地砖**（业主红框） |
| 外扩 0.05m      | 缝变窄但仍在；且相机一动缝宽就变                          |
| 内缩 0.35m      | 缝没了，但**墙顶横截面被整圈盖黑**，房间成了"顶被掀的盒子"          |

三种都试过，都不对 —— 因为问题不在数值，在**这个遮挡面是水平的**。

### E.4 修法：改成竖直幕墙

`FlowViewWalls`：贴当前房间**墙外表面**的一圈纯黑竖直面，Y 从 −1m 到 26m。

- **没有视差**：从房间内看向房间外的任何视线，都必然穿过"墙外表面"那一圈，
    
  与相机位置无关；
- **不挡墙顶剖面**：它是竖直的，俯视时只在墙外立着，房间四周 0.28m 宽的
    
  墙顶横截面完整可见 —— 正是业主 2026-10-28 要的「这样更有顶视角游戏的感觉」。

水平遮罩整体删除（`_build_flow_view_mask()` 现在只转发到 `_build_flow_view_walls()`）。

### E.5 顺带挖出的三个坑

| 坑                        | 现象                                         | 原因                                                                                |
| ------------------------ | ------------------------------------------ | --------------------------------------------------------------------------------- |
| 挂在 `Blocks/Expedition` 下 | 遮挡时灵时不灵                                    | 那是楼层几何容器，`visible` 归流送管，装配后实测 `is_visible_in_tree() = false`。改挂场景根                |
| `queue_free()` 后就建同名节点   | 新幕墙变成匿名 `@MeshInstance3D@NNN`，还被判成"塔楼高墙穿房" | `queue_free` 延迟，名字帧末才释放；Godot 因重名把**新**节点改名。改为先 `remove_child()` 再 `queue_free()` |
| 清理只看当前 parent            | 旧位置的幕墙永远残留（27m 高的墙，AABB 包住房间）              | 挂载点在历史上变过。改为按名字前缀**全树扫描**                                                         |

### E.6 防回归：像素级判据

观感这种东西，几何断言证明不了。`probe_expedition03_playable` 加了一条**像素级**测量：

对贴墙的四个站位，逐像素从相机发一条物理射线（掩码 1 = 墙/地），一条像素算"漏"必须三条件同时成立：

1. 射线终点在**房间足迹之外的地面**上（y ≤ 0.35m）；
2. 该像素**不是黑的**；
3. **关掉幕墙后该像素明显变亮**（Δ亮度 ≥ 0.05）。

第 3 条不能省：墙顶剖面本来就该可见，它的射线会从墙顶边缘擦过去落在墙外地面，
  
但显示的是房间自己的墙顶，幕墙开关对它毫无影响 —— 只看 ①② 会误判成漏光
  
（第一版探针就这么误报了几千个像素）。

结果：`wall_leak ≈ 102`（上限 `WALL_LEAK_LIMIT = 500`），四站位稳定复现同一量级。

**为什么不是 0**：全屏约 6400 个采样点里剩下的这一百来个是**几何边缘的混合像素** ——
  
幕墙顶边与远处交界被抗锯齿平均、以及"纯视觉件没有碰撞"（像素显示的是房间自己的构件，
  
但物理射线从它的碰撞空隙穿出去落到墙外地面）。它们的共同特征是**关掉幕墙后亮度只涨
  
0.05~0.09**；而真实漏缝会涨 0.1~0.4、且是**5000+ 个采样点**。两档差一个数量级，
  
所以上限取 500（对噪声 4 倍余量、对真漏缝 10 倍余量）。

> 第一版把上限设 30，结果带渲染时稳定 52~~103 —— 一个**永远红**的断言比没有断言更糟。
>

## 附录 F：2026-10-29 报单（第五轮：入口安全屋的出口标识）

### F.1 现象

业主截了一张入口安全屋的图，用红框圈住**退出门**，原话：「远征关卡03的安全屋的
  
回去的路这里。没有摆放远征01用的退出关卡的功能。帮我摆进去。那个 exit 的物品也要摆进来。」

一句话里两个诉求：

| 诉求                                              | 实际状态           |
| ----------------------------------------------- | -------------- |
| 「退出关卡的功能」                                       | **本来就有**，见 F.2 |
| 「那个 exit 的物品」= `ENV-BATTLE-EXIT-NEON-SIGN` 地面灯牌 | **真的缺**，见 F.3  |

### F.2 先排除的：「退出战局」交互没有丢

实测（`probe_expedition03_playable`）：

```
PLAYABLE retreat_door side=east has_leaf=true prompt=[E] 退出战局
PLAYABLE retreat_interact mode=configured_expedition_retreat opened=true overlay=true
```

门扇在、交互候选在、二次确认面板也弹得出来。所以这一轮**不动** `_append_closed_arrival_door_port()`
  
与 `_get_configured_base_door_bindings()` 的 `expedition_retreat` 绑定 —— 它们已经是好的。

业主看到"没有退出功能"，是因为**门外没有任何视觉标识**：一扇关着的门 + 门外黑幕，
  
在俯视相机下与普通房门无差别，玩家不知道那是弃局出口。

### F.3 根因：第三条建壳路径漏摆灯牌

`_build_safe_room_exit_sign()` 有三个调用点，原先只有两个：

| 建壳路径                                  | 谁走                              | 摆灯牌             |
| ------------------------------------- | ------------------------------- | --------------- |
| `_build_safe_room_shell()`（v007 动态壳体） | 塔楼模块壳安全屋                        | ✅ 一直有           |
| `_build_shell()` 静态布局分支（远征01/02）      | 有 `f00_*_static_layout.tscn` 的房 | ✅ 2026-10-12 补过 |
| `_build_shell()` **程序化壳体分支**          | **远征03 的 flow 房间**              | ❌ 从来没人补         |

修法：在程序化壳体分支的建门之后补一次，判据只按 `room_type == "STAIR_LOBBY"`，
  
**不认关卡 ID**（任何走程序化壳的安全房都同样成立，符合[关卡接入规范](../关卡接入规范.md)的「按能力分支」）。

顺手把 `safe_room_exit_sign` / `safe_room_exit_sign_direction` 两条房间 meta 收进
  
`_build_safe_room_exit_sign()` 内部统一写 —— 原来只有 v007 那条路径写，快照里看不到
  
远征03 有没有牌。
