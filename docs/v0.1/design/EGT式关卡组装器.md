# EGT 式关卡组装器 · 实现说明

代码：`src/map/EgtFlowAssembler.gd`（组装）、`src/map/EgtPlanBridge.gd`（桥接）
落地：`src/map/FloorPlanGenerator.gd` 的 `_generate_flow_floor()`
验收：`tests/verification/verify_egt_flow_assembler.gd` / `verify_egt_plan_bridge.gd` /
`verify_flow_floor_generation.gd`（三份均已登记进 `run_verification_suite.sh`）
出图：`docs/art/egt_flow_layouts/index.html`（房间表）、`docs/art/egt_shell_layouts/`（壳体）

---

## 1. 一句话原理

> **房间不存坐标，只存出口。** 拼装 = 从新房间取一个出口、从已放好的结构取一个出口，
> 凑成一对、对齐 —— 新房间的位置就确定了。

反编译原文：*"Exits are pre-defined locations in the metadata for each room."*

所以整套系统分两半：

| 一半 | 谁负责 | 本项目落点 |
|---|---|---|
| 出口在哪 | 房间模板 | `room_templates/*.json` 的 `wall_lane_table` |
| 怎么配对 | 组装器 | `EgtFlowAssembler._aligned_center()` |

## 2. 五段管线

| 段 | 函数 | 做什么 | 随机 |
|---|---|---|---|
| 1 选骨架 | `pick_flow()` | 从一层 4~8 张 flow 抽一张 | ★ |
| 2a 选模板 | `assign_templates()` | 每节点挑模板；池子够大时优先未用过的 | ★★ |
| 2b 注入 | `apply_injections()` | 按规则插特殊节点 | ★★ |
| 3 拆最小环 | `cut_loops()` | 每条 loop 边 + 它在树上的路径 = 一个环 | — |
| 4+5 拼装 | `_layout_all()` | 树 DFS + 补齐所有未落的边 | 部分 |

### 2.1 对齐公式（核心）

`_aligned_center(a, side_a, lane_a, b_size, side_b, lane_b)`：

```
side_a = east:  b.x = a.x + (a.w + b.w) / 2
                b.y = a.y + lane_a - lane_b      ← lane 是沿墙轴的偏移
side_a = west:  b.x = a.x - (a.w + b.w) / 2,  b.y 同上
side_a = south: b.y = a.y + (a.h + b.h) / 2
                b.x = a.x + lane_a - lane_b
side_a = north: b.y = a.y - (a.h + b.h) / 2,  b.x 同上
```

方向约定与 `RoomDoorLane.port_pair()` 一致：**north = −z，south = +z，east = +x，west = −x**。

`_best_pair()` 遍历「锚点侧全部空闲槽 × 子房侧全部候选槽」，先筛掉会重叠的，
再按"到锚点最近"打分（紧凑优先，图更容易连成一片）。

### 2.2 回溯 = 重抽模板，不是改边

原文：*"it will backtrack and regen the choice of room, up to 3 times."*

第一版理解错了，做成"接不上就换一个已放置房间当锚点"。后果很严重：

> 图上 `hub_01-n03` 相连，实际把 `n03` 接到了 `entry` 上 —— **生成的地图和设计不符，等于没复刻。**

正确做法（本实现）：某间房贴不上就**整次布局重来并重抽池子模板**，
最多 24 次（一张骨架 17 间房，3 次远远不够）。拓扑自始至终由 flow 决定。

### 2.3 三段式拼装：树 / 环 / 总装

原文的顺序是**切环 → 分别拼装（树与环两套算法）→ 总装**。本实现照此分三段：

| 段 | 做什么 | 代码 |
|---|---|---|
| 1. 树 | 从根深度优先，**跳过环成员**，只铺环外的部分 | `_layout_tree` / `_dfs_place` |
| 2. 环 | 每个环从接点出发，**两端往中间合** | `_layout_loop` / `_place_loop_node` |
| 3. 总装 | 环就位后解除排除，把剩余子树接上 | `_sweep_remaining` |

**为什么第 3 段必须存在**：环在 flow 里常是"树的一段 + 一条回边"，第 1 段跳过环成员后，
挂在环下面的整棵子树（boss / shop / exit…）在第 1 段走不到。第 3 段在环就位后补上它们。
少了第 3 段，实测 flow_01 每次都有 7 间房"与主图不连通"。

**环的两端合**：`_place_loop_node` 在环过半后传 `toward` = 另一侧开口的坐标，
`_best_pair` 据此把新房间往那条开口拉 —— 就是原文 *"bring the two unclosed ends closer together"*。
环前半段则偏好相对的两面墙（原文 *"with preference for opposing walls"*）。

### 2.4 走廊：EGT 的地图本来就比 flow 图多一层

这一条是**修图的直接原因**，单独记。

Boris 原文第 13 行：

> *"You may have spotted that the flow diagram and the map don't actually correspond
> perfectly. There's an extra room directly below the shopkeeper room that doesn't
> correspond, and **there's these weird corridor rooms**."*

也就是说：**实际地图上会多出 flow 里没有的走廊房间**。而上一版把每对门都贴成 gap=0，
画出来是一整片方块阵 —— 业主一眼看出"没有通道的样子"。

但同时也不能处处拉长走廊。原文对整体形状的取舍是：

> *"The generator emphasizes making **tight loops and short corridors** for the most
> central parts, and then tries to fit everything else around that."*

于是 `_corridor_gap()` 按"环内紧、环外疏"分：

| 情形 | gap |
|---|---|
| 两个端点同属一个环 | **0**（共墙贴合 → 紧环） |
| 其余连接，45% | 0（直接贴合） |
| 其余连接，33% | 5 m |
| 其余连接，16% | 10 m |
| 其余连接，6% | 15 m |

实测六张骨架共 **56 条走廊**，长度分布 `5m×39 / 10m×6 / 15m×9 / 20m×1 / 30m×1` —— 全在原文的 4~30 单位内。

**加了硬断言**：走廊长度必须落在 4~30 m（第一层，矿坑层才是 50）。这条专盯旧版那个
70 m 长蛇：环被 DFS 拉直时，最后只能拉一条穿越大半张图的走廊闭合。**走廊过长 = 环没被正确两端合**，
所以它是结构缺陷的探针，不是风格偏好。

### 2.5 树的选对偏好：不要奖励"对面墙"

原文对树的要求只有两条：**别相交 + 偏好离已有房间远**，没有朝向偏好。
曾经把"偏好相对两面墙"这一条也用在了树上，结果整条链被拉成笔直长蛇
（`boss → foyer → reward → shop` 排成一条竖线）。现在这条只用于环的前半段。

同理，`_spread_score` 的权重不能大：调到 2.0 时每个新房间都往最远处跑，整层变成一条斜线。
现在的做法是**紧凑为主 + 上限内轻微推开**（权重 0.35、封顶 45m），房间才会成团。

## 3. 注入

原文四要素：`{注什么类型, 注在哪, 概率, 前置条件}`。

- `dead_end_first`：只在死胡同（度 1 且非根）挂；没有死胡同按 `anchor_fallback_probability` 决定是否退到任意房间。
- `scope: "run"`（跨层预算）：**本层不决定**，如实记进 `skipped`，不静默忽略。
- 注入房的模板是**推定值**（`INJECTION_TEMPLATE`）—— flow 只声明 kind，不声明用哪个模板。

## 4. 验收

```
ASSEMBLE flow_01  12/12 ok  loops=1.0 corridors=6.8
…
ASSEMBLE_CHECKED runs=72 ok=72 checks=47620
EGT_ASSEMBLER_OK runs=72 checks=47620
```

六张骨架 × 12 个种子 = 72 次，**全部成功**，47620 项检查全绿：

| 断言 | 内容 |
|---|---|
| 不重叠 | 两两求矩形交集，面积 > 0 即失败（共墙贴合面积为 0，允许） |
| 每条边都落门 | `_verify_edges`：图上每条边都必须有对应 connection |
| 门位合法 | 每个门槽必在 `RoomDoorLane.lane_offsets(墙长)` 里 |
| 门坐标一致 | `direct` 连接：两门绝对坐标差 ≤ 1cm；`corridor` 连接：走廊长度盖得住门距 |
| **走廊长度在原文区间内** | `corridor` 连接：4 ≤ 长度 ≤ 30 m（第一层）。超长 = 环被拉直 |
| 无孤立房 | 每间房至少一个门 |
| 确定性 | 同 seed 两次坐标逐字节相同；换 seed 布局必须变 |

### 4.1 反向对照（证明门禁真的会红）

| 注入的错 | 结果 |
|---|---|
| 跳过环的闭合边 | ✅ 报「边 n06-reward_02 没有落门」 |
| 走廊长度只算一半 | ✅ 报「走廊 28m 盖不住门距 53.85m」 |
| 关掉重叠检查 | ✅ 报「boss 与 shop 重叠 10.00×5.00」 |
| 走廊上限收到 6m（现有 10/15m 会被拦） | ✅ 报「走廊 10m 超出原文上限 6m（说明环被拉直了）」 |

> 另有一条对照**没抓到**：把 `east` 分支的贴合距离改错。原因是算法会绕开那个方向、
> 用其他方向拼出合法图 —— 房间都贴合、门都重合，只是形状变差。这不算漏洞
> （契约仍然成立），但也说明「改坏一处 ≠ 一定失败」，所以门禁要验的是**契约**而非**形状**。

> **形状这类问题上，门禁不会替你判断。** 走廊缺失、房间排成斜线长蛇、整层摊成方阵 ——
> 这三版的缺陷**全部通过了当时那套断言**，都是出图看出来的。
> 纯逻辑断言验的是"能不能走通"，不是"像不像挺进地牢"。

## 5. 已知偏差（如实记录）

| 项 | 现状 | EGT |
|---|---|---|
| 走廊长度 | **5~30 m**，全部在原文区间内（已加硬断言） | 原文 4~30 单位（矿坑 50） |
| 环的"两端合" | 已按三段式实现：树跳过环成员 → 环两端合 → 总装补子树 | 同 |
| 走廊数量 | 六张骨架约 56 条，占边的 40~45% | 原文未给比例，只说"多出一些奇怪的走廊房间" |
| `CONNECTOR` 房型 | **10×30 / 30×10 窄长房，布局时按行进方向二选一**（见 §8） | 原文："often **long, thin** rooms" —— ✔ 已对齐 |
| 连接房穿堂率 | **62%**（101/162）；其余被夹在中间、只能从垂直面出去 | 未给数值 |
| 注入权重 | 只有 flow 声明的 3 条（隐藏房/NPC/壁炉） | 还有商人、牢房、电梯等，权重未公开 |
| 跨层预算 | 未实现（`scope: "run"` 只记录不执行） | 开局抽一次分配给将来某一层 |

**走廊占比为什么不是 100%**：连接房现在本身就能当"通道"用（窄长条），
所以"房间贴合 + 走廊 + 窄长连接房"三者混着出现，这比全是走廊更接近原作的地图观感。

## 7A. 桥接层：房间表 → 区块（`EgtPlanBridge`）

两侧的坐标系和契约都不一样，不能直接对接：

| | 组装器 | `build_block()` |
|---|---|---|
| 坐标 | 平面 `center` + `size`，y **向南** | Blender `bounds_x/y_m`，y **向北** |
| 门 | `ports = {side: [相对中心的 lane]}` | `doors = {side: 沿墙轴**绝对**坐标}` |
| 走廊 | `connections` 里一条 `kind: "corridor"` | 不存在 —— 走廊必须是**房间** |
| 格线 | 不保证 | 硬要求：bounds 落 5m 格线、门落 lane 中心 |

三条换算规则，每条都是实测出来的，不是推导：

### 7A.1 全局平移 +2.5m

组装器的对齐公式让所有房间中心的同余类由尺寸奇偶决定。实测 263 间房 × 4 条边 =
**1052 条边界全部落在 `5k + 2.5`**。整体平移 `(2.5, 2.5)` 后全部落回 5m 格线，同时
526 个门点**全部正好落在 lane 中心 `5k + 2.5`** —— 两个条件同时成立，所以只需要
**一个常量平移**，不需要逐房吸附（逐房吸附会破坏房间之间的贴合关系）。

### 7A.2 走廊补成房间

不补这一段，玩家就得跨过一片虚空。直走廊 = 5m 宽矩形；两门横向错开时 =
**两段直走廊在拐角处共墙 + 各开一门**。

为什么不是单块凹多边形：顶点绕向写反一次，`build_block()` 就判轮廓非法并让**整块**
退回程序化壳体 —— 一处局部问题放大成整层回退。两段矩形 + 拐角门洞在通行上等价，
且完全走已验证的直走廊路径。真实建筑里走廊转弯处本来也常有一道门。

### 7A.3 门槽盖章（关键决策）

组装器和本工程其余四个消费方用的**不是同一条门槽算法**：

| 谁 | 语义 |
|---|---|
| 组装器 `_aligned_center()` | **先选门槽，再由门槽反推位置** |
| `RoomDoorLane.port_pair()` | **先有位置，再反算共享门槽** |

实测 758 条连接：**`side` 100% 一致，`lane` 只有 18.6% 一致**。两者都是合法解，
只是选的槽不同。而 `LevelPlanValidator._validate_port_derivation()` 逐条比对设计源
`ports` 与 `port_pair()` 的派生值，不一致就报 `port_derivation_mismatch`。

- 直接写组装器的槽 → 校验器红掉 81% 的门；
- 改用 `port_pair()` → 校验器绿了，但组装器的布局没被采用。

**做法是盖章**：布局位置由组装器定（它才管拓扑和形状），门槽一律以本工程唯一实现为准。
代价为零 —— 758/758 条连接在盖章后两侧门点仍然重合，因为换的是**同一面墙上的另一条
合法共享槽**，房间位置不用动。

盖章是**保守**的：`port_pair()` 的 `b_lane` 是「共享绝对坐标 − b 的轴中心」，而共享坐标
取自 a 侧候选槽。两墙不等长时（a 25m / b 45m）减出来的 `b_lane` 落在 b 的合法槽之外 ——
实测这正是 13/2272 处越槽的来源。两侧都合法才采纳，否则保留组装器原槽。

实测采纳率 **2259/2272 = 99%**。

## 7B. 落地层：`_generate_flow_floor()`

`mode = "flow"` 在 `FloorPlanGenerator` 里的分支。三层职责一层不越界，本函数只做
「区块 → `floor_source`」的搬运与角色映射。

| 节点 kind | role | room_type | content_type |
|---|---|---|---|
| `ENTRANCE` | `stair_entry` | `SAFE_ROOM` | `STAIR_LOBBY` |
| `EXIT` | `extraction` | `EXTRACTION_ROOM` | `EXTRACTION` |
| `BOSS` | `boss` | `BOSS_ROOM` | `BOSS` |
| `BOSS_FOYER` | `boss_prep` | `COMMON_ROOM` | `UPGRADE` |
| `CONNECTOR` / 走廊房 | **`connector`** | `COMMON_ROOM` | **空** |
| 其余 | `main` | `COMMON_ROOM` | 留空，由内容洗牌分配 |

`connector` 加进了 `FUNCTIONAL_ROLES`：走廊房**enemyless**，不参与内容洗牌、不计入内容房。
否则走廊里会刷怪 —— 原文说得很直接：*"connector rooms, which are enemyless rooms"*。

**三处「不能照抄既有链路」的地方**（都是踩过才发现的）：

1. **不填 `parent_key`**。EGT 的骨架是带环的图，本来就没有"父子"。强行按 BFS 编一棵树，
   会让校验器的「父边净距 / 共轴」判据去检查一条实际并不相邻的边（boss 的 parent 被
   推成 boss_foyer，而两者之间隔着一条 10m 走廊房）。连通性分别由组装器 `_verify_edges()`
   与落地层验收的 BFS 保证。
2. **不填 `ports`，只写 `connection_ports`**。填了 `ports` 就触发上面那套
   `port_pair()` 逐条比对，必然对不上。
3. **`room_type` 不能留空**，走廊房的 `template_id` 可以空 —— 它的尺寸由两门缺口决定
   （5×5 … 5×30 连续变化），不可能有对应模板。校验器为此放开一条：`role == "connector"`
   允许空 `template_id`，其余几何契约（格线、端口贴边、不重叠）照旧。

### 7B.1 一个把「一半房间走不到」的 bug

门与门配对时，键里**不能带 lane**。lane 是相对**各房墙中心线**的偏移，共墙两房中心不同
（`boss_foyer` 中心 y=152.5、`boss` 中心 y=195），同一扇门在 a 是 `-2.5`、在 b 是 `0.0`。
用它当键，同一对门就算成两个不同的槽。实测结果是**恰好一半的门配上 target**，
整层一半房间不可达（24 局全部如此）。

键必须用「轴 + 墙平面 + 门的**绝对**坐标」，且**不带侧名**（共墙两房一侧是 `north`、
另一侧是 `south`）。换成绝对坐标后 `unreachable` 从 601 直接归零。

顺带修掉一个同类隐患：不要用 `"%.2f" % -0.0` 拼键（它是 `"-0.00"`，和 `"0.00"` 不等），
配对直接用对象引用，不做字符串二次解析。

## 7C. 形状只能靠出图

`docs/art/egt_shell_layouts/` 画的是**会进游戏的几何**（墙 / 门洞 / L 角件 / 地砖），
不是房间表。数据由 `export_egt_shell.gd` 真跑 `assemble → to_block → build_block` 产生。

这张图回答三个逻辑断言答不了的问题：

1. 每面墙是否补齐（少一格就是一条能走出去的缝）；
2. 门洞是否正好对着邻房的门洞（差一格就是空气墙）；
3. 走廊拐角是否真的连通（两段矩形共墙处必须各有一个门洞）。

墙的**视觉**厚度在图里放大到 1.1m（真实件 0.3m，在整层俯视图上不足 2px），只为可读 ——
缺墙靠 `build_block()` 新增的 `wall_gaps` 自检抓，不靠眼睛。

> `wall_gaps` 是这次给 `RoomShellLayoutBuilder3D` 加的**周长覆盖自检**：每条边界 lane
> 必须要么有墙（实墙/门墙）、要么被 L 臂占住。少一格就是一扇没门的洞，而这类缺口
> 不会让原有任何一条判据失败（lane 归属表里根本没这一条）—— 属于"静默少墙"。
> 它只写进 `validation`、不进 `errors`：既有楼层若本来就有缺口，不能被它顺带判死。

## 8. `CONNECTOR`：窄长房 + 布局时才选模板（已修）

原文两条要求：

> *"Not shown are **connector** rooms, which are enemyless rooms, often with a environmental
> hazard."*（Boris 第 11 行）
>
> *"Nodes of type connector work differently. **They have their rooms picked later, while
> layout occurs.** These are often **long, thin rooms**, so picking one with a sensible
> orientation is vital."*（Boris 第 22 行）

旧版两条都没做到：`conn_01` 用 `std_25x25`（25×25 方形），且模板在开局就定死。

### 8.1 数据侧：两份窄长模板，横竖各一

| 模板 | 尺寸 | 格数 | 长宽比 | 门在 |
|---|---|---:|---:|---|
| `connector_10x30` | 10×30 | 2×6 | 3.0 | 南北（长轴两端） |
| `connector_30x10` | 30×10 | 6×2 | 3.0 | 东西（长轴两端） |

**为什么是两份而不是一份加旋转**：本工程的房间尺寸是轴对齐的（`size_m` 是 x/y 两轴），
不支持运行时旋转，所以长轴方向只能由两份模板表达。

flow 里的 `CONNECTOR` 节点不再写 `template_id`，改成
`template_pool = ["connector_10x30", "connector_30x10"]`，
由生成器 `scripts/build_expedition03_level_plan.py` 直接产出这两份模板（幂等，不必手改 JSON）。

### 8.2 组装侧：在布局时按行进方向选

`_best_pair()` 现在最外层多一层**候选模板循环**：

```
for tpl in 候选模板:           ← 连接房有 2 个，其余只有 1 个
  for 锚点侧槽:
    for 子房侧:
      for 子房槽:
        算出位置 → 查重叠 → 查门是否对齐 → 打分
```

打分里 `CONNECTOR_ORIENTATION_BONUS = 1000`，**必须压过全部距离项**（距离项最大约 ±500）：

| 项 | 分值 | 语义 |
|---|---|---|
| 连接房朝向 | **+1000** | 长轴必须沿行进方向 |
| 锚点侧也是连接房 | **+1000** | 下一间房必须从它的长轴端接出去 |
| 环后半段拉近 | −距离 × 4 | 原文 "bring the two unclosed ends closer" |
| 环前半段对面墙 | +6 | 原文 "preference for opposing walls" |
| 树紧凑 | −距离 + 0.35×推开 | 见 §2.5 |

第二条（锚点侧）是踩过坑才加上的：只约束子房一侧时，连接房虽然被正确放置，
但**下一间房会从它的短边接进来**，长轴上只剩一个门 —— 穿堂变成侧岔。
实测每张含连接房的骨架都栽在这里（`0/2` 或 `1/2` 扇门在长轴上）。

### 8.3 一个隐蔽的 bug：`template_pool` 被丢掉了

`apply_injections()` 重建节点时只取了 `node_id / kind / template_id` 三个字段，
把 `template_pool` 丢了 —— 于是「连接房延迟选模板」的判据（`kind==CONNECTOR` 且池非空）
**从头到尾没成立过**，连接房退回成开局随机定一个模板。

这个 bug 特别隐蔽：组装仍然成功、当时断言全绿，**只有形状不对**。
修法是整个节点原样保留（`node.duplicate(true)`），只覆盖 `template_id`。

### 8.4 验收

| 断言 | 标准 | 实测 |
|---|---|---|
| 窄长 | 长宽比 ≥ 2.5 | 全部 3.0 ✔ |
| 朝向 | 至少一扇门在长轴端 | 全部满足 ✔ |
| 穿堂比例 | 所有门都在长轴端 | **109/162 = 67%** |
| 模板真的在选 | 横竖两向都出现过 | 120 局中两向都有 ✔ |

**为什么"至少一扇"而不是"两扇都在长轴端"**：连接房被夹在中间时（长轴两端都已被
已有房间占住），第二/第三扇门只能从垂直面出去。房间不能旋转也不能变形，这是几何限制，
不是朝向选错。所以硬要求定为"不是纯侧向使用"，真正的穿堂比例（67%）单独统计并设 50% 下限。

## 9. 多种子抽关测试

除了"六张骨架各跑 12 个种子"，还加了两层：

| 层 | 次数 | 断言 |
|---|---:|---|
| 骨架 × 种子 | 6 × 12 = **72** | 不重叠 / 每条边落门 / 门位合法 / 走廊 4~30m / 连接房窄长且朝向对 |
| **随机抽关**（`pick_flow()`） | **120** | 同上全部，另加成功率 ≥ 90%、连接房两向模板都出现过 |
| 压力测试（一次性，不入日常门禁） | **600** | 失败率、走廊最长值 |

实测：

```
LEVEL_DRAW seeds=120 ok=120
CONNECTOR_PASSTHROUGH 109/162 = 67%
EGT_ASSEMBLER_OK runs=72 checks=47620

STRESS runs=600 ok=600 fail=0 rate=0.00%
STRESS corridor_max=30.0m over30=0
```

600 局 0 失败，走廊最短 5m、最长 30.0m，全部落在原文的 4~30 单位内。

### 9.1 一个"重试等于没重试"的问题

环的起手侧原本固定为"先左"，每轮重试得到**同一个几何**，环闭合长度不变 ——
重试 24 次等于重试 1 次。实测 flow_05 有一个种子 24 轮全失败、闭合走廊 75m。

改法：起手侧由 rng 决定（`flip`），重试时 rng 前进，形状才真的会变。
另外三条边的小环（A→B→C→A）里，若 B 挂 A 北侧、C 又挂 A 东侧，闭合 B–C 要横跨 A 的对角
（实测 47m）。改成"在同一侧连续长"（A→B→C），闭合边只剩 C–A，环自然是紧环。

### 9.2 三条让「重试真的在变」的修复（2026-10-28，接桥接层时暴露）

接桥接层时，那些「画出来才有问题」的缺陷终于有了**可判定的形态**（走廊跨度为 0、
走廊压进别的房间），于是组装器里三处「重试等于没重试」的问题全部暴露：

| 问题 | 症状 | 改法 |
|---|---|---|
| 环的**起点**固定取"第一个已在场的成员" | 24 轮重试得到同一张图，环闭合那条边永远接不上 | 起点也进 rng：把所有已在场的环成员收进候选后抽一个 |
| `_try_direct_close()` 各侧只取**第一条**空闲 lane | 对不上就退回「补走廊」，而两房其实已贴住 ⇒ 走廊长度 **0** | 枚举两侧空闲 lane 的**全部组合** |
| 补走廊只按**中心差**硬选一侧 | 两房斜向共墙时，选中的那面沿行进轴缺口为 0 | 遍历**四面 × 空闲 lane**，并要求缺口 > 0、横向错位 ≤ 5m、不压第三间房 |

另外 `LAYOUT_ATTEMPTS` 从 24 提到 **64**：环的几何由起点与起手侧共同决定，样本空间比
"模板组合"大得多，24 次采样偏少（实测 flow_05 有 1/12 个种子在 24 次内撞不上）。

修复后回到 **72/72 + 120/120，checks=47620**（与修复前逐值相同，说明没有放宽任何判据）。

### 9.3 走廊占位要有宽度

组装器原先把走廊当**一条线**算位置，但桥接层会把它补成 **5m 宽的房间** ——
于是"这条线没压到任何房间"不等于"走廊房没压到"。实测这是 120 局里 8 局 `room_overlap`
的唯一来源。现在 `_corridor_hits_rooms()` 按 5m 宽（L 形还含拐角第二段）的包围矩形
避让，宁严不宽。

1. **房间字典没有 `kind`**。下游靠它映射 role，缺失 ⇒ 整层房间退化成
   `role=main` / `type=COMBAT`：BOSS 房变普通战斗房、入口失去安全屋身份。

2. **CONNECTOR 被接成叶子**（8/28 处单门）。房型配额、门数上限两项断言都通过；
   但 connector 的定义是**穿堂**，单门就成了一间空房间的尽头。
3. **拓扑按配额凑而非按图复刻**。房型计数全对、门数分布全错，而当时没有任何断言看分布。

修法不是"多写几条断言"，而是**把参考 CSV 的门数多重集抄进代码当断言**（`EXPECTED_DEGREES`），
再加**房型语义区间**（`DOOR_RANGE_BY_KIND`）—— 这两条一旦有，上面三处都活不下来。

| 问题 | 后果 | 改法 |
|---|---|---|
| 环接点只试第一个环成员（循环末尾无条件 `break`） | flow_01 的环 0/12 全灭 | 遍历「环成员 × 环外邻居」全部组合 |
| 环与总装**严格分段** | 环 A 放的 hub 是环 B 接点的父，环 B 永远等不到 | 改成「环 → 总装 → 环」交替迭代 |
| 三角环的"一侧连续长"对**所有**环生效 | 4~6 边环被拉成链，闭合边跨 100m+ | 只对 `total <= 3` 生效 |

另：环闭合从「失败即判死」改为「失败交给补边阶段」。原因是**看不见的未来房间** ——
环闭合时还没放的房间，撞房检查看不见；等总装后全体在场再补，才判得全。

## 11. 接进游戏后补的几层（2026-10-28）

组装器本身产出的是「房间表」。把它变成玩家能走的一层，中间还隔着四层，
每一层都曾经是"组装器全绿、游戏里走不动"的原因。逐条记在这里，
因为它们都是**同一种错误**：把一个上层概念当成下层的能力。

### 11.1 拓扑声明：`parent_key` 表达不了环

运行时声明边只读 `parent_key`（每房一个父 ⇒ 边数恒等于 `N − 1`）。
EGT 骨架是**带环的图**，于是 flow 模式 `_declared_edges = 0`
（对照：远征01 是 12、02 是 25）—— **一扇门都不建**。

修法：计划里另带一份 `connections`（无向边清单，存**运行时 id**），
`_prepare_floor_bundle()` 先按它声明，再回退 `parent_key`。

> 两个坑都在"id 换算"上：① 存 `parent_key` 那种 key 会在运行时 `_find_record` 查不到；
> ② 存 block 的原始 node_id 会漏掉改过名的那两间（`entry → start`、`n01 → room_01`），
> 表现是"只有一部分边生效"。

### 11.2 端口字段：`target` 与 `target_room_id` 都会被覆盖

`_append_plan_room_record()` 拿端口的 `target`（**key**）走 `_plan_spec()` 反查，
再用查到房间的 `id` **覆盖** `target_room_id`。只给 `target_room_id` 会被覆盖成空串，
端口就认不出对面是谁，门侧只能按"两房中心的方位"猜 —— 斜向相邻时猜错。

### 11.3 壳体归属：塔楼 5m 栅格 vs 白盒任意门位

塔楼的走廊连接器与楼层外墙是 **5m 栅格 + 11.9m 高**；
EGT 房间是 25m 级白盒，门位在**半个模块**上，枢纽还会**同侧双门**
（实测 40 局里 32 间房如此）。两套网格对不上，硬补连接器就会在房间内部
立起 11.9m 墙（业主 2026-10-28 报的"进房后刷出 11.9m 的墙和空阻挡"）。

判据：房间自持墙体（静态布局 **或** 程序化壳）⇒ **完全不建连接器几何**。

顺带一条：flow 房间改走**程序化壳**（`procedural_shell`），因为它按 lane 任意开门洞；
5m 模块壳每面墙只留一个门模块、门位必须在模块中心，表达不了这套门位。
这个字段必须先登记进 `room_from_source()` 的白名单，否则会被**静默丢弃**
（第一次改就是这么错的：生成器写了 `true`，运行时读到缺省 `false`）。

### 11.4 门与规则：门是门，不是通洞

一度把门洞做成 5m **纯通洞**（不建门扇），理由是"白盒阶段没刷怪、门打不开会卡死"。
那是把临时状态固化成了设计。现在按 Gungeon 的真实语义：

- 门宽 **2.2m**（`DOOR_CLEAR_WIDTH_M`）⇒ `_port_creates_door_leaf()` 会建实体门扇；
- **进战斗房自动落门封锁 → 清空敌人 → 门自动重开**；
- **无怪房**（走廊 / 入口 / 撤离 / 商店）不封锁 —— 原文：
  "connector rooms, which are enemyless rooms"；
- **不用房间钥匙、不弹命运卡**（本关规则独立，见《远征关卡03设计》§2.1）；
- **门扇是双扇对开**（`RoomDoor3D.set_opening_style("slide")`），不是升降。见 §11.6。

### 11.5 时序与视野：两件"接进游戏后才会暴露"的事

**时序**。EGT 的房门不是"跨过门槛就拍在脸上"。本工程的实现是三段常量：

| 段 | 常量 | 值 |
|---|---|---|
| 进门 → 落门 | `FLOW_ROOM_SEAL_DELAY_S` | 0.30s |
| 贴门洞时多等 | `FLOW_ROOM_SEAL_DOORWAY_WAIT_S` | 最多 0.90s |
| 落门 → 出怪 | `FLOW_ROOM_SPAWN_PAUSE_S` | 0.45s |

难点不在时长，在**顺序**：基类 `_on_room_entered()` 里 `_spawn_room_enemies()` 先跑，
封门在它之后 —— 原样接上去就是"怪先出现、门才落"。做法是覆盖
`_spawn_room_enemies()` 把刷怪推迟到落门之后，并让 `_prepare_revealed_hostile_room()`
在 flow 关卡返回 false（塔楼的"门一开就预刷下一间"会提前置真 `_spawned_rooms`）。

> 覆盖 `_spawn_room_enemies()` 时**不能只吞掉调用**：它同时被
> `_repair_hostile_room_progress()` 复用（重进未清房时补刷）。吞掉的话，玩家在落门
> 延迟窗口里快步走出去一次，该房就永远停在"无怪、未清、门也锁不上"。必须改成"排程"。

**视野**。房间壳体是**永久可见**的（流送契约），相机又在 10m 高、俯角 −60°，
视线必然越过 2.8m 墙顶看见隔壁房间。EGT 是"一次只有一间房是舞台"，
本工程用 `FlowViewWalls`（贴当前房间**墙外表面**的一圈纯黑**竖直**幕墙，Y = −1m~26m，
换房重建）达到同一观感。

**这里返工过三轮，教训值得记**：最早用的是"带洞的纯黑**水平面**"，它有两个治不好的毛病 ——
① 视差：平面在 2.88m、相机在 10.26m，视线交点比地面落点近约 0.72 倍，
所以"世界坐标的洞"和"屏幕上的洞"永不重合，洞外扩就露出墙外地面、内缩就盖住墙顶剖面；
② 观感：它正好盖掉房间四周的墙顶横截面，房间看着像"顶被掀了的盒子"。
竖直幕墙两者都没有 —— 视线必然穿过它（与相机位置无关），而俯视时它不遮挡水平剖面。
两个坑：遮罩材质必须 `disable_fog = true`（unshaded ≠ 不吃雾，漏了会被染成灰蓝）；
洞只能给当前房间（给所有房间挖洞等于没做）。

### 11.6 门扇开合与镜头：两个"借用既有实现"要小心的地方

**门扇**。EGT 的门在观感上是"两扇向两侧滑开"，而本工程既有的门扇一律是升降。
做法是给 `RoomDoor3D` 加一个开合方式开关（缺省仍是升降，既有全部关卡逐字不变），
远征03 由 `procedural_shell` 房间下发 `slide`。

踩过的坑，都是"看起来该用 0.5 结果不能用 0.5"：

| 坑 | 现象 | 正确值 |
|---|---|---|
| 门板按 50% 压扁 | 两扇拼起来只有约 2.0m 可见板面，**中间露一条竖缝** | 系数 1.10（每扇 1.21m），中间重叠 0.11m |
| 两扇同 z | 重叠区 z-fighting，关门时闪一条亮线 | 右扇门厚让开 0.008m |

门板美术四周有边框内缩 —— 这是"几何算对了、观感还是错的"的典型：
`门洞宽 × 0.5` 在数学上是对的，但美术的可见板面比包络小。

**镜头**。塔楼有一套"墙进镜头就抬高 + 收拢"的避让，业主明确不要。
但**只删调用是不够的**：删掉后镜头严格跟随，贴墙时会落到房间外 ——
而 flow 关卡房间外是黑幕，玩家会看到一片黑。所以必须补一条**纯水平**的
房间边界夹取（不改高度、不改俯角、不探测墙体）。

一句话区分：业主反对的是「撞墙就跳回去又弹回来」（碰撞避让），
不是「镜头顶在墙前」（边界限制）。

### 11.7 一条给验收的教训

这一层的两次"全绿但坏掉"，都是因为验收只验了**中间量**（房间建出来了、门洞配对了）。
现在 `probe_expedition03_playable` 验的是玩家能感知的事：

1. 用**玩家自己的碰撞掩码**打射线穿门洞（默认掩码会打到只给镜头用的低墙，把"能过"误报成"挡住"）；
2. >5m 高的墙不得与任何房间足迹相交；
3. 恰好 1 间房（当前房）头顶不被遮，其余全部被遮；
4. 站到退出门内侧 1.2m，走完整条 `get_interaction_candidate() → perform_interaction() → 弹窗`；
5. 真的进一间房：进房瞬间**不得**封锁 → 约 100ms 内封锁且 0 扇门开着 → 落门时存活数为 0
   → 静默结束后存活数 > 0 → 清房后门自动全开。

> 第 5 条里"每帧把玩家钉在房中心"不是作弊：测试里的人是瞬移进房的，物理会把边界附近的
> 瞬移纠正掉（实测会被挪到别的房间）。它模拟的是"玩家走进去并站在屋里"这个事实。
