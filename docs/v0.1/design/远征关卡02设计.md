# 远征关卡02 设计

工程版本 0.1.0。本页是**远征关卡02 作为一张独立关卡的目标设计**：它应该长什么样、玩家在里面怎么走、边界在哪里。
当前实现事实与接口见[关卡生成与爬楼](../05_技术施工_关卡生成与爬楼.md)；版图 schema 与门槽公式见[关卡版图白盒与生成规范](../05.2_关卡版图白盒与生成规范.md)；区块归属见[关卡区块设计 §3.0](../05.1_关卡区块设计.md)。

> **文档归属 —— 本页是设计文档，不是账本文档。**
>
> - **归类**：`docs/v0.1/design/`（v0.1 目标规则主设计区，按关卡编号归类；与按功能归类的设计页并列，见[设计区索引](README.md)）。
> - **主设计归属**：FeatureID **`WORLD-PLAN`**（关卡结构）与关联 **`ASSET-PIPELINE`**（组件/房间生产）。`FloorPlanGenerator` 负责关卡计划；Blender 源拥有组件几何材质；正式 Godot 房间 TSCN 拥有房内布局、灯光、启用和实例参数。
> - **资产事实的唯一权威是账本，不是本页。** AssetID、版本、制作状态、源文件路径、GLB/Prefab、哈希与授权一律以[美术资产账本](../../../assets/registry/README.md)的**场景分账本**为准。本页只**转述**账本状态并注明「转述自哪个 AssetID」，**不自行判定**某件资产做完了没有。本关尚无任何房型资产登记，§7 因此只写「需要什么、缺口在哪」。
> - **对外可接通的文档**分四类（账本文档 / 同类关卡产出文档 / 设计来源与施工对照 / 验收与门禁），逐条列在 **§11**。

> **这一关和远征关卡01 的区别：** 01 是**开放平房群**——8 个房型几乎全部单层平房、墙高 11.9 m、部分房型（走廊 / 桥房 / 标准房）本来就不带顶盖、靠 12 m 墙高承担部分遮挡。02 是**密闭室内长条**——所有房间封顶、墙体做低、可进入房间数多、加上可破坏件。**两者共用同一套设计源链路、门禁与登记流程，但空间口径不同。**

## 2. 玩法循环

**走向由南向北。** 入口在南、撤离点在北，主路整体沿**平面 −y** 方向推进（跨语言方位约定见 §4.2）。

```text
基地中央远征情报室（选关） / 塔3机房门（确认）
  → 读取界面（过场）
  → 门厅             南端起点，低矮密闭；这里有唯一的主动弃局门
  → 旅馆主轴长廊    以南→北为主线，沿途两侧开出可进入的房间
                     · 每间内容房的门后都是命运卡三选一
  → Boss 房          本关终局战斗
  → 撤离点           北端终点，常驻撤离信标
  → 撤离成功 → 结算 → 返回本次出发入口
```

**空间性格（本关的三条骨架，其余设计都挂在它们上）：**

| 骨架 | 含义 | 落地影响 |
|---|---|---|
| **密闭** | 所有房间封顶、不露天；墙体做低（目标 3 m） | 全室不受太阳直射（§5.2）；镜头必须压缩（§5.4）；怪恒为 `darkness` / `artificial_light`，不出现 `sunlight` |
| **长条** | 一条主轴自南向北贯通，版图包络呈窄长形 | 主路沿单轴推进；把「折返式」房型（`corridor_45x40` 的 `u_turn`）当节奏变化点，不把主轴搅成蛇形 |
| **多处可进入房间** | 主轴两侧分出多间可进的房间（客房 / 后厨 / 宴会厅 / 管廊） | 用 `role = "branch"` 挂支线（机制现成，远征01 只是自己没用）；被挂的主路房变 3 门（§4.3） |

**三个出口的语义：**

| 出口 | 触发位置 | 结果 |
|---|---|---|
| 撤离成功 | 北端撤离点的撤离信标 | 正常结算，带走本局收益 |
| 死亡 | 任意内容房 / Boss 房 | 按死亡规则结算 |
| 主动弃局 | 入口门厅的出口门 | 未开始就退出，不推进进度 |

**玩法节奏的核心变量是「进不进两侧的房间」。** 01 的节奏变量是「清房彻不彻底」；02 多了「探索广度」这一维 —— 主轴直走最快，进两侧房间拿构筑次数但暴露更久。**这个变量的代价与收益必须先定死（§12 L02-6），否则支线会退化成"必走"，长条主轴就没意义了。**

## 3. 房型库

### 3.0 模板锁定与两条候选路（**待裁决**）

**模板 id 是锁定集合** —— `05.2` §3.6 第 6 条与[新关卡设计表](新关卡设计表.md) §1.3 注均写明（2026-09-25 主人裁定）：**只许在已有模板里选，不许新增 / 改名 / 删除**；「同一房型的另一种摆法 / 朝向」用 `template_rotation_deg` 表达，**不许另起 id**。要改模板集合**须主人明示**。

因此「破败旅馆」的房型只有两条路：

| 路 | 做法 | 代价 |
|---|---|---|
| **甲 · 零新增 id（本页倾向）** | 用远征01 已锁定的 8 个模板拼旅馆主题（见 §3.1） | 主题契合度打折：「数据库机房」当后厨、「开放办公区」当大堂，**靠房内陈设与灯光救**，不靠房型名 |
| **乙 · 为旅馆另立模板集合** | 新增如 `hotel_corridor_*` / `hotel_room_*` / `lobby_*` | 需主人明示；且按 `05.2` §3.6 第 6 条**改动必须一次落全五处**：设计页、L1 `room_templates`、L2 `template_id` 引用、校验器、美术链路。**等于另起一整条美术生产线** |

> **本页按「甲」写。** 理由是 01 已经付过一遍代价：8 个模板背后是 8 套已验收的组件库与**已落地的顶盖遮光件**（§5.2），复用它们等于白拿封顶能力；另立旅馆模板则要重新走一遍「组件母版 → 房型源 → 稳定导入 → 顶盖碰撞」全链。
>
> ⚠️ **若选「甲」，房型名会与主题不一致**（例如「客房」的房型叫 `std_25x25` 标准房间）。本页的做法是：**房型 id 保持锁定名不变，中文名与房内陈设走旅馆主题** —— 和 01 里「模板 id 名嵌旧尺寸但锁定不改名」是同一种处理。

| 段 | 角色 | 房型来源 | 说明 |

## 4. 版图与主路

> ⚠️ **本节是形态与规则，不是坐标。** 几何（房表 / 坐标 / `ports`）**尚未落设计源**，按 §12 拍板后走填表流程。**不要把本节当"实跑一定长这样"。**

### 4.1 主路（草案）

```text
门厅 → 长廊段① → 客房区 → 宴会厅 → 折返走廊 → 中庭挑空 → 后厨/布草间 → 顶层套房(Boss) → 撤离点
```

**主轴自南向北一条线推进**，分歧点在两侧的`branch`房。逐段房型与门向随坐标一并定（填表阶段产出）。

### 4.2 走向与方位约定（跨语言红线，写错不报错）

```text
平面 +y  →  世界 +z  →  south（南）
平面 −y  →  世界 −z  →  north（北）
```

来源：`TowerDescent3D._plan_world_position`（`Vector3(x, -层高, y)`）+ `Dungeon3D._direction_between`（`delta.z >= 0 → "south"`）。

**「由南向北」在本关的落法：** 入口房在**平面 y 较大**的一侧，撤离点在**平面 y 较小**的一侧，主路整体沿 `−y` 推进。

> 🛑 **门侧写反不会让任何几何校验失败**（`lane_m` 仍然对），只会让门连错方向。历史上这条约定曾经整体反向却无人发现，现在靠 `port_derivation_mismatch` 断言盯住。**所以：不要目测，跑 §9 第 3 步取数。**

### 4.3 「多处可进入房间」的两种落法（**待裁决**）

| 落法 | 含义 | 代价 |
|---|---|---|
| **① 支线房（`role = "branch"`）** | 从主轴房延展出去的可进房间；被挂的房变 3 门 | 机制**现成**（`branch_count_range` 保留、顶级支线计数规则在）；远征01 只是自己把区间设成 `[0, 0]`。**本页倾向这条** |
| **② 破墙开洞（走可破坏墙）** | 主轴房侧墙做成可破坏件，打穿后进隔壁房间 | 依赖**尚未存在的**可破坏系统（§6）；且要把「房间」拆成不是单元房的东西，**会动摇设计源「一房一模板」的根基** |

> **本页按 ① 写。** 理由：② 需要先把可破坏系统立起来（§12 L02-3），而且它会让「房间」不再是可校验的单元 —— 校验器、门禁、存档的 `room_progress` 全按房单元走。

### 4.4 门与连接（沿用 01 契约，不改）

- 门契约全场统一：净空 **2.2 × 2.5 m**，门槛底 `0.3 m`，门楣底 `2.8 m`（`TowerGeometry3D.gd:6/7`）。
- 使用 L2 `floor_00.json.connection_ports` 作为真实门洞真源；每个端口写稳定 `A/B/C...` 编号、房间局部坐标与局部朝外方向。
- 连接按端口编号成对声明；**两端锚点世界坐标必须重合、朝外方向必须相反**，端口与房型内容（含刷怪盒）一起随整房旋转。
- 一条边只生成一套门墙、门扇、碰撞和 `RoomDoor3D`；非所有者端不建第二面共墙，只登记同一门对象；空 `target` 的候选端口必须由本房普通实墙封住。
- **入口房运行时 id 必须字面量 `start`**（设计源 key 是 `entry`，靠 `legacy_room_id = "start"` 映射）；**撤离房 key 必须字面量 `extraction`**。写错**完全静默**：几何校验、`port_derivation`、两条门禁判据全都照样绿，只有真装配一次场景才看得见。

数值（血量 / 伤害 / 速度）一律**由引擎统一出**，设计源只写「要谁、几只、掉什么」。

### 4.6 随机性边界

建议沿用 01 的三层口径：**房型/变体按房号固定**（`pin_content_templates = true`）、**整房摆位**在已声明端口约束内搜索平移与直角旋转、**房内布局**由正式 TSCN 拥有、**玩法内容**按房号固定。

> ⚠️ `mode` 取 `authored` 还是 `constrained` 会影响 `layout_id` 与存档指纹。**单层关卡（`floor_index = 0`）不进塔楼的整档恢复比对**（01 已实测），但**几何随机性会归零或保留**这件事必须显式裁决，不能默认。

## 5. 空间口径：墙高、封顶、窗、镜头（本关特有）

> 这一章 01 没有。01 的房型本来就带 12 m 墙、部分房型无顶；02 要求**低矮 + 全封顶 + 压缩镜头**，四件事必须一起想。

### 5.1 墙体高度：3 m 与项目固定基线的冲突

**全项目固定基线（[新关卡设计表](新关卡设计表.md) 第三部分，不可改）：**

| 项目 | 值 | 出处 |
|---|---|---|
| 网格单位 | 5.0 m | `TowerGeometry3D.gd:8` |
| 层高 | 12.0 m | `TowerGeometry3D.gd:40` |
| 可视墙高 | **11.9 m** | `TowerGeometry3D.gd:43`（`FLOOR_HEIGHT_M − 0.1`） |
| 门净宽 / 净高 | 2.2 m / 2.5 m | `TowerGeometry3D.gd:6/7` |

**远征关卡的房间目前全部是 12 m 墙。** 依据：房间 record 由塔楼/远征共用的构造函数生成，其中 `TowerDescent3D.gd:2378` 无条件写 `record["tower_module_shell"] = true`；远征 01 的每个房间都经 `_append_plan_room_record` → `_append_tower_record` 拿到这个 `true`。

**项目里唯一低于 12 m 的房间壳体**是 `Dungeon3D` 自建战局关卡（基地关卡 01–04，`scenes/levels3d/*.tscn`）的普通房间分支：墙心 `y = 1.4` ⇒ 墙高 **2.8 m**，且 `2.8` 是**硬编码字面量、没有命名常量**（`DungeonRoom3D.gd:4171`，快照字段见 `:779`）。这条分支**没有天花板、不走房型模板链路、不是远征链路**。

**⇒ 结论：3 m 墙高在远征链路里没有任何现成路径，必须新开一条。**

**三个选项：**

| 选项 | 做法 | 代价 / 风险 |
|---|---|---|
| **甲 · 房间级墙高覆写** | 给房间 record 加可选字段（如 `wall_height_m`，默认 11.9），本关写 3.0 | 新字段要过**四道白名单**（源→规范化层→运行时计划→塔楼 record→房实例 `configure`）；**绝不能进 `layout_id`**（那是存档指纹）；且顶盖件标高、门楣、刷怪净空、镜头探针**全部要复核** |
| **乙 · 走普通房间壳体** | 改走 `tower_module_shell = false` 分支并把 2.8 提到 3.0 | 该分支**没有顶盖件、没有房型模板、没有静态 TSCN 链路** ⇒ 等于**另起一条关卡壳**，01/02 的整条资产链都用不上 |
| **丙 · 逻辑墙高不变，压视觉净高** | 玩法层仍是 12 m，用**吊顶件**把房间视觉净高压到 3 m（顶盖件下沿 `y ≈ 3.0`） | 零基线改动、封顶天然成立、镜头可维持现状；代价是「墙高 3 m」只在**视觉**成立，**玩法层的空间高度仍是 12 m** |

> **本页倾向：丙起步，甲作为后续增量。** 理由：丙是唯一**不需要**新字段、不改 `layout_id`、不改基线的做法，而且它把「密闭低矮」这个**观感目标**直接完成了；甲动的是全项目几何基准的适用面，代价与收益不成比例。
>
> **但丙有个必须说的缺口：** 若玩法层留 12 m，那么「玩家/怪在 3 m 吊顶下的活动是否真的被限制」这件事就没做 —— 怪的活动体假设是 `SPAWN_BODY_HEIGHT_M := 2.6`（`DungeonRoom3D.gd:350`），3.0 m 净高只剩 **0.4 m** 余量。**若要让 3 m 真正约束玩法（而不是只有观感），必须选甲。**

**门与 3 m 墙的冲突（无论选哪个都要处理）：**

```text
门楣底 = 门槛底 0.3 + 门净高 2.5 = 2.8 m
3.0 m 墙上，门楣之上只剩 0.2 m 过梁
```

⇒ 美术上必须把门框做到顶（或改吊顶在门口收边），否则门会像「墙被挖掉一块」。**这条要在房型源阶段就定，不能等装配时用手调陈设掩盖。**

### 5.2 封顶与「不受太阳照射」——映射到既有硬契约

**好消息：这一条现成，而且刚在 2026-10-12 落地成硬契约。**

**判定机制（不要理解成"画面上有阴影"）：** `src/enemy3d/EnemyIllumination3D.gd` 的 `_evaluate_sunlight()`（L160）从怪物**身体采样点**（脚 / 躯干 / 头三点，L298）沿**主太阳方向的反方向**打一条 `occlusion_mask = 1`（关卡静态世界层，L20）的物理射线，命中即判「在投影里」。判据（L183-184）：

```text
3 点采样 ⇒ 要求 2 点暴露，且中心点必须暴露
```

**⇒ 只要房间上方有带 layer 1 碰撞体的顶盖，射线必被挡，全室不受日照。「封顶 = 不受太阳照射」自动成立。**

**但「视觉有顶 ≠ 玩法判为投影」—— 这是已经踩过的坑。** 远征01 的 `room_02/06/10` 与 Boss 房就是实例：天花板视觉齐全、遮出了阴影，实测仍有 **81%~100%** 的身体采样点直达太阳、每秒掉 2% 最大生命；根因是顶盖件是 `visual_only`。修复后 0%。记录见[远征01 天花板遮光](../development/2026-10-12_expedition01_ceiling_sun_occlusion.md)。

**因此本关把「封顶」直接接在既有硬契约上，`06_技术施工_怪物精英与Boss.md` §7.3.1 要求三项全真（缺一即视为未封顶）：**

1. **有顶盖件** —— 房型布局实例清单里存在覆盖整片屋顶的构件；
2. **该 prefab 带 `layer = 1` 碰撞盒** —— `collision_policy = "structural_box_proxy"`、盒尺寸 = 组件全包络、位置 `y = +高/2`；
3. **静态场景里真落成同名节点**，且 `authored_layout_room_type_component_count` 计入它。

配套两条口径不能改：

- **顶盖件的 `slot_role` 必须是 `room_type_component`，不得是 `solid_wall`** —— 水平顶盖不是墙，写成墙会被门槽判据当墙统计、污染 lane 台账；
- **顶盖用全包络盒，不照几何切段** —— 包络盒把中空周圈的内侧封成整片顶盖。

**本关的封顶要求比 01 严：01 只有 6 个房型封顶（走廊 / 桥房 / 标准房 / 撤离房 / 安全房**本来就不带顶盖件**），02 要求「**所有房间封顶**」。⇒ 需要为 01 未封顶的房型补顶盖件（安全房 / 走廊 / 桥房 / 标准房 / 撤离屋），或改走甲选项（见 §5.1）。**这是一笔独立工作量，不是调参。**

**受光三态的后果（`06` §7.7，本关全程适用）：**

| 受光状态 | 移动速度 | 攻击频率 | 生命效果 | 本关预期 |
|---|---:|---:|---|---|
| `darkness` 黑暗中 | 100% | 100% | 无 | **本关基线**（房间灯关掉时） |
| `artificial_light` 受到灯光 | **40%** | **40%** | 无 | 开灯后 |
| `sunlight` 受到太阳光 | 100% | 100% | 每秒损失最大生命 2% | **本关要求为 0%** |

⇒ **本关的灯光不是氛围装饰，是战斗变量：关灯 = 怪不减速。** 这与 01 的开放平房完全不同，必须在关卡节奏里当成一条机制来设计（例如「宴会厅必须开灯打」）。

### 5.3 窗户：与遮光**不冲突**，但必须钉死口径

**为什么自由：** 遮光判据是从身体采样点**沿太阳方向朝上**打射线（§5.2）。窗户开在**竖直墙**上，射线朝上要穿过的是**顶盖**，不是墙。**⇒ 只要房间封顶，窗不破坏遮光。**

**但要钉死三件事：**

| # | 口径 | 理由 |
|---|---|---|
| 1 | **窗必须是纯视觉件**（或只带 `camera_only` 层碰撞），**不得在 layer 1 上留豁口** | 一旦墙被挖穿且该处没有 layer 1 遮掩，低太阳角下射线可能从洞口斜穿进来 ⇒ 窗边怪被判 `sunlight` |
| 2 | **窗不提供 `artificial_light`** | 受光判定只认显式登记的主太阳灯、注册灯具与玩家手电（`06` §7.2）。**窗边的怪在房间关灯时仍是 `darkness`（不减速）** —— 不要指望「窗边亮所以怪变慢」 |
| 3 | **逐房实测「直接见太阳比例 = 0%」** | 用现成探针 `probe_expedition_room_sun_occlusion`（逐房沿太阳方向打射线、打印比例），**窗的那一面向也必须覆盖** |

### 5.4 室内镜头：**没有现成机制，必须新做**

**现状（已核实）：** 现有收镜机制只有两种，都由玩家所在房决定，**与房间净高无关**：

| 机制 | 位置 | 触发 |
|---|---|---|
| 墙后抬升收镜 | `TowerDescent3D.gd:1669` `_update_camera_lower_wall_lift()` | 探针打到带 `camera_lower_wall` 元数据的碰撞体（**只有南北向实体墙 / 门墙 / 门 / 内部横隔墙**，判据见 `:1931` 与 `DungeonRoom3D.gd:3885/4051/4240`） |
| 楼梯楼板下压 | `TowerDescent3D.gd:1783` `_update_camera_stair_slab_drop()` | 只认带 `camera_stair_slab` 元数据的**楼梯斜楼板** |

**没有的东西：**

- ❌ **没有「按房间净高压缩镜头距离 / 俯角」的任何逻辑**；
- ❌ **没有房间级相机参数覆写入口** —— `DungeonRoom3D.configure()`（`DungeonRoom3D.gd:491-526`）**不接受任何 camera 键**，房间 record 里也没有相机键；
- ❌ 唯一的「相机接管」是**全局短路**（剧情摄影机 / 主菜单 / 设施菜单，`TowerDescent3D.gd:1618`），不是房间级。

**现有镜头唯一事实源（`TowerDescent3D.gd:156-160`，塔楼与两个远征关卡共用）：**

| 常量 | 值 |
|---|---|
| `CAMERA_HEIGHT_M` | `9.993940` |
| `CAMERA_DEFAULT_TRAILING_M` | `3.699625` |
| `CAMERA_LOOK_HEIGHT_M` | `0.45` |
| `CAMERA_LOOK_AHEAD_M` | `0.75` |
| `CAMERA_FOV_DEG` | `65.0` |

> 🛑 **这里是本关最硬的一处冲突：默认相机高度 9.99 m，远高于目标净高 3 m。**
>
> 在「12 m 逻辑墙 + 3 m 吊顶」的房间里，**相机在天花板之上**，视线会被吊顶挡死。**⇒「压缩镜头」不是美化项，是低矮房间的**前置条件**。**不解决它，§5.1 丙方案（压视觉净高）也走不通。**
>
> 相对的：若**不**压视觉净高（维持 12 m 观感），镜头可维持现状 —— 但那就不叫「密闭低矮旅馆」了。**这两件事必须一起拍。**

**提案（**待裁决**，含公式）：** 给房间 record 加可选 `camera_profile`，未写则完全走现状，写了按净高等比缩放：

```text
cam_h = clear_m − CAMERA_CEILING_CLEARANCE_M     # 0.9 m 顶部净空
cam_t = cam_h × (CAMERA_DEFAULT_TRAILING_M / CAMERA_HEIGHT_M)   # 等比 ⇒ 俯角与 FOV 不变
下限保护：cam_h ≥ CAMERA_LOOK_HEIGHT_M + 0.6      # 1.05 m，否则相机穿到玩家头下
```

按 `3.0 m` 净高代入：

```text
CAMERA_DEFAULT_TRAILING_M / CAMERA_HEIGHT_M = 3.699625 / 9.993940 ≈ 0.37019
cam_h = 3.0 − 0.9 = 2.10 m
cam_t = 2.10 × 0.37019 ≈ 0.777 m
```

⇒ 主体变形缩到默认的约 **37%**，画面明显「贴脸」—— 这正是「压缩视角」的观感，**但必须实机确认可玩性**（可辨识距离、战斗瞄准、拾取可见性）。

**落地纪律（与 01 的房间级可选字段同一条）：** 新字段要走**四道白名单**（源 → 规范化层 → 运行时计划 → 塔楼 record → 房实例 `configure`），漏任何一道都**静默丢字段**；且**绝不能进 `_data_driven_layout_id()`** —— 镜头参数是表现，不是几何，进指纹会让既有存档失配。**必须另写手写 patch 探针**直接驱动中间层函数，否则「没有关卡在数据里写这个字段」时端到端断言就是 0 样本空跑、照样绿。

## 6. 可破坏墙壁与场景组件：**本项目 0 基础**

**核查结论（`src/` 全库 + `docs/` 全库）：**

| 找什么 | 结果 |
|---|---|
| 可破坏物 / 破坏状态机 / 组件耐久 | **不存在。** 无 `DestructibleComponent` / `BreakableWall` / `damage_state` / `structural_health` 之类节点或系统 |
| 最接近 ①：`scene-art-damage-variant-kit` | **只是「破损外观变种」** —— 把模块化构件派生 N 个「看起来破」的变种、运行时按确定性随机换一部分实例。**没有 HP、没有破坏事件、打不掉** |
| 最接近 ②：`src/training3d/TrainingTarget3D.gd` | 训练场**靶子**（有 `damaged` / `destroyed` 信号与 `max_hp`），但只在训练场，**不是场景墙/组件** |
| `docs/` 里「可破坏」的命中 | 全是**假阳性** —— 「不可破坏的已有规则」「跨系统不可破坏契约」都是「invariant」的意思，与玩法无关 |
| 场景组件可被玩家/敌人破坏的设计文档 | **没有** |

⇒ **「可破坏墙壁与场景组件」是全新立项，不属于「按现有规则处理」。** 要做，至少要新造：**组件 HP + 破坏状态机 + 破坏判定入口 + 破坏后表现（换 mesh / 生成碎块 / 移除或改碰撞）+ 与 AI、导航、流送的接口**。

**四种口径（**待裁决**，§12 L02-3）：**

| 口径 | 做什么 | 代价 |
|---|---|---|
| **① 只做视觉破损** | 用现成 damage variant kit，破败旅馆的墙/女儿墙随机换成破损外观 | **零新系统**；但没有「打掉墙」这件事，玩法上等于只换了美术 |
| **② 只做可破坏的独立组件**（家具 / 门板 / 隔断级） | 新增组件级破坏系统，**承重墙不可破坏** | 中等；不影响结构、导航、遮光 |
| **③ 承重墙也可破坏** | 墙塌 → 改碰撞 → 改导航 → **可能漏光（破坏封顶遮光）** | 最高；**会连带封顶遮光、门槽 lane 台账、存档** |
| **④ 不做** | 主题上「破败」靠破损外观 + 灯光 + 陈设表达 | 零代价；但用户明确要求了这一项 |

> **本页倾向：① + ② 起步，③ 留到第二版。**
>
> 理由很具体：**承重墙一破，「封顶 = 不受日照」这条硬契约会跟着塌** —— 顶盖件的支撑（`structural_box_proxy`）按「组件全包络、位置 `y = +高/2`」冻结，墙没了它不一定掉，但**规范上「房间已封顶」的三项全真判定里没有任何一项描述"墙被打掉之后"**。③ 要连规范一起改。
>
> 另外三条必须一起定的口径：
> 1. **破坏后存档不落瞬时态** —— 对齐「存档不保存瞬时受光状态；读档 / 进房 / 开门后按当前世界重新计算」的既有纪律（`06` §7.4）；
> 2. **破坏不得把门洞封死或伪造出通路** —— 破坏后若能穿行，就会绕过 `room_progress` 与门锁；这是玩法级变更，不是表现级；
> 3. **破坏件不得进 `layout_id`** —— 同上，表现不进指纹。

## 7. 设计边界：这一关不做什么

| 不做 | 原因 |
|---|---|
| 下行楼梯 / 电梯 | 单层结构，没有下一层可下。**中庭挑空的下层是同层内的高差，不是楼层** |
| 设施房（`facility`） | 那是基地的功能房，不属战斗内容 |
| 塔楼四区块内容 | 独立场景，只挂 `Blocks/Expedition` |
| 由设计源改写玩法数值 | 设计源只写「要谁、几只、掉什么」，单只怪的血量/伤害/速度一律由引擎出 |
| **另建模板 id** | 除非主人明示（§3.0 乙路）；否则只在锁定集合里选 |
| **用美术缩放掩盖结构错位** | 模板尺寸与局部真实端口锁定；版图只选择端口配对与整房变换，不能用 ≤5 m 容差或门口净空吸收错位 |
| **让窗户成为玩法光源** | 受光判定只认注册灯具与太阳（§5.3） |
| **未裁决就宣布「3 m 墙」已实现** | §5.1 甲乙丙三选一没定，等于几何基准没定 |

## 10. 落地流程（填表 → 设计源 → 校验）

**本页只到「设计意图」。** 几何按下面的顺序落：

1. **拍板 §12** —— 待裁决没定，不动任何设计源。
2. **填表** —— 走[新关卡设计表](新关卡设计表.md)（表在 `09-level-plan-authoring` 里，**只填第一部分**，第二部分不改用默认，第三部分不能改）。已填实例可照[新关卡设计表 · 测试关卡99](新关卡设计表_测试关卡99.md)的字段口径。
3. **取门槽数据（禁止手算）**：

```bash
Godot_v4.6.3-stable_win64_console.exe --headless --path . \
  res://tests/verification/verify_level_plan_design_source.tscn -- \
  --emit-ports --level=expedition_02
```

4. **校验（两条判据缺一不可）**：

```bash
Godot_v4.6.3-stable_win64_console.exe --headless --path . \
  res://tests/verification/verify_level_plan_design_source.tscn -- --level=expedition_02
```

```text
LEVEL_PLAN_VALIDATE_OK levels=1 checks=... rooms=... templates=...
LEVEL_PLAN_RUNTIME_GUARD_OK levels=1 rooms=... checks=... plans=... rewards=...
```

第一条查设计数据自洽；第二条**真的调一次生成器**，查产出可用。**跑完必须 grep `ERROR`，不能只 grep `*_OK`。**

5. **登记与报告** —— 是否加进 `verify_level_plan_design_source.gd` 的 `TARGET_LEVELS` 要显式取舍：**不登记** ⇒ 以后没人自动检查它，改坏了没提示；**登记** ⇒ 每次批量校验都覆盖它，但基线数字会变、docs 里记的基线要同批更新。**纯测试用、可能随时删的关卡默认不登记。**

> ⚠️ **不要把 `generation_policy.runtime_enabled` 翻成 `true`**，除非你明说接受代价：切数据驱动会改 `layout_id`，且版图几何从「每局旋转/镜像」变成设计源里的固定坐标。单层关卡不会整档失效，但**几何随机性会归零**。这件事和 §12 是同一批裁决。
