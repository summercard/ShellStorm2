## A. 触发语义规范（规则修改）

### A.1 硬规则一：触发条件必填

<span style="color:#791F1F">**每条登记进 `NarrativeCatalog` 的剧本，必须在 `trigger` 里声明触发方式与语义档位；缺任一项 = 校验不过、整体拒绝加载（不半播）。**</span>

- 现在 `trigger` 缺省 = `manual` 要**废掉**：未写 `trigger` 的剧本直接判错。
- `manual` 仍然保留为**合法值**（触发脚本驱动，08 §4.3），但必须**显式写出** `"kind": "manual"`。
- 校验器给出明确错误码文案（照现有风格）：
  `「%s：缺少必填字段 trigger —— 每条剧情必须声明触发条件（event / point / manual 三选一）。」`

### A.2 硬规则二：四档消耗语义（`once` 规范化）

| 规范值 | 中文名 | 起播条件 | **消耗条件**（决定"是否算播过"） | 落盘 | 对应用户原话 |
|---|---|---|---|---|---|
| `run` | 一次性（跨存档） | 条件满足 且 历史未完成 | **完整收口** 才计入 | ✅ 写 profile | 「有一次性的」 |
| `forever` | 可重复 | 条件满足 且 过冷却（可选 `max_times` 上限） | 不消耗 | 不写（仅本局诊断计数） | 「有可以重复的」 |
| `retry` | **未达成可重触发**（新增） | 条件满足 且 历史未完成 | **只有完整收口才计入**；中断/未完成/被抢占 ⇒ **不计消耗**，下次条件再成立仍会触发 | ✅ 写 profile | 「有未达成条件依然再次触发的」 |
| `never` | 禁用 | **永不起播**（登记保留，供占位/调试/待启用） | — | 不写 | （本次裁定，见 §A.3） |

**关键定义：「完整收口」的判定表**（写在 `NarrativeDirector3D._finish(reason)` 一处，唯一判定点）

| 收口路径 | reason 来源 | 是否算「完成」 | 理由 |
|---|---|---|---|
| 演到 `duration` 自然结束 | `duration` | ✅ 算 | 内容全部播完 |
| `flow.end` cue | `flow_end` | ✅ 算 | 作者显式收口 |
| 玩家 `skip()` | `skip` | ✅ 算 | 玩家主动表示「我看过了」；不算会导致按跳过键的玩家被反复打断 |
| 被更高优先级剧本抢占（`_finish("interrupted")`） | `interrupted` | ❌ **不算** | 内容没演完，属"未达成" |
| `abort()`（死亡 / 撤离 / 场景卸载 / 解析失败） | `abort` | ❌ **不算** | 同上；这正是业主说的"未达成条件依然再次触发" |
| 剧本加载或校验失败 | — | ❌ 不算 | 压根没播 |

### A.3 `never` 的裁定

取 **「登记但永不自动触发」**（= 现有实现口径），理由：

1. 文档 §4.3 写的「不限制，仅受 `cooldown` 管」与 `forever` 完全重复，没有存在价值 —— 一档语义重复是规范缺陷。
2. 内容生产真实需要一个「先登记、暂不启用」的档位（对齐 `design_only` 内容不进运行池的既有纪律，见 `DOCUMENTATION_STANDARD` §4）。
3. ⇒ 本方案同步**修正 08 §4.3 表格的 `never` 描述**（文档向实现对齐，并说明为什么改）。

### A.4 触发条件可选补充：`require`（"做灵活"的落点）

为了让 `retry` 档真正表达「条件未达成 ⇒ 不消耗」，`trigger` 允许一个**可选** `require` 块：

```json
"trigger": {
  "kind": "event",
  "on": "room_entered",
  "filter": { "room_id": "floor_01_main_02" },
  "once": "retry",
  "require": { "flag": "opening_02_seen_zombies" }
}
```

- `require` **只支持两种**形态，**不引入表达式引擎**（08 §10 明确「条件表达式引擎不在范围」，本方案不破这条线）：
  - `{"flag": "<key>"}` —— 读 `NarrativeDirector.get_flag()`（本局标记，既有机制）；
  - 代码驱动：触发脚本的 `check: Callable`（既有机制，08 §4.3）。
- 语义：`require` 不满足 ⇒ **判定为假、本轮跳过**（与"条件不满足"同待遇），**绝不写历史**。
- 校验规则：`once = "retry"` 时 `require` **必填**（否则 `retry` 与 `run` 完全等价，属作者笔误，直接判错）。

### A.5 兼容与迁移

- **两个既有值不改名**：`run` / `forever` 直接沿用为规范名 ⇒ **现有内容零迁移**（两条开场剧本的 `"once": "run"` 无需改）。
- 新增 `retry`、修正 `never`；`NarrativeScript3D` 的合法值集合从 3 个变 4 个。
- 校验器对**旧档/旧内容**不做静默兜底：`once` 非法值 ⇒ 判错（现有行为 L207-213 已如此，只是加了 `retry`）。

## B. 跨局历史落盘（规则修改）

### B.1 数据所有者与字段（唯一写入权）

<span style="color:#1565C0">**唯一所有者 = `BaseManager`（profile 长期档）。`NarrativeDirector` 只持有本局内存态，绝不直写文件。**</span>

`BaseData` 新增字段（**形状照抄既有 `elite_archive_records`**，L88-90 的注释纪律同样适用：只放 JSON 安全字段，**不得放场景节点与玩家 weapon_instance_id**）：

```gdscript
# 跨局剧情历史。键 = 稳定 narrative_id；值只含 JSON 安全字段。
# 「完成」= 08 §4.3 定义的完整收口；被中断/中止不算（见方案 §A.2）。
var narrative_history: Dictionary = {}
```

值结构：

```json
{
  "nar_tower_opening_01_wake": {
    "completed_count": 1,
    "first_completed_unix": 1790134177,
    "last_completed_unix": 1790134177,
    "last_result": "flow_end"
  }
}
```

`last_result` 取值 = 收口路径（`duration` / `flow_end` / `skip`），**只允许这三者**（不完整的收口不写入，故不会出现 `abort`）。

### B.2 存档兼容：**不升 `SAVE_VERSION`**

- `BaseData.SAVE_VERSION` 保持 `"2.0"`（`DOCUMENTATION_STANDARD` §4：存档 schema 与游戏版本是不同轴）。
- `_to_dict()` 增加一行 `"narrative_history": narrative_history`；
- `from_dict()` 增加 `if d.has("narrative_history") and d["narrative_history"] is Dictionary:` 分支 ⇒ **旧档缺字段 = 空历史**，与 `elite_archive_records` 同款先例。
- **已知副作用（明说）**：老玩家升级后，历史上已看过的 `run` 档剧情会**再播一次**，之后永久不再播。这是"从无历史到有历史"的必然，**接受并写入 08 文档**，不做补齐。

### B.3 命令与查询（`BaseManager` 新增）

| 类型 | 签名 | 语义 |
|---|---|---|
| 命令 | `commit_narrative_completion(narrative_id: String, result: String) -> bool` | 计数 +1、更新时间戳；内部走 `save_base("narrative_completed:<id>")`；**写盘失败则回滚内存并返回 false**（照抄 `save_base` L106-108 的回滚模式） |
| 查询 | `has_narrative_completed(narrative_id: String) -> bool` | 供 `_try_fire` 裁决（`completed_count > 0`） |
| 查询 | `get_narrative_history(narrative_id: String) -> Dictionary` | 供验收与将来的"档案/回顾"系统复用 |
| 查询 | `get_narrative_history_snapshot() -> Dictionary` | 全量只读投影，供验收断言 |

### B.4 写入时机与接线（含 AGENTS 存档隔离红线）

- **写入点唯一**：`NarrativeDirector3D._finish(reason)` 内，判定 `reason ∈ {duration, flow_end, skip}` 且当前剧本 `once ∈ {run, retry}` 时调用一次 `commit_narrative_completion()`。
- **`forever` 档不写档**（不消耗，写盘只增加 IO 与档体积）。
- <span style="color:#791F1F">**`NarrativeDirector` 不得在 `_ready()` 触碰 `user://`**（`AGENTS.md` 存档隔离约定 + 08 §8.10）。</span>因此：
  - `_arm_catalog_triggers()`（L95）**不预读历史**；
  - 触发裁决时**惰性查询** `BaseManager.has_narrative_completed(id)`（BaseManager 是 autoload 且注册在 `NarrativeDirector` 之前，`load_base()` 已完成）；
  - 这样读档路径与验收的"隔离用户目录"约定不冲突。
- **与既有 `reset_run_state()`（L597-606）的关系**：两者**并存、不互相取代**。
  - `_armed.fired_count` = 本局内存态（防同一局内重复播）；
  - `narrative_history` = 跨局持久态（防重开游戏重播）；
  - 裁决 = **两者取并集**：本局播过 **或** 历史上完成过 ⇒ 不再播。
  - 复位存档（`game_save_reset_completed`）会清空 profile ⇒ 历史自然为空 ⇒ 开场可重播，这比现有"仅内存归零"更彻底、更符合"新档"语义。

### B.5 失败收口

| 失败场景 | 处置 |
|---|---|
| 读不到字段（老档） | 视为未完成（会重播一次，已声明接受） |
| 写盘失败 | 内存回滚 + `push_error` + **本局仍记内存态**（同一局内不重复播）；下次上线可能重播，留痕不静默 |
| `narrative_id` 已从 `NarrativeCatalog` 移除 | 历史行**不删**（旧档可追溯），裁决时只按 id 查询，不遍历表 ⇒ 无副作用 |
| 历史字典被写坏（非 Dictionary） | `from_dict` 回落空字典 + `push_warning`；不阻断读档 |

### E.3 验收判据（正常 / 拒绝 / 重试 / 读档 + 反向对照）

- **四档语义**：`run` 第二次不播；`forever` 每次满足都播且受冷却；`retry` 被 `abort` 后**能再播**、正常收口后**不再播**；`never` 永不播。
- **必填校验**：缺 `trigger`、缺 `once`、`retry` 缺 `require`、`once` 非法值 ⇒ **各有一条拒绝用例**。
- **落盘**：完整收口后 `BaseData.narrative_history` 出现该 id 且 `completed_count` 递增；`abort`/`interrupted` 后**不出现**。
- **读档**：写盘 → 重载 `BaseData` → 裁决仍为"已播过"。
- **新档边界**：复位存档 ⇒ 历史清空 ⇒ 开场可重播（现有 C5 用例升级为"走真实信号 + 历史清空"）。
- **老档兼容**：构造缺 `narrative_history` 的 2.0 档 ⇒ 不报错、不判为坏档、行为 = 未播过。
- **落点 bug**：正例（`scope=base/room=start` + `tutorial_completed=true`）**不得**走开场分支、**不得**清空武器；反例（真新档）行为逐值不变。
- **反向对照（每组必须精准变红后还原）**：① 把新判据改回 `_should_start_on_rooftop_for_entry()` ⇒ 落点用例变红；② 让 `_finish` 在 `abort` 时也写历史 ⇒ `retry` 用例变红；③ 把裁决改成只看内存（不看历史）⇒ 跨局用例变红。
- **证据要求**：写盘/读回类用例断言**磁盘档内容**（不是内存投影）；真实渲染类（开场画面）另附真机证据。
