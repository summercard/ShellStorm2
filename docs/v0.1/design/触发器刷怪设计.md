# 触发器刷怪（Spawn Box）设计契约

> 业主裁定 2026-09-26：**废弃现有公式刷怪，改为可摆放的「触发盒」**。
> 职责分层：**盒子只负责出怪**（含延迟秒数），**调用机制与盒子分开写**。
> 试点范围：**远征01**。

## 1. 为什么改（现状证据）

现有刷怪只有**一个入口** `Dungeon3D._spawn_room_enemies(room)`（`src/world3d/Dungeon3D.gd:2135`），
触发时机写死在 `_on_room_entered`（L2124）：

```gdscript
if room.room_type in HOSTILE_ROOM_TYPES:
    _spawn_room_enemies(room)          # 玩家进房 → 一次刷满
```

它**本身就是一个"触发盒"**，只不过被写死成唯一一个、且不可配置：

| 维度 | 现状（硬编码） |
|---|---|
| 盒范围 | **整个房间**，不可调、不可摆 |
| 触发条件 | **玩家进入**，唯一，不可选 |
| 刷什么 | 三条路并存：①设计源 `enemy_spawn_plan` ②房型分支 BOSS/ELITE/TRAP/BASEMENT ③**公式兜底** |
| 刷几只 | count 区间随机 + 公式补兵 + 命运卡加兵，**共 5 处代码在改同一件事** |

其中**公式兜底**（L2190）是维护成本的主源：

```gdscript
var desired := 4 + floor * 2 + (2 if room.size_class == "large" else 4 if room.size_class == "arena" else 0)
```

⇒ 业主判定：**不可控、维护成本巨大**，改为显式可摆放的触发盒。

## 2. 设计目标：三层解耦

业主原话要点：
- 触发盒**本身是一个独立的文件**，可以用来调用，**类似 prefab**；
- **每个房间独立调用**触发盒的放置位置，进入房间后每个触发盒可独立调整；
- 调用触发盒的**机制本身不和触发盒一起写**；**触发盒只负责出怪**，可以出现**延迟几秒**出怪的选择；
- 玩家进入战斗房 → 房间机制调用**第一波**（第一波触发**几个盒子**）→ 本波全灭 → 触发第二波；
  **这一整套（波次推进）都要做好**。

⇒ 拆成三层，各自独立演进：

```
┌─ ① 盒子资产层（独立文件，类似 prefab）────────────────────┐
│  data/spawn_boxes/<box_id>.json                          │
│  只管：范围默认尺寸、出什么怪、几只、每条延迟几秒          │
│  不知道：哪个房间用它、什么时候用                          │
└──────────────────────────────────────────────────────────┘
                        ↓ 被引用
┌─ ② 房间放置层（每个房间独立声明）─────────────────────────┐
│  floors/floor_XX.json 房间记录：spawn_placements[]        │
│  声明：在本房局部坐标 (x,z) 放 <box_id>，尺寸/朝向可覆盖   │
└──────────────────────────────────────────────────────────┘
                        ↓ 被调度
┌─ ③ 调用机制层（与盒子分开写）─────────────────────────────┐
│  encounter.stages[]：第 N 波调用哪几个盒子实例            │
│  复用现有波次推进：全灭 → 2s 间隙 → 下一波                 │
└──────────────────────────────────────────────────────────┘
```

**关键取舍**：远征版图 `mode=constrained`，几何由**生成器按种子现算**（不是一张手工搭好的
关卡场景），故**不存在可在 Godot 编辑器里直接拖盒子的关卡场景**，「手动摆放」落在**数据层**：
盒子写成独立文件、房间用**局部绝对砖心**引用（§3.2.1）。
2026-09-26 起主路房型**钉死**（`pin_content_templates`）⇒ 每局同一张图 ⇒ 砖心坐标跨种子稳定、
可逐盒精调（「01 号盒往北挪一格砖」）。
摆放辅助 = 砖格图（`_scratch/expedition_spawn_boxes/dump_tile_grid.py`，标出可作盒心的砖）
＋ 落点散点预览图（`render_box_map.py`）。

## 3. 数据契约

### 3.1 盒子资产 `data/spawn_boxes/<box_id>.json`

```json
{
  "schema": "shellstorm2.battle.spawn_box",
  "schema_version": 1,
  "box_id": "box_corner_ambush",
  "note": "角落包夹（小盒 3×3 m）：近战×2 贴身起手，共 2 只。",
  "shape": "box",
  "size_m": [3.0, 3.0, 3.0],
  "spawns": [
    { "type": "melee_chaser", "count": 2, "delay_sec": 0.0 }
  ],
  "placement_policy": { "min_spacing_m": 1.7, "wall_recess_tiles": 1 }
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `box_id` | ✅ | 全局唯一，与文件名一致 |
| `shape` | ✅ | `box` \| `cylinder`（`cylinder` 用 `size_m[0]` 作直径） |
| `size_m` | ✅ | 盒子默认尺寸 `[width, height, depth]`（米）；**取 (x,z) 作盒面**，放置层可覆盖。**逐实例生效尺寸不得 < 2×2 m** |
| `spawns` | ✅ | **出怪清单**，盒子唯一的职责 |
| `spawns[].type` | ✅ | 怪物类型 ID。6 类普通怪（`melee_chaser`/`ranged_caster`/`summoner`/`shielded`/`exploder`/`ambusher`）+ `elite`/`boss` 两种身份指派 |
| `spawns[].count` | ✅ | 整数或 `{min,max}` 区间 |
| `spawns[].delay_sec` | ➖ | 该条**出怪延迟**，默认 0 |
| `placement_policy.min_spacing_m` | ➖ | 盒内分离度下限（实际下限 = `max(怪体直径 1.7, 本值)`） |
| `placement_policy.wall_recess_tiles` | ➖ | **整盒（含边缘）**离墙内缩圈数（1 圈 = 5 m），默认 `1`；`0` = 允许贴墙。⚠ 判的是**盒边**不是盒心（2026-09-26 收紧，见 §3.2.1 / §7.1-H） |
| ~~`placement_policy.prefer_edge`~~ | ⛔ | **2026-09-26 废弃**：盒内一律随机撒点、不贴边。仍从 JSON 读出仅为兼容旧资产，运行时不再使用（见 §7.1 / §9 缺口 b） |

**盒子不含**：房间引用、波次序号、触发条件 —— 那是 ②③ 层的事。

#### 3.1.1 盒子一律是**小型单位**（业主 2026-09-26 口径）

业主原话：*「一个房间可以触发多个盒子，每个盒子都是一个小型单位」* —— 故 6 类盒全部重定义
为小盒（`box_boss_arena` 是唯一例外，Boss 需要更大活动面）：

| `box_id` | 盒面 | 编成（→ 表示延迟后补） | `min_spacing_m` |
|---|---|---|---|
| `box_corner_ambush` | **3×3** | 近战×2（共 2 只） | 1.7 |
| `box_center_elite` | **4×4** | 精英×1 → 0.5s 近战×1 | 2.0 |
| `box_corridor_column` | **2×4** | 近战×2 → 1.5s 壳甲×1（共 3 只） | 1.7 |
| `box_wall_arc` | **4×2** | 远程×1~2 | 1.7 |
| `box_room_spread` | **4×4** | 近战×2 → 1.0s 爆×1（共 3 只） | 1.8 |
| `box_boss_arena` | **8×8** | Boss×1 → 1.5s 精英×2 → 3.0s 召唤者×1 | 2.8 |

> **2026-09-26 收敛编成**（业主裁定「数据侧收敛编成」，消解容量告急）：`box_room_spread` 5×5→**4×4**
> 且 4 只→**3 只**（去伏击）；`box_corridor_column` 2×5→**2×4**；`box_corner_ambush` 保 3×3、
> 3 只→**2 只**（去 1.0s 远程）。改后 6 盒全部满足「盒面 ≤ 4 m、一盒 ≤ 3 只」的小盒口径。

⇒ 每盒出 **1~4 只**、每房摆 **3~5 盒**（远征01 共 **43 盒**：10 间内容房 **39** ＋ Boss 房 **4**；其中 `room_09` 是 **`EVENT` 双职房**，见 §3.5）。
「一房几个刷怪点」由**放置实例数**决定，不再由单个大盒的面积决定。

### 3.2 房间放置 `spawn_placements`

房间记录新增数组字段（与 `enemy_spawn_plan` 同级）：

```json
"spawn_placements": [
  { "box": "box_corner_ambush", "center_m": [-22.5, -17.5] },
  { "box": "box_wall_arc",      "center_m": [-12.5, -17.5], "rotation_deg": 90 },
  { "box": "box_room_spread",   "center_m": [-2.5, -12.5] }
]
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `box` | ✅ | 引用 `box_id` |
| `center_m` | ✅ | 盒心**房间局部坐标** `[x, z]`（与房表 `center_m` 同坐标系、同朝向）。🔴 **必须是 5m 地砖的砖心** —— 见 §3.2.1 |
| `size_m` | ➖ | 覆盖盒子的 `[width, depth]`（省略＝用资产默认）；**不得 < 2×2 m**。**归一约定：只在与资产默认不同时才写**（与默认逐值相同的覆盖一律省略 —— 2026-09-26 已把 `floor_00.json` 里 39 处与默认相同的内联覆盖删除） |
| `rotation_deg` | ➖ | 绕 Y 轴旋转，默认 0；**只许 0 / 90 / 180 / 270** |
| `delay_sec` | ➖ | 整个盒子的**额外启动延迟**（叠加在 `spawns[].delay_sec` 之上） |

**实例序**：数组下标即**盒子实例 id**，供 ③ 层按序引用。

#### 3.2.1 🔴 盒心 = **绝对砖心**（业主 2026-09-26 裁定「固定房型 + 绝对砖心」）

业主原话要点：
> *「这些刷怪的盒子都**以地砖（5×5 地砖）的中心位置为中心**，我就可以说这个房间的
> 01 刷怪盒子应该怎么调整。」*
> *「我看刷怪点都是靠近墙边的地砖，**最好往里挪一圈到 2 圈**」*（1 圈 = 1 块地砖 = 5 m）
> *「最小是 2x2」*（= 2 米，见 §3.1 的 `size_m` 约束）

⇒ 配套两条硬约束（都已落成门禁判据，见 §7-G/H）：

1. **盒心必落在砖心相位**：全局 5m 砖格的格心恒在 `5k + 2.5` 两个轴上独立成立
   （已用远征01 全部 13 房的实测 `tile_cells_local` 逐值验证）。非砖心的声明值会被运行时
   `snap_box_center_to_tile` **静默挪走** ⇒「01 号盒我调了却没生效」的根因。
2. **整盒（含边缘）离房墙净距 ≥ `5 × wall_recess_tiles`**：默认内缩 1 圈（盒边净距 ≥ 5 m）。
   最外圈砖心净距恰为 2.5 m，故「1 圈」这个阈值能把最外圈干净地排除掉。
   ⚠ **2026-09-26 由「判盒心」收紧为「判盒边」** —— 业主原话：
   *「这个房间的刷怪点都是在房间周边外圈的地砖，这样体验不好，**最外一圈不要刷怪**，
   往里头布置刷怪盒子。」* 为什么必须判边：怪只在**盒内**取样，故「盒不压进最外一圈」
   ⇔ 那圈必然无怪；只判盒心时（盒心 ≥5 m ＋ 盒半宽 2 m）盒边可以只离墙 3 m，
   仍盖住最外一圈 ⇒ 怪照样出在贴墙第一排。**收口证据见 §8 P3 第三轮**。

**「第几行第几列砖」的可读写法**：房局部砖心集合 = `-size/2 + 2.5 + 5k`（两轴独立）。
故盒心也可以读作「沿 x 的第 i 列、沿 z 的第 j 行地砖中心」，逐盒精调时按此换算。

**为什么能写绝对砖心**：`mode = constrained` 的远征原本**每局按种子重洗房型**，房型一变砖格就变。
2026-09-26 已把主路房型**钉死**（`pin_content_templates`，见 §4.1），同一关卡每次生成
**同一张图**（三种子逐值实测：`origin` / `dimensions` / `doors` / `tile_cells_local` 全一致）
⇒ 绝对砖心才成立。**代价**：失去每局版图变化（业主已知并接受）。

⚠ 门禁对**砖心相位**这条判据只在「本房真有授权地砖」时执行（`authored_layout_room_id` 非空）。
没有授权壳体的房（如远征入口）没有砖格，`snap_box_center_to_tile` 直接原样返回声明点，
此时砖心相位无意义。

### 3.3 调用机制 `encounter`

```json
"encounter": {
  "stages": [
    { "boxes": [0, 1] },
    { "boxes": [2] }
  ],
  "intermission_sec": 2.0
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `stages` | ➖ | 波次表，每波引用一组**盒子实例下标**；省略＝全部实例一波出 |
| `stages[].boxes` | ✅ | 本波调用的实例下标数组（「第一波触发几个盒子」即此项长度） |
| `intermission_sec` | ➖ | 波间隙秒数，默认沿用 `ROOM_WAVE_INTERMISSION_SECONDS`（2.0） |

推进规则（**复用现有机制**，`_schedule_room_wave_intermission` / `_spawn_next_room_wave`）：
本波敌人全灭 **且** 无预留召唤 **且** 本房无存活节点 → 等 `intermission_sec` → 下一波。
无合法落点 → `_room_spawn_blocked`，暂停并保房解锁。

### 3.4 登记点（4 处必须同改）

房间级可选字段是**白名单重建**，漏登记会被**静默丢弃**（不报错、不红）：

| # | 文件 | 位置 | 动作 |
|---|---|---|---|
| 1 | `src/map/LevelPlanLoader.gd` | `normalize_floor` 房间字典 | 登记 `spawn_placements` / `encounter`；层字段 `spawn_boxes_only` **逐房下发** |
| 2 | `src/map/FloorPlanGenerator.gd` | `_constrained_slot` / `_constrained_slot`→`_constrained_floor_from` / `attach_authored_layout_shell` | 生成器透传（`spawn_placements` / `encounter` / `spawn_boxes_only`） |
| 3 | `src/map/LevelPlanValidator.gd` | `_validate_spawn_boxes` | A–K 判据（见 §7） |
| 4 | `src/framework/GameDesignConfig.gd` | `ROOM_TYPES_WITH_HOSTILES` / `room_type_uses_spawn_boxes` / `EVENT_ROOM_TYPE` | 房型口径 —— ⚠ 「**必须**有盒」（`ROOM_TYPES_WITH_HOSTILES`）与「**允许**摆盒」（`room_type_uses_spawn_boxes`，**已纳入 `EVENT`**，业主 2026-09-26，见 §3.5）是**两件事** |

> **「只认盒子」标记为什么必须下发而不是运行时再查层**：`Dungeon3D` 只拿得到**房间记录**，
> 拿不到层的规范化结构；不下发 ⇒「没盒子就不刷」在运行时无从判断、规则静默失效。

#### 3.4.1 几何权威性标记 `geometry_authoritative`（🔴 判据门控的钥匙）

`mode = constrained` 的 L2 文件里 `center_m` / `size_m` 只是「拓扑蓝图 + 样例 / 兜底」，
**真几何由生成器按种子算**（实测教训：远征 `room_05` 房表声明 `30×60`、运行时是 `60×30`
—— 生成器按连接方向做了转置）。因此判据 B / G / H 被门控：

| 结构来源 | `geometry_authoritative` | 依赖真实尺寸的判据 |
|---|---|---|
| `LevelPlanLoader.normalize_floor`（读 L2 文件） | `mode != "constrained"` ⇒ authored 房 `true`、constrained 房 **`false`** | 跳过（否则把合法盒位误报成「越出房间」） |
| `FloorPlanGenerator._constrained_floor_from`（真几何） | 恒 `true` | 全开 |

⇒ 生成器把产出交给 `LevelPlanValidator.validate_normalized` 时，判据打的是**真正会用到的几何**。
缺任一侧，门禁就会「要么全盲（拿样例几何照样判、误报），要么全哑（真几何也不判、漏报）」。
判据 I / J / K 只用**房内相对量**（局部盒心、盒尺寸、旋转角），与几何权威性无关，恒执行。

### 3.5 `EVENT` 双职房：`EVENT` 房也可摆盒出波（2026-09-26 业主裁定）

业主原话要点：*「`room_09` 为什么不刷怪，帮我也刷 3 波」* —— `room_09` 的内容类型是 `EVENT`
（异常信号终端），此前**只出事件、不出怪**。裁定后改为「**事件 ＋ 战斗**」双职房。

**判据是「显式摆了盒」，不是「房型」：**

- `EVENT` **不在**公式刷怪的入口门 `ROOM_TYPES_WITH_HOSTILES` 里 —— 这是刻意的：
  塔楼 / 主题池里**程序化生成的无盒 `EVENT` 房照样不刷怪**（不因本条裁定被顺带刷上随机怪）。
- 只有 `EVENT` 房**显式写了 `spawn_placements`** 才按盒出波。运行时判据 =
  `Dungeon3D._event_room_has_authored_combat(room)`（只看设计源 `room.spawn_placements` 是否非空，
  进房首帧即定、不看运行态）。
- 「**可否摆盒**」的唯一口径 = `GameDesignConfig.room_type_uses_spawn_boxes(content_type)`，
  **已纳入 `EVENT`**（与「**必须**有盒」的 `ROOM_TYPES_WITH_HOSTILES` 是**两件事**）；
  静态判据见 §7.1-A 的「② 允许摆盒」侧。

**放行条件叠加**：本房 `cleared` 需**战斗清完 且 事件已结算**，二者缺一不可 ——
战斗侧由 `Dungeon3D._room_has_pending_combat()` 判（存活 / 在途预约 / 待发波 / 本波间歇，四者任一即算未清）。

**现状落地**：远征01 `room_09`（办公室 30×40）＝ `EVENT` ＋ **4 盒 / 3 波**（盒位与同房型 `room_03`
一致）。逐房编成见 `远征关卡01设计.md` §4.5 / §4.5.0。

## 4. 运行时链路（改造后）

```
进房（`room_type ∈ HOSTILE_ROOM_TYPES`，或 `EVENT` 房且**显式摆了盒** ⇒ 双职房，见 §3.5）
  ↓ Dungeon3D._spawn_room_enemies(room)          ← 保留为唯一入口
  ↓ 读 room.spawn_placements + room.encounter
  ↓ 每实例解析盒心/尺寸 → 解析「落地盒」（容量不足则整体平移，见 §4.1）
  ↓ 每实例：候选点 = 盒**自身**按 1.0 m 网格采样（盒局部系步进 → 转房间局部系）
  ↓ 逐个过「地砖覆盖 + 离墙净距」与「实体障碍」两道闸
  ↓ 盒内取点：**带种子随机序 + 首适配**，间距硬下限 = max(怪体直径 1.7 m, 盒 `min_spacing_m`)；
     首轮取不满则**换种重洗**（有界，见 §9 缺口 c），宁少出不穿模
  ↓ 组成本波「(config, position) 列表」→ _commit_room_waves
  ↓ 复用 _room_wave_queues / _spawn_next_room_wave / 2s 间隙 / 全灭推进
```

**落点变化**：由「房间级贪心最远点」改为「**盒内**取点」——
候选池限定在本盒范围内。⚠ 盒是**独立采样域**（按 `SPAWN_BOX_SAMPLE_STEP_M = 1.0 m` 步进），
**别复用房间级 5 m 砖子点池**（窄盒会穿模）。
盒内取点 = **带种子随机序 + 首适配**（`_scatter_box_pick`），只保最小间距、排不下就少出；
`prefer_edge` 贴边加权已废弃（§3.1）。
`spawns[].delay_sec` 由 `Enemy3D` 延迟激活（或波内二次调度）。

### 4.1 主路房型已**钉死** ⇒ 盒位可写绝对砖心（2026-09-26 裁定，取代原「意图锚点」口径）

**变更前的口径（已废止）**：`mode = constrained` 每局按种子重洗房型，`content_template_pool`
里 5 类模板（`std_25x25` / `office_60x70` / `db_70x50` / `corridor_45x40` / `bridge_60x50`）
的可通行区逐块求交**交集为空** ⇒ 当时结论是「不存在任何固定局部坐标能让盒在全部房型下
都落在可通行区」，于是 `center_m` 只当**意图锚点**、运行时解析「落地盒」兜底。
该结论**仍然成立**（它只依赖各模板的可通行区形状），但**已不再是本关的处境**。

**变更后（现行）**：业主裁定「**固定房型 + 绝对砖心**」——主路房型不再洗牌，
`floor_00.json` 的 `template_id` 变成**硬约束**（`pin_content_templates`），10 间房尺寸固定。
配套修掉一个确定性缺陷：`FloorPlanGenerator._anchored_direction_order` 的并列 tie-break
原先按**数组下标**（继承按种子打乱的 `rest` 序）⇒ 换种子会翻方向 ⇒ 换门位 ⇒ 换变体轮廓
⇒ 换砖格。改为按**固定方向优先级**（`DIRECTION_PRIORITY = east < north < west < south`）定序后：

- 三种子（`77001199` / `12345` / `999999`）的 `origin` / `dimensions` / `doors` /
  `tile_cells_local` **逐值一致** ⇒ 同一关卡每局同一张图 ⇒ **绝对砖心成立**。
- 代价（业主已知并接受）：**失去每局版图变化**。

**因此现行口径**：

- `spawn_placements[].center_m` 是**真砖心**（不是意图锚点）。房局部砖心集合 =
  `-size/2 + 2.5 + 5k`，可读作「沿 x 第 i 列、沿 z 第 j 行的地砖中心」。
- 声明值已含内缩 1 圈余量时，运行时 `snap_box_center_to_tile` 的漂移量 **= 0**
  （声明的是真砖心、且满足内缩 ⇒ 吸附到自身）。
- 运行时仍保留「**落地盒**」兜底（容量不足才平移），但**正常数据下恒不触发**。
  实测（2026-09-26，seed 77001199，钉死房型前）：4 种子 × 17 盒 = 68 盒次中 64 盒次零移动。
- ⚠ **容量判定与选点必须共用同一条规则**（二者同调 `_scatter_box_pick` + 同一 `seed_value`）——
  曾经落地侧用「池点数 ≥ 需求」判够不够，而选点侧受 `min_spacing` 硬下限约束只取得到一半，
  于是出现「25 个点的盒只排出 4 只怪」却**始终不触发**落地平移（实测 room_01 / room_04）。
  2026-09-26 又修一版：原「随机序 + 首适配」在**先抽到居中点**时会一次吃光小盒余量
  （3×3 盒 / 间距 1.7 m 时中心到任一点 ≤1.414 m）⇒ 误判容量不足、触发平移且**随种子翻面**。
  改为**有界重洗**（首轮取不满则换种再试）后，12 种子 × 39 盒 = 468 盒次全部 `shift = 0`（§8 P3 第二轮）。
- ⚠ 盒是**独立采样域**（`SPAWN_BOX_SAMPLE_STEP_M = 1.0`），怪间距硬下限用
  `ENEMY_BODY_RADIUS_M = 0.8`（**不是**离墙净距 `SPAWN_CLEARANCE_M`）。

## 7. 验收判据（门禁）

> 字母表与 `LevelPlanValidator._validate_spawn_boxes` 的代码注释**逐字对齐**（一物一名）。
> **静态判据 A–D / F–K**（校验器，`LEVEL_PLAN_*` 门禁）；**E 是运行时探针判据**；
> **R1 / R2 是报告项**，不影响 `PASS/FAIL`。

### 7.1 静态判据（`LevelPlanValidator`）

| # | 判据 | 几何门控 |
|---|---|---|
| **A** | 两侧表述（与 `LevelPlanValidator` 函数头注释逐字对齐）：**①「必须有盒」** —— `room_type ∈ ROOM_TYPES_WITH_HOSTILES` 且非 `authored_layout_peaceful` 的房间，`spawn_placements` **非空**（否则该房永远空房 → 报错；⚠ **`EVENT` 房例外**：默认纯事件房、**允许没有盒**）；**②「允许摆盒」** —— 判据 = `GAME_DESIGN_CONFIG.room_type_uses_spawn_boxes`（真敌对房 **＋ `EVENT`**，业主 2026-09-26，见 §3.5），**不在此判据**里的房型摆了盒 ⇒ `spawn_placement_on_non_hostile_room` | — |
| **B** | 每个实例的盒（旋转后 AABB）**完全落在本房名义包围盒内** | ✅ |
| **C** | `encounter.stages[].boxes` 下标**不越界**、**不重复**，且**每个实例至少被一波引用**（摆了却永不排到 = 一个永远不出怪的盒） | — |
| **D** | 盒子引用的 `box_id` 在资产库中**存在**且文件合法；`spawns[].type` 在可用类型内 | — |
| **F** | 旧字段 `enemy_spawn_plan` 在 `spawn_boxes_only` 层里**归零**（残留即报错） | — |
| **G** | 盒心必须是**砖心相位**（全局 5m 格心恒 `5k + 2.5`）；否则运行时会被 `snap_box_center_to_tile` 静默挪走 | ✅ ＋ 本房有授权砖 |
| **H** | **整个盒（按旋转后的 AABB，含边缘）**到房墙净距 ≥ `5 × wall_recess_tiles` ⇒ **最外一圈地砖无任何刷怪点**（业主 2026-09-26「最外一圈不要刷怪」）。⚠ 判**盒边**不是盒心 —— 详见 §3.2.1 | ✅ |
| **I** | 同房内两个实例**盒心不得重合**、**AABB 不得互叠**（重复刷 = 必是笔误；互叠 ⇒ 两盒各自贪心、互不知情，落点会挤在一起） | — |
| **J** | **逐实例生效尺寸**（资产缺省 or 实例覆盖）不得 < `SpawnBoxCatalog.MIN_SIZE_M` = **2×2 m** | — |
| **K** | `rotation_deg` 只许 **0 / 90 / 180 / 270**（斜置盒的 AABB 与砖格对不上） | — |

**几何门控**（✅ 列）：依赖「房间真实尺寸 / 真实位置」的 B / G / H 只在
`geometry_authoritative == true` 时执行；读 L2 文件得 `false`、生成器算完覆写成 `true`
（见 §3.4.1）。I / J / K 只用房内相对量，恒执行。

**门禁字母 E 为空号**：E 属运行时探针判据（见下），静态校验器不含 —— 这是刻意的，
不靠改号来凑连续。

### 7.2 运行时探针判据（E）

- **E** 盒内落点自检（判据取自**落地盒**）：
  ① 落点在**落地盒**内；② **离墙净距 ≥ 1 圈（5 m）⇒ 不得落在最外一圈地砖上**（业主口径；
  与静态判据 H 成对 —— 静态判**声明盒**、运行时判**真实落点**，后者能看见家具/柱/凹口
  把候选池挤向墙的情况）；③ 与实体碰撞体不相交；④ 两两间距 ≥ `max(怪体直径 1.7 m, 盒 min_spacing_m)`。
  ⚠ 门禁用**怪体直径**（`ENEMY_BODY_RADIUS_M` = 0.8 m 半径），**不可**拿 `SPAWN_CLEARANCE_M`（离墙净距）当怪半径。
  ⚠ ② 的实现：`room._spawn_floor_contains(point, 5.0)` —— 该函数判「以点为心的 10×10 方框
  完整落在地砖并集内」⇔ 到墙 L∞ 净距 ≥ 5 m ⇔ 点不在最外一圈。
  ⚠ 旧版 ② 用的是 `SPAWN_CLEARANCE_M = 1.15 m`，那只能保证「不贴墙」，**管不住最外一圈**。

### 7.3 报告项（非门禁）

- **R1** 每个盒的**落地盒容量 ≥ 该盒一次可能出的最大只数**（`spawns[].count.max` 之和）。
  不达标 ⇒ 数据侧应缩盒 / 降 `count` / 移 `center_m`；运行时只会按有限点截断（不锁死房间）。
- **R2** 盒心**落地漂移量**：声明位置与落地位置的位移。绝对砖心口径下**应恒为 0**（见 §4.1），
  非 0 即说明声明值不是本局真砖心 —— 是设计侧要看的数，不是运行时的错。
- **R3** 盒内落点散布（体验项）：见 §7.4。

### 7.4 盒内落点散布（体验判据，报告项，非门禁）

> **不是门禁**，不影响 `PASS/FAIL`；用于观察「盒的面积有没有被用上」。

- 同一盒次内，怪物落点在盒内**两轴跨度**应铺开，不应退化成一条线。
  - **退化（一列 / 一行）**：某一维跨度 = 0.0 m。
  - **单侧堆积**：某一维跨度 < 盒宽的 25 %。

**第一轮实测（2026-09-26，seed 77001199，旧大盒版）**：17 盒 / 66 只落点。
退化 5 个盒次、单侧堆积 3 个盒次，合计 8 个盒次异常，**全部 `prefer_edge = true`**。

🔴 **根因定性：8 / 8 为机制侧，不是数据侧。** 证据：这些盒的**候选点池铺满了整盒**
（12×8 的盒池跨 11.0×8.0、10×10 的盒池跨 10.0×10.0、14×8 的盒池跨 14.0×8.0），
说明盒底下**没有**家具 / 柱 / 凹口挡着，点本来取得到 —— 是**盒内选点规则**把它们挑成了一条线。
⇒ 该问题已由 **`prefer_edge` 废弃**（§3.1）+ **小盒重定义**（§3.1.1）一并消解。

**第二轮复验（2026-09-26，小盒新数据，3 种子）**：`degenerate` 全部是 **n = 2 的盒**
（盒里只有 2 只怪：两点构不成「面积用没用上」的判据，故本项**统计口径收窄为 n ≥ 3**）。
**n ≥ 3 的盒次：退化 = 0、单侧堆积 = 0**（3 种子逐种子复核）。

⚠ 该判据须在**建好家具碰撞之后**取样（探针先 `ensure_shell_built()` + `ensure_detail_built()`），
否则落点偏乐观、看不到遮挡。落点散点图：`outputs/expedition01_spawn_box_map.html`。

## 9. 待修缺口与本轮收尾清单（2026-09-26）

### 缺口 a — 同波多盒之间没有排斥（**仍未修**）

- **现象**：同一波内若有多个盒，各盒**各自**贪心取点、**互不知情**；后一个盒不会避让
  前一个盒已占的点。两盒挨得近时，可能出现跨盒的怪互相靠到怪体直径以下（穿模）。
- **本关实测**：第一轮最小同波间距 **2.83 m** 达标（判据 ≥ 1.70 m），但这是**数据凑巧、
  不是机制保证**。第一轮只有 `room_05` 第1波 `#0 #1` 属同波多盒。
  第二轮改为「一房 3~5 盒」后，同波多盒的**场合显著变多**（如 `room_08` 第1波 `#0 #1`、
  `room_05` 第1波 `#0 #1`），该缺口的影响面随之扩大。
- **已做的缓解（静态层）**：判据 **I**（§7.1）拦住「盒心重合 / AABB 互叠」——
  最坏的那一类（两盒重叠 ⇒ 两组怪必然挤在一起）已在设计源层被拒。
  但「盒挨得近但不重叠」仍可能在运行时出现跨盒穿模。
- **建议修法**：给 `Dungeon3D._collect_box_stage_entries` 加一条「同波前序盒已占点」的排斥集；
  并在校验器补判据「同波多盒 ⇒ 盒间距 ≥ 怪体直径」。
- **状态**：**等业主点头后再动代码。**

### 缺口 b — `prefer_edge` 把怪压到盒的同一条边（**已由废弃解决**）

- **现象**：`prefer_edge = true` 的实现（`DungeonRoom3D._box_edge_point`）是给
  「距盒边 ≤ margin 的点」**加一个 spacing 的分** ⇒ **所有贴边点同分**；贪心每轮取
  同一条边的下一个点 ⇒ 怪在盒里排成一条线，盒的面积等于没用上（见 §7.4）。
- **实测**：第一轮 8 个异常盒次**全部** `prefer_edge = true`。
- **处置（2026-09-26 第二轮，业主口径「盒内一律随机撒点、不贴边」）**：
  **`prefer_edge` 字段废弃**（§3.1）—— 运行时不再读取，盒内选点只保最小间距。
  6 盒资产全部改写为 `placement_policy: {min_spacing_m, wall_recess_tiles}`，
  旧的 `prefer_edge: true` 已从数据里移除。
- **状态**：✅ **已解决**（机制侧）。新数据的盒内散布待 `probe_box_map` 复验。
