## 1. 三份文档的分工

| 文档 | 回答的问题 | 改它的时机 | 不写什么 |
|---|---|---|---|
| 本文（节点表） | 主线在哪几个节点演、演什么、多久、锁不锁操作 | 增删节点、挪触发点、改时长或锁操作 | 台词原文、分镜逐秒、触发引擎语义 |
| [剧本](主线剧情剧本.md) | 玩家具体看到什么：地点、动作、台词、镜头、操作交还 | 改表演内容 | 触发条件、接口、验收 |
| [08 剧情触发](../08_技术施工_剧情触发.md) | 系统怎样执行：触发源、时间轴、指令、占用归还、失败语义 | 改系统能力或契约 | 剧情正文 |

三份文档按剧情编号一一对应；同一改动同时影响两份以上时，必须一次改完，不允许只改一份。

## 3. 编号体系现状

现行编号是插段累积出来的，**能读，但不连续**：

`01 → 02 → 2.1 → 2.2 → 2.3 → 2.5 → 03 → 3.1 → 3.2 → 3.3`；原 `04 → 05` 保留为天台支路，不在主线演出期间抢播。

- 2.1/2.2/2.3/2.5 是 02 与 03 之间插入的段，2.4 从未定义。
- **已裁决（2026-10-20，最省方案）：不重排显示号。** `2.4` 留给后续在 02 与 2.5 之间新增的段；更靠后的插段继续用小数号（如 05.1、06.1）。运行 ID、`spawn_key` 与 JSON 文件名一律不动。
- 02 与 05 各含两个地点，仍共用一个主编号，靠「·第二房 / ·第四房」「·天台怪群 / ·吊桥前」区分子段。
- 整段重排方案不采用：编号已写进 `narrative_id`、`spawn_key` 与跨局完成历史（`narrative_history`），重排只能加一层「显示号 ↔ 运行 ID」映射，成本高于收益。

## 4. 覆盖边界

- **已编排**：原98F→99F→100F天台吊桥前；新增03→3.1→数据库3.2→钥匙自动返航→基地3.3→解锁无限公馆；章节专项、真渲染fixture与业务集成证据已汇总，仍不等于纯新档人工全关验收。
- **目标保留未实现**：后续三Boss、集齐四把钥匙、中心塔最终战；不宣称本轮完成四区域全流程。
- **当前能挂的触发源**：`gameplay_started`、`room_entered`、`point`、`room_cleared`、`kill_recorded`、`door_motion_finished`、`light_toggled`、`extraction_started/completed`、`run_completed`、`hp_ratio_below`。
- **当前挂不上的**：`boss_defeated`（无法区分是哪个 Boss）、`kill_of_elite`（无身份化事件）、`floor_entered`（代码不存在）、`item_acquired`（无上行事件）。这些通用事件缺口仍在；但3.1—3.3使用 `MainStoryChapter3D` 的窄条件检查和 `story.*` 指令，不退化为纯位置过线：领取须同时通过真实首领已败、指定高级箱和设计源映射，不能绕过Boss领钥匙。

## 6. 维护流程

1. **加一个节点**：先在本表登记一行（楼层 / 节点 / 编号 / 时长 / 锁操作 / 副作用）。
2. 在[剧本](主线剧情剧本.md)写对应章节（地点、动作、台词、镜头、操作交还）。
3. 在 `data/narrative/` 落 JSON，并在 `src/narrative/NarrativeCatalog.gd` 登记 `narrative_id`。
4. [08](../08_技术施工_剧情触发.md) 只在该节点带来新接口、新触发源或新失败路径时更新。
5. 跑 `python scripts/check_documentation_contracts.py`；涉及运行行为时另跑对应 `verify_*` 专项。
