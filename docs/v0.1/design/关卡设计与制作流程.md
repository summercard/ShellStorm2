## 2. battle 与 expedition 分支边界

| 维度 | battle 战局 | expedition 远征 |
|---|---|---|
| 关卡身份 | 塔楼战斗区，使用自己的 `level_id` | 独立关卡，使用自己的 `level_id` 与运行身份 |
| 场景归属 | 塔楼场景的 `Blocks/Battle`；垂直连接归 `Blocks/Stairs` | 独立场景的 `Blocks/Expedition`；不加载塔楼四区块游玩内容 |
| 楼层 | 按塔楼层号、物理层序和推进契约执行 | 当前单层契约：`floor_number / floor_index / sequence_index` 为 0 |
| 拓扑与推进 | 按塔楼主设计决定楼梯、到达门、区段等；不擅自重开冻结范围 | 按本关主设计决定主路、支线、终点与撤离；不继承塔楼下行规则 |
| 模板和内容 | 只读取本分支批准的房表、模板和策略 | 只读取本关批准的房表、模板和策略；不复制旧关的尺寸与数量 |
| 结构保留区 | 读取塔楼核心筒及楼梯约束 | 单层无塔楼核心筒、无楼梯保留区；不得因层序 0 套用天台轮廓 |
| 正式入口 | 由塔楼接入负责人核对已有入口及开放边界 | 由远征接入负责人核对关卡登记、独立场景、读取与返回路径 |
| 可复用内容 | 已验收组件、稳定 Prefab、公共实现 | 同左；记录来源 AssetID、路径与版本 |

复用安全房、墙体或家具，不等于复用来源关卡的楼层、拓扑、房间身份或推进规则。跨分支资源引用必须显式登记，不改资产路径来伪装归属。

`authored` 表示采用已确认版图；`constrained` 表示在已确认约束内生成。两者都不决定房内变体必须随机。房型、变体、内容类型、整房摆位分别声明固定或随机，不以一个模式名代替全部设计决定。

## 3. 设计前置表单与人工确认

### 3.1 开始条件

1. 新关卡先建立主设计意图，填写[新关卡设计表](新关卡设计表.md)。实际收集需求时使用原表，不另造简化版，不擅自添加样例。
2. 第一部分由负责人填写；可调项采用默认前，必须核对是否适用于目标分支。固定几何基准不得在关卡任务中修改。
3. 每个待决定项写明问题、责任人、影响步骤和状态。关键拓扑、坐标或端口未确认，不落正式设计源。
4. 每批携带 `block_id / level_id / floor_range / design_scope / scene_design_docs / asset_ledger`。美术产物再携带稳定 AssetID、源版本和来源关系。

### 3.2 人工输入与工具派生分工

| 项目 | 必须由人工决定或确认 | 工具职责与禁止项 |
|---|---|---|
| 目标定位 | 关卡身份、用途、目标平台、进出路径、体验目标、禁止项 | 不从目录名或旧关卡推定新关卡意图 |
| 楼层与模式 | 所属分支、层清单、`authored / constrained`、允许随机项 | 按选定分支检查层号关系，不混用两套规则 |
| 房表与主路 | `key / role / parent_key / template_id`、尺寸、旋转、主路、支线及共墙例外 | 检查引用、连通、尺寸和主路计数；不补猜父子边 |
| 默认坐标 | `center_m` 与手绘默认图；受约束模式还要确认约束及回退默认图 | 未给坐标时可提出网格草案，但须确认后才能定稿；不能静默代填 |
| 显式端口 | 真实局部门洞锚点、朝外向量、稳定端口号及配对关系；来自模板/白盒的作者结构输入 | 检查成对连接、局部坐标和旋转；不能用矩形中心猜真实门洞 |
| 旧式中心门槽 | 选择兼容旧式门槽路径，确认模板可开门面与连接意图 | 从唯一实现取合法槽及端口结果；不得手算、目测或跨语言复刻 |
| 内容与固定覆盖 | 内容池、固定内容及确有要求的刷怪、首领或奖励引用 | 可选覆盖默认不填；不猜波数、不造内容ID、不修改数值公式 |
| 运行身份 | 人工确认分支映射和既有兼容限制 | 生成 `room_id / layout_id` 并检查契约；不要求作者手写指纹或擅改旧ID |
| 统计与派生量 | 审阅结果，决定是否调整设计 | 派生世界方位、走廊记录、面积和包络；不复制成第二套人工几何源 |
| 正式接入 | 是否接入游戏、测试集范围、旧档影响与授权 | 校验通过不自动开启运行时数据驱动，也不自动完成菜单/场景注册 |

### 3.3 表单旧口径的使用边界

- 结构执行以 05.2 的现行条款为准。场地边界与总面积目前只供参照、统计，不作为准入上限；不因此免除重叠、端口、净空和性能检查。
- 新关卡优先核对显式 `connection_ports`。一条边任一端使用显式端口，两端都须声明；不得与旧 `ports[].lane_m` 混合决定同一边。
- 旧式门槽读取 `RoomDoorLane` 的结果。需要固化时用设计源校验器的 `--emit-ports` 取数；不能在 Python 等语言复制公式。
- 平面 `+y` 对应世界 `+z`，即南。Blender/Godot 的上轴与正面转换另按资产规范核验，不能把平面坐标直接当 Blender 高度。
- 模板ID集合锁定。旋转用 `template_rotation_deg` 表达，不新增转置模板；支线是角色，不新增同物异名模板。修改集合须明确授权并同步主设计、L1引用、L2引用、校验及美术链。
- 表单中“数据驱动全关”“自动兼容旧档”等历史概括，不作为新关卡承诺。开关逐关核对；存档影响另评估。单层与多层的恢复路径不同，不能一律写成整档失效或完全无影响。

## 4. 主设计意图层与 L1/L2/L3 结构层

| 层级 | 回答的问题 | 应维护内容 | 不应拥有的内容 |
|---|---|---|---|
| 关卡主设计 | 为什么做、希望玩家经历什么 | 定位、流程、节奏、房间构成、随机边界、内容引用、禁止项、待裁决项 | 不复制算法，不把工具现状自动提升为目标规则 |
| 设计表 | 作者确认哪些结构输入 | 已确认房表、主路、模板选择、默认坐标和例外 | 不成为第二套运行时配置或资产台账 |
| L1 `level_plan.json` | 这张关卡有哪些层、采用何种策略 | 层清单、模板池、生成策略及规则版本 | 不写具体房间坐标和组件陈设 |
| L2 `floors/floor_<NN>.json` | 本层哪些房间、怎样连接 | 房间身份、角色、主路、默认坐标、旋转、连接、保留区与合法覆盖 | 不写组件ID、材质或房内视觉布局 |
| L3 `room_templates/<template_id>.json` | 房型能怎样拼接 | 尺寸、轮廓、结构端口/合法门槽、净空与模板接口 | 不写层号、层内世界坐标或连接目标 |
| 运行时计划 | 本次实际生成了什么 | 由结构源与种子得到的房间/边/方位/包络/指纹 | 不反向改写设计意图或房内美术布局 |

结构源落在 `source/art/whitebox/tower_zones/<level_id>/<version>/data/`。默认版本目录按加载器约定使用 `v001`；非默认目录必须核对 `LevelPlanLoader.DATA_ROOT_OVERRIDES`。白盒同版本配套 `blender/`、`renders/`、`validation/`，不把白盒 Blend 当正式美术。

L1/L2/L3 是结构数据分层；“房型 → 房间变体 → 具体房间”是美术复用分层。两者不是一一对应的三个文件。L3 中的历史 `variants` 示例不证明通用注册器已经完成。

当主设计被特定出图脚本解析时，明确被解析章节、表头和字段。图纸只是同源视图，不再抄一份坐标。改动解析范围须验证派生结果；图注方位也应由坐标推导。

## 5. 从设计到交付的完整步骤

本表是未来任务应执行的顺序，不是已完成清单。每步留下输入版本、产物、责任人和门禁结果；未通过不得放行依赖它的下一步。

| 步骤 | 输入 | 操作与产物 | 编辑权及工具路由 | 放行条件 |
|---|---|---|---|---|
| 01 目标与分支定位 | 用户目标、目标主设计、规范 | 冻结关卡身份、进出路径、范围、平台、禁止项及追溯字段 | 关卡负责人；09、scene-full-pipeline | 分支明确；不套用旧关拓扑；依赖决策已确认 |
| 02 房表与主路 | 主设计、原设计表、批准模板 | 确认房号、角色、父子边、尺寸、默认坐标、主路、例外和允许随机项 | 关卡设计；09 | 表单关键项完整；不猜坐标、内容或门位 |
| 03 L1/L2/L3 | 已确认表单、模板结构接口 | 按现存 schema 落三层源；显式端口配对，或从唯一实现取旧式门槽 | 结构设计源；09、05.2 | 引用及版本明确；房型旋转与实际尺寸相符 |
| 04 白盒验证 | 三层源、白盒、候选摆位 | 生成同源结构视图，验证网格、轮廓、连接、桥跨、净空、碰撞、导航和镜头空间 | 结构/白盒负责人；结构专项 | 两条结构判据齐全；白盒可拼、可走；失败回结构源 |
| 05 风格参考 | 通过的白盒、风格需求 | 在无文字顶视图上制作风格稿；标白盒版本，补必要立面、近景 | 表现设计；scene-full-pipeline，按需 ImageGen | 轮廓可对照；不私改尺寸、门洞、路线与净空 |
| 06 组件规划 | 白盒、风格稿、复用库 | 冻结唯一组件清单、族、状态轴、AssetID、接口、来源与实例估算 | 建模前调用02 | 新资产满足50/3/5；历史例外具体可查 |
| 07 Blender模块化制作 | 冻结计划、结构接口 | 制作组件母版；用链接实例表达默认房型；输出Blend、catalog、输出集合及初始化清单 | Blender几何/材质源；01、blender-game-prop-standard | 无整屋焊死资产；定义与实例分开；源可维护 |
| 08 组件美术验收 | 源、游戏输出、预览和清单 | 检查造型、尺寸、原点、方向、色盘UV、材质角色、接口和完整性 | Blender阶段专项 | 脚本判据与目视均通过；插件同步不代替验收 |
| 09 Godot组件导入 | 已验收游戏输出、碰撞/挂点契约 | 逐组件导出稳定GLB，建立PackedScene，配置碰撞、挂点、标签与资源引用 | 组件导入规范 | 独立加载成功；碰撞不封凹口；路径稳定；禁止整屋GLB |
| 10 房型与变体选择 | 稳定组件、默认布局、目标房间 | 选择默认继承、Godot变体或可选Blender差异布局；明确具体房间引用 | 03；变体/正式TSCN | 接口兼容；固定选择合法；不假称已存在通用登记能力 |
| 11 首次装配或正式维护 | 选定布局、白盒、稳定Prefab | 无正式场景才初始化；已有正式TSCN直接维护实例、灯光、启用和参数 | 04；Godot正式房间 | 不展开复制组件内部网格；不从JSON覆盖手改 |
| 12 玩法、门与导航交接 | 正式房间、端口、身份、既有内容配置 | 交接门/走廊所有权、净空、导航、刷怪接口、入口及撤离绑定；核对正式注册 | 关卡/玩法负责人；09接入部分 | 场景引用真正生效；不只验证生成计划；玩法变更另立任务 |
| 13 运行验收 | 正式入口、可复现种子、隔离测试数据 | 验证加载、实际组件、手改保留、通行、导航、主路、返回、性能与真实画面 | 对应专项；按需运行探针 | 日志、退出码和样本有效；无头结果不代替画面验收 |
| 14 登记交付 | 分阶段产物、证据、遗留项及回滚基线 | 核对源完成/组件转正/房间接入，登记稳定引用、版本、哈希和验收范围 | 导入规范、账本登记及关卡负责人 | 缺项如实标未执行；账本与正式引用一致；回滚可定位 |

### 5.1 玩法、门、导航交接单

| 交接对象 | 必须提供 | 接收方核验 |
|---|---|---|
| 关卡入口 | `level_id`、运行身份、主场景路径、结构源版本、区块归属 | 菜单/读取/续局/返回路径引用同一登记源；新增远征核对 `GameDesignConfig.EXPEDITION_LEVELS` |
| 房间身份 | 设计 `key` 与运行时 `room_id` 的明确映射 | 远征入口运行ID `start`、撤离ID `extraction` 的现有硬依赖；其他房号按本关约定，不复制实例清单 |
| 房间场景 | 房型/变体标识、稳定正式TSCN、组件清单和覆写 | 正式入口真正加载该场景；初始化清单不冒充实际节点树 |
| 门与走廊 | 两端真实端口、方向、旋转、共墙边、门洞净空、碰撞归属 | 共墙连接只由一个端点持有门墙、门扇、碰撞和门状态机；另一端共享引用；闲置候选端口保持封墙 |
| 导航与落点 | 可走面、洞口、桥面、障碍、刷怪/交互净空 | 美术只交接几何条件；导航构建、运行更新及刷怪安全由功能所有者验收 |
| 内容接口 | 已批准的内容ID、触发位置、可选覆盖字段及默认行为 | 验证字段到真实房实例的透传，不只检查JSON或FloorPlan；无样本不能算覆盖通过 |
| 开关与存档 | 本次是否修改运行开关、身份、拓扑、指纹及旧档影响 | 逐关授权；当前塔楼冻结路径不擅自打开；兼容方案未定不代做迁移 |

### 5.2 房型、变体与具体房间的选择记录

| 层级 | 职责 | 选择与交付要求 |
|---|---|---|
| 房型 | 定义结构接口、组件集合和默认实例布局 | 复用批准的模板与组件；接口变化不能伪装成纯布局变体 |
| 房间变体 | 复用房型组件，保存允许的布局、灯光、启用和参数差异 | 可直接继承默认，也可维护独立Godot场景；不强制每房Blender差异源，不因变体重复造组件 |
| 具体房间 | 在目标关卡中承担稳定身份，并选择正式场景 | 记录房型/变体/正式TSCN映射；世界摆位与连接由结构计划决定 |

固定选择与明确声明的按种子选择均合法。当前映射先按既有接入能力逐项核实；本表是交接记录要求，不声明已经存在新的JSON字段、通用注册表或解析器。

新关卡还须明确是否加入 `verify_level_plan_design_source.gd` 的 `TARGET_LEVELS`，以及专属门禁的套件归属。只用 `--level=<level_id>` 单次通过，不等于进入后续默认回归。正式登记与验证注册按已授权工程任务完成，不在仅美术或仅文档任务中顺手改代码。

## 6. 编辑权与事实源边界

| 对象 | 唯一编辑权/事实源 | 允许操作 | 禁止替代 |
|---|---|---|---|
| 设计目标 | 对应关卡主设计 | 确认目标、范围和待裁决项 | 用代码现状抹去未实现设计 |
| 关卡结构 | 已确认的 L1/L2/L3 | 房间身份、拓扑、世界摆位策略、尺寸、结构端口与保留区 | 由房内陈设、效果图或旧模型反推正式结构 |
| 组件几何与材质 | Blender源 | 几何、材质、UV、原点、方向与资产接口 | 用Godot临时缩放修复上游尺寸错误 |
| 组件运行包装 | 稳定PackedScene/Prefab | 组件碰撞、挂点、交互接口、标签与元数据 | 把视觉GLB当整套交互逻辑，或在每间房复制内部网格 |
| 房内作者布局 | 正式Godot房间/变体TSCN | 模块实例增删、变换、灯光、初始启用状态与实例参数 | 用默认JSON、Blender参考布局或生成器覆盖已手改场景 |
| 初始化与追溯 | `component_instances.json / room_layout.json`及导出清单 | 首次初始化、记录来源；经授权审查后再导入 | 宣称它们是唯一运行布局源或自动双向同步源 |
| 运行状态 | 对应玩法模块 | 门状态、灯开关状态、刷怪、导航、流送、存档、结算 | 把运行状态写进美术源并绕过功能所有者 |
| 资产状态 | 索引指向的分账本 | 分阶段状态、版本、路径、哈希及证据 | 在本文或catalog另造一份资产状态权威 |

房间根在关卡中的世界摆位受结构计划约束；房间根以下模块的局部摆位由正式TSCN维护。局部编辑一旦改变外轮廓、门位或跨房净空，必须回到结构接口审查，不能以“房间可手改”绕过结构契约。

组件升级定点替换稳定 `components/`、`runtime/` 资源。版本放在源文件、manifest、账本和根节点 `metadata/asset_version`，不在运行路径派生版本目录。保留正式房间的实例变换与覆写；共享组件变化仍须核查所有使用房间。

## 7. 新资产50/3/5与历史例外

| 规则 | 计数与执行方式 |
|---|---|
| 50 | 新房型计划中，自有和引用的唯一组件定义合计不超过50。一个组件放多次只算一个定义；实例数量另记 |
| 3 | 同族常规变体最多3个。族按功能、轮廓与接口归并，不靠改名拆族绕过 |
| 5 | 有明确状态轴的同族最多5个。计划中写清状态轴与每项差异；不能把任意外观堆叠称为状态轴 |
| 规划时机 | 正式建模前由02冻结。新房型、新增组件/组件变体或新增几何定义均先审核新生产范围 |
| 历史基线 | 以具体既有路径、AssetID、源版本和组件集合界定。保留原资产，不追溯删件、归并、改名、重导或重生成 |
| 例外记录 | 写明实际超限事实与基线；不能记为预算门禁已通过，不豁免资源完整性、碰撞或通行检查 |
| 不得扩大例外 | 旧目录、新版本、改名复制或“历史”标签不能豁免新增定义；范围不清先确认 |
| 既有房间维护 | 只调实例、灯光、启用或参数，不触发旧库归并；不新增几何的Godot布局差异不按新增组件定义计数 |

超限时先减项、复用或澄清范围；不得拆成多个文件规避计数。确需改变规则，应另行申请裁定，不能在制作过程中自行放宽。

## 8. 组件更新、房间手改与回滚

### 8.1 更新分流

| 改动类型 | 正确编辑位置与动作 | 必须保留 | 复验范围 |
|---|---|---|---|
| 仅布局/灯光/启用/参数 | 直接修改正式Godot房间或变体TSCN | 其他实例和作者覆写；不反写JSON要求重建 | 本房端口净空、碰撞、导航与真实画面 |
| 组件几何/材质 | Blender源定点修改、美术验收后重导稳定资源 | 稳定路径、AssetID、房间变换与覆写；新几何先审计划 | 所有引用房间的视觉、尺寸与碰撞 |
| 组件碰撞/挂点 | 在Prefab修复，并同步其生成定义以防再生丢失 | 既有房间布局；避免同slug误命中其他组件 | 独立碰撞、交互射线、门口与导航 |
| 原点/包络/接口 | 先核对Blender和结构契约；列出受影响房间再实施 | 已有摆位与连接意图；不靠缩放或挪门掩盖 | 所有使用处的世界位置、端口、通行与玩法接入 |
| 拓扑/尺寸/门洞/路线 | 回主设计、设计表及L1/L2/L3，重做相关白盒门禁 | 房内手改快照；运行身份和旧档影响单独评估 | 结构、多种子、正式场景、门/导航及兼容性 |
| 确需重建房间 | 按8.2保全、审阅候选并人工合并 | 原正式TSCN及全部已确认手改 | 差异保留、组件引用、结构与运行全链 |

### 8.2 正式房间重建的强制保护步骤

1. 先记录工作区状态。保存正式TSCN、相关依赖版本、哈希、当前实例/灯光/启用/参数差异。包括未提交手改。
2. 列出“保留、回填、放弃、待确认”四类差异。明确目标房间和资源范围，取得重建授权。
3. 在隔离副本或已核实不会写正式路径的候选环境生成。现有静态生成器会写回原路径，不能凭筛选房号当保护措施。
4. 对比旧初始化基线、当前正式场景和新候选。此处是人工审查要求，不是已有自动三方合并功能。
5. 只把已批准差异合入正式TSCN。保留稳定组件引用，不展开内部网格，不顺手覆盖其他房间。
6. 复验实际实例、覆写、端口、碰撞、导航与真实画面，再更新阶段状态。出现未解释丢件或覆写丢失即停止交付。

### 8.3 失败回滚

回滚以本次改动前的文件和依赖版本为基线，不以Git HEAD代替用户未提交手改。按失败所有者恢复：结构恢复对应设计源；组件恢复同稳定路径的上一可用资源；房间恢复已保全TSCN及手改差异。

回滚后复验受影响引用，并记录失败原因、恢复版本、哈希、结果及剩余问题。禁止全仓重置、批量接受哈希漂移或删除失败断言来掩盖问题。回滚成功只说明回到已知状态，不等于新版本验收成功。
