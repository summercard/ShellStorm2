两条判据都出：第一条查设计数据自洽（63 项检查），第二条真的调一次生成器查产出可用。
`boss_ids=1` 就是 1.8 里给 `boss` 房填的首领指派**真的带到了运行时**；
`plans=0` 是 1.7 留空的如实反映（本关唯一内容房走全局公式，无刷怪计划样本）；
`rewards=0` 是 1.9 留空的如实反映，各配 `NOTE` 声明，**不是**「已验证」—— 该透传由
`verify_test_level_99_flow` 的手写 patch 探针（`TEST_LEVEL_99_REWARD_OK`）单独覆盖。

**登记状态**

本关**已**登记进 `verify_level_plan_design_source.gd` 的 `TARGET_LEVELS`（现为 `expedition_01` / `battle_level01` / `99`），
所以省略 `--level=` 的批量校验也会覆盖它。批量结果：

```text
LEVEL_PLAN_VALIDATE_OK levels=3 checks=207 rooms=27 templates=13
LEVEL_PLAN_RUNTIME_GUARD_OK levels=3 rooms=27 checks=3 plans=0 boss_ids=1 rewards=0
```

本关另有专属门禁 `tests/verification/verify_test_level_99_flow.tscn`
（判据 `TEST_LEVEL_99_FLOW_OK` + `TEST_LEVEL_99_REWARD_OK`），查的是设计源之外的接入链路：关卡清单登记、
数据驱动真的生效（而不是静默回退内置房表）、独立单层场景结构、内容外框按 4 间房收缩、
免费入口门、撤离信标、以及 99F 菜单里的入口按钮与读取界面终点；`reward_plan` 的
入口白名单 / 出口透传 / `reward_slots` 投影（含 `ref`）/ `layout_id` 指纹隔离 / 静态校验
也由这份的手写 patch 探针覆盖。
1.8 的首领指派口径在这里逐条实测（`_verify_boss_identity`），本关 `boss` 房填的
`boss_monitor002` 也在这里验透传。

**能不能在游戏里玩到**

**能。** 入口在 **99F 基地 → 远征情报室** 的菜单页里，标题「测试关卡99」下面多了一个
「进入测试关卡99」按钮；点它 → 读取界面 → `ExpeditionLevel99_3D`。

**注意：房间的运行时编号不是 `fxx_` 那套。** 塔楼层用 `f%02d_<key>`（如 `f98_hub`），
但远征关卡运行时是**按字面量认房**的：入口房恒叫 `start`、撤离房恒叫 `extraction`、
Boss 房叫 `boss`、主路叫 `room_01…room_0N`。所以本关 L2 里把 `entry` 的 `room_id` 写成 `start`、
其余三间（`room_01` / `boss` / `extraction`）与 key 同名。写错不会让任何几何或静态校验失败，
只会让玩家出生点取不到房、撤离信标挂到一个不存在的房上 —— 这就是 `verify_test_level_99_flow` 存在的理由。
