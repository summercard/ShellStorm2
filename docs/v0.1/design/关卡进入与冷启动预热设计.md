# 关卡进入与冷启动预热设计

功能ID：**WORLD-ENTRY**（唯一事实所有者：`ExpeditionLoadingScreen` + `IrisTransition` 的加载契约）
工程版本：0.1.0 · 设计修订：r2（2026-11-09，新增逐房渲染预热）

本页定义「玩家从任何入口进入一张战斗关卡」时，**读取页必须做什么、预热必须覆盖什么、什么时候才允许把操作还给玩家**。它约束所有关卡，不针对某一关。

当前实现事实与接口见 [关卡生成与爬楼](../05_技术施工_关卡生成与爬楼.md)；读取页布局与分帧装配见[读取记录](../development/2026-10-12_loading_animation_budget.md)；本轮交付见[预热闭环记录](../development/2026-11-07_loading_warmup_gate.md)与[逐房渲染预热记录](../development/2026-11-09_loading_room_render_warm.md)。

---

## 1. 要解决的问题

进入关卡那一帧的冷启动不是均匀分布的，而是集中在五个"第一次"上：

| 时机 | 典型代价 | 玩家的感受 |
|---|---:|---|
| 关卡画面第一次真实渲染（SDFGI/管线初始化） | 2.1~2.7 s | 黑屏久、光圈开得慢 |
| 每个怪种本局第一次生成 | 460 ms | 进门第一只怪出现时卡一下 |
| 战斗特效首次装配 | 20~65 ms / 件 | 第一次开火、第一杀连顿 |
| 首波整批生成（10 只同帧） | ~166 ms | 进战斗房第一帧卡一下 |
| **每间房第一次上屏（材质管线编译）** | **200~1100 ms** | **每推开一道门顿一下** |

最后一项是 r2 新增的认知。它不是"资源没加载"：实测跨门那一帧 `OBJECT_RESOURCE_COUNT` 恒定（3928~4276，前后差 0~29）、`render_gpu` 只有 7~9 ms、draw call 也不变。资源早在装配期随壳体一起 load 完了，卡的是**渲染管线第一次遇到这间房的材质组合时的同步编译**——同一间房走第二遍，p95 就从 354 ms 掉到 191 ms。

读取页是全局唯一的空档：玩家操作被锁、画面被黑幕与光圈盖住、**没有战斗在跑**。本设计只做一件事——把这些代价**搬进这个空档并等它做完**，不改任何玩法时序。

## 2. 进入通道：只有一个

**任何进入战斗关卡的场景切换都必须经过 `ExpeditionLoadingScreen`。**

| 入口 | 当前路径 | 状态 |
|---|---|---|
| 基地全息城市选关 | `RogueMapSelectMenu._commit_departure()` → 读取页 | 已接入 |
| 塔3天台门 | `RooftopExpeditionEntrance3D` → 读取页 | 已接入 |
| 远征撤离 / 死亡 / 主动退出返航 | `TowerDescent3D._return_to_scene_after_settlement()` → 读取页 | 已接入 |
| 冷启动进主场景 | `StartupLoadingScreen`（另一条启动链，职责不同） | 已接入，不在本页范围 |
| 基地四个地牢传送门 | `BaseWorld3D._on_dungeon_entrance_activated()` **直切场景** | 未接入，见 §8 |

目标场景的解析有两条，二者互斥：

1. **显式路径**：调用方写 `IrisTransition.loading_destination_scene`（任意场景，如返航目标、塔楼）。
2. **远征清单**：调用方写 `GameDesignConfig.pending_expedition_level_id`，读取页用 `expedition_level_scene(level_id)` 查表。清单真源是 `GameDesignConfig.EXPEDITION_LEVELS`。

> **禁止**：新增 `change_scene_to_file(<战斗关卡>)` 的直切。绕开读取页就等于绕开预热与全黑交接，表现为"进门卡一下"，而且不会报错。

## 3. 交接时序（硬契约）

顺序不可调换，每一步都以"上一段已完成"为前提：

```
装配完成 → loading_scene_ready=true
  ↓
读取内容淡出 → IrisTransition.cover_now()（全黑）
  ↓
prepare_loading_render()（放开子视口，让关卡真正开始渲染）
  ↓
预热 A：逐帧排空 VFX 队列 + 三个怪基类（与关卡无关）
  ↓
预热 B：逐房各画一帧（与关卡房间表有关）
  ↓  ← 本页的核心约束
_wait_for_basic_scene_ready()（2 帧）
  ↓
release_loading_scene(target)（恢复玩家输入 / 子树处理）
  ↓
open_after_scene()（开圈）
```

**规则 3.1：两段预热都必须在 `release_loading_scene` 之前完成。**

这不是"最好等"而是正确性要求。预热协程与玩家操作的竞争结果是确定的：不等待时，玩家已经能动、读取页已经销毁，剩余特效、怪模型、房间管线会在战斗帧里逐个编译——正是本设计要消除的那些顿帧，只是换了个位置出现，且更难归因。

**规则 3.1a：A 与 B 是两套不同的集合，缺一不可，且顺序固定（A 先、B 后）。**

A 编译的是特效与怪物的材质，B 编译的是每间房自己的结构与陈设材质。B 排在 A 之后，是因为 A 会顺带把公共管线（地面、墙面等共用材质）先编译掉，B 就只剩各房独有的那部分——实测顺序反过来的话 B 要多花约 0.5 s。

**规则 3.1b：预热期间不得把操作还给玩家，也不得把状态文字停在"读取完成"。**

B 实测 1.1~1.7 s，玩家看到的是全黑屏。状态文字在进入预热前改成"正在准备关卡…"，否则就是"读取完成"之后黑屏好几秒，读作卡死。

**规则 3.2：预热未完成也允许开圈，但必须留痕。**

超预算或帧上限触发时，读取页不得把玩家按在加载页里等死，但必须：

- `push_warning` 记录截断原因；
- 在目标场景写 `loading_warmup_completed = false`；
- 该次进入在验收上记为**未通过**，不得当作可用。

## 4. 预热覆盖范围

预热集合**与关卡无关**，对所有关卡取同一套。理由如下：

1. `EnemyAvatar3D.FORMAL_NORMAL_SCENES` 只有三个基类有正式 GLB（`melee_chaser` / `ranged_caster` / `fat_zombie03`）；其余基类（`summoner` / `shielded` / `exploder` / `ambusher` / `boss`）是程序化外壳，没有读盘成本，只有毫秒级材质创建。
2. 全部 `egt_*` 复刻怪通过 `EnemyAvatar3D.PROXY_ASSET_KIND` 借用这三个资产之一；同一资产的第二次装配是缓存命中。
3. 因此逐关枚举怪种没有收益，只会把加载时间拖长。

| 预热项 | 来源 | 数量 |
|---|---|---:|
| 战斗特效 | `VfxPool3D.COMBAT_PREWARM` | 11 件 |
| 怪物表现基类 | `EnemyWarmup.BASE_KINDS` | 3 个 |

两队在**同一条逐帧循环**里推进（特效池自己每帧排空一件，循环每帧挂一个影子怪），总等待取二者较大值而不是相加。

**规则 4.1：新增一个"有正式 GLB 的普通怪基类"时，必须同时加进 `EnemyWarmup.BASE_KINDS`。** 漏加的症状是该怪种第一次出现时卡 460 ms，而不是报错。

**规则 4.2：预热实例只造表现层（`EnemyAvatar3D`），不造 `Enemy3D`。** 后者会牵连 AI 登记、房间编成、血条与击杀记账，在加载期造实例的风险远大于收益。

### 4.3 预热 B：逐房渲染（与关卡房间表相关）

上表两套集合与关卡无关；B 相反，**按本局实际房间表逐间取景画一帧**，实现是唯一一份 `Dungeon3D.warm_room_materials()`，加载页与验收探针共用。

| 参数 | 值 | 理由 |
|---|---:|---|
| 视口尺寸 | 480×270 | 管线编译与应用分辨率无关；720p 与 480×270 的收益差在噪声内，成本差一倍多 |
| 每房帧数 | 1 | 第 1 帧就把管线编译掉，第 2 帧只多花时间 |
| 取景 | 房心 +2.6 m，俯 12°、偏 35° | 一帧里同时看到两面墙与角落陈设 |
| 时间预算 | 4000 ms | 实测 24~27 间 1.1~1.7 s，留一倍余量 |

**规则 4.3：B 只用独立 `SubViewport` + 临时 `Camera3D`，且 `own_world_3d = false`。**

这样画的就是关卡本身，同时**不动玩家**——不触发 `_on_room_entered`、不建 `RuntimeDetail`、不刷怪、不动 `_spawned_rooms`，玩法时序一个字节都没改。禁止为了"预热"去瞬移玩家或改流送状态。

**规则 4.4：禁止在 B 里建 `RuntimeDetail`。**

实测多建一次再卸掉（换来陈设也上一次屏）只把跨门 max 再压 40 ms，但要多付 0.28 s 加载时间，且会把"卸载重建"这条路径重新拉回主线程。不值。

**规则 4.5：B 的收益必须用"同一进程内预热前后各走一遍"的对照来量，不能拿两次独立启动比。**

管线编译是**进程级一次性**的开销，第二次启动会命中 Godot 的着色器缓存，读数天然更好看。对照脚本见 `tools/_exp03_hitch_trace.gd --warm`。

## 5. 预算口径

| 参数 | 值 | 含义 |
|---|---:|---|
| `WARMUP_MAX_FRAMES` | 48 | 硬上限，防止队列异常把玩家锁在加载页 |
| `WARMUP_EXTRA_BUDGET_MS` | 2500 | 允许额外等待的毫秒，**从预热第一帧结束后起算** |
| `ROOM_WARM_VIEW_SIZE` / `ROOM_WARM_FRAMES_PER_ROOM` | 480×270 / 1 | 预热 B 的视口与每房帧数 |
| `ROOM_WARM_BUDGET_MS` | 4000 | 预热 B 的时间预算，超了截断 |

**规则 5.1：预热第一帧不参与预算判定。**

`_restore_world_render()` 之后是关卡画面的第一次真实渲染（SDFGI/管线初始化），这笔代价与预热量无关，但在这一帧结算。把它算进预算的结果是"预热永远超时、永远只做第一项"——这是 2026-11-07 之前实际发生的故障。

**规则 5.2：预算起点与读取页出现时刻无关。** 预热在装配完成之后才启动，而装配可能耗时十几秒；用读取页起始时间加固定时长做期限，等于期限恒已过期。

## 6. 完成判据与对外接口

预热完成后，读取页向目标场景写入四个 meta：

| 键 | 类型 | 语义 |
|---|---|---|
| `loading_warmup_report` | `Dictionary` | `completed` / `skipped` / `vfx_total` / `vfx_pending` / `kinds_done` / `kinds_total` / `frames` / `first_frame_ms` / `elapsed_ms` / `warmup_ms` / `truncated` |
| `loading_warmup_completed` | `bool` | 上一项 `completed` 的便捷投影 |
| `loading_room_warm_report` | `Dictionary` | `skipped` / `rooms` / `total` / `elapsed_ms` / `truncated`（预热 B） |
| （无投影键） | — | 预热 B 是否完成看 `rooms == total and truncated == ""`，不另设布尔键——多一个键就多一处口径 |

判据只有一条：

```
预热A.completed = (kinds_done == kinds_total) and (vfx_pending == 0)
预热B.completed = (rooms == total) and (truncated == "")
```

`VfxPool3D.has_pending_prewarm()` 是唯一查询口，`pending_prewarm_count()` 只用于报告与断言——只有布尔值时"剩 0 件"和"剩 9 件"无法区分。

**规则 6.1：预热 B 的截断不得写进 `loading_warmup_completed`。**

那是预热 A 的判据，是 11-07 那条既有验收的牙齿。两段预热各有各的报告，不能串味。

## 7. 失败与降级

| 情况 | 行为 |
|---|---|
| headless（无渲染管线） | A、B 都整段跳过；A 报 `skipped=true, completed=true`，B 报 `skipped=true, truncated="headless"`（不适用，不是通过） |
| 超预算 | A 报 `truncated="budget"` / B 报 `truncated="budget"`，warning，继续开圈 |
| 超帧数上限 | A 报 `truncated="frames"`，warning，继续开圈 |
| 目标场景在预热期间被替换/销毁 | 中止交接，`_finalizing=false`，不恢复操作 |
| 特效池脚本缺失 | `vfx_enabled=false`，只预热怪基类，报告照写 |
| 目标场景不提供 `warm_room_materials()`（如基地场景） | B 报 `skipped=true, truncated="unsupported"`，不影响交接 |
| 手动对照（`-- --no-room-warm`） | B 报 `skipped=true, truncated="disabled"`，只用于 A/B 对照测帧，不进正式包 |

## 8. 验收要求

1. **链路**：入口 → 读取页 → 目标场景 → 玩家落地。headless 可验。
2. **预热完成度**：真渲染下断言 `loading_warmup_completed == true`，以及
   `loading_room_warm_report.rooms == total and truncated == ""`。
   ⚠️ headless 下两段预热都按"不适用"跳过，这条断言没有牙齿；只有真渲染运行才是门禁。
3. **交接后帧时间**：真渲染 + `--disable-vsync`，统计恢复操作后 2.5 秒的 p50/p95/超 33 ms 帧数。
4. **跨门帧时间**：真渲染 + `--disable-vsync`，同一进程内预热前后各走一遍全图，比 p95 / max。
   口径与探针见 [落点归因](../development/2026-11-08_expedition03_hitch_trace.md)。

**规则 8.1：落地判定必须在加载页交接完成之后。**

交接前读取页把目标树 `process_mode` 设成 `DISABLED`，而 Godot 的 `CollisionObject3D.disable_mode` 默认是 `REMOVE` ⇒ 碰撞体暂时不在物理空间里，这时候打射线必然"脚下没地面"。2026-11-09 加预热 B 时就是因为探针没等交接，报了一次假红。判据用 `tower.can_process() and player.can_process()`。

正式入口：`probe_expedition03_entry_chain`（断言第 2、3 项）、`tools/_exp03_hitch_trace.gd`（第 4 项）。其余关卡共用同一读取页与同一份 `warm_room_materials()`，不需要逐关复制探针。

## 9. 未覆盖与待统一

| 项 | 现状 | 影响 |
|---|---|---|
| Boss / 收租人精英的正式表现 | 走 `BossContentCatalog.presentation_scene`，首次出场才加载 | Boss 房入场可能有一次读盘 |
| 首波敌人整批同帧生成 | `Dungeon3D._spawn_enemy_batch()` 无分帧预算 | 一房 10 只 ≈ 一帧 166 ms |
| 首次枪声 / 命中声 / Boss 音乐 | 音频侧同步 `load()` | 首次开火可能有一次加载 |
| **跨门剩下的 200~250 ms** | 预热 B 只消掉管线编译那部分（p95 368→257 ms）；其余是 `RuntimeDetail` 重建（均值 30 ms / 最贵 97）、释放旧房（`queue_free` 落帧末）、物理空间同步 | 仍是可感知的一次顿挫；要消掉必须把这串拆帧（改造面在 `set_stream_state` 与 `_update_room_streaming`） |
| **首次进某房时的 0.4~0.9 s** | 少数房间（奖励房、商店）在进房时还会加载 250+ 个资源 | 预热 B 不解决这类；`loading_room_warm_report` 不会体现，需要单独的资源清单预热 |
| 基地四个地牢传送门 | `BaseWorld3D` 直切 `IronFrontier3D` / `RustFoundry3D` / `SporeDepths3D` / `AbyssArchive3D` | 这四个入口无读取页、无预热、无全黑交接 |

**四大地牢待统一的改造范围**：这四张场景的根是 `scenes/Dungeon3D.tscn`（未挂 `TowerDescent3D.gd`），因此没有加载契约——没有 `loading_scene_ready` 上报、没有 `prepare_loading_render()`、没有装配期可见性保护。要接入读取页，必须先给 `Dungeon3D` 补一套与 `TowerDescent3D` 等价的加载契约（可见性、玩家锁定、进度上报、完成信号），再把 `BaseWorld3D` 的两处 `change_scene_to_file` 改成经读取页。`Dungeon3D` 是八个关卡场景的基类，改动面覆盖塔楼与远征，须独立一轮施工与回归，不在预热修复这一轮内进行。
