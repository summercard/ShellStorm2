# 关卡区块设计

状态：WORLD-BLOCKS r4，适用工程版本 `0.1.0`。本文件是塔楼场景区块、命名、制作阶段和资产追溯的事实所有者；房间生成、门与区段卸载规则仍由[关卡生成与爬楼](05_技术施工_关卡生成与爬楼.md)定义。

## 1. 目标

塔楼主场景固定按四个区块管理。区块只负责场景树归属、楼层范围和资产追溯，不改变房间生成、碰撞、门、楼梯通行、存档或流送规则。

```text
TowerDescent3D
└─ Blocks
   ├─ Rooftop
   ├─ Base
   ├─ Battle
   └─ Stairs
```

编辑器和运行时使用同一组区块节点。`GeneratedRooms` 与 `GeneratedCorridors` 保留为父类兼容入口，不再作为塔楼主要浏览层级。

## 2. 简化命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 四个区块节点 | 固定英文单词，不附加楼层、版本或用途长句 | `Rooftop`、`Base`、`Battle`、`Stairs` |
| 局内关卡编号 | `局内关卡` + 两位数字；编号是稳定身份 | `局内关卡01`、`局内关卡02` |
| 局内关卡设定名 | 独立保存，可随设计修改，不参与路径和逻辑判断 | `顶部数据库` |
| 局内关卡显示名 | `{level_code}-{setting_name}` | `局内关卡01-顶部数据库` |
| 楼层节点 | `Floor_楼层号` | `Floor_100`、`Floor_99`、`Floor_98` |
| 房间节点 | 直接使用稳定 `room_id` | `start`、`facility`、`floor_01_entry` |
| 水平走廊 | `Corridor_序号` | `Corridor_02` |
| 首两段楼梯 | 固定短名 | `Stair_A`、`Stair_B` |
| 后续楼梯 | `Stair_上层_下层` | `Stair_98_97` |
| 独立电梯位 | `Elevator_楼层F` | `Elevator_98F` |
| Godot 区块资产文件 | `zone_区块_v###.tscn` | `zone_rooftop_v021.tscn` |
| 正式 Blender 源文件 | 保留现有生产名称和中文集合 | 仅适用于已进入 Blender 美术阶段的区块 |
| 白盒文件 | `whitebox_范围_v###` | `whitebox_battle_98_95_v011.json` |

名称只用于浏览。`level_number=1`与`level_code=局内关卡01`负责稳定编号，`setting_name=顶部数据库`负责可变设定名，`display_name`只负责组合显示。稳定身份始终使用 AssetID、`room_id`、`floor_number`、`block_id`、`level_number` 和楼梯端点元数据，禁止从显示名或设定名反推玩法逻辑。

## 3. 四区块分布

| block_id | 节点 | 中文显示 | 当前楼层 | 内容边界 |
|---|---|---|---|---|
| `rooftop` | `Blocks/Rooftop` | 天台区 | 100F | 天台楼板、围护、聚落美术、出生房 |
| `base` | `Blocks/Base` | 基地区 | 99F | 基地房、基地美术布局、设施和基地电梯入口 |
| `battle` | `Blocks/Battle` | 局内关卡01-顶部数据库 | 98–95F | 编号`局内关卡01`；设定名`顶部数据库`；首个 Boss 区段的楼层、房间、水平走廊和战斗内容 |
| `stairs` | `Blocks/Stairs` | 楼梯区 | 100→99、99→98 | 初始两段楼梯及后续运行时生成的垂直连接器 |

初始场景必须能直接看到四个区块。`Stairs` 初始包含两种资产身份：

- `Stair_A`：100F→99F，AssetID `ENV-TOWER-STAIRWELL-ROOFTOP-12M`。
- `Stair_B`：99F→98F，AssetID `ENV-TOWER-STAIRWELL-GENERIC-12M`。

基地内部的东侧过渡楼梯和西北 L 型楼梯属于 `Base` 的结构资产，不计入上述两段层间楼梯。

### 3.1 3Dgame-design 区块同步契约

`tools/3Dgame-design` 以本节“区块分布”表为区块目录的唯一来源。工具按 `block_id` 建立上层容器，区块下再新建、列出和读取场景；本表按现有五列格式新增有效区块行后，工具刷新时自动出现，不另设平行配置文件。

工具场景保存到 `tools/3Dgame-design/save/blocks/<block_id>/<scene_name>/`，其中 `<scene_name>.blend` 是用户交付与后续 Blender 打开的最终场景文件，`scene.json` 是网页恢复拖放、分组和变换编辑所需的伴随数据。两者必须在同一次保存事务中生成成功；Blender 生成失败时不得用新 JSON 覆盖上次可用版本。场景 JSON 的 `project` 字段记录 `blockId / blockName / blockNodePath / floorRange` 对照快照，但区块当前名称仍以本表为准。已有平铺存档只保留兼容读取，不自动迁移、不混入正式区块列表。

网页编辑范围固定为组件实例的创建、删除、拖放、分组、位置、旋转、缩放和工具已提供的参数化尺寸，不提供顶点、UV、材质节点、修改器或骨骼编辑。保存由本机 Blender 后台把同一场景状态写成 Z-up、米制 `.blend`；读取仍使用同目录伴随 JSON，以保证网页功能完整可逆。本链路不触发 Godot 导入、GLB 导出或运行时引用更新。工具生成的 Blend 是白模/布局工作源，不因扩展名成为已验收的正式美术资产。

顶部“打开 Blender”是所有区块共用的文件入口：用户先选择区块，再选择任意 `.blend`，工具按文件名建立该区块下的场景工作副本。导入器优先把名称以“资产包”结尾的 Collection 中顶层网格根识别为可编辑组件；没有资产包集合时使用场景顶层、且自身或后代包含网格的对象。真实网格通过仅供网页显示的 GLB 缓存加载，网页修改根对象的移动、旋转、缩放或删除并写回工作副本，保留未编辑的子网格、集合与材质。再次选择工作副本可读取 Blender 中发生的根变换修改。

楼梯区以 `env_tower_stairs_12m_source_v001.blend` 作为首个双向验收样本，两个资产包映射为 `Stair_A / Stair_B`。实验工作副本保持 `Stair_B` 沿 X 偏移35m的并排布局；该偏移不写回正式源。

组件库分为“通用组件”和“区块专用组件”。通用组件在所有区块可见；区块专用组件只在选中对应 `block_id` 时显示，标题必须使用本文件“中文显示”的正式名称，不能在工具中维护另一份显示名。当前角色、建筑属于通用组件；家具、办公属于 `battle`（`局内关卡01-顶部数据库`）专用组件；道具属于 `rooftop`（`天台区`）专用组件。组件归属只控制编辑器目录与可选范围，不改变既有组件类型、场景实例或资产身份。

### 3.1.1 楼梯间原位拼装与固定组件

楼梯间重建以v013 Blender实际世界坐标为基准：A根位置(-32.5,0,0)、Z旋转180°；B根位置(32.5,0,-9)、Z旋转0°。原有楼板完成面、门口缺口、转向平台及围护轮廓均需保留。历史v012并排预览JSON不能覆盖实际源坐标；v014原点装配已撤销为当前入口。

墙壁和地板通过固定组件拼接，实例及包含它们的分组禁止缩放，尺寸面板只读。地板主体使用5×5×0.3m标准件，墙体母件仍为5×0.3×12.9m。遇原源非整模数的平台边缘、门洞边缘或围护截面，使用记录精确尺寸的固定收边件；收边件按原边界裁切，不通过放大标准件补齐。本次原位恢复保留原围护的11.9m可见高度，作为12.9m母件的裁切规格，不改通用母件尺寸。

直梯复用同一参数化母组件；另一跑旋转180°。原型剖面保留坡板、踏步及护栏，水平长度与坡度决定升高，截面厚度不随高度拉伸。组件场景JSON为编辑状态所有者，Blender保存包含同一JSON及根对象标识；重新打开时恢复参数和各实例当前变换。写盘失败保留上次可用文件。独立验收需逐物件核对原坐标与包络、拼接体积、Scale=1，以及Blend读写后参数和坐标。

### 3.1.2 Blender 原生关卡搭建插件

`ASSET-LEVEL-BUILDER r2` 以 `tools/blender_addons/shellstorm_level_builder/` 为主要关卡组件搭建入口。事实所有者是当前 `.blend`：对象变换、网格编辑、组件锚点、Collection 归属和资产包元数据均直接保存在 Blender 数据中；网页 `tools/3Dgame-design` 保留旧场景读取和迁移兼容，不再要求承担新场景的唯一人工编辑入口。

- 插件复用 Blender 原生选择、移动、旋转、缩放、吸附、编辑模式和撤销，不维护平行交互实现；同时提供显式吸附按钮（吸附到网格、贴齐到活动对象、对齐轴、移到游标）和一键开启原生吸附+`5m` 视口网格，避免吸附开关状态不明。
- 组件库提供参数化白盒墙、地板、拐角柱、门洞、直梯、栏杆和固定设施占位；墙体新建默认尺寸为 `5×0.3×11.9m`。每个组件生成单个网格对象，锚点默认在底面中心（与游戏内实墙 GLB 一致）；切换“对齐游戏资产”时地砖使用厚度居中原点，与 `env_tower_floor_tile_5m_top3d_v002.glb` 一致。“重设锚点”只移动网格数据并保持世界坐标不变。
- 项目资产库扫描 `asset_manifest.json`，仅列出具有有效源 `.blend` 和 Collection 的记录，字段兼容本项目既有清单（`source_blend`/`source`、`blender_collection`/`collection`/`output_collection`），并给出可用与跳过数量的诊断，避免清单有问题时只看到空列表；添加时使用 Append 生成本地可编辑数据，不建立易失的外部链接。
- 场景 Collection 固定区分 `01_白盒布局_可编辑`、`01_制作组件_按设施拆分`、`02_游戏输出_独立资产包_v###` 和 `90_展示与验收_灯光相机`。游戏输出下按建筑结构、地面系统、区域固定设施和环境支持分类；末级 `资产包` 才是独立维护与导出边界。
- “归入资产包”把所选组件根及其完整子层级移入唯一末级包。同步前验证空包和多包归属；成功后按 `component_packages_v###/<category>/<asset_slug>/` 写 `asset_manifest.json`，并生成总 `catalog.json` 与 `tree.txt`。
- 预览与统计提供白盒配色、线框描边、布局包围盒统计、顶视图标注（组件中文名/尺寸、`5m` 模块网格底板、总尺寸标题）和正交顶视图渲染，产物写入 `renders/`，用于补足白盒阶段顶视图证据；渲染使用工作台引擎并在完成后恢复原渲染设置。配色与描边是即时开关，“显示标注”只管显隐、生成与删除各有独立按钮。
- 插件不自动导出 GLB、不修改 Godot 引用、不宣称运行时已接入。同步清单要求先保存 `.blend`，且在没有资产包或验证失败时拒绝写盘，不得覆盖已有清单；现阶段清单同步以显式按钮触发。

安装命令：`powershell -ExecutionPolicy Bypass -File tools/blender_addons/install_shellstorm_level_builder.ps1`。独立验收使用 Blender 4.5 后台运行 `tools/blender_addons/test_shellstorm_level_builder.py`，覆盖锚点、吸附贴合、清单写盘守卫、既有清单扫描追加和顶视图渲染。

### 3.2 场景美术设计挂钩

每个 3D 场景生产批次都必须填写一个主 `block_id`，并将它持续写入白盒 JSON、风格稿、Blender资产包、GLB、PackedScene、导出清单和验收记录。跨区块资产以主要归属区块为主，并列出关联区块；不能因为共享资源而省略归属。场景美术流程见[3D场景美术生产流程](10.1_3D场景美术生产流程.md)，资产登记唯一入口为[美术资产台账](../../assets/registry/ShellStorm2_美术资产台账_v001.xlsx)的 `3D-场景通用` 表。

| `block_id` | 概念稿必须定位的范围 | 场景设计依据 | 台账追溯 |
|---|---|---|---|
| `rooftop` | 100F天台、出生房、天台聚落、围护或其独立设施 | 本文件§3、[关卡生成与爬楼](05_技术施工_关卡生成与爬楼.md) | `ENV-ROOFTOP-SHELTER-90X80`及其独立组件条目 |
| `base` | 99F基地房、基地楼中楼、设施区、基地内部结构楼梯或电梯入口 | 本文件§3、[基地设施](07_技术施工_基地设施.md) | `ENV-BASE99-ART-LAYOUT-3D`及其独立设施/结构条目 |
| `battle` | `局内关卡01-顶部数据库`的98–95F战斗层、内容房、走廊、隔离间、Boss房或程序化组件；主路内容房02已有美术源，其余保持白盒状态 | 本文件§3、[关卡生成与爬楼](05_技术施工_关卡生成与爬楼.md) | `ENV-TOWER-DESCENT-KIT-3D`及其模块条目；仅 `ENV-BATTLE-L01-ROOM-MAIN-02` 可标记 Blender 美术源完成，不代表运行时接入 |
| `stairs` | 100→99、99→98及后续楼层之间的楼梯间、接驳走廊和垂直连接器；Blender v021正式美术已以GLB/PackedScene v002接入运行时 | 本文件§3、[关卡生成与爬楼](05_技术施工_关卡生成与爬楼.md) | `ENV-TOWER-STAIRWELL-ROOFTOP-12M`、`ENV-TOWER-STAIRWELL-GENERIC-12M`；源、导出、包装与运行引用分别登记 |

整个流程都使用同一组字段：`block_id / floor_range / design_scope / scene_design_docs / asset_ledger`。白盒 JSON 使用同名字段；Blender 和 Godot 导入记录继续沿用对应 AssetID，确保从场景范围可追溯到正式资产。

## 4. 资产与源文件对照

Godot 区块入口统一放在 `assets/art/environments/tower_zones/`：

├─ rooftop/runtime/
├─ base/runtime/
├─ battle/runtime/

## 5. 区块元数据契约

每个区块根至少保存 `block_id`、`display_name`、`floor_range`、`asset_ids`、`runtime_owner`、`source_blends`。楼层节点额外保存 `floor_index / floor_number / block_id`。垂直楼梯额外保存 `upper_floor_index / lower_floor_index / from_room_id / to_room_id / stair_asset_id`。修改节点显示名不得改变这些字段。

## 6. 修改流程

1. 先在本文件更新区块范围和名称。
2. 修改 `TowerDescent3D.tscn` 的四区块根及 Godot 包装文件名。
3. 修改运行时代码的归属和短名，保持玩法 ID 不变。
