# 关卡区块设计

状态：WORLD-BLOCKS r3，适用工程版本 `0.1.0`。本文件是塔楼场景区块、命名、制作阶段和资产追溯的事实所有者；房间生成、门与区段卸载规则仍由[关卡生成与爬楼](05_技术施工_关卡生成与爬楼.md)定义。

## 1. 目标

塔楼主场景固定按四个区块管理。区块只负责场景树归属、楼层范围和资产追溯，不改变房间生成、碰撞、门、楼梯通行、存档或流送规则。

```text
TowerDescent3D
└─ Blocks
   ├─ Rooftop
   ├─ Base
   ├─ Battle
   └─ Stairs
```

编辑器和运行时使用同一组区块节点。`GeneratedRooms` 与 `GeneratedCorridors` 保留为父类兼容入口，不再作为塔楼主要浏览层级。

## 2. 简化命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 四个区块节点 | 固定英文单词，不附加楼层、版本或用途长句 | `Rooftop`、`Base`、`Battle`、`Stairs` |
| 楼层节点 | `Floor_楼层号` | `Floor_100`、`Floor_99`、`Floor_98` |
| 房间节点 | 直接使用稳定 `room_id` | `start`、`facility`、`floor_01_entry` |
| 水平走廊 | `Corridor_序号` | `Corridor_02` |
| 首两段楼梯 | 固定短名 | `Stair_A`、`Stair_B` |
| 后续楼梯 | `Stair_上层_下层` | `Stair_98_97` |
| 独立电梯位 | `Elevator_楼层F` | `Elevator_98F` |
| Godot 区块资产文件 | `zone_区块_v###.tscn` | `zone_rooftop_v021.tscn` |
| 正式 Blender 源文件 | 保留现有生产名称和中文集合 | 仅适用于已进入 Blender 美术阶段的区块 |
| 白盒文件 | `whitebox_范围_v###` | `whitebox_battle_98_95_v011.json` |

名称只用于浏览。稳定身份始终使用 AssetID、`room_id`、`floor_number`、`block_id` 和楼梯端点元数据，禁止从显示名反推玩法逻辑。

## 3. 四区块分布

| block_id | 节点 | 中文显示 | 当前楼层 | 内容边界 |
|---|---|---|---|---|
| `rooftop` | `Blocks/Rooftop` | 天台区 | 100F | 天台楼板、围护、聚落美术、出生房 |
| `base` | `Blocks/Base` | 基地区 | 99F | 基地房、基地美术布局、设施和基地电梯入口 |
| `battle` | `Blocks/Battle` | 首关战斗区 | 98–95F | 首个 Boss 区段的楼层、房间、水平走廊和战斗内容；后续程序生成战斗层沿用该运行区块 |
| `stairs` | `Blocks/Stairs` | 楼梯区 | 100→99、99→98 | 初始两段楼梯及后续运行时生成的垂直连接器 |

初始场景必须能直接看到四个区块。`Stairs` 初始包含两种资产身份：

- `Stair_A`：100F→99F，AssetID `ENV-TOWER-STAIRWELL-ROOFTOP-12M`。
- `Stair_B`：99F→98F，AssetID `ENV-TOWER-STAIRWELL-GENERIC-12M`。

基地内部的东侧过渡楼梯和西北 L 型楼梯属于 `Base` 的结构资产，不计入上述两段层间楼梯。

### 3.1 场景美术设计挂钩

每个 3D 场景生产批次都必须填写一个主 `block_id`，并将它持续写入白盒 JSON、风格稿、Blender资产包、GLB、PackedScene、导出清单和验收记录。跨区块资产以主要归属区块为主，并列出关联区块；不能因为共享资源而省略归属。场景美术流程见[3D场景美术生产流程](10.1_3D场景美术生产流程.md)，资产登记唯一入口为[美术资产台账](../../assets/registry/ShellStorm2_美术资产台账_v001.xlsx)的 `3D-场景通用` 表。

| `block_id` | 概念稿必须定位的范围 | 场景设计依据 | 台账追溯 |
|---|---|---|---|
| `rooftop` | 100F天台、出生房、天台聚落、围护或其独立设施 | 本文件§3、[关卡生成与爬楼](05_技术施工_关卡生成与爬楼.md) | `ENV-ROOFTOP-SHELTER-90X80`及其独立组件条目 |
| `base` | 99F基地房、基地楼中楼、设施区、基地内部结构楼梯或电梯入口 | 本文件§3、[基地设施](07_技术施工_基地设施.md) | `ENV-BASE99-ART-LAYOUT-3D`及其独立设施/结构条目 |
| `battle` | 98–95F战斗层、内容房、走廊、隔离间、Boss房或程序化组件；当前为白盒阶段 | 本文件§3、[关卡生成与爬楼](05_技术施工_关卡生成与爬楼.md) | `ENV-TOWER-DESCENT-KIT-3D`及其模块条目，状态不得写成正式美术源 |
| `stairs` | 100→99、99→98及后续楼层之间的楼梯间、接驳走廊和垂直连接器；正式 Blender 源已完成，运行时未重导入 | 本文件§3、[关卡生成与爬楼](05_技术施工_关卡生成与爬楼.md) | `ENV-TOWER-STAIRWELL-ROOFTOP-12M`、`ENV-TOWER-STAIRWELL-GENERIC-12M`；源文件与运行接入状态分别登记 |

整个流程都使用同一组字段：`block_id / floor_range / design_scope / scene_design_docs / asset_ledger`。白盒 JSON 使用同名字段；Blender 和 Godot 导入记录继续沿用对应 AssetID，确保从场景范围可追溯到正式资产。

## 4. 资产与源文件对照

Godot 区块入口统一放在 `assets/art/environments/tower_zones/`：

```text
tower_zones/
├─ rooftop/runtime/
├─ base/runtime/
├─ battle/runtime/
└─ stairs/runtime/
```

各区块目录只承载 Godot 入口和管理说明。Rooftop、Base 的正式 Blender 源暂时保留原生产目录；Battle 白盒和 Stairs 的历史/反推白盒数据统一进入 `source/art/whitebox/tower_zones/<version>/`。Stairs 正式源放在环境资产 `source/stairs_12m/`。已导入 GLB 和组件包继续保留运行目录；未来重新导入时按区块逐批迁移，禁止为了目录整齐一次性搬动全部 GLB。

| 区块 | AssetID | Godot 入口 | 当前制作来源 |
|---|---|---|---|
| Rooftop | `ENV-ROOFTOP-SHELTER-90X80` | `assets/art/environments/tower_zones/rooftop/runtime/zone_rooftop_v021.tscn` | `assets/art/environments/rooftop_shelter_3d/source/env_rooftop_shelter_90x80m_top3d_v021.blend` |
| Base | `ENV-BASE99-ART-LAYOUT-3D` | `assets/art/environments/tower_zones/base/runtime/zone_base_v002.tscn` | `source/art/blender/base_facility_layout/source/base_facility_runtime_layout_hq_v026.blend` |
| Battle | `ENV-TOWER-DESCENT-KIT-3D` | `scenes/TowerDescent3D.tscn` + 程序生成 | 白盒：`source/art/whitebox/tower_zones/v011/data/whitebox_battle_98_95_v011.json` → `blender/whitebox_tower_battle_stairs_v011.blend` |
| Stairs | `ENV-TOWER-STAIRWELL-ROOFTOP-12M`、`ENV-TOWER-STAIRWELL-GENERIC-12M` | `TowerDescent3D` 运行时包装，现有 GLB 不改名 | 反推合同：`source/art/whitebox/tower_zones/v012/data/whitebox_stairs_v012.json`；正式源：`assets/art/environments/tower_descent_3d/source/stairs_12m/env_tower_stairs_12m_source_v001.blend` |

Battle 尚未进入正式 Blender 美术制作，现有 v011 文件只作为白盒 Blender 输出管理。Stairs 已从当前两份 Godot GLB 反推为只含楼梯间的正式源文件；其 `.glb` 和 `.glb.import` 路径保持不变，本轮没有重新导入，不能把“源完成”登记为“运行时已更新”。Rooftop 与 Base 的正式 Blender 源暂时保留原目录。

## 5. 区块元数据契约

每个区块根至少保存 `block_id`、`display_name`、`floor_range`、`asset_ids`、`runtime_owner`、`source_blends`。楼层节点额外保存 `floor_index / floor_number / block_id`。垂直楼梯额外保存 `upper_floor_index / lower_floor_index / from_room_id / to_room_id / stair_asset_id`。修改节点显示名不得改变这些字段。

## 6. 修改流程

1. 先在本文件更新区块范围和名称。
2. 修改 `TowerDescent3D.tscn` 的四区块根及 Godot 包装文件名。
3. 修改运行时代码的归属和短名，保持玩法 ID 不变。
4. 在 Blender 正式源文件补充 `godot_block`、`godot_runtime` 和命名契约元数据，不改中文集合和几何。
5. 同步资产台账、全局导入账本、模块索引和开发记录。
6. 运行路径残留检查、场景解析和区块结构专项；模型重新导入另行执行。

## 7. 验收

- 主场景存在且仅存在 `Blocks/Rooftop`、`Base`、`Battle`、`Stairs` 四个区块根。
- 100F/99F/战斗楼层分别挂到正确区块；房间节点名等于稳定 `room_id`。
- 初始两段楼梯分别命名为 `Stair_A`、`Stair_B`，AssetID 和端点元数据正确。
- `zone_rooftop_v021.tscn` 与 `zone_base_v002.tscn` 可加载，旧活动路径不再被正式代码、场景、测试或生产工具引用。
- 资产台账能从每个区块的 Godot 入口追溯到原始 Blender 文件。
- Blender 中文集合、几何、材质和导出状态不变；本轮不执行 GLB 重新导入。
