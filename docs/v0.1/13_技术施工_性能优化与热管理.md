# 技术施工｜性能优化、长时运行与热管理 v0.1

关联文档：[技术架构总则](02_技术架构总则.md)｜[关卡生成与爬楼](05_技术施工_关卡生成与爬楼.md)｜[测试与发布](11_测试与发布.md)｜[完成度清单](12_全游戏完成度清单.md)

## 1. 文档目标与边界

本文负责正式 3D 主流程的 CPU、GPU、内存、节点、物理查询、渲染频率、长时稳定性和开发工具进程生命周期。性能优化不能改变战斗规则、命运结算、房间拓扑或存档语义；优化前后必须由同一玩法回归证明结果一致。

“短场景帧耗时达标”不等于“机器不会发热”。验收必须同时覆盖：

1. 单帧 CPU/GPU 预算。
2. 30 分钟以上持续运行。
3. 暂停、静止和后台状态的降频。
4. 场景切换后的节点、对象与进程回收。
5. 测试/诊断进程是否按时退出。
6. 系统级 CPU、内存压力和热状态。

## 2. 2026-08-05 实机现场检查

检查设备为 Apple M1、8 核 CPU、8GB 内存的 MacBook Pro。检查时正式调试游戏已经停止，Godot 编辑器进程约为 `0.7% CPU / 38–47MB RSS`，不是当时的主要热源。

发现 14 个已脱离父进程的 Godot 无界面诊断实例：

```text
Godot --headless --path . -s tools/diag_wall_v2.gd
Godot --headless --path . -s tools/diag_test.gd
```

现场事实：

| 指标 | 结果 |
|---|---:|
| 残留诊断进程 | 14 个 |
| 父进程 | 全部为 PID 1，原启动器已经退出 |
| 已持续时间 | 约 4 天 21 小时 |
| 五次采样合计 CPU | 约 71% |
| 两个最高实例 | 各约 25%–28% CPU；早期采样曾达到 38%–40% |
| 合计 RSS | 约 131MB |
| 内存压力 | `kern.memorystatus_vm_pressure_level = 2`，压缩页较高 |
| macOS 热警告 | `pmset -g therm` 未记录系统热/性能警告 |

结论：当前机器明显发热的首要原因是诊断进程泄漏，而不是已经停止的游戏窗口。macOS 尚未触发系统热警告不代表没有持续功耗和外壳升温。

<span style="color:#2E7D32">**[P0｜已清理]** 用户确认后已按上述 14 个精确 PID 发送 `TERM`，没有使用 `killall`，没有关闭编辑器或改动项目文件。清理后残留诊断进程为 0；核心套件结束后再次检查，仍只有原 Godot 编辑器，约 `0.7% CPU / 31MB RSS`，没有测试子进程残留。</span>

## 3. 已确认的热源与风险

### 3.1 P0｜诊断工具没有退出契约

残留脚本文件当前已经不存在，但进程仍持有已加载脚本并持续跑 SceneTree。高占用实例的采样栈落在：

```text
Main::iteration
→ SceneTree::physics_process / process
→ GDScriptFunction::call
→ Array::filter
```

以后所有诊断/验收入口必须同时具备：

- 脚本成功、失败、超时三条路径都调用 `get_tree().quit(exit_code)`。
- 使用统一 `VerificationQuitter` 或等价生命周期守卫。
- 外层启动器设置明确超时，并在超时时终止整个子进程组。
- 测试套件结束后执行 Godot 子进程残留扫描；发现残留即判失败。
- 禁止使用没有退出条件的临时 `diag_*.gd` 长期运行。

### 3.2 P0｜每个物理帧调用完整房间诊断快照

`TowerDescent3D._physics_process()` 每个物理帧调用 `_update_floor_visibility_state()`。该方法遍历全部 66 个房间，并通过 `room.get_room_snapshot()` 只读取 `stream_state`。

问题是 `DungeonRoom3D.get_room_snapshot()` 不是轻量 getter，它还会：

- 两次读取全场景节点组并执行 `Array.filter` 统计家具和灯。
- 递归扫描房间树，统计实墙、门墙、拐角和材质变体。
- 遍历灯、门和服务终端生成诊断字典。

这相当于用“完整验收报告”读取一个整数，并在 60Hz 下重复扫描。它与现场高占用采样栈完全吻合。

已施工：

- 已新增 O(1) `get_stream_state()` / `is_streamed()`，正式流送和敌人预热不再读取完整快照。
- `get_room_snapshot()` 只允许测试、调试面板和明确的低频采样使用。
- 楼梯过渡仍低成本轮询当前连接器，但只有“加载楼层集合改变”时才重写 Stage、66 房可见性和处理状态；普通站立不再执行全房施工。
- 快照新增 `floor_visibility_poll_count / apply_count / runtime_state_read`，自动验收轻量读路径。

### 3.3 P1｜视野与手电物理查询密度

`PlayerVision3D` 当前每 `0.04s` 刷新一次：

- 视野扇形 49 条射线。
- 近身范围 29 条射线。
- 手电开启时再增加约 49 条射线。
- 随后遍历敌人、掉落、钥匙、陷阱、服务终端和撤离信标，并对目标做遮挡查询。

手电开启时理论上限约为 127 条基础射线/次，即约 3175 条/秒，尚未计入目标遮挡。表现网格还可能在平滑阶段逐帧重建 `ImmediateMesh`。

已施工首批：

- 地面视野扇形物理采样为 15Hz，逐帧变换、边界平滑和目标显隐保持原有节奏。
- 近身圆盘当前不绘制，也不参与玩法判定，已移除每次 29 条无输出射线，仅保留兼容点阵数据。
- 目标显隐仍为 25Hz，手电开启时仍逐帧跟随，不改变敌人出现与瞄准反馈。
- 手电扇形与视野扇形共享命中缓存；目标遮挡按距离和类型分批预算。
- 只有距离缓存变化超过阈值时重建网格。

### 3.4 P1｜摄像机每帧遮挡查询

塔楼摄像机每个物理帧执行后墙探针和角色遮挡轮廓探针。后墙探针有多个横向偏移并允许多次命中跳过，轮廓探针再发送多条相机到角色射线。

已施工首批：

- 镜头位置、抬升和收拢平滑仍为 60Hz；物理探针在玩家水平移动时 60Hz、静止时 30Hz并复用上次命中。
- 墙边、门边和楼梯移动没有新增一帧延迟；`verify_tower_descent_flow` 和相机下墙回归继续覆盖碰撞结果。
- 房间切换时缓存当前房间可参与相机探测的碰撞体，避免对无关世界几何查询。

### 3.5 P1｜HUD、小地图和数组整理频率

当前 `Dungeon3D._process()` 每帧更新计时文本、楼层文本、玩家地图状态，并过滤当前房敌人引用。小地图自身按 20Hz 重绘；部分 HUD 仍每帧检查生命颜色、悬停卡位置和角色状态。

已施工首批：

| 内容 | 目标频率 |
|---|---:|
| 行动计时文本 | 1Hz |
| 楼层文本 | 进房/换层事件驱动 |
| 小地图玩家与敌人 | 15Hz（已施工） |
| 门附近提示 | 12.5Hz（已施工） |
| HP/弹药/状态文本 | 信号驱动 |
| 低血量呼吸动画 | 30Hz 上限 |
| 悬停卡位置 | 鼠标移动或布局变化时 |

行动计时文本现为 1Hz；楼层文本只在15Hz预算点且内容变化时写入。门提示只检查当前房，离房时只清理上一个房间，不再每帧/每周期遍历66房。

### 3.6 P1｜渲染、阴影与楼层流送

当前使用 `gl_compatibility`。塔楼同时保留最多五个物理层的楼层 Stage 表现，而且98–95F候选Node在初始化时隐藏预分配；这会让已离开的楼层继续占用节点、资源引用和部分运行维护成本。太阳开启动态阴影，玩家手电含一盏阴影 SpotLight，当前房可再有一盏阴影灯。全局雾、透明视野扇形和大面积楼板会继续增加 GPU 填充与阴影成本。

施工要求：

- 按新关卡循环改为到达门成功后才创建当前FloorBundle，不在启动时预分配98–95F全部Node。
- 房间级流送保留当前层与必要相邻空间；区段级卸载在隔离提交后彻底释放98–95F等旧区段，而不是继续隐藏Stage。
- 区段卸载必须释放Node、Mesh/材质引用、碰撞、导航、敌人、掉落、音频/VFX、小地图缓存、信号、计时器和对象池借用；只隐藏`visible`不算完成。
- 生成下一FloorBundle前先完成纯数据规划与验证；隔离间后门锁定后再提交旧物永久遗失并卸载旧区段，避免无效布局把玩家困在空世界。
- 阴影只允许太阳、手电主光、当前房主灯三者按质量档竞争预算；低档最多两盏实时阴影灯。
- 关闭灯具时从渲染光源列表移除，而不只把能量写为 0。
- 为雾、阴影距离、阴影分辨率和手电表现建立质量档。
- 增加 GPU 帧时间、Draw Call、可见对象、阴影 Pass 的真实渲染采样；现有 headless 节点测试不能替代 GPU 验收。

### 3.7 P1｜没有显式帧率与节能策略

`project.godot` 已明确 `application/run/max_fps=60` 与 `display/window/vsync/vsync_mode=1`，发布包不再依赖平台默认值或无上限渲染。失焦/暂停专用15FPS策略仍待后续实机验证后接入，避免改变暂停输入和编辑器联调行为。

目标策略：

- 默认 60 FPS，明确启用 VSync；不允许发布包无上限渲染。
- 可选 30/60 FPS 档，不以 120 FPS 作为 v0.1 默认目标。
- 暂停菜单、失焦和玩家长时间静止时降低非玩法刷新频率；失焦可降至 15 FPS。
- 物理仍保持确定的 60 tick，表现降频不得改变射击、敌人和计时结果。

### 3.8 P0｜Boss 区段“数据常驻、表现流送”重构方案（2026-08-12冻结）

#### 3.8.1 结论

98–95F 必须继续作为一个可自由往返的完整玩法循环，但不应让这个循环的全部 `Node / Mesh / Collision / Light / AI` 同时常驻。正式方案采用：

> **区段一次确定，运行状态常驻；房间表现按图距离预取、按滞回距离释放。**

玩家首次通过98F循环入口时，用同一行动种子一次生成并验证98–95F完整 `SegmentPlan`。该计划冻结全部房间、门、楼梯、内容槽、遭遇计划与确定性子种子，但不立即实例化全部场景节点。到达门仍保留原有进度门、Boss门和命运卡节奏；它从“现场重新随机下一层”改为“提交已经验证的计划切片”。因此优化不会提前向玩家公开地图、敌人或奖励，也不会改变开门顺序。

当前逐层 `FloorBundle` 可作为过渡实现继续运行，但目标架构应升级为 `SegmentPlan + FloorSliceCommit`：

```text
进入98F大循环
→ 由行动种子一次生成98–95F SegmentPlan（纯数据）
→ 验证完整拓扑、楼梯接口、Boss路线和95→94隔离接口
→ 只实例化98F入口及近场房间
→ 玩家开到达门时提交对应 FloorSlice，不再重新随机
→ 玩家移动时预取前方房间、释放远处房间表现
→ 95→94隔离提交后销毁整个 SegmentRuntimeState
```

#### 3.8.2 四层所有权

| 层 | 生命周期 | 保存内容 | 明确禁止 |
|---|---|---|---|
| `SegmentPlan` | 进入区段生成，离开区段销毁 | 房间ID、5m网格坐标、拓扑、门槽、楼梯、房型、内容槽、EncounterPlan ID、确定性子种子 | 保存任何 Node、RID 或临时实例ID |
| `SegmentRuntimeState` | 整个98–95循环常驻，可写行动存档 | 门状态、访问/清房、容器、灯开关、地面物、怪物状态、事件与Boss阶段 | 依赖场景节点才能解释状态 |
| `RoomPresentationInstance` | 近场临时存在 | Mesh、材质实例、灯具表现、碰撞、交互体、导航区域、音频与VFX挂点 | 作为玩法事实源或持有其他远房节点引用 |
| `NearFieldSimulation` | 当前房及必要邻域 | 活跃AI、投射物、实时阴影、精确物理与高频感知 | 扫描整个区段或离屏持续高频运行 |

`SegmentRuntimeState` 是往返一致性的核心，最低应包含：

```text
segment_id / seed / revision
committed_floor_slices / current_room_id
rooms[room_id]: visited / cleared / event_state / light_state
doors[door_id]: open / locked / consumed_key / fate_result
containers[content_id]: opened / resolved_loot
ground_items[item_instance_id]: item_data / transform / claimed
enemies[enemy_persistent_id]: archetype / hp / transform / alive / phase
                               status_effects / encounter_membership / ai_memory_summary
boss_state / extraction_state / unique_elevator_state
```

卸载房间时先把节点状态写回上述稳定ID；重新加载时从状态恢复，而不是再次调用掉落表、怪物生成器或命运随机流。已经死亡的怪物不得复活，已拾取物不得重生，已开启容器不得再次结算，灯和门保持玩家离开前状态。

#### 3.8.3 房间流送状态机

房间采用五态，不再以 `visible=false` 代替卸载：

```text
DATA_ONLY
  → PREFETCHING      异步取资源、准备共享资产，不进入玩法世界
  → SHELL_READY      门后安全壳/楼板/必要碰撞已就绪
  → ACTIVE           完整表现、交互、AI与精确碰撞
  → HIBERNATING      冻结输入，回写运行状态，等待池对象归还
  → DATA_ONLY        场景节点和RID全部释放
```

流送决策以**房间拓扑距离和门/楼梯可达性为主，世界距离为辅**。塔楼上下层在XZ上可能重叠，禁止只用欧氏距离，否则97F会错误加载98F/96F大量房间。

推荐首版阈值：

| 区域 | 保留内容 |
|---|---|
| 当前房 `graph_hop=0` | 完整 ACTIVE |
| 已开启的一跳邻房 | ACTIVE或完整预取；保证过门无停顿 |
| 前进方向二跳、或距目标门35m内 | PREFETCHING/SHELL_READY |
| 超过二跳且距玩家55m以上持续3秒 | HIBERNATING后释放 |
| 楼梯过渡 | 上下端房和楼梯同时保留；完成落地后再释放远端 |
| Boss战、撤离读条 | 相关竞技场和事务节点强制Pin，事务结束前禁止卸载 |

35m加载、55m卸载和3秒延迟构成滞回区，防止玩家在门口来回移动造成反复创建/销毁。阈值最终由实机走位测试调整，但“加载阈值小于卸载阈值”和“门后安全壳先就绪”是不可取消的结构规则。

房间以下情况不得卸载：玩家或玩家投射物仍在其中；门切换事务未结束；Boss/撤离/命运选择正在提交；对象池仍有借用对象；状态写回失败；导航或物理回调仍在执行。失败时房间保持休眠实例并记录原因，不能为了省内存丢失玩法状态。

#### 3.8.4 加载尖峰控制

- `ResourceLoader` 可在线程中准备 GLB、纹理和PackedScene；场景树挂接、物理RID和导航变更仍在主线程分帧提交。
- 每帧流送施工 CPU 预算建议 `≤2ms`，按“安全壳→碰撞→主要表现→装饰→交互/AI”顺序时间切片。
- 玩家靠近门前即预取一跳/二跳目标；目标房 `SHELL_READY` 前门保持关闭并显示正常开门反馈，不允许玩家进入空世界。
- 共享 Mesh、材质、纹理和GLB资源由资源缓存复用；释放的是场景实例和独立运行资源，不应反复读取磁盘或复制贴图。
- 反向返回与前进使用同一预取优先级；不得为了鼓励前进而让返回98F出现明显加载卡顿。
- 加载队列按 `当前门目标 > 当前房缺失 > 一跳返回路径 > 二跳预测 > 装饰细节` 排序，玩家转向时允许取消尚未挂树的低优先任务。

#### 3.8.5 怪物、掉落和机关的休眠规则

- 未进入ACTIVE房的怪物只保留 `EnemyRuntimeState`，不保留`Enemy3D`、血条、Avatar、光照传感器和物理体。
- 玩家离房时，未清怪物冻结在最后合法导航位置；离屏期间默认不继续战斗、追击或互相伤害，返回时恢复。这与当前“远房AI暂停”设计一致。
- 已产生但未拾取的掉落写成数据记录；只有房间激活时创建 `GroundLootPickup3D`。区段隔离提交后仍按现有设计永久销毁未拾取物。
- 门、容器、灯开关和事件终端以稳定内容ID恢复，信号只在实例活跃期连接，卸载时显式断开或随房间所有权一起释放。
- 当前房投射物和VFX必须先回收到池；不能把临时效果写入房间状态。持续地面危险若属于玩法，需要单独序列化剩余时间与参数。

#### 3.8.6 全局系统必须改为空间注册表

表现实例减少后，如果全局系统仍扫描历史字典，CPU仍会随探索增长。以下必须配套处理：

1. `MonsterAIManager` 按 `segment/floor/room` 注册活跃怪物；预激活只查询当前房、可达邻房和38m空间桶，不遍历历史房间数组。
2. 怪物列表先 `is_instance_valid` 再类型转换；释放事件立即注销。任何 `Trying to cast a freed object` 都属于P0失败。
3. 灯光使用 `LightSpatialRegistry` 按楼层/房间登记；怪物光照传感器只读取附近有效灯，不再每秒对每只怪物调用全场景节点组扫描。
4. 小地图直接读取 `SegmentPlan + SegmentRuntimeState`，不依赖远房场景节点；已发现但未实例化的房间仍能正确显示。
5. 楼层流送由“进房、门状态、进入楼梯、跨楼层”事件触发；物理帧只更新正在发生的楼梯过渡，不扫描全部历史连接器。
6. 相机、声音、光照、AI共享同一近场查询结果或空间索引，禁止各自遍历整个区段。

#### 3.8.7 不改变游戏设计的硬约束

- 98–95F完整拓扑、路线、Boss位置、唯一95→94电梯及返回能力不变。
- 同一种子和同一操作序列在是否发生流送的情况下，门、敌人、容器、掉落、命运卡和Boss阶段结果完全一致。
- 玩家在95→94隔离提交之前可以返回98F；返回只重建表现，不重新生成玩法内容。
- 区段内房间卸载不是永久遗失。只有现有隔离间确认与提交事务才可永久销毁98–95F未拾取物和区段状态。
- 不用雾、黑屏、空气墙或降低视距掩盖加载；门后和楼梯出口必须在进入玩家视野前准备完成。
- 存档保存 `SegmentPlan revision + SegmentRuntimeState`，不保存Node路径、RID或当前内存加载集合；读档后的加载集合由玩家位置重新推导。

## 4. 优化后的模块边界


- 视野、相机和小地图各自重复查询同一目标集合。
- 测试工具绕开统一启动器直接留下常驻进程。

## 8. 性能施工验收定义

一项性能优化只有同时满足以下条件才算完成：

- 优化前后使用相同种子、房间、敌人数量、武器和镜头路径。
- 玩法、画面可读性、碰撞、命运卡和小地图专项不回退。
- 提交 CPU/GPU 帧时间和系统进程采样，而不只提交平均 FPS。
- 通过 30 分钟持续运行、暂停/失焦、场景切换和退出清理。
- 测试结束没有孤儿 Godot 进程。
- 连续完成至少3次Boss区段隔离提交，旧区段节点、导航、敌人、掉落和地图缓存全部归零，RSS不存在逐区段单调增长。
- 文档记录测量设备、分辨率、渲染后端、质量档和异常后台进程。
