# 角色美术制作与动作导入流程

本规范仅管理角色表现。玩家的 `CharacterBody3D`、碰撞胶囊、移动、战斗、输入、存档、状态机与武器功能树继续由原系统拥有。新骨架使用表现适配器对接既有节点，不要求搬动功能节点。

## 一、两份工作文件

当前工作包：`assets/art/characters/player/chr_player_capsule01_3d/variants/bunny01/production/v009/`。

| 文件 | 编辑内容 | 禁止混入 |
|---|---|---|
| `source/model/chr_bunny01_model_v009.blend` | 几何、UV、材质、贴图、配件变体、静止骨架、绑定 | 玩法碰撞、控制器、状态转换、动作生产副本 |
| `source/animation/chr_bunny01_animation_v009.blend` | 同骨架的 Pose Actions、关键帧、动作预览 | 独立修改模型几何或静止骨架 |

模型母版中的骨架为 `SKEL-BUNNY01-001`。两份文件必须具有相同骨名、父子关系、静止矩阵和单位，导出器重新计算 SHA-256 比较，不信任手填版本号。动作文件关联模型库中的 Mesh/材质，保留独立 Pose 和 Action；骨架副本仅用于动作制作，静止姿势调整必须从模型母版同步并重新验收。

Blender 米制，创作总高 1.5m，运行时既有展示倍率 0.7，默认含耳可见高 1.05m。玩法碰撞不跟随制作尺寸变化。Blender `-Y` 对应 Godot `-Z`，地面为 Blender Z=0 / Godot Y=0；不得把未应用旋转或临时预览缩放当作接口。

## 二、集合归属

模型集合固定分为 `00_共享骨架`、`01_部件`、`90_预览环境_不导出`。在 `01_部件` 中使用二级集合：

```text
01_部件
├─ 身体
│  └─ 身体__bunny_white
├─ 头部
│  ├─ 头部__bunny_white
│  └─ 头部__chibi_anime
├─ 左手 / 右手 / 左脚 / 右脚
│  └─ 对应部件__bunny_white
├─ 帽子
│  ├─ 帽子__bunny_ears_l
│  └─ 帽子__bunny_ears_r
├─ 眼镜
│  └─ 眼镜__none
└─ 下身配件
   └─ 下身配件__none
```

配件名称必须是 Collection，不得用一个同名 Mesh 冒充文件夹。Collection 的 `slot_id`、`variant_id` 是导出元数据；集合里可放多个 Mesh，共同组成一个配件样式。新增样式复制该样式集合并给予唯一变体 ID。只增加颜色时复用几何与贴图，不重复制作根角色。

当前程序帽子/眼镜仍是已登记的程序占位；`none` 表示没有已制作网格，不代表已经制作完成。后续替换沿用衣柜合法 ID，不能通过美术导入增加玩法槽位。

## 三、建模、绑定与预览

1. 从已验收模型母版复制到新版本目录，保留上一版。设计配件时先选归属部件和样式集合。
2. 在共享骨架静止姿势下对齐。当前悬浮分件使用单骨刚性权重，所有顶点权重为 1；未来需要软变形的网格可以多骨权重，但不得改变已有骨架契约。
3. 身体、头、左右手脚、左右耳分别归属对应骨。头部配件跟随 `head`；下身附件挂点继续继承现有 `BodyJoint`。
4. 模型文件保存并关闭编辑事务后，在动作文件重载关联模型；验证骨架签名一致再开始动作制作。
5. 在 Action Editor 选择 `anim_bunny01_<state>_v009`，编辑骨骼关键帧。动作文件有真实 Pose 关键帧与模型预览，不在模型文件另维护一套动作。

首版动作由现有表现采样迁移，保留既有视觉节奏供美术继续编辑；迁移脚本只运行一次。以后导出只读取保存后的动作文件，绝不重新运行迁移脚本覆盖美术关键帧。

## 四、动作与状态归属

| 动作 ID | 播放方式 | 时间来源 |
|---|---|---|
| idle | 循环 | 表现时钟 |
| moving | 循环，随平面速度调整 | 实际移动速度 |
| dashing | 单次 | 原冲刺表现进度 |
| hurt | 单次 | 原受击恢复进度 |
| locked | 循环 | 已存在的 locked 状态 |
| falling | 播放后保持 | 已存在的 falling 状态 |
| landing | 单次 | 原落地恢复进度 |
| dead | 单次并保持末帧 | 角色死亡进度 |

`Player3D` 状态机输出状态和进度；表现层只选择、采样对应动作。美术动作结束不得发放伤害、结束死亡、解锁角色或切换玩法状态。动作文件禁止 root motion 驱动 `CharacterBody3D`。

瞄准 yaw、武器握持、换弹/射击/蓄力/近战与击飞的实时校正仍是表现约束：其输入来自真实武器与角色数据，不能被离线动画自带的计时器替代。当前基础骨骼动作库与这些约束分别维护；有武器时双手以握持约束为最终结果。灯光/VFX/材质反馈继续读取既有状态。

## 五、导出与严格中转

命名统一为 `chr_<角色>_<部件或用途>_vNNN`、`anim_<角色>_<动作或库>_vNNN`。一个版本包只允许一份模型母版和一份动作母版。生产输出位于 `exports/`，机器账本位于版本包根，资产主账本仍为 `assets/registry/ShellStorm2_美术资产台账_v001.xlsx`。

导出命令（从项目根运行，替换本机 Blender 路径）：

```sh
blender --background --python scripts/blender/export_character_bundle.py -- assets/art/characters/player/chr_player_capsule01_3d/variants/bunny01/production/v009
```

导出器校验骨架签名、绑定和八态完整性，生成模型 GLB、分件 GLB、动作 GLB、动作采样库及 `character_transfer_ledger_v009.json`。其中动作采样库从 Blender 评估后的骨姿势生成；Godot 的刚性节点适配器消费它，标准动作 GLB保留供 Skeleton3D 消费者及跨工具检查。两者必须在同一次导出中生成。

导出后运行 `python3 tools/asset_pipeline/import_character_bundle.py <版本包目录>`。该命令先复算全部源/输出哈希，再生成表现包装；不会自动修改玩家功能场景。对照新旧包围盒与专项通过后，只切换 `Player3D.tscn` 的 Avatar PackedScene 引用。

当前适配器以原程序逻辑计算武器姿势、状态进度和实时反馈，再以导入骨动作确定身体/头/脚/耳和无武器双手的最终姿势。此兼容步骤保留在 `PlayerAvatar3D` 中，尚未将所有武器覆盖动作迁入 Blender；这些覆盖动作仍应列作后续动作制作项，不能把八态基础库当作全部武器动作库。

账本记录：稳定 AssetID、版本、源模型、源动作、骨架 ID/签名、部件与样式、导出文件、每文件 SHA-256、字节数、动作名/时长/循环/帧数、运行时消费者、碰撞所有者、制作尺寸与展示倍率、校验状态。

状态顺序：`authored → exported_pending_godot_validation → validated → active`。未通过签名、哈希、状态/挂点/尺寸验收的包不得标记 active。重新编辑任一源文件，原导出即视为过期；重新导出并验收后再更新台账。不得手工复制导出文件后跳过账本。

## 六、Godot 集成边界

角色视觉节点的稳定接口包括 `BodyJoint`、`HeadJoint`、`HandJointL/R`、`FootJointL/R`、耳部节点和 `LowerBodySocket`。`CharacterMotionLibrary3D` 把骨姿势映射到这些表现节点，衣柜仍通过原 `set_avatar_customization()` 入口装配。

角色模型根缩放为 1；既有 0.7 展示倍率仍由外层角色展示契约负责。可见网格保持 avatar layer 2，GI 与投影由既有运行时渲染契约统一设置，本次不修改。GLB 中不得包含碰撞、脚本、相机、灯、武器或预览地面。

## 七、验收与回滚

必须检查：两份 Blend 可重新打开、共享骨架签名、权重和集合归属、动作首末帧与循环接缝、八态播放、独立移动步态、左右手握持、帽子/眼镜与头部互斥、配件随父骨、换装保存恢复、源与输出哈希一致。

Godot 至少运行 `verify_player3d_avatar_bounds`、`verify_player3d_animation_flow`、`verify_player3d_diy_flow`、`verify_player3d_head_accessory_flow`、`verify_player3d_lower_body_socket_flow`、武器姿势/碰撞及动作覆盖专项。最终在 `Player3DStateGallery.tscn` 验收真实状态和灯光画面。测试失败时包保留为 pending，正式资源引用继续使用已验证版本。

批量校验命令：`python3 tools/asset_pipeline/validate_character_bundle.py <版本包目录>`。它核验源/导出/包装哈希、循环接缝并执行11项角色专项，将真实结果写回中转JSON。执行 `node tools/asset_pipeline/update_character_registry.mjs` 可将当前 v009 中转记录同步到 XLSX（需配置脚本中的 bundled artifact-tool 运行库路径）。

当前脚本实现针对 Bunny v009；其他角色或版本必须先参数化文件名、消费者和骨名映射，再运行导出/导入。命令不能仅换版本目录就宣称支持任意角色。

回滚依据是上一份已验证包和台账，而不是临时改骨名或调整碰撞。v008 是本次迁移前的回滚资产。敌人/NPC/Boss 后续制作遵循相同双文件流程，但各自建立骨架 ID、动作表和适配器，不套用 Bunny 骨名或玩家八态。

仅标记 `assembly_version=v009` 的包装启用导入动作适配器，回退 v008 后恢复原程序动作。批量校验全部通过且玩家场景实际引用该包时，中转状态记为 `active`；未被引用的合格包记为 `validated`。
