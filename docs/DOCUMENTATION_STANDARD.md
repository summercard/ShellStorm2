# 文档驱动开发规范

状态：本次用户要求的文档与开发记录分离规则。适用工程：0.1.0 起。生效日期：2026-09-12。

## 1. 三种文档各自回答一个问题

| 文档 | 回答的问题 | 包含 | 不包含 |
|---|---|---|---|
| 设计与工程契约 | 功能应当怎样工作、由谁负责 | 目标、规则、命令/事件、数据定义、失败语义、验收标准 | 某次运行通过数、提交清单、修补过程 |
| 开发记录 | 某次交付实际改变了什么 | 功能ID、设计修订、代码基线、改动、测试结果、遗留项 | 新的隐含玩法规则、把历史通过当现行标准 |
| 版本状态与审计 | 当前哪些已经具备、哪些仍未闭环 | 功能索引、状态、证据定位、缺陷、计划 | 复制整份设计和整份日志 |

当前规范正文继续使用 `docs/v0.1/01…16…md` 等既有主题路径。`design/README.md` 是设计阅读目录，不复制正文。`development/` 保存交付日志，`development/history/` 保存拆出的既有记录，`audits/` 保存可追溯审计。历史条目中“当前”“最新”“已通过”只对原记录时点成立。

## 2. 开发顺序

1. 在 [功能索引](v0.1/MODULE_INDEX.md)确定稳定功能ID、当前所属版本和唯一主设计；多个功能共享的规则只在所有者文档定义。
2. 先核对设计与实现差异。修复实现偏离时引用已有设计；改变功能语义时先更新设计段落，说明来源、约束和兼容性。未冻结的新玩法保留为提案，不反向把代码现状写成用户设计。
3. 写清接口、状态所有者、输入/输出数据、拒绝与回滚，再实施代码、内容或资产。仅移动文件不视为完成解耦。
4. 先跑相关基线，再跑变更专项；按影响范围执行 smoke/core/full。正式档与自动化验收档必须隔离。需要真实渲染的用例不得算入无头通过。
5. 在 `development/CHANGELOG.md` 追加独立交付记录；设计正文只维护现行规则、实现范围与验收要求。
6. 同步状态索引、内容数据库和资产台账中的受影响条目。完成设计、实现、验证三者交叉检查后再标记已验收。

一般工程维护按已授权范围自主进行，不因这份规则增加重复审批。涉及尚未明确的玩法变更时保留提案，继续推进不依赖该决定的工作。

## 3. 功能的最小工程契约

每个功能必须能够定位以下字段，可写在所属模块文档的独立章节，无须一个按钮建一个文件：

| 字段 | 要求 |
|---|---|
| feature_id / module_id | 稳定标识，不随显示名变化 |
| 版本 | 目标工程版本、设计修订号、首次实现版本、验证基线分别记录 |
| 来源与状态 | 用户设计/工程补充与计划/部分实现/已实现/已验收分开 |
| 事实所有者 | 只有一个服务或数据域拥有最终写入权 |
| 输入命令 | 参数、前置条件、幂等键、结果结构、错误码 |
| 输出事件/查询 | payload/schema、稳定ID、事件产生时机、订阅者；尚未实现的事件明确标为目标 |
| 数据链 | 内容ID→运行实例→持久化字段→UI/资产；记录单位、默认值、引用、迁移 |
| 失败收口 | 输入无效、资源不足、实例化失败、写盘失败、场景卸载、重试与回滚 |
| 独立开发入口 | 领域测试或替身、最小场景、允许依赖和禁止的反向访问 |
| 正式接入 | 主入口中触发该功能的具体操作路径 |
| 验收 | 正常/拒绝/重试/读档路径；需要表现时同时给出真实渲染证据 |
| 开发记录 | 关联交付记录与遗留项，不用勾选框替代证据 |

## 4. 版本与状态规则

- 工程版本读取 `project.godot`，当前为 `0.1.0`。同版本继续施工用设计修订和代码提交区分，不擅自改成0.2。
- 设计修订采用功能内递增修订，如 `WORLD-FLOOR r2`；跨模块语义变化同步相关契约。历史修订通过 Git 和开发记录追溯，不复制成多个“最新”文件。
- 存档 schema（当前 `BaseData 2.0`、`runtime_player_state_v2`）、资产 `_vNNN`、设计修订与游戏版本是不同轴，不能互相代替。
- `[已实现]`表示正式运行路径具备能力；`[已验收]`必须附基线、日期和结果。最近测试失败时保留目标设计，将当前验收标为未通过/待核验。
- `design_only` 内容不进入运行池；实现ID与设计ID不一致必须显式映射或迁移，不能依中文名字默认同物。
- 文档更新不等于测试通过。一个聚合测试退出0但含非预期脚本错误，也不能签署无错误验收。

## 5. 内容与资产同步

当前 XLSX 尚未自动生成全部运行时配置。过渡期同时维护内容表与代码投影，并留下逐字段对照结果；仅扫描公式错误不等于内容一致。

资产哈希变化必须先确认是已批准替换、版本递增或不应发生的修改，再回填台账。禁止为消除审计红项批量接受所有当前哈希。内容表和台账修改遵循各自生产技能。

## 6. 提交前检查

- 设计变更先存在，功能ID、所有者和契约可定位。
- 日志记录本次事实，设计正文不追加“本轮通过N项”。
- `python3 scripts/check_documentation_contracts.py` 检查版本导航、功能索引中的文件引用和必要元数据。
- 对应逻辑/失败专项通过；真实渲染和目标设备测试按功能需要执行。
- 未通过项、未执行项、预期失败注入分别记录，不能混入成功总数。

上述文档检查是显式本地命令，当前尚未接入 CI 或 Git hook；不能宣称已自动阻断所有脱离文档的提交。语义与冻结来源仍需要审阅。
