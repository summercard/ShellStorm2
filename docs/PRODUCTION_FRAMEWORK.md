# 制作框架 · 三层结构与工作矩阵

> 版本：2026-10-20 草案
> 位置关系：**《创作链路·五层结构》回答「项目怎么组织」；这一份回答「每个模块怎么达成、谁来做」。** 一份是纵轴，一份是横轴。
> 实例：ShellStorm2（`I:\工作项目\shellstrom2\ShellStorm2`）
> 配图：`制作框架_三层结构.png` / `.svg`

## 0 一句话说清

**所有活都能归进两个大类（玩法 / 包装）；每个模块必须装满四件套（流程、工具、方法论、工程结构）；装满之后才谈谁来做——这就是工作矩阵，矩阵第一行是主人，不是执行者。**

## 1 总图（文字版）

```
第一层  两大分类
├─ 玩法模块 ── 功能 · 3C · 测试 · 打包 · 数据
└─ 包装模块 ── 美术 · 动画 · 特效 · 音效 · 音乐 · 交互体验
                 ↓ 每个模块都要装满四格
第二层  模块四件套
① 制作流程（流程表 + 验收标准）
② 制作工具（软件 + skill + 脚本）
③ 制作方法论（技巧 + 方式 + 禁忌）
④ 工程结构（落哪个目录、谁拥有写入权）
                 ↓ 四格装完才谈谁做
第三层  工作矩阵
决策层（主人）→ 调度层（杰西卡 / 业务线 agent）→ 执行层（四台机器）→ 沉淀层（资料库 / 账本 / 日志）
```

# 第一层 · 两大分类

## 2 分类的原则

判据只有一条：**这个模块出问题，玩家感受到的是「不好玩 / 不稳」，还是「不值 / 不好看」？**

| | 玩法模块 | 包装模块 |
|---|---|---|
| 决定什么 | 好不好玩、稳不稳 | 看起来值不值、手感顺不顺 |
| 失败表现 | 卡关、崩、数值崩坏、读档丢东西 | 画面糙、动作僵、没声、点了没反馈 |
| 验收靠什么 | 探针 + 数据 + 完整流程跑通 | 真实渲染截图 + 人耳人眼判断 |
| 能否量化 | 大部分能（帧数、错误数、口径一致） | 一半能量化（分辨率、码率），一半靠审 |
| 出错代价 | 高（返工要动逻辑） | 中（可替换资产，不动逻辑） |

**唯一的交点：数据。** 数据既决定玩法数值，也决定包装的资产引用；所以「数据」放在玩法侧，但它必须给包装侧提供只读视图。

## 3 玩法模块 · 五个子域

| 子域 | 管什么 | Storm2 落点 | 现成文档 |
|---|---|---|---|
| **功能** | 系统与规则：命运卡、枪械工坊、基地经济、叙事触发 | `src/{base,combat3d,rewards,narrative,weapons,game}/` | `design/命运卡六关投放设计`、`基地经济与存档结算设计` 等 43 篇 |
| **3C** | Character / Camera / Control：移动、视角、输入、手感 | `src/player3d/`（32 文件 9182 行）、`src/player3d` 相机与调试键 | `development/` 内 v039/v041/v042 系列 |
| **测试** | 探针、回归、验收脚本 | `tests/verification/` 130+ 探针、`tests/tooling/` pytest | `tests/README.md` |
| **打包** | 导出预设、包体、平台差异、启动参数 | `export_presets.cfg`、`android/`、`tools/` 构建脚本 | `02_技术架构总则.md` |
| **数据** | 存档 schema、内容表、账本、迁移 | `data/`、`assets/**/asset_manifest.json`(626)、`*_ledger*.json`(34) | `12_全游戏完成度清单.md` |

## 4 包装模块 · 六个子域

| 子域 | 管什么 | Storm2 落点 | 现成文档 |
|---|---|---|---|
| **美术** | 场景、角色、道具、贴图、风格统一 | `assets/`、`art_source/`（Blender 源 1283 份） | `10.1_3D场景美术生产流程.md`(15k)、`10.2_道具低模美术生产流程.md`(6.9k) |

| **特效** | VFX、后处理、屏幕效果 | `src/vfx/`(45 文件 4995 行)、`src/postfx/` | `14.6_特效系统与制作规范.md`(102.5k) |
| **音效** | 反馈音、空间声、混音 | `src/audio/`(5 文件 629 行)、`audio/` | `音效系统与资产设计` |

**包装模块的特别规则**：这六个子域里，只有「美术」有源文件（`.blend`），其余五个的产物直接进运行态。所以美术要过账本，其余五个要过「版本号 + 触发条件」登记。

# 第二层 · 每个模块的四件套

四件套不是四个建议，是**四道门**。少任何一格，这个模块就算「没人负责」。

## 5 ① 制作流程（流程表 + 验收标准）

### 5.1 流程表必须写清的六列

| 列 | 内容 | 反例（不合格） |
|---|---|---|
| 步骤号 | 01、02… 不跳号 | "先做主体再细化" |
| 输入 | 参考图 / 上一版 / 规范文件的具体路径 | "看情况" |
| 动作 | 具体操作，可被第二个人复现 | "调整到满意" |
| 工具 | 软件名 + 版本 + 在哪台机器 | "用建模软件" |
| 产物 | 文件名 + 落盘绝对路径 + 进哪个账本 | "生成模型" |
| 判据 | 这一步怎么算过（数字化） | "看起来对" |

### 5.2 验收标准一律分四级

| 级别 | 含义 | 谁验 | 通过标志 |
|---|---|---|---|
| **L1 专项** | 只测这个模块本身，环境隔离 | 执行者自测 | 探针输出全绿 / 单图通过 |
| **L2 真实渲染** | 在实际渲染管线出图，不看视口 | 执行者 + 调度层看图 | 截图与参考对得上 |
| **L3 完整工程** | 在主工程里跑通，不崩、不掉帧 | 调度层 | 无报错、帧率达标 |
| **L4 设备** | 目标机器/手机上实跑 | 主人 | 主人认可 |

**硬规矩：L1 没绿不许报 L2，L2 没过不许说"完成了"。** Storm2 的 252 篇交付记录里，凡是写「已通过」的必须指明是哪一级。

### 5.3 通用六步（所有模块都套这个骨架）

```
① 定身份   模块 ID + 事实所有者，写进 MODULE_INDEX
② 写规则   设计文档里写清「什么算对、什么算错」
③ 立入口   独立场景 / 探针脚本，不依赖主流程
④ 实现     在模块目录内完成，禁止跨模块写别人字段
⑤ 取证     L1 探针 + L2 截图，落盘到 development/
⑥ 归档     追加交付记录 + 账本条目 + 更新完成度清单
```

## 6 ② 制作工具（软件 + skill + 脚本）

### 6.1 工具清单要写三件事

**软件名+版本 / 装在哪台机器 / 用它做哪一步。** 少一样，换个人就接不上。

| 类别 | 工具 | 机器 | 用途 |
|---|---|---|---|
| 引擎 | Godot 4.6 | 2 号机 | 编码、场景、探针运行 |
| 编码 agent | Codex CLI | 2 号机 | 批量改代码、跑测试 |
| 建模 | Blender（`blender --background --python`） | 3 号机 | 像素风长方体建模 |
| 出图 | ComfyUI（7091 / 8189） | 工作站 / 4 号机 | 素材批量生成 |
| 视频 | ffmpeg（`~/.local/bin/ffmpeg`） | 1 号机 / 4 号机 | 录制、拼接、压码率 |
| 截图 | Chrome headless + `view_image` | 1 号机 | 网页与图表出图 |
| 文档 | 本地 md + `feishu_doc` | 1 号机 | 交付与归档 |

### 6.2 Skill 的角色

Skill 是**把流程表压成"照着做就行"的操作手册**。判据：一个没做过的人拿到 skill，能在不看别的东西的情况下做出 80% 的结果。

现成可复用（与本框架直接相关）：

| Skill | 对应模块 | 解决什么 |
|---|---|---|
| `comfyui-remote-run` | 美术 / 特效 | 远程跑 ComfyUI，不碰别人端口 |
| `sprite-sheet-animation` | 动画 | N 帧角色动画一次成型 |
| `ffmpeg-shot-assembly` | 音乐 / 成片 | 分段录制 + 拼接校验 |
| `app-interaction-recording` | 交互体验 | 录制应用实际操作 |
| `render-preview-grading` | 美术 | 渲染图打分与调色 |
| `comfyui-workflow-readiness` | 美术 | 判断工作流能不能用 |
| `openclaw-scheduled-jobs` | 测试 / 打包 | 定时回归 |

### 6.3 脚本优先于手工

凡是「要做第二遍」的动作，必须变成脚本。Storm2 现状：`tools/` 下一批 `probe_*.gd`、`scripts/*.py`（资产检查、footprint 校验、偏好生成）。

**判据：同一个手工动作做过两次 → 第三次必须写成脚本。**

## 7 ③ 制作方法论（技巧 + 方式 + 禁忌）

### 7.1 十二条可落地的方法（每条都对应一个真实踩过的坑）

| # | 方法 | 用在哪 | 为什么 |
|---|---|---|---|
| 1 | **一次只改一个变量** | 3C、数值、特效 | 同时改三个数，出问题不知道谁背锅 |
| 2 | **先冻基线再动手** | 所有模块 | 没基线就没法证明"变好了" |
| 3 | **量出来的数 > 文档里的百分比** | 美术、3C | 参考图实测优先于任务书估算 |
| 4 | **能截图的不写字，能写数的不写形容词** | 验收 | "明显改善"无法复验 |
| 5 | **单元先过，再进大场景** | 美术、特效 | 大场景里的问题 90% 是小单元的问题 |
| 6 | **同一构件尺寸差不超过 3 倍** | 像素风建模 | 超过就显脏、不统一 |
| 7 | **单级转角 ≤6°** | 建模 | 大了破坏方块语言 |
| 8 | **动作先对齐握点，再调发力方向** | 动画 | 顺序反了要重做全部帧 |
| 9 | **音效先做「有/无」再做「好不好」** | 音效 | 玩家先感知缺失，后感知质感 |
| 10 | **UI 先过可读性，再过美观** | 交互体验 | 看不清的漂亮界面等于没做 |
| 11 | **回归只跑受影响的那几条探针** | 测试 | 全量跑一遍的时间成本会让人放弃测试 |
| 12 | **失败也要记录，写原始报错** | 日志 | 同样的错不踩第二次 |

### 7.2 三条禁忌（踩了必返工）

1. **不许在没写规则的情况下开始做**——"先做出来再说"的结果一定是推翻重做
2. **不许跨模块直接改别人的数据字段**——改一次，后面所有引用它的模块都要查一遍
3. **不许用"完成了"三个字交付**——必须给：产物路径 + 验收到第几级 + 遗留什么

### 7.3 分模块的方法侧重

| 模块 | 最吃的方法 | 最容易犯的错 |
|---|---|---|
| 功能 | 先写失败收口再写正常路径 | 只做 happy path，异常一来就崩 |
| 3C | 每个参数单独调、单独记 | 手感靠"感觉"，下次调不回来 |
| 测试 | 一条探针只测一件事 | 探针里塞三个断言，红了不知道哪个坏 |
| 打包 | 每平台单独验，别假设一致 | 桌面能跑就以为手机能跑 |
| 数据 | schema 加版本号，只加不删 | 直接改字段名，旧存档全废 |
| 美术 | 参考图先量尺寸比例 | 凭印象开工，做完发现比例全错 |
| 动画 | 先定关键帧，再补中间帧 | 从头一帧帧推，改一个动作全废 |
| 特效 | 先做灰度版看节奏 | 一上来堆颜色，节奏不对白做 |
| 音效 | 先做最吵的那一个，再往下压 | 每个都调到位，混在一起糊 |
| 音乐 | 先定段落时长，再写旋律 | 写完了发现切不进去 |
| 交互体验 | 先做最坏情况（小屏/低配/密集信息） | 只在理想状态验，上线就崩 |

## 8 ④ 工程结构

### 8.1 模块必须满足的四条

| 条 | 内容 | 检查方式 |
|---|---|---|
| **独立目录** | 一个模块一个目录，不散落在多处 | `src/<module>/` 存在且能列出文件 |
| **独立入口** | 有探针或最小场景能单跑 | 不启动主流程也能验证 |
| **单一事实源** | 数据只有一处写入权 | 搜字段名，只有一个 `set` |
| **可回滚** | 改动可单独撤销 | 交付记录写了基线 commit |

# 第三层 · 工作矩阵

## 9 五层四角色

| 层 | 角色 | 谁 | 干的事 | **不干的事** |
|---|---|---|---|---|
| **决策层** | 唯一决策节点 | **主人（sc）** | 给意图、给参考、判通过/打回 | 写代码、逐条改文档、盯每一步 |
| **调度层** | 拆解与判卷 | 杰西卡（1 号机） | 需求拆任务书、判卷单、文档、归档、剪辑 | 替主人拍板玩法 |
| **调度层** | 业务专线 | `video` / `model3d` agent | 只读定义卡 5 份，交结论+产物路径 | 继承主会话历史、扩大读取 |
| **执行层** | 主编码 | 2 号机（Windows） | 写代码、跑探针、出交付记录 | 自行改需求与数值 |
| **执行层** | 建模/搜集 | 3 号机（Arch） | 像素风建模、ComfyUI、资料搜集 | 装软件、碰 9876 |
| **执行层** | 渲染出片 | 4 号机（公用） | 单条串行渲染、质检 | 留私人资料、并发 |
| **执行层** | 大模型出图 | 工作站（4090+3090） | 素材批量生成 | 承载私人项目 |
| **沉淀层** | 记忆与复用 | 资料库 / 账本 / 日志 | 归档、可检索、下轮起点 | 收过程噪音、收一次性失败 |

## 10 主人（sc）在矩阵里的确切位置

**主人不是「审一下」，主人是整条链的唯一开关。**

| 主人做什么 | 什么时候 | 输出什么 | 谁接 |
|---|---|---|---|
| 给一句话意图 | 项目起点 | 核心体验一句话 | 杰西卡 → 三份文档 |
| 给参考图/参考片 | 包装模块开工前 | 图/片 + 一句话"要哪个感觉" | 执行机 |
| 定「不做什么」 | 每个模块开工时 | 边界清单 | 杰西卡写进任务书 |
| **一审** | 首版产物出来 | 通过 / 打回 + 一句理由 | 杰西卡转修改单 |
| **二审** | 修改单执行完 | 通过 / 停手 | 杰西卡归档 |
| 裁定冲突 | 规则打架时 | 一句话结论 | 写进判据库 |
| 最终验收（L4） | 上设备 | 认可 / 不认可 | 归档成片 |

**三条只属于主人的权力：**
1. **定标准**——"什么算好"只有主人能改
2. **喊停**——任何模块任何时候可以停，不需要理由
3. **改结构**——资料库一级目录、大类增删改名，必须主人点头

**主人不该碰的三件事（碰了会拖慢自己）：**
- 不写代码、不改文档正文（说了要什么，剩下的交给链路）
- 不盯执行过程（只看产物和判卷单）
- 不重复给同一条指令（第三次还不对，是链路的问题，不是主人没说清）

## 11 交接物只有四种

| 交接物 | 方向 | 必须含 | 不许含 |
|---|---|---|---|
| **任务书** | 主人/杰西卡 → 执行机 | 要做什么、验收标准、产物路径、边界 | 轮次、共几次、后续计划 |
| **修改单** | 杰西卡 → 执行机 | 构件 → 现状 → 改成什么值 → 怎么验 | 完整重述任务书 |
| **判卷单** | 杰西卡 → 主人 | 各维打分 + 数字依据 + 结论 | 过程叙述 |
| **交付包** | 执行机 → 资料库 | 产物 + 证据 + 日志 + 账本条目 | 中间稿、tmp 文件 |

**不做口头交接。** 一切以上面四种文件为准；聊天里说的"改好了"不算完成。

## 12 一条任务在矩阵里的完整走法

```
主人一句话
   ↓ 杰西卡拆成任务书（含验收四级口径）
业务 agent / 执行机
   ↓ L1 探针 + L2 截图 + 交付记录
杰西卡判卷（五维：功能/视觉/性能/数据安全/可回归）
   ↓ 通过 → 判卷单给主人一审
   ↓ 不通过 → 修改单（只写 delta）
主人一审 → 通过 → 归档 + 账本条目 + 完成度清单更新
        → 打回 → 修改单（最多两轮，第三次换方法或放弃并写未解决项）
```
